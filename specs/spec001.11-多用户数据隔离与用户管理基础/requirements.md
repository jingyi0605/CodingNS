# 需求文档 - 多用户数据隔离与用户管理基础

状态：Draft

## 简介

当前项目已经有登录体系，但它还不是一个真正的多用户系统。

现在很多数据虽然带了 `userId`，但核心对象并没有统一归属：

- 工作区还是全局共享
- 会话核心绑定还是全局共享
- Butler 还是默认全局单实例
- 一些后台链路仍然直接拿“第一个用户”继续执行

这会导致一个很危险的中间态：看起来支持多人登录，实际上数据会串。

所以这次不追求一步到位做团队协作，而是先把最基础的事情做对：

- 谁登录，看到谁自己的工作区和会话
- 后端执行时知道当前到底是哪个用户
- 关键业务对象都有清晰归属
- 默认不会因为代码偷懒把数据串给别人

## 术语表

- **Host**：当前桌面端或服务端实例，负责保存本地工作区、会话、任务和运行态数据。
- **用户归属**：一条数据明确属于哪个用户，后端读取时默认只允许这个用户访问。
- **共享资源**：不是某个用户私有的数据，比如插件定义、系统级配置。
- **工作区归属**：工作区记录和相关入口明确属于某个用户，而不是整个 Host 默认共享。
- **用户作用域**：后端接口、后台任务、会话运行时执行时必须带上的当前用户上下文。

## 范围说明

### In Scope

- 用户管理基础入口
- 工作区归属隔离
- 会话核心归属隔离
- Butler 按用户拆分
- 清理“默认第一个用户”的单用户假设
- 核心 API、WebSocket、后台任务的用户作用域校验
- 关键数据迁移与兼容策略

### Out of Scope

- 团队、组织、租户、多级权限系统
- 工作区多人共享协作和成员管理
- 所有历史边缘表一次性全量重构
- 外部通讯平台复杂权限模型重做

## 需求

### 需求 1：管理员可以正式管理多个用户

**用户故事：** 作为 Host 管理员，我希望系统能正式创建、查看和管理多个用户，以便这个 Host 不再只有“第一次初始化的那个账号”可用。

#### 验收标准

1. WHEN 管理员进入用户管理入口 THEN System SHALL 显示当前已有用户列表和每个用户的基础状态。
2. WHEN 管理员创建新用户 THEN System SHALL 创建独立用户记录，并允许该用户用自己的账号登录。
3. WHEN 管理员停用或删除用户的登录态 THEN System SHALL 立即使该用户现有登录凭证失效，不影响其他用户。

### 需求 2：工作区必须有明确归属，默认不能跨用户可见

**用户故事：** 作为普通登录用户，我希望我只能看到属于我的工作区，以便不会误看到别人的项目列表。

#### 验收标准

1. WHEN 用户读取工作区列表 THEN System SHALL 默认只返回该用户可见的工作区。
2. WHEN 用户导入、创建或克隆工作区 THEN System SHALL 把该工作区归属到当前用户。
3. WHEN 另一个没有权限的用户读取该工作区详情、列表或相关入口 THEN System SHALL 返回无权限或不可见结果，而不是把数据暴露出去。

### 需求 3：会话和 Butler 核心对象必须按用户隔离

**用户故事：** 作为登录用户，我希望我的会话、Butler 项目和控制会话只属于我自己，以便不会和别人的 AI 对话、运行态或摘要串在一起。

#### 验收标准

1. WHEN 用户创建或续接会话 THEN System SHALL 将会话核心绑定到当前用户，而不是共享到整个 Host。
2. WHEN 用户访问 Butler 项目、Butler 会话或 Butler 控制会话 THEN System SHALL 只返回当前用户自己的数据。
3. WHEN 另一个用户尝试访问不属于自己的会话或 Butler 对象 THEN System SHALL 阻止访问，并返回明确错误。

### 需求 4：后台任务和运行态必须带上用户作用域

**用户故事：** 作为系统维护者，我希望后台刷新、订阅、权限请求和运行时回调都知道当前用户是谁，以便后台链路不会默默把数据写到错误的人名下。

#### 验收标准

1. WHEN 后台任务因用户操作启动 THEN System SHALL 显式保存并传递该任务所属的用户。
2. WHEN watcher、刷新、订阅、权限请求或运行态回调触发 THEN System SHALL 使用明确的用户作用域处理数据，而不是直接取“第一个用户”。
3. WHEN 后台任务缺少合法用户上下文 THEN System SHALL 终止执行并记录明确错误，而不是静默降级到默认用户。

### 需求 5：现有数据迁移后不能把用户数据搞丢

**用户故事：** 作为已有实例的使用者，我希望升级到多用户隔离后，原有工作区和会话还能继续用，以便这次改造不会把旧数据搞坏。

#### 验收标准

1. WHEN 老实例升级数据库 THEN System SHALL 把原有核心数据迁移到明确的用户归属模型下。
2. WHEN 旧数据只能推断出一个已有用户归属 THEN System SHALL 采用兼容策略把历史数据挂到默认历史拥有者，并记录迁移结果。
3. WHEN 迁移失败或遇到无法安全推断的数据 THEN System SHALL 停止破坏性写入，并给出可排查的错误信息。

## 非功能需求

### 非功能需求 1：安全性

1. WHEN 任意业务接口读取用户私有数据 THEN System SHALL 在后端按用户作用域做校验，不能只靠前端隐藏。
2. WHEN 用户访问不属于自己的资源 THEN System SHALL 返回明确拒绝结果，不能泄露对方数据是否存在的更多细节。

### 非功能需求 2：可靠性

1. WHEN 后台刷新、订阅或运行态恢复 THEN System SHALL 维持正确的用户归属，不因重连或重放把数据串给其他用户。
2. WHEN 数据迁移执行 THEN System SHALL 提供可回放、可审计的迁移结果，避免半迁移半旧结构长期并存。

### 非功能需求 3：可维护性

1. WHEN 后续新增工作区、会话、Butler、任务相关表或服务 THEN System SHALL 明确说明该对象是用户私有还是实例共享。
2. WHEN 开发者排查多用户问题 THEN System SHALL 在日志、任务上下文和错误信息里带上用户标识。

## 成功定义

- 第二个用户登录后，看不到第一个用户的工作区和会话列表
- 关键核心表完成用户归属改造，并通过最小必要测试
- 代码里不再出现 `listIds()[0]` 这种默认第一个用户的核心链路实现
- Butler、会话、后台任务至少主链路完成用户作用域隔离

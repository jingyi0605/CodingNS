# 设计文档 - 多用户数据隔离与用户管理基础

状态：Draft

## 1. 概述

### 1.1 目标

- 把“能多人登录”改成“多人登录后核心数据默认隔离”
- 给工作区、会话、Butler、后台任务补齐明确的用户归属
- 保证旧实例升级后还能继续使用，不把现有数据搞坏

### 1.2 覆盖需求

- `requirements.md` 需求 1：管理员可以正式管理多个用户
- `requirements.md` 需求 2：工作区必须有明确归属，默认不能跨用户可见
- `requirements.md` 需求 3：会话和 Butler 核心对象必须按用户隔离
- `requirements.md` 需求 4：后台任务和运行态必须带上用户作用域
- `requirements.md` 需求 5：现有数据迁移后不能把用户数据搞丢

### 1.3 技术约束

- 后端：Fastify + TypeScript
- 前端：React + user-app 现有工作台与登录体系
- 数据存储：Host SQLite（统一走 `better-sqlite3` 封装）
- 认证授权：现有 `auth_users / auth_tokens / auth_devices` 体系
- 后台任务：必须接入现有 `TaskManager`，不能自己再长私有调度器

## 2. 架构

### 2.1 系统结构

这次改造不新增一套平行系统，直接在现有结构里补齐“数据属于谁”这件事。

主链路分成四层：

1. **登录层**  
   负责识别当前用户是谁，给 HTTP、WebSocket、工作区 scoped token 提供稳定用户上下文。

2. **资源归属层**  
   负责定义工作区、会话、Butler、任务这些核心对象归谁所有。

3. **访问校验层**  
   负责在接口、查询、刷新、后台任务里默认按用户过滤，阻止跨用户读写。

4. **迁移兼容层**  
   负责把旧实例里的全局数据挂到明确用户下，避免升级后直接失效。

### 2.2 模块职责

| 模块 | 职责 | 输入 | 输出 |
| --- | --- | --- | --- |
| 认证与用户管理 | 管理用户、登录态和设备会话 | 用户名、密码、管理员操作 | 用户记录、Token、用户管理结果 |
| 工作区归属服务 | 管理工作区归属和访问范围 | 当前用户、工作区操作请求 | 仅当前用户可见的工作区结果 |
| 会话与 Butler 归属服务 | 管理会话、Butler 项目、控制会话的归属 | 当前用户、会话或 Butler 请求 | 用户私有会话和 Butler 数据 |
| 后台任务与运行态 | 在刷新、订阅、回调中传递用户作用域 | 用户操作、运行态事件 | 带用户归属的后台结果 |
| 数据迁移 | 升级旧表结构并补齐归属 | 旧数据库、已有用户 | 新结构数据和迁移日志 |

### 2.3 关键流程

#### 2.3.1 新用户创建与登录

1. 管理员在用户管理页面创建新用户。
2. 后端写入 `auth_users`，并生成最小必要初始状态。
3. 新用户使用自己的账号登录，后端签发独立 Token。
4. 后续所有业务请求都从 `authContext.user.userId` 往下传。

#### 2.3.2 用户读取工作区与会话

1. 用户携带自己的登录态请求 `/api/workspaces` 或 `/api/sessions`。
2. 后端先校验登录态，再根据用户归属查询工作区和会话。
3. 如果请求访问不属于自己的资源，直接返回拒绝，而不是继续查全局共享表。

#### 2.3.3 后台任务执行

1. 用户触发刷新、权限回复、Butler 跟进或其他后台动作。
2. 任务创建时把 `userId` 明确写入任务输入和持久化记录。
3. watcher、订阅或回调恢复执行时，继续沿用这个 `userId`。
4. 如果没有合法 `userId`，任务直接失败并记录日志。

#### 2.3.4 老数据迁移

1. 启动升级时读取现有用户列表和旧核心表。
2. 选择历史默认拥有者，把旧工作区、旧会话、旧 Butler 数据挂到该用户。
3. 写入新字段、新索引和迁移记录。
4. 迁移成功后才切换到新的查询逻辑。

## 3. 组件和接口

### 3.1 核心组件

覆盖需求：1、2、3、4、5

- `AuthService / AuthController`：继续负责登录，但补用户管理能力和更严格的用户态约束。
- `WorkspaceService / WorkspaceRepository`：从“全局工作区列表”改成“按用户读取工作区”。
- `Session*Service / Session*Repository`：给会话核心绑定补用户归属。
- `Butler*Service / Butler*Repository`：把默认全局 Butler 对象改成按用户独立。
- `TaskManager` 接入任务：所有与多用户相关的后台动作必须显式带 `userId`。

### 3.2 数据结构

覆盖需求：1、2、3、5

#### 3.2.1 用户归属分类

| 对象 | 归属方式 | 说明 |
| --- | --- | --- |
| `auth_users` | 用户自身 | 登录账号主体 |
| `workspaces` | 用户私有 | 第一阶段不再默认全局共享 |
| `session_bindings` / `session_indices` / `session_forks` | 用户私有 | 会话核心归属必须补齐 |
| `butler_profiles` / `butler_projects` / `butler_sessions` / `butler_control_sessions` | 用户私有 | Butler 不再只有一个全局默认对象 |
| 插件定义、系统级配置 | 实例共享 | 继续实例级共享，但访问时仍可带操作者 |

#### 3.2.2 关键表改造

| 表 | 改动 | 目的 |
| --- | --- | --- |
| `workspaces` | 新增 `owner_user_id` | 明确工作区属于谁 |
| `session_bindings` | 新增 `user_id` | 明确会话核心归属 |
| `session_indices` | 新增 `user_id` 或通过外键跟随 `session_bindings` 校验 | 防止会话索引跨用户串读 |
| `session_forks` | 新增 `user_id` 或跟随父会话归属 | 保证分叉链路隔离 |
| `butler_profiles` | 从全局 `default` 改成按 `user_id` 唯一 | 每个用户有自己的 Butler 档案 |
| `butler_projects` | 新增 `user_id` | 项目级隔离 |
| `butler_sessions` | 新增 `user_id` | 会话级隔离 |
| `butler_control_sessions` | 新增 `user_id` | 控制面会话隔离 |

#### 3.2.3 迁移记录

| 字段 | 类型 | 必填 | 说明 | 约束 |
| --- | --- | --- | --- | --- |
| `migration_name` | string | 是 | 迁移名称 | 唯一 |
| `legacy_owner_user_id` | string | 是 | 老数据默认挂载到哪个用户 | 必须存在于 `auth_users` |
| `started_at` | string | 是 | 迁移开始时间 | ISO 时间 |
| `finished_at` | string | 否 | 迁移结束时间 | ISO 时间 |
| `status` | string | 是 | `running/succeeded/failed` | 枚举 |
| `summary_json` | string | 否 | 迁移统计结果 | JSON |

### 3.3 接口契约

覆盖需求：1、2、3、4

#### 3.3.1 用户管理接口

- 类型：HTTP
- 路径或标识：`/api/admin/users`
- 输入：当前管理员登录态、创建/停用/查看用户请求
- 输出：用户列表、用户详情、操作结果
- 校验：只有管理员能操作；用户名唯一；不能删除当前唯一可用管理员
- 错误：无权限、用户名冲突、用户不存在、非法状态转换

#### 3.3.2 工作区与会话读取接口

- 类型：HTTP
- 路径或标识：`/api/workspaces`、`/api/sessions` 及详情接口
- 输入：当前用户登录态、资源 ID
- 输出：只属于当前用户的工作区和会话数据
- 校验：后端必须根据资源归属做过滤和授权
- 错误：未登录、无权限、资源不存在

#### 3.3.3 后台任务与运行态接口

- 类型：HTTP / Event / Function
- 路径或标识：现有后台任务入口与运行态恢复链路
- 输入：当前用户、任务输入、运行时事件
- 输出：带用户归属的任务执行结果
- 校验：缺少用户作用域时直接失败
- 错误：缺少用户上下文、资源无权限、任务状态不合法

## 4. 数据与状态模型

### 4.1 数据关系

本期统一采用一条简单规则：

- **用户私有对象必须能直接或稳定地追到 `user_id`**
- **共享对象必须明确写明为什么共享**

关键关系如下：

- `auth_users` 1:N `workspaces`
- `auth_users` 1:N `session_bindings`
- `auth_users` 1:N `butler_profiles`
- `auth_users` 1:N `butler_projects`
- `auth_users` 1:N `butler_sessions`
- `auth_users` 1:N `butler_control_sessions`
- `workspaces` 1:N `session_bindings`
- `butler_projects` 1:N `butler_sessions`

如果某张表无法直接加 `user_id`，至少要保证：

1. 通过父对象能稳定拿到唯一用户归属  
2. 所有查询都先按父对象做归属校验  
3. 不允许先全表查再在内存里“顺手过滤”

### 4.2 状态流转

#### 4.2.1 用户状态

| 状态 | 含义 | 进入条件 | 退出条件 |
| --- | --- | --- | --- |
| active | 可正常登录和使用 | 新建成功或重新启用 | 被停用或删除登录态 |
| disabled | 不允许继续登录 | 管理员停用用户 | 管理员重新启用 |

#### 4.2.2 迁移状态

| 状态 | 含义 | 进入条件 | 退出条件 |
| --- | --- | --- | --- |
| pending | 还没开始迁移 | 升级前 | 开始执行迁移 |
| running | 正在迁移 | 执行迁移脚本 | 成功或失败 |
| succeeded | 迁移成功 | 所有关键写入完成 | 无 |
| failed | 迁移失败 | 任一关键步骤失败 | 修复后重试 |

## 5. 错误处理

### 5.1 错误类型

- `USER_SCOPE_REQUIRED`：执行链路缺少当前用户
- `RESOURCE_NOT_VISIBLE`：资源存在但当前用户不可见
- `LEGACY_MIGRATION_FAILED`：旧数据迁移失败
- `USER_STATE_INVALID`：用户状态不允许当前操作

### 5.2 错误响应格式

```json
{
  "detail": "当前用户没有访问这个资源的权限",
  "error_code": "RESOURCE_NOT_VISIBLE",
  "field": "workspaceId",
  "timestamp": "2026-01-01T00:00:00Z"
}
```

### 5.3 处理策略

1. 输入验证错误：直接返回 4xx，说明是哪个字段或哪个状态不合法。
2. 业务规则错误：返回明确错误码，比如当前用户不能访问该工作区。
3. 外部依赖错误：保留原有错误包装，但日志里必须带 `userId`。
4. 重试、降级或补偿：后台任务只在用户归属明确时允许重试；归属不明确时直接失败，不做默认降级。

## 6. 正确性属性

### 6.1 属性 1：用户私有数据默认不可跨用户读取

*对于任何* 已登录用户 A 和用户 B，只要某个工作区、会话或 Butler 对象归属于 A，系统都应该满足：B 不能通过正常 API、WebSocket 或后台刷新读到该对象的私有内容。

**验证需求：** `requirements.md` 需求 2、需求 3、需求 4

### 6.2 属性 2：后台任务不会偷偷退回“第一个用户”

*对于任何* 需要用户上下文的后台任务、刷新、订阅或运行态回调，系统都应该满足：执行时使用明确的 `userId`，而不是通过 `listIds()[0]` 或同类逻辑猜一个默认用户。

**验证需求：** `requirements.md` 需求 4

### 6.3 属性 3：迁移不会无声破坏旧数据

*对于任何* 从旧实例升级到新结构的场景，系统都应该满足：要么成功把关键旧数据迁到明确用户下，要么明确失败并停止继续破坏性写入。

**验证需求：** `requirements.md` 需求 5

## 7. 测试策略

### 7.1 单元测试

- 用户管理服务：创建、停用、登录态失效
- 工作区与会话归属校验
- Butler 按用户读取与写入
- 缺少 `userId` 的后台任务拒绝执行

### 7.2 集成测试

- 两个用户读取工作区和会话时互相不可见
- 同一用户新建工作区、会话、Butler 对象后能正常读取
- 旧数据迁移后仍可继续访问
- 权限请求、后台刷新、运行态恢复带用户作用域

### 7.3 端到端测试

- 管理员创建第二个用户后，第二个用户可独立登录
- 两个用户在工作台看到不同的数据
- Butler 主链路不会跨用户串项目和会话

## 8. 风险与待确认项

### 8.1 风险

- 旧表里有些数据可能无法 100% 自动推断正确归属
- 工作区从全局共享改成用户私有后，可能碰到现有 UI 逻辑假设失效
- Butler 相关表较多，局部改一半最容易留下串数据的口子
- 后台刷新链路如果漏掉一个 `userId`，问题会非常隐蔽

### 8.2 待确认项

- 第一阶段用户角色是否仍然只保留管理员，还是允许先引入普通用户角色
- 旧实例迁移默认挂载到“第一个用户”是否足够，还是要提供显式迁移确认
- 哪些系统级资源继续共享，哪些必须同步纳入用户私有范围

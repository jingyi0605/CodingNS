# 需求文档 - spec006-终端核心能力

状态：Draft

## 简介

这个 Spec 解决的是真问题：用户需要在同一个工作区里稳定使用多个终端，并且在网络抖动后能续上，不丢关键输出。

如果终端能力不先定清楚，后面会出现三类烂问题：

- 终端和进程概念混在一起，模型越做越乱
- 断线后只能“重开一个”，上下文全断
- WebSocket 没有统一鉴权，安全边界到处漏风

本 Spec 只做终端核心能力，不做进程调度，不做花哨装饰。

## 术语表

- **System**：`码不能停` 的 Host + 客户端终端能力整体
- **TerminalInstance（终端实例）**：一个绑定在工作区下的 PTY 会话
- **PTY（伪终端）**：后端创建并管理的终端运行实体
- **Output Buffer（输出缓存）**：终端最近输出的滚动缓存，用于断线后补回
- **Command Template（命令模板）**：工作区内可复用的终端命令预设
- **Terminal Gateway（终端网关）**：终端相关 HTTP 与 WebSocket 接口入口

## 范围说明

### In Scope

- PTY 生命周期管理（创建、运行、断开、关闭、异常回收）
- 多终端实例能力（同工作区多 tab）
- 终端实例和工作区的强绑定关系
- 终端断线重连与输出缓存恢复
- 命令模板管理与执行
- 终端 HTTP API 和 WebSocket 通道统一鉴权

### Out of Scope

- 进程发现、启动、重启、停止（归 `spec007`）
- 浏览器端本地假终端实现
- 终端 UI 装饰动画、主题皮肤等非核心功能
- 多人共享同一终端实例

## 需求

### 需求 1：终端模型必须和进程模型分离

**用户故事：** 作为系统维护者，我希望终端和进程是两套清晰模型，以便后续扩展时不会互相污染。

#### 验收标准

1. WHEN 设计终端数据模型 THEN System SHALL 只包含终端会话所需字段，不包含进程编排字段。
2. WHEN 终端接口提供能力 THEN System SHALL 不承担进程发现、进程重启、端口扫描职责。
3. WHEN 需要进程能力 THEN System SHALL 明确通过 `spec007` 的进程服务协作，而不是把逻辑塞进终端服务。

### 需求 2：PTY 生命周期必须由后端统一管理

**用户故事：** 作为开发者，我希望终端创建、关闭、异常回收都有统一规则，以便系统稳定运行。

#### 验收标准

1. WHEN 用户创建终端 THEN System SHALL 在后端创建 PTY 并返回终端实例 ID。
2. WHEN 终端异常退出或客户端主动关闭 THEN System SHALL 正确更新状态并回收资源。
3. WHEN Host 重启或连接抖动 THEN System SHALL 有明确恢复策略，避免僵尸会话和资源泄漏。

### 需求 3：必须支持工作区下多终端实例

**用户故事：** 作为重度用户，我希望一个工作区可以并行开多个终端，以便同时跑不同命令。

#### 验收标准

1. WHEN 用户在同一工作区重复创建终端 THEN System SHALL 允许并返回不同的终端实例。
2. WHEN 用户查看终端列表 THEN System SHALL 按工作区返回当前可用终端实例及其状态。
3. WHEN 用户操作某个终端 THEN System SHALL 只影响目标终端，不影响其他终端实例。

### 需求 4：终端接口和 WebSocket 通道默认受鉴权保护

**用户故事：** 作为管理员，我希望终端能力只对已登录用户开放，以便避免未授权访问工作区命令执行入口。

#### 验收标准

1. WHEN 客户端调用终端 HTTP API 且未携带有效令牌 THEN System SHALL 返回未授权错误。
2. WHEN 客户端建立终端 WebSocket 通道且令牌无效 THEN System SHALL 拒绝握手或拒绝订阅。
3. WHEN 登录态失效 THEN System SHALL 阻断终端输入输出通道，直到令牌恢复有效。

### 需求 5：断线重连后必须能恢复关键终端输出

**用户故事：** 作为移动端或远程用户，我希望网络短断后回到同一终端上下文，以便不中断排查和开发流程。

#### 验收标准

1. WHEN WebSocket 连接中断 THEN System SHALL 保留终端实例运行状态，不立刻销毁 PTY。
2. WHEN 客户端重连成功 THEN System SHALL 基于输出缓存补回断线期间关键输出。
3. WHEN 缓存窗口外的数据无法补回 THEN System SHALL 明确告知用户并提供刷新策略。

### 需求 6：命令模板必须支持工作区复用与安全执行

**用户故事：** 作为开发者，我希望常用命令可保存为模板并一键执行，以便减少重复输入和误操作。

#### 验收标准

1. WHEN 用户创建命令模板 THEN System SHALL 绑定到工作区并保存必要元数据。
2. WHEN 用户执行命令模板 THEN System SHALL 在指定终端实例或新建终端中执行命令并输出结果。
3. WHEN 模板包含非法路径或越权参数 THEN System SHALL 拒绝执行并返回明确错误。

## 非功能需求

### 非功能需求 1：性能

1. WHEN 创建终端实例 THEN System SHALL 在正常负载下快速返回可用终端（目标 P95 < 1 秒）。
2. WHEN 终端高频输出 THEN System SHALL 保持输出流稳定，避免前端卡死或严重积压。

### 非功能需求 2：可靠性

1. WHEN 网络抖动导致连接中断 THEN System SHALL 支持短时重连并恢复输出流。
2. WHEN PTY 异常退出 THEN System SHALL 正确更新状态并记录可排查日志。

### 非功能需求 3：可维护性

1. WHEN 终端能力扩展 THEN System SHALL 通过终端服务内部模块扩展，不改动进程服务边界。
2. WHEN 排查终端问题 THEN System SHALL 提供 `workspaceId + terminalId + connectionId` 级别日志。

## 成功定义

- 用户可以在同一工作区稳定使用多个终端实例
- 终端断线重连后可恢复关键输出，不需要频繁重开终端
- 所有终端 API 与 WebSocket 都在鉴权保护下运行
- 终端与进程边界清晰，不出现职责混杂

# 设计文档 - spec004.2.1-演示文稿视图布局编辑一期

状态：Draft

## 1. 概述

### 1.1 目标

- 在现有演示文稿视图上补齐基础布局编辑能力
- 让位置和尺寸编辑从“字段输入”升级到“画布直接操作”
- 为多选和对齐补一套稳定状态模型
- 保持现有 HTML 回写、保存和导出链路不被破坏

### 1.2 覆盖需求

- `requirements.md` 需求 1：布局编辑入口和模式切换
- `requirements.md` 需求 2：布局编辑节点准入规则
- `requirements.md` 需求 3：单节点拖动位置
- `requirements.md` 需求 4：单节点调整尺寸
- `requirements.md` 需求 5：同页多选
- `requirements.md` 需求 6：多选后的基础对齐
- `requirements.md` 需求 7：不破坏现有编辑主链路

### 1.3 与前置 Spec 的关系

- `spec004` 负责文件读写和版本保护
- `spec004.1` 负责文件查看器壳和多模态预览
- `spec004.2` 负责静态 HTML 演示文稿的导入、页面模型、文字编辑、保存与导出
- `spec004.2.1` 只解决一个现实问题：把现有演示文稿视图补成能做基础版面编辑

一句人话：

`spec004.2` 已经让编辑器能写字，`spec004.2.1` 要让它会摆东西。

### 1.4 技术约束

- 前端仍然基于 `React + TypeScript`
- 现有 `StaticHtmlPresentationView` 仍是主入口，不重做宿主壳
- 现有 `DocumentProject / DocumentNode` 模型继续复用
- HTML 保存继续复用 `spec004.2` 的回写链路
- 第一阶段不引入新的重型画布库

## 2. 总体方案

### 2.1 系统结构

这一轮只在前端编辑壳内补三层，不动后端协议。

1. **布局模式层**
   - 管理当前是否处于布局编辑模式
   - 管理单选、多选和当前操作类型
2. **几何操作层**
   - 负责拖动、缩放、对齐后的几何计算
   - 只改 `DocumentNode.box`
3. **节点准入层**
   - 判断节点是否允许布局编辑
   - 禁止不稳定节点进入几何操作链路

### 2.2 模块职责

| 模块 | 职责 | 输入 | 输出 |
| --- | --- | --- | --- |
| `StaticHtmlPresentationView` | 演示文稿视图主壳，承接模式切换、选区和保存联动 | `DocumentProject`、用户操作 | 视图状态、项目草稿状态 |
| `LayoutEditingState` | 管理布局模式、单选、多选、当前页选区 | 当前页、节点 ID、操作事件 | 稳定选区状态 |
| `LayoutCapabilityResolver` | 判断节点是否允许布局编辑 | `DocumentNode`、页上下文 | 布局可编辑能力结果 |
| `LayoutGeometryUpdater` | 拖动、缩放、对齐后的几何计算 | 选区、拖动参数、对齐命令 | 更新后的 `DocumentProject` |
| `HtmlProjectWriter` | 把已更新的几何信息写回 HTML | `DocumentProject`、原始 HTML | 保存版 HTML |

### 2.3 关键流程

#### 2.3.1 进入布局编辑模式

1. 用户在演示文稿视图点击布局编辑入口。
2. 视图进入 `layout` 模式。
3. 画布选择逻辑从“文字内容优先”切到“组件外框优先”。
4. 右侧面板从单节点文字样式面板切到布局面板或混合面板。

#### 2.3.2 拖动或缩放单节点

1. 用户选中一个布局可编辑节点。
2. 系统根据外框和手柄开始记录拖动或缩放会话。
3. 操作过程中只更新该节点的 `box`。
4. 操作结束后把变更写入项目草稿，并进入撤销历史。

#### 2.3.3 多选并执行对齐

1. 用户在同一页内追加选择多个布局可编辑节点。
2. 系统生成稳定的 `selectedNodeIds` 顺序。
3. 用户触发左对齐、右对齐、顶对齐或底对齐。
4. 系统根据统一基准批量改写多个节点的 `box`。
5. 保存时沿用现有 HTML 回写链路落盘。

## 3. 数据与状态模型

### 3.1 为什么现状不够

当前视图只有单个 `selectedNodeId`，它足够做文字编辑，但不够做布局编辑。

问题很直接：

- 没有多选集合
- 没有模式状态
- 没有节点是否允许布局编辑的显式判断结果
- 没有统一的几何操作入口

所以这一轮必须先补状态模型，再补交互。

### 3.2 新增视图状态

覆盖需求：1、3、4、5、6、7

#### 3.2.1 `EditorInteractionMode`

| 字段 | 类型 | 必填 | 说明 | 约束 |
| --- | --- | --- | --- | --- |
| `mode` | `"content" \| "layout"` | 是 | 当前交互主模式 | 默认仍是 `content` |

说明：

- `content` 模式继续优先支持文字编辑、双击原位输入、文本样式调整。
- `layout` 模式优先支持组件外框选中、拖动、缩放、多选和对齐。

#### 3.2.2 `LayoutSelectionState`

| 字段 | 类型 | 必填 | 说明 | 约束 |
| --- | --- | --- | --- | --- |
| `pageId` | `string \| null` | 是 | 当前选区所属页面 | 不允许跨页 |
| `selectedNodeIds` | `string[]` | 是 | 当前布局选区 | 至少 0 个 |
| `primaryNodeId` | `string \| null` | 是 | 主选中节点 | 必须属于选区或为空 |
| `operation` | `"idle" \| "dragging" \| "resizing"` | 是 | 当前几何操作状态 | 一次只允许一种 |

说明：

- 单选其实就是 `selectedNodeIds.length === 1` 的特例。
- 多选能力不要再发明第二套状态。

#### 3.2.3 `LayoutCapability`

| 字段 | 类型 | 必填 | 说明 | 约束 |
| --- | --- | --- | --- | --- |
| `movable` | `boolean` | 是 | 是否允许拖动 | 明确计算结果 |
| `resizable` | `boolean` | 是 | 是否允许缩放 | 明确计算结果 |
| `alignable` | `boolean` | 是 | 是否允许参与多选对齐 | 明确计算结果 |
| `reason` | `string \| null` | 是 | 不允许时的原因 | 禁止静默失败 |

### 3.3 节点准入规则

覆盖需求：2、3、4、6

第一阶段允许进入布局编辑的节点必须同时满足：

1. 节点 `editable === true`
2. 节点不属于只读 `svg / html / decoration`
3. 节点不是页面根节点
4. 节点不是文本 run 内层代理节点
5. 节点具备稳定几何回写条件

第一阶段稳定几何回写条件限定为：

- 已带 `draft-clone` 或等价草稿几何标记的节点
- 已被显式切换为几何覆盖写回的节点
- 节点的 `box` 会在保存时真实进入 HTML 内联样式

明确不允许进入布局编辑的节点：

- 只读 `svg` 节点
- 只读复杂 `html` 节点
- 装饰层节点
- 页根容器
- 主要依赖文档流、`flex / grid / transform` 才成立，且当前保存链路无法稳定回写的节点

### 3.4 对齐基准

覆盖需求：6

第一阶段对齐基准使用当前选区的包围盒。

- 左对齐：所有节点 `x` 取选区最小左边界
- 右对齐：所有节点 `x + width` 取选区最大右边界
- 顶对齐：所有节点 `y` 取选区最小上边界
- 底对齐：所有节点 `y + height` 取选区最大下边界

这样做的好处很朴素：

- 算法简单
- 结果稳定
- 不需要额外理解“以主节点为基准”或“以最后选中节点为基准”的复杂心智

## 4. 交互与实现策略

### 4.1 画布交互策略

覆盖需求：1、3、4、5、7

第一阶段采用“现有 iframe 预览 + 外层命中与覆盖层”的方式，不重做渲染器。

建议做法：

1. 继续用现有 iframe `srcDoc` 负责视觉渲染
2. 在外层增加布局模式的选中框和缩放手柄覆盖层
3. 用节点外框信息驱动拖动和缩放
4. 操作完成后统一回写 `DocumentProject`

这样做比直接把 iframe 内 DOM 当编辑器可靠，原因很简单：

- 现有保存链路本来就围绕 `DocumentProject`
- 直接操作 iframe DOM 很容易变成“看起来动了，状态里没变”

### 4.2 拖动与缩放策略

覆盖需求：3、4

拖动：

1. 记录拖动起点指针位置
2. 记录节点起始 `box`
3. 根据指针位移换算新的 `x / y`
4. 实时更新项目草稿
5. 操作结束后压入撤销历史

缩放：

1. 记录手柄方向
2. 记录起始 `box`
3. 根据拖动方向计算新的 `width / height`
4. 必要时同步修正 `x / y`
5. 约束最小尺寸，防止出现负尺寸或零尺寸

第一阶段明确不做：

- 比例锁定
- 旋转手柄
- 八方向复杂缩放

只做最小可用的一组常见手柄即可。

### 4.3 多选策略

覆盖需求：5、6

建议先支持最朴素的多选方式：

- 点击主选中
- 带修饰键追加或取消单个节点
- 只允许同页多选

先不要一上来做框选。

原因很现实：

- 框选要处理 iframe 坐标、遮挡、命中排序和文本代理节点
- 复杂度高
- 对这轮“基础对齐”不是必要前提

### 4.4 回写策略

覆盖需求：2、3、4、6、7

这轮的核心原则只有一句：

**只允许保存那些真的能回写的几何编辑。**

具体要求：

1. 布局编辑只改 `DocumentNode.box`
2. 保存继续通过 `HtmlProjectWriter`
3. 只有被判定为几何可写的节点，才允许把 `left / top / width / height` 写进 HTML
4. 不允许让用户做出保存后丢失的拖动、缩放和对齐

## 5. 错误处理

### 5.1 错误类型

- 节点准入错误：节点当前不允许布局编辑
- 选区错误：跨页、多选对象失效或主节点不存在
- 几何计算错误：计算后出现非法尺寸或非法坐标
- HTML 回写错误：项目状态已更新，但保存链路不能稳定落盘

### 5.2 处理策略

1. 节点准入错误：禁止进入布局编辑，并显示明确原因。
2. 选区错误：清理无效选区，回退到空选或单选状态。
3. 几何计算错误：拒绝提交非法几何结果，不写入历史。
4. 保存错误：继续复用现有文件保存失败提示，不另造一套壳。

## 6. 正确性属性

### 6.1 属性 1：不允许假布局编辑

*对于任何* 被系统标记为可拖动、可缩放、可对齐的节点，系统都应该满足：用户完成操作后，该结果可以进入项目状态、参与保存，并在重开文件后保持一致。

**验证需求：** `requirements.md` 需求 2、需求 3、需求 4、需求 6

### 6.2 属性 2：不允许跨页脏选区

*对于任何* 布局多选操作，系统都应该满足：同一时刻选区只属于当前页，切页后不会继续持有上一页的布局选区。

**验证需求：** `requirements.md` 需求 5、需求 7

## 8. 风险与待确认项

### 8.1 风险

- 现有 iframe 预览的组件外框测量如果不稳定，会直接影响拖动和手柄定位。
- 如果普通流式节点被错误放进布局编辑，会把保存结果改坏。
- 多选与现有文字原位编辑抢焦点，容易出现模式串线。

### 8.2 待确认项

- 第一阶段是否需要立即支持框选，还是先只做修饰键多选。
- 第一阶段缩放手柄做几个方向最合适，是否先只做右下角手柄。
- 现有普通节点是否需要新增持久化标记字段，还是继续复用 `draft-box` 类运行时标记并把它转成可保存状态。

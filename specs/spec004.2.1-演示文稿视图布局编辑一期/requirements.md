# 需求文档 - spec004.2.1-演示文稿视图布局编辑一期

状态：Draft

## 简介

`spec004.2` 已经让静态 HTML 演示文稿具备“能编辑”的基础能力，但当前的布局编辑体验还是半成品：

- 用户只能通过字段改位置和大小
- 不能在画布里直接拖
- 不能拉伸
- 不能多选
- 不能对齐

这不是小毛病，这是演示文稿编辑器最基本的交互缺口。

所以这次要做的事情很具体：

把现有演示文稿视图补成“能做基础版面编辑”的第一版，而且范围必须收紧，不能一脚踩进通用网页编辑器的大坑。

## 术语表

- **System**：CodingNS 静态 HTML 演示文稿编辑器，以及嵌入文件管理后的演示文稿视图
- **布局编辑模式**：以组件位置、尺寸、多选和对齐为主的编辑模式，不等同于文字编辑模式
- **布局可编辑节点**：允许进入位置和尺寸编辑的节点，必须满足明确的几何可写条件
- **几何信息**：节点的 `box.x / box.y / box.width / box.height / box.zIndex`
- **对齐操作**：对多个选中节点批量执行左对齐、右对齐、顶对齐、底对齐

## 范围说明

### In Scope

- 在演示文稿视图里增加布局编辑模式
- 支持符合条件的单个组件拖动位置
- 支持符合条件的单个组件调整尺寸
- 支持多选组件
- 支持多选后的左对齐、右对齐、顶对齐、底对齐
- 支持把布局编辑结果写回 `DocumentProject`
- 支持把布局编辑结果保存回 HTML
- 对不支持布局编辑的节点给出明确限制和提示

### Out of Scope

- 任意网页节点的通用拖拽布局编辑
- 旋转、等距分布、吸附参考线、磁吸网格
- 组合、解组、层级面板重排
- 框选套索、跨页多选
- 复杂 `svg / html` 只读节点的布局编辑
- 自动把 `flex / grid / transform` 布局重写成绝对定位布局

## 需求

### 需求 1：系统必须提供明确的布局编辑入口和模式切换

**用户故事：** 作为演示文稿编辑者，我希望明确进入“布局编辑模式”，这样我知道当前是在改版面，不会和文字编辑状态打架。

#### 验收标准

1. WHEN 用户打开可编辑的演示文稿视图 THEN System SHALL 提供明确的布局编辑入口或模式切换状态。
2. WHEN 用户进入布局编辑模式 THEN System SHALL 让画布选择逻辑优先面向组件外框，而不是只面向文字内容。
3. WHEN 用户退出布局编辑模式 THEN System SHALL 恢复现有文字编辑和样式编辑主链路，不允许两套交互长期互相抢焦点。

### 需求 2：系统必须只允许符合条件的节点参与布局编辑

**用户故事：** 作为维护者，我希望系统明确哪些节点能拖、能缩放，哪些节点不能碰，这样保存链路才不会把原 HTML 改成垃圾。

#### 验收标准

1. WHEN 用户选中节点 THEN System SHALL 根据节点类型、只读状态和几何可写条件判断该节点是否允许布局编辑。
2. WHEN 节点属于只读节点、装饰节点、复杂 HTML 节点或几何来源不稳定节点 THEN System SHALL 禁止布局编辑并给出明确限制说明。
3. WHEN 节点允许布局编辑 THEN System SHALL 保证后续位置和尺寸改动可以写回项目状态并参与保存。

### 需求 3：系统必须支持单节点拖动位置

**用户故事：** 作为演示文稿编辑者，我希望直接在画布里拖动组件位置，而不是每次都去改 `X / Y` 字段。

#### 验收标准

1. WHEN 用户在布局编辑模式下拖动一个布局可编辑节点 THEN System SHALL 实时更新节点位置并在画布中立即反映。
2. WHEN 用户结束拖动 THEN System SHALL 把最新位置写入该节点的几何信息，而不是只停留在临时 DOM 状态。
3. WHEN 用户保存并重新打开文件 THEN System SHALL 保持拖动后的组件位置一致。

### 需求 4：系统必须支持单节点调整尺寸

**用户故事：** 作为演示文稿编辑者，我希望直接拉伸组件大小，而不是只能手工输入宽高。

#### 验收标准

1. WHEN 用户在布局编辑模式下操作尺寸手柄 THEN System SHALL 更新节点宽度和高度，并在画布中立即反映。
2. WHEN 节点尺寸更新成功 THEN System SHALL 保证相关几何信息进入项目状态并参与保存。
3. WHEN 节点不支持尺寸调整 THEN System SHALL 明确禁止该操作，而不是表现成“可以拖但保存后失效”。

### 需求 5：系统必须支持同页多选

**用户故事：** 作为演示文稿编辑者，我希望一次选中多个组件做统一操作，而不是一页里反复一个个点。

#### 验收标准

1. WHEN 用户在同一页内通过约定手势或交互追加选择组件 THEN System SHALL 维护稳定的多选集合。
2. WHEN 多选集合变化 THEN System SHALL 在画布和侧边面板中明确显示当前选中数量和选中目标。
3. WHEN 用户切页、退出布局模式或选区失效 THEN System SHALL 清理不再有效的多选状态，避免跨页脏选区。

### 需求 6：系统必须支持多选后的基础对齐

**用户故事：** 作为演示文稿编辑者，我希望对多个组件做左对齐、右对齐、顶对齐、底对齐，这样我不用自己算像素。

#### 验收标准

1. WHEN 用户对同页多个布局可编辑节点执行左对齐 THEN System SHALL 以稳定基准批量更新这些节点的横向位置。
2. WHEN 用户执行右对齐、顶对齐或底对齐 THEN System SHALL 只修改必要的几何字段，不额外改动文本、样式或节点结构。
3. WHEN 对齐完成后用户保存并重新打开文件 THEN System SHALL 保持对齐后的版面结果一致。

### 需求 7：系统必须保持现有演示文稿编辑主链路不被破坏

**用户故事：** 作为现有用户，我希望新增布局编辑后，原来的文字编辑、保存和导出还能正常工作，而不是引入一堆回归问题。

#### 验收标准

1. WHEN 用户继续使用现有文字编辑、样式编辑和页面切换 THEN System SHALL 保持原有能力可用。
2. WHEN 用户不进入布局编辑模式 THEN System SHALL 不强行改变现有交互主链路。
3. WHEN 新增布局编辑能力上线 THEN System SHALL 不破坏现有 HTML 保存、PDF 导出和 PPTX 导出主链路。

## 非功能需求

### 非功能需求 1：可预测性

1. WHEN 某个节点支持布局编辑 THEN System SHALL 保证该操作结果可保存、可重开、可重现。
2. WHEN 某个节点不支持布局编辑 THEN System SHALL 明确禁止，而不是让用户做出保存不了的假操作。

### 非功能需求 2：交互稳定性

1. WHEN 用户在布局编辑和文字编辑之间切换 THEN System SHALL 避免焦点抖动、误选中和状态串线。
2. WHEN 用户连续执行拖动、缩放和对齐 THEN System SHALL 正确进入撤销历史，不丢失当前选区。

### 非功能需求 3：可维护性

1. WHEN 后续要继续扩展分布、吸附或组合能力 THEN System SHALL 基于统一的多选与几何编辑状态继续扩展，而不是在各个按钮里各写一套逻辑。
2. WHEN 排查布局编辑问题 THEN System SHALL 能区分“节点准入判断错误”“几何更新错误”“HTML 回写错误”三类问题。

## 成功定义

- 演示文稿视图中，符合条件的组件可以直接拖动和拉伸。
- 同页内可以稳定多选，并执行左对齐、右对齐、顶对齐、底对齐。
- 保存后重新打开，位置、尺寸和对齐结果保持一致。
- 不支持布局编辑的节点有明确限制，不再出现“看起来能改，实际上存不住”的假交互。
- 现有文本编辑、页面切换、保存和导出能力不回退。

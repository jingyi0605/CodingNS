# spec003.4-会话活动状态权威源与稳定显示

## 当前定位

这个 Spec 只解决一件事：

- 会话的“活动中 / 已停止 / 已完成 / 已失败 / 已中断”到底由谁说了算

现在的问题不是前端不会显示，而是后端没有单一真相源：

- Host 自己持有的 runtime handle 会给一套状态
- provider 事件或外部 snapshot 会给一套状态
- 原始日志 / 文件推断又会给一套状态
- 前端还会把导航摘要、本地 store、实时事件混着吃

结果就是状态抖动、迟到覆盖、推断态冒充权威态。

一句话说清楚：这一步不是再补一个判断分支，而是把“活动状态”收口成一个唯一、可信、稳定的后端裁决结果。

## 计划覆盖

- 定义统一的会话活动状态模型
- 区分状态来源和可信度
- 为 Host 自己发起的 run 增加 watchdog
- 统一后端 API 和 WS 的状态输出
- 前端只消费后端统一裁决结果，不再自己脑补

## 本阶段明确不做

- 不重写聊天页面结构
- 不把 provider 原始会话格式落库存成第二套正文库
- 不靠操作系统进程扫描作为主状态来源
- 不顺手扩展新的 provider 能力

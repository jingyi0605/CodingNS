# 需求文档 - spec003.1 原生会话实时对话运行时

状态：Draft

## 简介

当前项目已经能发现 `Claude Code` 和 `Codex` 的会话，也能把历史消息读出来展示，但它还不是一个真正能继续对话的产品。现在的核心问题很直接：

- 新建会话主要是在写原生会话文件，不是真正启动 agent
- “继续会话”主要是在读文件，不是真正恢复对话执行
- “发送消息”主要是在追加用户消息，不保证 `Claude Code` / `Codex` 真会接着跑

这会导致两个很糟糕的结果：

1. 页面看起来像聊天，实际上只是一个会话文件浏览器。
2. 用户没法相信“在这里发出去的消息，回到原生 `Claude Code` / `Codex` 里还能接上”。

这次要解决的不是“界面上多一个发送按钮”，而是把真正的对话执行链路打通。参考项目 `C:\Code\CodingNS\data\claudecodeui` 已经证明这条路应该怎么走：`Claude` 走 SDK 流式执行，`Codex` 走 SDK 线程恢复与流式事件，而不是继续拿 jsonl 文件硬凑。

成功后，这个项目要服务三类真实场景：

- 用户在本项目里新开会话，马上实时对话
- 用户加载外部现有会话，在本项目里继续聊
- 用户在本项目里开的会话，之后回到 `Claude Code` / `Codex` 原生环境继续聊，不丢上下文，不分叉

## 术语表

- **System**：`CodingNS`，包含 `user-app`、`host` 和 provider 运行时适配层
- **原生会话**：`Claude Code` 或 `Codex` 自己认可的真实会话，不是本项目自造的聊天记录
- **Provider Runtime**：负责启动、恢复、发送、流式接收和中断原生会话的运行时层
- **运行中会话**：当前已经在执行中的原生会话，可能正在输出消息、推理或调用工具
- **原生会话 ID**：provider 自己的会话标识，例如 Claude session id、Codex thread id
- **运行时事件**：provider 在执行过程中持续产生的增量事件，例如 AI 文本片段、推理、工具调用、完成、失败
- **会话映射**：项目内 `sessionId` 和原生 `providerSessionId` 的绑定关系，用于权限、工作区归属和 UI 路由

## 范围说明

### In Scope

- 新建 `Claude Code` / `Codex` 原生会话并立即进入实时对话
- 加载已有 `Claude Code` / `Codex` 原生会话并继续对话
- 在本项目中创建的会话可回到原生 `Claude Code` / `Codex` 继续
- 后端维护运行中会话注册表，支持恢复订阅、状态查询和中断
- 前端消费真实流式事件，实时刷新消息、推理和工具状态
- 历史消息同步与实时事件合并，保证消息真相只有一份

### Out of Scope

- 新增第三个 provider
- 重新设计整套聊天 UI 视觉风格
- 多人同时协作同一会话
- 离线缓存完整消息副本
- 将 `Claude Code` 和 `Codex` 抽成完全统一、无差异的能力模型

## 需求

### 需求 1：系统必须能新建原生会话并立即开始实时对话

**用户故事：** 作为开发者，我希望在本项目里点击新建会话后就能直接和 AI 实时对话，以便不用再切回原生 CLI 手工启动。

#### 验收标准

1. WHEN 用户在指定工作区选择 `Claude Code` 或 `Codex` 新建会话 THEN System SHALL 通过对应 provider 的真实运行时创建原生会话，而不是只创建一个本地占位记录。
2. WHEN 用户提交首条消息 THEN System SHALL 立即启动该原生会话的执行链路，并持续把 AI 增量输出推送到前端。
3. WHEN 新会话创建成功 THEN System SHALL 保存项目内会话映射和原生会话 ID，后续可以继续恢复这个原生会话。

### 需求 2：系统必须能接着已有的原生会话继续对话

**用户故事：** 作为开发者，我希望把已经在 `Claude Code` 或 `Codex` 里存在的会话加载进来，并继续发送消息，以便不中断我原来的工作流。

#### 验收标准

1. WHEN 用户打开已同步进系统的原生会话 THEN System SHALL 能读取该会话的历史消息、能力描述和最近运行状态。
2. WHEN 用户在该会话继续发送消息 THEN System SHALL 调用对应 provider 的恢复能力，真正把消息发送到原生会话上下文里。
3. WHEN 该原生会话当前已经在外部运行 THEN System SHALL 能识别并订阅它的后续增量事件，而不是创建一个新的分叉会话。

### 需求 3：在本项目中创建的会话必须还能回到原生环境继续

**用户故事：** 作为开发者，我希望在本项目里开的会话，之后回到 `Claude Code` 或 `Codex` 依然能继续，以便不会被锁死在某一个 UI 里。

#### 验收标准

1. WHEN 本项目创建新会话 THEN System SHALL 使用 provider 认可的原生会话创建方式，得到真实原生会话 ID。
2. WHEN 用户之后在原生 `Claude Code` 或 `Codex` 中打开这个会话 THEN 该会话 SHALL 能看到本项目发送过的消息和后续上下文。
3. WHEN System 持久化会话关系 THEN System SHALL 只保存映射关系和必要索引，不得把项目自造 ID 当成原生会话真相。

### 需求 4：实时消息流必须和历史消息同步层保持同一个真相来源

**用户故事：** 作为开发者，我希望实时输出、历史记录和工具状态是同一条链路上的数据，而不是 UI 看到一套、原生会话里又是一套。

#### 验收标准

1. WHEN provider 产生流式事件 THEN System SHALL 将其归一化为统一消息事件，再写入实时通道和历史同步层使用的同一套模型。
2. WHEN 前端收到实时增量和后端历史补偿 THEN System SHALL 以原生消息标识或稳定去重键合并，避免重复渲染。
3. WHEN 消息存在暂态状态（例如发送中、工具执行中） THEN System SHALL 在收到权威事件后收敛为原生真实状态。

### 需求 5：运行中会话必须支持恢复订阅、中断和失败回传

**用户故事：** 作为开发者，我希望会话在运行时可恢复、可中断、出错可见，以便不会遇到“AI 卡住了但页面毫无反馈”的垃圾体验。

#### 验收标准

1. WHEN 前端刷新页面或 WebSocket 断开重连 THEN System SHALL 能重新附着到同一个运行中会话，并继续收到后续事件。
2. WHEN provider 支持中断 THEN System SHALL 暴露中断接口并将中断结果反馈给前端。
3. WHEN provider 执行失败、权限拒绝或运行时崩溃 THEN System SHALL 把错误作为结构化事件回传，而不是只在服务端日志里报错。

### 需求 6：Provider 参数映射必须清楚且可降级

**用户故事：** 作为开发者，我希望模型、推理强度、权限模式这些参数在支持时能生效，不支持时也别装作支持，以便我知道自己到底在控制什么。

#### 验收标准

1. WHEN 前端传入 `model`、`reasoningLevel` 或权限模式 THEN System SHALL 只把 provider 真支持的参数下发给对应运行时。
2. WHEN 某参数当前 provider 不支持 THEN System SHALL 明确忽略并返回可理解的能力说明或限制说明。
3. WHEN 前端读取会话能力 THEN System SHALL 得到基于真实运行时的能力，而不是写死的静态常量。

### 需求 7：系统必须保持工作区归属和安全边界不被破坏

**用户故事：** 作为系统维护者，我希望继续对话时不会把消息发到错误工作区，也不会让用户越权接触不属于自己的会话。

#### 验收标准

1. WHEN 用户对某会话发消息或恢复会话 THEN System SHALL 校验该会话绑定的工作区和用户归属。
2. WHEN 原生会话路径、工作目录或 provider 元数据与项目映射不一致 THEN System SHALL 拒绝继续执行并返回明确错误。
3. WHEN WebSocket 订阅运行中会话 THEN System SHALL 继续沿用现有鉴权和会话归属校验，不允许匿名订阅。

## 非功能需求

### 非功能需求 1：实时性

1. WHEN 用户发送消息 THEN System SHALL 在 500ms 内返回“已受理/发送中”的前端反馈。
2. WHEN provider 开始产生首个流式事件 THEN System SHALL 尽可能在 1 秒内转发到前端，不额外引入轮询延迟。

### 非功能需求 2：可靠性

1. WHEN 页面刷新、WS 重连或短暂网络抖动 THEN System SHALL 尽量恢复到同一运行中会话，而不是重复启动新一轮执行。
2. WHEN Host 重启后运行中注册表丢失 THEN System SHALL 至少能安全退化为“重新读取历史 + 提示当前运行状态不可恢复”，不能伪造仍在运行。

### 非功能需求 3：可维护性

1. WHEN 新增 provider 真实运行时 THEN System SHALL 只需要实现统一的 `Runtime Adapter` 合同，而不是复制整套会话逻辑。
2. WHEN 排查线上消息错乱 THEN System SHALL 能通过会话映射、原生会话 ID、事件序号和原始引用快速定位问题。

## 成功定义

- 用户可以在本项目里新建 `Claude Code` / `Codex` 会话并看到实时输出。
- 用户可以加载外部已有会话并继续对话，且不会分叉出第二条假会话。
- 本项目里创建的会话能在原生 `Claude Code` / `Codex` 中继续。
- 历史同步层和实时运行时层不再互相打架，消息真相只有一份。

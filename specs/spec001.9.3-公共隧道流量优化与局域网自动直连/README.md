# spec001.9.3-公共隧道流量优化与局域网自动直连

## 当前定位

这是 `spec001.9` 下的新子 Spec。

它只解决一件事：

- 把当前“公共隧道能连上，但流量偏大、同网段时还在傻走 relay”的链路，收口成更省流量、更聪明的远程访问体验。

一句人话：
不是再发明一套新的远程访问方案，而是把现有公共隧道这条链路修到不浪费流量、能本地直连就别绕远路。

这次真正要解决的是两个硬问题：

- 现在 relay 数据面有明显的包体膨胀和全量传输，流量消耗不合理
- 客户端虽然已经支持 relay 和 direct 两种传输，但还没有“识别同一台 Host 的局域网地址并自动切过去”的能力

## 计划覆盖

- 远程访问链路里的流量放大点盘点和治理顺序
- Host 候选访问地址模型，不再只剩一个 `baseUrl`
- 客户端对远程 Host 候选地址的探活、验身和自动切换
- 局域网直连优先、relay 热备回退的切换规则
- 远程访问读链路的缓存与版本协商边界
- `workbench` / `fileTree` / `git` / `terminalManager` 这些高频快照的减量传输策略
- 与现有多 HOST、桌面端本机发现、Tailscale、公共隧道设置页并存的规则

## 本阶段明确不做

- 不新造第二套远程访问协议，不推翻 `spec001.9` 已经定下来的端到端加密边界
- 不把公共隧道重写成支持无限多网络供应商的抽象层
- 不做局域网广播扫描、mDNS、UPnP 这类大范围网络发现
- 不在第一阶段就把 relay 的所有 HTTP 链路全部改成全新二进制流式协议
- 不为了“自动切换”破坏用户现有可访问的远程域名和登录态

## 这次的边界

这次必须把边界写死：

- **先做最值钱的改动**：候选地址模型、自动局域网直连、读链路减量
- **后做高风险改动**：relay 传输层协议瘦身

原因很简单：

- 能同网直连时，relay 流量可以直接降到接近零
- 版本协商和增量快照能明显减少“没变也整包重传”
- 传输层二进制化收益很大，但改动面最广，必须排在后面

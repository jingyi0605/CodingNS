# 需求文档 - spec001.9.3 公共隧道流量优化与局域网自动直连

状态：Draft

## 简介

`spec001.9` 已经把公共隧道主链路跑通了，`spec001.9.1` 也把上线和运营边界继续收口了。

但现在还有两个非常现实的问题：

1. 远程访问时流量消耗偏大
2. 客户端和 Host 明明可能已经在同一局域网，却还在继续走 relay

这不是“用户感觉不太好”的小问题，而是当前数据结构和传输策略都还不够好：

- Host 还是单一 `baseUrl` 模型，没有候选地址集合
- 客户端没有“先验证是不是同一台 Host，再自动切本地地址”的机制
- 一些远程读链路还是整包快照思路，没有稳定版本号和差量协商
- relay 数据面对大包体有二次包装放大

这次要解决的事情很明确：

1. 给远程 Host 补“候选连接地址”模型
2. 给客户端补“可达且验身成功时自动局域网直连”
3. 给高频只读链路补“本地缓存 + 版本协商 + 尽量少传”
4. 明确 relay 传输层的后续瘦身边界，但不在第一步把所有协议全推翻

## 术语表

- **候选连接地址**：同一台 Host 对外可用的多个入口，例如局域网 IPv4、Tailscale 地址、当前远程域名
- **验身**：客户端确认一个地址背后确实是“同一台 Host”，而不是随便一个能响应 HTTP 的东西
- **自动局域网直连**：客户端在后台探测到可用局域网地址后，自动把业务请求切到本地地址
- **relay 热备**：局域网直连失败时，客户端立即退回公共隧道，不把用户访问打挂
- **版本协商**：客户端带上自己已知的版本号或摘要，请求服务端只返回变化部分或明确告知“没变”
- **减量传输**：不重复下发完整快照，而是返回差量、复用缓存或直接返回未变化

## 范围说明

### In Scope

- Host 候选连接地址的数据结构和读取接口
- 局域网地址、Tailscale 地址、当前远程域名的优先级规则
- 客户端候选地址探活、验身、切换、失败回退
- 远程访问模式下的连接状态与当前链路来源展示
- 高频只读链路的本地缓存、版本字段、未变化短路
- `workbench`、`fileTree`、`git`、`terminalManager` 的减量传输方案
- relay 流量优化的阶段切分和验收口径

### Out of Scope

- mDNS、Bonjour、子网广播扫全局机器
- 服务端主动反向拨回客户端做 NAT 打洞
- 重新设计现有业务认证体系
- 把所有 HTTP 接口统一重写成流式二进制协议
- 团队共享链路策略、企业网络策略和多租户策略

## 需求

### 需求 1：同一台 Host 必须能表达多个候选访问地址

**用户故事：** 作为远程访问用户，我希望系统知道同一台 Host 不只一个入口，这样客户端才有机会自动选更近、更省流量的那条路。

#### 验收标准

1. WHEN Host 进入远程访问运行态 THEN System SHALL 能返回同一台 Host 的多个候选访问地址，而不是只返回单一 `baseUrl`
2. WHEN 返回候选访问地址 THEN System SHALL 至少标明地址类型、协议、端口、优先级建议和过期语义
3. WHEN 候选地址被客户端使用 THEN System SHALL 能让客户端判断这些地址背后是不是同一台 Host

### 需求 2：客户端必须只在验身成功后自动切本地直连

**用户故事：** 作为用户，我希望系统在局域网可达时自动走本地，但前提是别误连到错误机器，也别把现有远程访问搞挂。

#### 验收标准

1. WHEN 客户端拿到候选地址 THEN System SHALL 在后台探活这些地址，不打断当前会话
2. WHEN 某个局域网地址可达 THEN System SHALL 继续校验该地址背后的 Host 身份是否与当前远程 Host 一致
3. WHEN 可达且验身成功 THEN System SHALL 自动把后续业务流量切到该局域网地址
4. WHEN 自动切换失败或直连中断 THEN System SHALL 立即回退到 relay，不要求用户手动修复
5. WHEN 用户关闭自动本地直连 THEN System SHALL 继续允许强制走远程链路

### 需求 3：远程访问高频读链路必须尽量少传

**用户故事：** 作为移动端或公网用户，我希望页面刷新、工作台同步和状态更新不要每次都整包重传，浪费流量也拖慢响应。

#### 验收标准

1. WHEN 客户端已经持有最近一次快照 THEN System SHALL 支持带版本号或摘要发起后续请求
2. WHEN 服务端判定数据未变化 THEN System SHALL 返回“未变化”结果，而不是再次返回完整正文
3. WHEN 服务端判定数据有变化 THEN System SHALL 优先返回差量或最小必要字段，而不是无条件全量重发
4. WHEN 客户端刚重新进入页面 THEN System SHALL 能先使用本地缓存快速恢复最近视图，再在后台做校验

### 需求 4：高频快照必须有清晰的减量顺序

**用户故事：** 作为维护者，我希望先处理最耗流量、最容易落地的快照链路，而不是一次把整个系统改成没人看得懂的协议泥球。

#### 验收标准

1. WHEN 本阶段落地 THEN System SHALL 优先覆盖 `workbench`、`fileTree`、`git`、`terminalManager` 四类高频快照
2. WHEN `git` 状态没有变化 THEN System SHALL 不再重复下发昂贵的历史和分支数据
3. WHEN 文件树或工作台快照未变化 THEN System SHALL 支持沿用客户端已有快照
4. WHEN 某条链路暂时无法做真正差量 THEN System SHALL 先补版本短路，避免“没变也整包发”

### 需求 5：现有多 HOST、Tailscale 和公共隧道语义不能被破坏

**用户故事：** 作为现有用户，我希望升级后以前能连的 Host 继续能连，而不是为了自动优化把旧行为搞坏。

#### 验收标准

1. WHEN 用户继续使用手工配置的远程域名 THEN System SHALL 保持现有访问方式可用
2. WHEN 用户配置了 Tailscale 地址 THEN System SHALL 允许把 Tailscale 地址纳入候选连接地址，但不强制覆盖现有选择
3. WHEN 客户端无法获取候选地址或后台探活失败 THEN System SHALL 继续使用当前远程链路
4. WHEN Host 还是旧版本 THEN System SHALL 保持向后兼容，不把旧 Host 直接判成不可用

### 需求 6：relay 传输层优化必须分阶段，而不是一次推翻

**用户故事：** 作为维护者，我希望把风险最高的传输层改动放到后面，先拿到大头收益，再慢慢处理协议瘦身。

#### 验收标准

1. WHEN 本阶段立项 THEN System SHALL 先交付候选地址和自动局域网直连
2. WHEN 本阶段继续推进 THEN System SHALL 先交付高频读链路的缓存与版本协商
3. WHEN 讨论 relay 二进制化 THEN System SHALL 作为后续阶段单独切分，不与第一步自动直连绑死交付

## 非功能需求

### 非功能需求 1：向后兼容

1. WHEN 新客户端连接旧 Host THEN System SHALL 能继续走现有链路，不得因为缺少新字段直接失败
2. WHEN 新 Host 面对旧客户端 THEN System SHALL 不要求旧客户端必须理解新候选地址结构

### 非功能需求 2：稳定性

1. WHEN 自动切换链路 THEN System SHALL 避免频繁抖动，不得在直连和 relay 之间来回乱跳
2. WHEN 直连探测失败 THEN System SHALL 在后台处理失败，不把当前前台会话直接打断

### 非功能需求 3：安全性

1. WHEN 客户端尝试自动局域网直连 THEN System SHALL 先做 Host 身份校验，再切业务流量
2. WHEN 身份校验失败 THEN System SHALL 不得把该地址纳入可用直连入口

### 非功能需求 4：可观测性

1. WHEN 链路来源发生变化 THEN System SHALL 能记录当前使用的是 `relay`、`lan`、`tailscale` 或其他候选入口
2. WHEN 远程访问流量优化上线 THEN System SHALL 能比较切换前后的流量和命中情况

## 成功定义

- Host 不再只有单一 `baseUrl` 视角，而是能表达多个候选入口
- 客户端能在后台发现并验证同一台 Host 的局域网地址
- 局域网可达时自动直连，不可达时稳定回退 relay
- 高频只读链路开始支持本地缓存和版本协商
- 远程访问流量明显下降，且不破坏现有远程可用性

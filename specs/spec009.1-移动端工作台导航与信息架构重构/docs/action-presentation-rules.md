# 动作呈现规则

这份文档回答的是：

- 一个动作到底应该是按钮、菜单、sheet，还是编辑模式

如果这件事不先定，后面实现时就会回到最熟悉也最烂的做法：

- 能塞图标就先塞图标

## 1. 总原则

### 1.1 先分级，再决定控件

任何动作都先回答两个问题：

1. 这个动作是不是高频主流程
2. 这个动作误触代价大不大

### 1.2 手机上禁止默认思路

- 禁止“默认就是小图标”
- 禁止把 3 个以上次操作长期并排暴露在标题栏
- 禁止把低频高认知成本动作做成主界面常驻按钮

## 2. 呈现方式规则

### 2.1 主操作

判断标准：

- 高频
- 用户完成主流程离不开
- 需要快速直达

推荐呈现：

- H5：顶部主按钮或页面底部主按钮
- iOS：Navigation Bar 右侧主按钮
- Android：FAB 或 Top App Bar 主按钮

例子：

- 新建会话
- 发送消息
- 进入当前工作区的主任务

### 2.2 常用但不必常驻的大动作

判断标准：

- 经常使用
- 但不值得占据主按钮位

推荐呈现：

- 顶部文字按钮
- 顶部 icon + 明确标签
- 工具首页入口

例子：

- 搜索
- 切换工具页
- 收藏

### 2.3 次操作

判断标准：

- 低频
- 不影响主流程
- 常常和某个对象绑定

推荐呈现：

- 更多菜单
- 长按菜单
- bottom sheet / action sheet

例子：

- 重命名
- 克隆工作区
- 导入工作区
- 切换工作区

### 2.4 风险操作

判断标准：

- 误触会有明显损失
- 操作前需要让用户停一下

推荐呈现：

- 菜单后再确认
- 编辑模式
- 独立确认流

例子：

- 归档
- 批量归档
- 高风险提交

## 3. 平台差异规则

### 3.1 H5 移动端

- 不追求假原生
- 更重视按钮可读性和点击区
- 更多动作优先放 `sheet` 或菜单列表

### 3.2 iOS

- 主操作优先放 Navigation Bar
- 次操作优先放 `menu`、`context menu`、`action sheet`
- 列表对象相关动作可以长按呼出

### 3.3 Android

- 主操作优先考虑 FAB 或 Top App Bar 主按钮
- 次操作优先放 overflow menu 或 bottom sheet
- 列表对象相关动作可以长按或用 contextual action

## 4. 当前动作的标准答案

| 动作 | 标准呈现 | 说明 |
| --- | --- | --- |
| 新建会话 | 主操作 | 必须保留一级直达 |
| 发送消息 | 主操作 | 固定在输入区 |
| 搜索 | 常用动作 | 顶部入口 |
| 导入工作区 | 次操作 | 更多菜单 |
| 克隆工作区 | 次操作 | 更多菜单 |
| 切换工作区 | 次操作 | 列表点击或菜单 |
| 批量选择会话 | 风险 / 低频动作 | 编辑模式入口 |
| 重命名会话 | 次操作 | 行尾菜单或长按 |
| 收藏会话 | 常用动作 | 行尾菜单或滑动 |
| 归档会话 | 风险动作 | 菜单 + 确认 |
| 文件 / Git / 终端 | 能力入口 | 工具页，不再是右侧栏 tab |

## 5. 标题栏容量规则

### 5.1 手机端标题栏最多常驻什么

- 返回
- 标题
- 1 个主操作
- 1 个更多菜单

已经到头了。

再继续塞，就是垃圾。

### 5.2 什么时候必须用“更多”

满足任意一条就应该进“更多”：

- 不是高频主流程
- 用户第一次进入页面时不需要立刻看到
- 动作超过 2 个
- 误触风险高

## 6. 验收口径

后续评审时，看到下面任何一种情况，都算不通过：

1. 手机标题栏并排 3 个以上小图标
2. 低频动作和主操作抢一级位置
3. 文件 / Git / 终端还在手机上作为右侧栏 tab 存在
4. 用户必须打开抽屉才能完成主操作

# 需求文档 - spec009.1 移动端工作台导航与信息架构重构

状态：Draft

## 简介

当前 `apps/user-app` 的工作台，桌面端思路太重。

现在的真实情况是：

- PC 端是左导航 + 中舞台 + 右信息栏的三栏结构
- 移动端虽然有断点和抽屉，但本质上还是把桌面侧栏藏进手机
- 左右边缘手柄、抽屉、桌面式小图标、密集工具入口，都会让手机体验变差

真正的问题不是“功能太多”，而是“手机上的入口排得太蠢”。

这次要解决的事很明确：

1. 保留 PC 端完整功能
2. 让 H5 移动端、iOS、Android 分别按各自习惯呈现
3. 把当前三栏工作台改造成移动端可理解、可返回、可触达的结构

## 术语表

- **PC 三栏工作台**：当前 `workbench` 的左导航、中央主舞台、右信息栏结构
- **紧凑宽度**：手机竖屏等单栏优先场景
- **中宽度**：大屏手机横屏、小平板、折叠屏半展开等可显示列表 + 详情的场景
- **大宽度**：平板、桌面 Web、桌面壳等可恢复双栏或三栏的场景
- **工作区首页**：移动端进入后的工作区总览页
- **工作区详情页**：某个工作区内的会话、文件、Git、终端、进程入口页
- **会话详情页**：以消息流和输入区为核心的全屏对话页
- **工具页**：承载文件、Git、终端、进程、日志等辅助能力的页或子页
- **主操作**：用户高频、需要一键直达的动作，例如新建会话、发送消息
- **次操作**：用户低频或带风险的动作，例如归档、批量选择、切换工作区

## 范围说明

### In Scope

- 重新定义移动端工作台的信息架构
- H5 移动端、iOS、Android 的导航容器和页面职责
- 当前 PC 三栏各区域到移动端页面的映射关系
- 当前桌面小图标动作改造成移动端按钮、菜单、sheet、全屏页的规则
- 会话页、工作区页、工具页的职责边界
- 紧凑宽度、中宽度、大宽度下的响应式策略
- `apps/user-app` 中移动端壳、平台 UI、共享路由意图的边界

### Out of Scope

- 重写 `spec003` 到 `spec008` 已定义的业务协议
- 在本子 Spec 中详细设计通知、分享、权限、生物识别等系统适配接口
- 桌面端信息架构重做
- 新增当前 PC 端尚不存在的业务能力

## 需求

### 需求 1：移动端必须保留 PC 端完整功能，但操作路径必须重新组织

**用户故事：** 作为用户，我希望手机上能完成和 PC 端同一套事情，但不希望为了完成一件事翻两个抽屉、点一排小图标。

#### 验收标准

1. WHEN 某项能力已在 PC 端工作台提供 THEN System SHALL 在移动端提供等价入口和完成路径，不允许因为进入了移动端就直接消失。
2. WHEN 移动端承载 PC 端能力 THEN System SHALL 优先通过页面重组、操作分层、菜单归并来简化路径，而不是删功能。
3. WHEN 用户执行高频主流程 THEN System SHALL 让入口一眼可见，不要求用户先理解桌面三栏结构。

### 需求 2：当前 PC 三栏工作台必须被拆成适合移动端的页面结构

**用户故事：** 作为移动端用户，我希望手机看到的是正常的页面流，而不是左右侧栏缩小后的抽屉迷宫。

#### 验收标准

1. WHEN 当前 PC 端左侧导航承载工作区、会话、搜索和管理入口 THEN System SHALL 将其拆分到工作区页、会话页、搜索页或顶部入口，不再作为移动端常驻侧栏。
2. WHEN 当前 PC 端中间主舞台承载消息流或终端主内容 THEN System SHALL 在移动端保留为全屏主内容区。
3. WHEN 当前 PC 端右侧信息栏承载文件、Git、终端管理等辅助能力 THEN System SHALL 将其改造成工具页、sheet 或全屏子页，而不是移动端常驻第二个侧栏。

### 需求 3：H5 移动端必须遵守移动 Web 最佳实践，而不是假装自己是桌面网页

**用户故事：** 作为手机浏览器用户，我希望 H5 端像正常移动 Web 应用，不想被桌面布局、浏览器工具栏抖动和奇怪滚动折腾。

#### 验收标准

1. WHEN 应用运行在 H5 移动端 THEN System SHALL 使用单栏优先的响应式壳，并正确处理 `safe area`、动态视口高度、键盘顶起和底部固定导航。
2. WHEN 用户在 H5 移动端进行高频导航 THEN System SHALL 提供明确的应用内返回和一级导航入口，而不是只依赖浏览器返回。
3. WHEN 页面包含触控入口 THEN System SHALL 使用适合手指点击的点击区和可读标签，不允许继续依赖桌面级小图标。

### 需求 4：iOS 端必须遵循 iPhone 用户熟悉的导航和呈现方式

**用户故事：** 作为 iPhone 用户，我希望应用像 iOS 应用，而不是 Android 壳或缩小网页。

#### 验收标准

1. WHEN 应用运行在 iOS 紧凑宽度场景 THEN System SHALL 优先使用 Tab Bar、Navigation Bar、push、sheet、full-screen modal 等结构。
2. WHEN 用户从列表进入详情页 THEN System SHALL 支持符合 iOS 习惯的返回路径和手势，不把核心入口压在左右边缘手柄上。
3. WHEN 页面存在次操作 THEN System SHALL 优先通过导航栏菜单、context menu、action sheet 呈现，而不是在头部塞满小图标。

### 需求 5：Android 端必须遵循 Android / Material 的导航和反馈习惯

**用户故事：** 作为 Android 用户，我希望应用尊重系统返回、底部导航和菜单习惯，而不是套一层 iOS 样子。

#### 验收标准

1. WHEN 应用运行在 Android 紧凑宽度场景 THEN System SHALL 优先使用 Top App Bar、Bottom Navigation、Bottom Sheet、标准 back stack 等结构。
2. WHEN 用户使用系统返回或 predictive back THEN System SHALL 与页面导航状态保持一致，不得因为自定义边缘手势而冲突。
3. WHEN 页面存在多项次操作 THEN System SHALL 优先收进 overflow menu、bottom sheet 或 contextual action，而不是继续堆桌面 icon cluster。

### 需求 6：PC 端的小图标操作必须改造成适合移动端的操作模型

**用户故事：** 作为移动端用户，我希望知道按钮是干什么的，也点得到，而不是看见一排意义不明的小图标。

#### 验收标准

1. WHEN 某个动作在 PC 端只表现为小图标 THEN System SHALL 在移动端将其改造成带文字的按钮、菜单项、sheet 动作或长按动作之一。
2. WHEN 某个动作是高频主操作 THEN System SHALL 保留一级直达入口，而不是塞进深层菜单。
3. WHEN 某个动作是低频、批量或高风险操作 THEN System SHALL 移入“更多”菜单、编辑模式或确认流，不继续常驻占位。

### 需求 7：文件、Git、终端、进程等辅助能力必须以“工具流”接入，而不是继续占据移动端侧栏

**用户故事：** 作为用户，我希望会话页保持沉浸，但也能方便进入文件、Git、终端和进程。

#### 验收标准

1. WHEN 用户处于会话详情页 THEN System SHALL 让消息流和输入区成为绝对主内容，不让文件树、Git 面板、终端管理器长期挤占主视区。
2. WHEN 用户需要文件、Git、终端、进程等辅助能力 THEN System SHALL 通过工具页、上下文 tab、sheet 或全屏子页承载。
3. WHEN 工具进入重操作状态 THEN System SHALL 允许升级为全屏页面，不强迫用户在半屏抽屉里完成复杂操作。

### 需求 8：移动端必须基于宽度等级自适应，不能只靠一个断点硬切

**用户故事：** 作为平板和折叠屏用户，我希望界面能利用更多空间，而不是单栏页面硬拉宽。

#### 验收标准

1. WHEN 页面处于紧凑宽度 THEN System SHALL 采用单栏堆栈式结构。
2. WHEN 页面处于中宽度 THEN System SHALL 允许采用列表 + 详情双区或主内容 + 辅助区结构。
3. WHEN 页面处于大宽度 THEN System SHALL 允许回到双栏或三栏工作台，但不破坏移动端已建立的导航意图。

### 需求 9：移动端改造不能破坏桌面端现有工作台

**用户故事：** 作为现有用户，我希望移动端重构不会顺手把桌面端搞坏。

#### 验收标准

1. WHEN 引入移动端专属壳和页面 THEN System SHALL 保持桌面端三栏工作台的主路径不变。
2. WHEN 共享业务状态与路由意图被重构 THEN System SHALL 把平台差异限制在移动端壳、平台 UI 和自适应层，不污染桌面主流程。
3. WHEN 回归 PC 端 THEN System SHALL 继续支持当前工作区、会话、文件、Git、终端等工作流。

## 非功能需求

### 非功能需求 1：可发现性与可触达性

1. WHEN 页面提供可点击动作 THEN System SHALL 保证触控点击区足够大，文字或图标语义清楚。
2. WHEN 某个动作对流程关键 THEN System SHALL 让用户无需猜测它藏在哪个边缘或抽屉里。

### 非功能需求 2：状态连续性

1. WHEN 用户在工作区、会话、工具页之间切换 THEN System SHALL 保持当前工作区、当前会话、当前工具上下文连续。
2. WHEN 设备旋转、窗口宽度变化或键盘弹出 THEN System SHALL 保持页面状态和输入上下文，不出现主流程丢失。

### 非功能需求 3：实现边界

1. WHEN 实现移动端工作台 THEN System SHALL 优先改造 `apps/user-app`，不得另起一个脱节的历史前端目录。
2. WHEN 新增页面文案 THEN System SHALL 继续使用统一 i18n 字典，不允许硬编码用户可见文案。

## 成功定义

- 用户在 H5 移动端、iOS、Android 上都能完成与 PC 端等价的主工作流。
- 当前桌面三栏不再被粗暴缩成手机双抽屉，而是被拆成清晰的移动端页面结构。
- 小图标和密集工具入口被改造成手机用户可理解、可触达的操作模型。
- iOS 看起来像 iOS，Android 看起来像 Android，H5 看起来像合格的移动 Web 应用。

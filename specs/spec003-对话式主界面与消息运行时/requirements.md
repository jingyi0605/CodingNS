# 需求文档 - spec003 对话式主界面与消息运行时

状态：Draft

## 简介

这个 Spec 要解决的是：我们不能把产品做成“后台页面 + 一个聊天框”。
主界面必须把对话放在正中间，把消息运行时做稳，把输入区做成高频操作面板，并且保证能力差异、登录态和断线重连都可控。

这一步的价值很直接：

- 用户打开后第一眼就是会话工作区，不是杂乱控制台
- 不同 CLI 能力差异可见、可理解、可降级
- 会话消息只来自 Host / provider，不造第二份假聊天记录
- 未登录用户看不到受保护数据

## 术语表

- **System**：`码不能停` 客户端与 `CodingNS Host` 交互层
- **Session Runtime（会话运行时）**：管理会话消息加载、增量更新、发送状态、重连状态的前端运行时模块
- **Capability Descriptor（能力描述）**：后端返回的能力声明，用于告诉前端某个 provider / session 支持哪些操作
- **Auth Guard（登录保护）**：在页面和请求层统一拦截未登录访问的机制
- **Raw Reference（原始引用）**：消息可追溯到 provider 原始消息的引用标识

## 范围说明

### In Scope

- 对话主界面的信息架构和交互边界
- 会话消息渲染与消息运行时状态管理
- 输入区复合操作面板的能力门控
- 会话头部的状态与能力提示
- 已登录态下的数据访问约束
- WebSocket 实时更新与断线重连体验

### Out of Scope

- 文件 / Git / 终端 / 进程的具体业务实现
- provider 适配实现细节（由 `spec002` 负责）
- 团队协作、多人会话权限模型
- 桌面壳与移动壳分发策略（由 `spec008`、`spec009` 负责）

## 需求

### 需求 1：主界面必须以对话为工作区

**用户故事：** 作为高频使用 AI CLI 的开发者，我希望打开页面就进入会话工作区，以便我能直接续接工作，而不是在后台风页面里找入口。

#### 验收标准

1. WHEN 用户进入会话页 THEN System SHALL 让消息流成为视觉中心，并把输入区放在高频操作路径上。
2. WHEN 桌面端展示多栏布局 THEN System SHALL 保持中间区域为对话工作区，侧栏只作为上下文辅助，不抢主焦点。
3. WHEN 移动端展示会话页 THEN System SHALL 优先保证消息沉浸和输入舒适度，不把复杂工具面板堆到主视图。

### 需求 2：页面行为必须由能力描述驱动

**用户故事：** 作为用户，我希望不同 CLI 的可用功能差异被明确展示，以便我知道当前会话能做什么、不能做什么。

#### 验收标准

1. WHEN 页面加载会话上下文 THEN System SHALL 读取 provider / session 的 `Capability Descriptor` 作为功能门控依据。
2. WHEN 某能力不支持 THEN System SHALL 隐藏或置灰对应操作，并给出可理解的原因提示。
3. WHEN 开发新增或修改交互入口 THEN System SHALL 通过统一门控模块处理能力差异，不允许在多个组件散落 `if provider === ...` 分支。

### 需求 3：会话消息必须只有一个真相来源

**用户故事：** 作为用户，我希望看到的消息和 CLI 原始会话一致，以便我续接时不会遇到“前端一套、CLI 一套”的混乱。

#### 验收标准

1. WHEN 会话页加载历史消息 THEN System SHALL 通过 Host 读取 provider 原始会话链路返回的数据，不使用前端自造持久聊天记录。
2. WHEN 页面渲染消息 THEN System SHALL 保留 `Raw Reference` 追溯能力，用于定位消息来源。
3. WHEN 消息更新发生冲突 THEN System SHALL 以 Host 同步结果为准，前端本地状态只做暂态展示。

### 需求 4：所有受保护数据必须建立在已登录态之上

**用户故事：** 作为系统管理员，我希望未登录用户不能访问会话数据，以便工作区信息不会裸奔暴露。

#### 验收标准

1. WHEN 用户未登录访问会话相关页面 THEN System SHALL 拦截并跳转到登录流程，不展示任何受保护数据。
2. WHEN access token 失效 THEN System SHALL 触发刷新或重新登录流程，并阻断受保护请求继续执行。
3. WHEN 建立 WebSocket 会话通道 THEN System SHALL 在握手阶段附带并校验登录凭证，校验失败时拒绝订阅。

### 需求 5：消息运行时必须支持实时更新和断线重连

**用户故事：** 作为在弱网络场景下使用移动端或远程访问的用户，我希望断线后能自动恢复会话同步，以便不中断工作。

#### 验收标准

1. WHEN 网络短暂中断 THEN System SHALL 把会话状态切到重连中，并提示当前连接状态。
2. WHEN 连接恢复 THEN System SHALL 自动重订阅并补齐缺失消息，保证消息序列连续。
3. WHEN 重连失败达到阈值 THEN System SHALL 给出明确错误提示和手动重试入口，不静默失败。

### 需求 6：输入区必须是复合操作面板

**用户故事：** 作为重度用户，我希望输入区不仅能发文字，还能直接看到关键上下文和可执行操作，以便减少来回跳转。

#### 验收标准

1. WHEN 用户进入会话页 THEN System SHALL 提供输入框、发送控制、会话状态提示和能力相关快捷操作。
2. WHEN 某快捷操作受能力限制 THEN System SHALL 在输入区直接展示限制状态与原因，不让用户点了才报错。
3. WHEN 用户发送消息 THEN System SHALL 显示发送中、成功、失败三态，并支持失败重试。

## 非功能需求

### 非功能需求 1：响应性能

1. WHEN 用户打开会话页 THEN System SHALL 在 2 秒内完成首屏骨架与基础状态呈现（不含超长历史全量加载）。
2. WHEN 历史消息分页加载 THEN System SHALL 保持滚动与输入响应，不因单次请求阻塞主交互。

### 非功能需求 2：可靠性

1. WHEN WebSocket 连接抖动 THEN System SHALL 自动重连并保持状态机一致，不出现“已连接但不收消息”的假状态。
2. WHEN Host 返回能力描述变更 THEN System SHALL 在当前会话中即时更新门控状态，避免旧按钮继续可点。

### 非功能需求 3：可维护性

1. WHEN 新 provider 接入 THEN System SHALL 在不改页面主流程的前提下，仅通过 capability 映射完成大部分 UI 行为适配。
2. WHEN 发生线上消息错乱问题 THEN System SHALL 能通过日志和原始引用快速定位是渲染问题、同步问题还是 provider 数据问题。

## 成功定义

- 交付后，用户能在桌面端和移动端稳定续接同一会话，不再出现前端自造聊天记录分叉。
- 交付后，能力差异在会话头部和输入区可见，且不再出现 scattered provider 特判。
- 交付后，未登录无法访问受保护会话数据，WebSocket 未鉴权连接被拒绝。
- 交付后，断线重连后可补齐消息并恢复交互，失败时有明确反馈路径。

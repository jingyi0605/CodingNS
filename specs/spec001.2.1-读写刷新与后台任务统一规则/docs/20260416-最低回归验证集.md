# 20260416-最低回归验证集

这份文档只定义“最低限度必须做什么”。
目标是防止新增服务只测功能，不测卡顿、抖动和长期运行退化。

## 1. 适用范围

满足任意一条就必须执行这份验证集：

1. 新增或改动了刷新型服务（含 `schedule/refresh/ensure/invalidate`）
2. 新增或改动了 watcher / 订阅 / 广播链路
3. 新增或改动了 `TaskManager` 任务类型
4. 新增或改动了缓存 + 脏标记 + 冷却策略

## 2. 最低验证项（必须全部通过）

| 编号 | 验证项 | 通过标准 | 证据 |
| --- | --- | --- | --- |
| V1 | 纯读语义验证 | `get/list/read/peek` 入口不触发后台任务入队 | 测试断言 + 日志片段 |
| V2 | 显式刷新语义验证 | 只有显式刷新入口会推进后台任务 | 测试断言 |
| V3 | 去重与冷却验证 | `running` 不重复入队，`cooldown` 无新脏标记时复用结果 | 测试断言 + 任务计数 |
| V4 | 失败兜底验证 | 刷新失败时返回契约稳定（最近结果或明确降级） | 测试断言 |
| V5 | watcher 生命周期验证 | 订阅关闭后 watcher/timer/AbortController 释放 | 测试断言 + 资源计数 |
| V6 | 广播链路验证 | 广播不直接现算重任务，只读缓存或最近结果 | 测试断言 |
| V7 | 高频触发稳态验证 | 30 秒高频事件下没有明显重复重活风暴 | 指标快照 |
| V8 | 长稳验证 | 连续运行 30 分钟后关键任务耗时和队列无持续恶化 | 指标对比 |

## 3. 指标采集口径（必须记录）

至少记录以下指标，缺任何一个都不算完成：

1. 任务启动次数、去重次数、完成次数、失败次数、超时次数
2. 任务平均执行时长和 P95（如果当前框架没有 P95，先记录最大值）
3. 缓存命中次数和命中率
4. watcher 数量、事件触发频率、释放次数
5. 事件循环延迟或主线程阻塞相关指标

## 4. 推荐执行顺序（快）

1. 先跑定向集成测试：覆盖 V1~V6
2. 再跑短时压力：高频触发 30 秒，覆盖 V7
3. 最后跑长稳观察：30 分钟，覆盖 V8

如果时间非常紧，允许先合并 V1~V6 + V7，V8 作为发布前门槛，但必须写清补测时间。

当前规格里已经有三类可以直接复用的定向用例：

1. `tests/integration/workbench-service.test.ts`
2. `tests/integration/workbench-ws-hub.test.ts`
3. `tests/integration/session-history-background-tasks.test.ts`

以后新增类似服务时，优先按这三类测试思路补，不要再从零发明一套名字和断言口径。

## 6. 验收输出格式（必须）

每次回写 `tasks.md` 时，验证结果至少包含：

1. 跑了哪些测试（文件或测试名）
2. 哪些指标有对比（开始值/结束值）
3. 是否存在残留风险（有就写清楚）

示例：

- 已通过 `tests/integration/workbench-*.test.ts` 的定向用例
- 30 秒高频触发下 `workspace.discovery` 启动次数从每秒 20+ 降到每秒 2 以下
- 30 分钟长稳期间未出现持续上升的排队时长
- 残留风险：大仓库 watcher 句柄上限仍需继续观察

对这次 `spec001.2.1` 的工作台治理，最低应至少补下面三句：

- `getSnapshot()` 已验证为纯读，不再隐式推进 discovery
- Git watcher 事件已验证经过 quiet window 合并，不会连续触发刷新风暴
- 工作区状态补刷已验证 `running` 合并脏请求、`failed` 进入冷却后再重试

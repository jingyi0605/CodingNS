# 20260416-新增服务接入检查清单

这份清单的目标只有一个：
新增服务在动手写代码前，先把读、写、刷新、watcher、任务、缓存、指标讲清楚。

如果下面的问题答不清，先别写代码。

## 1. 使用方式

1. 先明确这次新增的是“读接口”“写接口”“刷新任务”还是“重扫描任务”
2. 按下面 8 个部分逐项填写
3. 代码评审时按同一份清单逐项复核
4. 没通过的项要写“暂不处理原因”和“补齐计划”

当前仓库里已经有三个现成例子，可以直接对照：

1. `WorkbenchService.getSnapshot()` 现在是纯读入口，不能再顺手排 discovery
2. `WorkspaceFileWatcher` 现在把文件树和 Git watcher 分开，文件树只盯展开目录，Git 只盯 `.git` 元数据
3. `WorkbenchWsHub` 里的 Git 刷新现在走 quiet window 合并，不再靠高频 abort 硬顶

## 2. 基础信息

| 项 | 必填内容 |
| --- | --- |
| 服务名 | 例如 `workspace-management-service` |
| 目标用户场景 | 一句话说明用户要完成什么 |
| 主入口 | HTTP / WS / 定时器 / 文件事件 / 其他 |
| 主要模块文件 | 预计改哪些文件 |
| 风险等级 | 低 / 中 / 高（按主线程压力和触发频率） |

## 3. 读路径检查（必须）

| 检查项 | 通过标准 | 结果 |
| --- | --- | --- |
| 方法分类 | 每个入口方法都归类到五类之一：纯读 / 缓存读 / 请求内写 / 后台刷新 / 重扫描 | `PASS/FAIL` |
| 只读命名 | `get/list/read/peek` 不排任务、不改缓存状态、不发广播 | `PASS/FAIL` |
| 混合语义 | 读 + 刷新是否拆成“纯读入口 + 显式刷新入口” | `PASS/FAIL` |
| 结果契约 | 返回值是否能表达“最近结果 + 是否过期” | `PASS/FAIL` |

## 4. 写路径检查（必须）

| 检查项 | 通过标准 | 结果 |
| --- | --- | --- |
| 请求内写边界 | 仅单资源、短事务、必须立即返回的写操作留在请求链路 | `PASS/FAIL` |
| 重写拆分 | 批量 upsert/delete/关系修正已分批处理并主动让出事件循环 | `PASS/FAIL` |
| 一致性边界 | 失败时不会写一半靠隐式重试补救 | `PASS/FAIL` |

## 5. 刷新与任务检查（必须）

| 检查项 | 通过标准 | 结果 |
| --- | --- | --- |
| 刷新状态模型 | 资源状态包含 `fresh/stale/running/cooldown/failed` | `PASS/FAIL` |
| 最小状态字段 | `dirtyReasons`、`lastRequestedAt`、`lastStartedAt`、`lastCompletedAt`、`lastFailedAt`、`nextAllowedAt`、`runningTaskId` 完整 | `PASS/FAIL` |
| 去重策略 | `running` 合并脏标记，`cooldown` 复用最近结果 | `PASS/FAIL` |
| TaskManager 准入 | 跨请求、需观测、需取消/超时/重试的任务已进 `TaskManager` | `PASS/FAIL` |
| 私有 inflight 边界 | 仅用于短生命周期同资源 Promise 复用，没有演化成私有任务系统 | `PASS/FAIL` |

## 6. watcher 与订阅检查（必须）

| 检查项 | 通过标准 | 结果 |
| --- | --- | --- |
| 监听范围 | 优先当前目录/展开节点/`.git`，默认禁止整仓库递归 watcher | `PASS/FAIL` |
| 生命周期 | 订阅关闭后 watcher、timer、AbortController 会及时释放 | `PASS/FAIL` |
| 广播职责 | 广播链路只读缓存，不在广播前同步现算重任务 | `PASS/FAIL` |
| 观测口径 | watcher 数量、触发频率、释放日志可观测 | `PASS/FAIL` |

## 7. 缓存与失效检查（必须）

| 检查项 | 必填内容 | 结果 |
| --- | --- | --- |
| 缓存键 | 明确资源 key（不能用模糊 key） | `PASS/FAIL` |
| TTL | 写明 TTL 和理由 | `PASS/FAIL` |
| 脏标记来源 | 文件变化 / 手动刷新 / 定时器 / 其他 | `PASS/FAIL` |
| 冷却策略 | 冷却时长、触发条件、回到 `stale` 的条件 | `PASS/FAIL` |
| 兜底策略 | 刷新失败时返回最近结果还是空结果，必须写清 | `PASS/FAIL` |

## 8. 指标与日志检查（必须）

| 检查项 | 通过标准 | 结果 |
| --- | --- | --- |
| 任务指标 | 至少能看排队时长、执行时长、成功/失败/超时/取消 | `PASS/FAIL` |
| 主线程影响 | 能看到事件循环压力变化或批处理耗时 | `PASS/FAIL` |
| 缓存命中 | 能看到缓存命中率与重复触发情况 | `PASS/FAIL` |
| 错误定位 | 错误日志包含资源 key、触发来源、任务类型 | `PASS/FAIL` |

## 9. 合入门槛

必须同时满足下面三条才能合入：

1. 上面 8 个部分没有 `FAIL`
2. 最低回归验证集已执行并记录结果
3. `tasks.md` 对应任务已回写 `DONE`，写清验证证据

如果这次改动触发了工作台、Git 面板、文件树、会话列表其中任意一条链路，评审时必须额外回答一句人话：

- “这次改动最容易重新把哪条链路拖慢？”
- “我这次用什么边界把它钉住了？”

## 10. 常见拒绝理由（评审直接打回）

1. `get*` 方法里偷偷 enqueue 刷新任务
2. 私有 `inflight` 长出重试、定时器、跨入口触发
3. watcher 默认监听整个工作区且没有成本说明
4. 刷新失败后没有最近结果兜底，直接把入口打挂
5. 只测功能，不测长时间运行后的卡顿与抖动

# 20260416-全仓库读写刷新现状盘点

这份盘点只回答四个问题：

1. 当前仓库里哪些地方已经做对了
2. 哪些地方是确定的反模式
3. 哪些地方不是绝对错误，但边界没写清
4. 第一批应该先改谁

## 1. 已经做对的地方

### 1.1 Butler 总览已经走摘要，不再先造整锅快照

正例：

- `apps/host/src/modules/butler/context-aggregator.ts`

现状：

- `getOverview()` 先取项目上下文，再直接裁到项目、会话、收件箱、巡检、验证的展示上限
- 这比“先造完整快照再截前几条”靠谱得多

结论：

- 这是以后所有概览接口该遵守的正例

### 1.2 重扫描已经开始搬进 helper

正例：

- `apps/host/src/modules/sessions/session-history-service.ts`
- `apps/host/src/modules/provider/provider-discovery-helper-*`
- `apps/host/src/modules/workspace/workspace-service.ts`

现状：

- `workspace.discovery_scan`
- session title read
- `workspace.code_composition_scan`

这些重活已经有 helper 承接。

结论：

- “重扫描离开 Host 主线程”这条路是对的，后面应该继续按这个方向推进

### 1.3 Git 面板已经有“先轻后重”的雏形

正例：

- `apps/host/src/modules/workbench/workspace-panel-snapshot-service.ts`

现状：

- 先查轻量级 status
- 只有状态变化时才补 history / branches

结论：

- 这种“先便宜判断，再决定要不要做贵动作”的模式，应该推广到更多刷新链路

## 2. 已经确认的反模式

### 2.1 `getSnapshot()` 带副作用

反例：

- `apps/host/src/modules/workbench/workbench-service.ts`

现状：

- `getSnapshot()` 内部会 `scheduleWorkspaceRefreshes()`

问题：

- 名字像纯读
- 行为却会排后台刷新
- 调用方只想拿快照，却顺手把 discovery 打出去了

结论：

- 这是第一批必须清掉的坏味道

### 2.1.1 已确认的“名字像读，实际会推动刷新”的案例

| 位置 | 方法 | 现在实际做了什么 | 判定 |
| --- | --- | --- | --- |
| `apps/host/src/modules/workbench/workbench-service.ts` | `getSnapshot(userId)` | 读取工作台快照前顺手 `scheduleWorkspaceRefreshes()` | 明确反模式 |
| `apps/host/src/modules/workbench/workbench-service.ts` | `refreshSnapshot(userId)` | 显式刷新后再读取快照 | 名字和行为一致，可接受 |
| `apps/host/src/modules/butler/context-aggregator.ts` | `getOverview(userId)` | 读取摘要时只走 `syncMode: "background"`，不在方法里偷偷放重扫描 | 可接受 |
| `apps/host/src/modules/workspace/workspace-service.ts` | `getManagementSummary(workspaceId)` | 名字叫 `get`，但实际 enqueue `workspace.management_summary` | 边界不清，建议后续改成 `schedule/ensure + getCached` 二段式 |

这里最危险的不是“偶尔多做一步”，而是调用方根本看不出它会不会顺手打后台任务。

### 2.2 工作台链路里还保留大量私有刷新状态

反例：

- `apps/host/src/ws/workbench-ws-hub.ts`

现状：

- `refreshTask`
- `titleSyncTask`
- `refreshController`
- 多个 `setInterval`

问题：

- 局部状态太多
- 订阅、刷新、广播耦在一起
- 很容易继续长出 abort 风暴和重复刷新

结论：

- 工作台链路需要继续整理成“缓存读 + 显式刷新 + 统一状态”的模式

### 2.2.1 已确认的工作台链路局部状态

| 位置 | 局部状态 | 现在用途 | 判定 |
| --- | --- | --- | --- |
| `apps/host/src/ws/workbench-ws-hub.ts` | `refreshTask` | 合并用户级工作台刷新 | 可短期保留，但后续要压成更清晰状态机 |
| `apps/host/src/ws/workbench-ws-hub.ts` | `titleSyncTask` | 合并标题同步广播 | 可短期保留，但要减少广播链路职责 |
| `apps/host/src/ws/workbench-ws-hub.ts` | `refreshController` | Git 刷新 abort 控制 | 当前抖动来源之一，需继续治理 |
| `apps/host/src/modules/sessions/session-history-service.ts` | `workspaceStateRefreshInflight` | 工作区最近状态补刷去重 | 已经接近“小型私有任务系统”，应该收编到统一刷新状态模型 |

### 2.3 文件树和 Git 现在还是整工作区 watcher

反例：

- `apps/host/src/modules/workbench/workspace-file-watcher.ts`

现状：

- `chokidar.watch(workspace.path)`

问题：

- 对大仓库句柄成本高
- 文件变更噪音大
- 跟 Git 面板刷新叠在一起时很容易把系统拖脏

结论：

- watcher 范围必须继续缩

### 2.3.1 watcher 盘点

| 位置 | watcher 范围 | 当前订阅来源 | 判定 |
| --- | --- | --- | --- |
| `apps/host/src/modules/workbench/workspace-file-watcher.ts` | `workspace.path` 整工作区递归 | `fileTree.subscribe`、`git.subscribe` | 明确反模式 |
| `apps/host/src/ws/workbench-ws-hub.ts` | 用户级 `setInterval` 定时器 | `workbench.subscribe` 后长期存在 | 不是 watcher，但属于持续刷新源，必须纳入统一规则 |

### 2.4 广播链路和刷新链路边界还不够硬

反例：

- `apps/host/src/ws/workbench-ws-hub.ts`

现状：

- 订阅建立、文件变化、定时器 tick 都会推动多种 refresh

问题：

- 虽然很多重活已经后台化了
- 但广播链路仍然承担了太多刷新组织责任

结论：

- 广播链路以后必须只负责“发最近结果”

## 3. 不是绝对错误，但边界没写清的地方

### 3.1 私有 `inflight` 不是一律错误

例子：

- `apps/host/src/config/opencode-base-url-resolver.ts`
- `apps/host/src/modules/provider/codex-model-options.ts`
- `apps/host/src/modules/workbench/workspace-panel-snapshot-service.ts`

现状：

- 这些地方用私有 Promise 去重复用短生命周期结果

为什么不能一刀切：

- 其中一些只是同资源、同进程、短 TTL 的缓存填充
- 真把它们全塞进 `TaskManager`，代码反而会变得更蠢

需要补的不是“禁止”，而是边界：

- 什么时候局部 `inflight` 合理
- 什么时候已经长成散装任务系统

### 3.1.1 现有私有 `inflight` 分类

#### 可保留的局部 `inflight`

| 位置 | 资源范围 | 原因 |
| --- | --- | --- |
| `apps/host/src/config/opencode-base-url-resolver.ts` | 同一工作区 baseUrl 发现 | 短 TTL、局部 Promise 复用、不是正式后台任务 |
| `apps/host/src/modules/provider/codex-model-options.ts` | 单个模型快照读取 | 仅做 5 秒缓存填充 |
| `apps/host/src/modules/provider/opencode-model-options.ts` | 单个 cacheKey 模型发现 | 同资源局部去重 |
| `apps/host/src/modules/workbench/workspace-panel-snapshot-service.ts` | 文件树 / Git / 终端面板快照填充 | 局部缓存填充，可接受，但 Git 那条要继续稳住抖动 |
| `apps/host/src/modules/git/workspace-repo-guard.ts` | 工作区 repo root 解析 | 短生命周期局部复用 |

#### 需要继续治理的局部状态

| 位置 | 现状 | 判定 |
| --- | --- | --- |
| `apps/host/src/modules/sessions/session-history-service.ts` | `workspaceStateRefreshInflight` 已经承担后台补刷语义 | 应并入统一刷新状态模型 |
| `apps/host/src/ws/workbench-ws-hub.ts` | 多类 `refreshTask/titleSyncTask/refreshController` 叠加 | 应收敛为更清晰的订阅刷新模型 |

#### 已经进统一任务系统的正例

| 位置 | 任务 |
| --- | --- |
| `apps/host/src/modules/sessions/session-history-service.ts` | `workspace.discovery`、`workspace.discovery_scan`、`provider.capability_refresh` |
| `apps/host/src/modules/workbench/workspace-panel-snapshot-service.ts` | `terminal.manager_snapshot`、`terminal.template_runtime_status_discovery` |
| `apps/host/src/modules/workspace/workspace-service.ts` | `workspace.management_summary`、`workspace.code_composition_scan` |

### 3.2 请求内同步文件读写也不是一律错误

例子：

- `apps/host/src/modules/file/file-content-service.ts`

现状：

- 单文件读
- 单文件写
- 单文件版本校验

这类动作的特点：

- 用户当前请求必须立刻拿结果
- 资源边界明确
- 体量小

结论：

- 不该把这类小动作也强行后台化
- 真正该盯的是跨目录、跨仓库、跨大量记录的同步重活

### 3.2.1 同步文件 I/O 与事务热点分类

## 4. 第一批必须处理的对象

### 4.1 `WorkbenchService.getSnapshot()`

原因：

- 读接口带副作用
- 是很多工作台链路的入口

### 4.2 `WorkbenchWsHub`

原因：

- 私有刷新状态过多
- 定时器和订阅组织逻辑集中在这里

### 4.3 `WorkspaceFileWatcher`

原因：

- 整仓库 watcher 句柄成本高
- 已在真实运行实例里暴露出明显压力

### 4.4 Git 面板刷新链路

原因：

- 现有 `snapshot aborted` 说明刷新抖动还没完全稳住

### 4.5 `workspaceStateRefreshInflight`

原因：

- 说明刷新状态模型还没真正统一

### 4.6 `workspaceService.getManagementSummary()`

原因：

- 名字是 `get`
- 行为却是 enqueue 后台任务
- 这是仓库里另一个“命名骗你它很纯”的例子

## 5. 阶段 1 盘点结论

这轮盘点已经能把阶段 1 的三件事说清楚了：

1. 读接口副作用确实存在，而且不止一个地方
2. 私有 `inflight` 不能一刀切，但 `workspaceStateRefreshInflight` 和工作台链路这类状态已经该收编
3. 同步文件 I/O 不能一刀切，单文件读写没问题，真正危险的是批量事务和跨目录扫描

所以后面规则必须是：

- 反对的是“副作用藏在读里”和“重活藏在主线程里”
- 不是反对一切同步代码，也不是反对一切局部 Promise 复用

## 6. 这份盘点的结论

当前仓库不是没有规则，而是规则还没统一成仓库级标准。

已经有一批正例：

- 摘要优先
- helper 承接重扫描
- 后台任务统一调度

也还有一批稳定风险：

- 读接口带副作用
- 广播链路承担刷新组织
- 整仓库 watcher
- 散装刷新状态

`spec001.2.1` 后面的工作，就是把这些经验收成统一标准，然后按标准去改第一批高风险链路。

## 7. 运行期证据补记

这次不是只靠读代码猜。
从你提供的并行任务调试面板里，已经能看到“卡顿会复发”的运行期证据：

| 指标 | 观测值 | 说明 |
| --- | --- | --- |
| `workspace.discovery` 启动次数 | 23123 | 刷新触发过密，已经不是偶发行为 |
| `workspace.discovery` 平均执行 | 3322.06 ms | 单次成本高，重复触发会持续占资源 |
| `workspace.discovery_scan` 启动次数 | 23123 | discovery 和 scan 形成连锁重复执行 |
| `workspace.discovery_scan` 平均执行 | 3248.06 ms | helper 虽然接住了重活，但重复触发仍然会把系统拖脏 |
| `workbench.sync_titles` 平均执行 | 8508.93 ms | 广播链路相关任务明显过重 |
| `terminal.manager_snapshot` 启动次数 | 2034 | 面板型快照也在高频运行 |
| 缓存命中中 | 5931 | 已经在做缓存，但触发模型还不够收敛 |

这些数字说明一件事：
问题不只是“某个任务慢”，而是“读、刷新、广播、watcher 的边界不清，导致系统长期高频重复做贵动作”。

所以阶段 2 的规范不是文书工作，而是把下面三件事写死：

1. 读接口不能顺手排任务
2. 刷新必须有统一状态和冷却
3. watcher 和私有 `inflight` 必须有准入边界

# 20260416-全仓库读写刷新现状盘点

这份盘点只回答四个问题：

1. 当前仓库里哪些地方已经做对了
2. 哪些地方是确定的反模式
3. 哪些地方不是绝对错误，但边界没写清
4. 第一批应该先改谁

## 1. 已经做对的地方

### 1.1 Butler 总览已经走摘要，不再先造整锅快照

正例：

- `apps/host/src/modules/butler/context-aggregator.ts`

现状：

- `getOverview()` 先取项目上下文，再直接裁到项目、会话、收件箱、巡检、验证的展示上限
- 这比“先造完整快照再截前几条”靠谱得多

结论：

- 这是以后所有概览接口该遵守的正例

### 1.2 重扫描已经开始搬进 helper

正例：

- `apps/host/src/modules/sessions/session-history-service.ts`
- `apps/host/src/modules/provider/provider-discovery-helper-*`
- `apps/host/src/modules/workspace/workspace-service.ts`

现状：

- `workspace.discovery_scan`
- session title read
- `workspace.code_composition_scan`

这些重活已经有 helper 承接。

结论：

- “重扫描离开 Host 主线程”这条路是对的，后面应该继续按这个方向推进

### 1.3 Git 面板已经有“先轻后重”的雏形

正例：

- `apps/host/src/modules/workbench/workspace-panel-snapshot-service.ts`

现状：

- 先查轻量级 status
- 只有状态变化时才补 history / branches

结论：

- 这种“先便宜判断，再决定要不要做贵动作”的模式，应该推广到更多刷新链路

## 2. 已经确认的反模式

### 2.1 `getSnapshot()` 带副作用

反例：

- `apps/host/src/modules/workbench/workbench-service.ts`

现状：

- `getSnapshot()` 内部会 `scheduleWorkspaceRefreshes()`

问题：

- 名字像纯读
- 行为却会排后台刷新
- 调用方只想拿快照，却顺手把 discovery 打出去了

结论：

- 这是第一批必须清掉的坏味道

### 2.2 工作台链路里还保留大量私有刷新状态

反例：

- `apps/host/src/ws/workbench-ws-hub.ts`

现状：

- `refreshTask`
- `titleSyncTask`
- `refreshController`
- 多个 `setInterval`

问题：

- 局部状态太多
- 订阅、刷新、广播耦在一起
- 很容易继续长出 abort 风暴和重复刷新

结论：

- 工作台链路需要继续整理成“缓存读 + 显式刷新 + 统一状态”的模式

### 2.3 文件树和 Git 现在还是整工作区 watcher

反例：

- `apps/host/src/modules/workbench/workspace-file-watcher.ts`

现状：

- `chokidar.watch(workspace.path)`

问题：

- 对大仓库句柄成本高
- 文件变更噪音大
- 跟 Git 面板刷新叠在一起时很容易把系统拖脏

结论：

- watcher 范围必须继续缩

### 2.4 广播链路和刷新链路边界还不够硬

反例：

- `apps/host/src/ws/workbench-ws-hub.ts`

现状：

- 订阅建立、文件变化、定时器 tick 都会推动多种 refresh

问题：

- 虽然很多重活已经后台化了
- 但广播链路仍然承担了太多刷新组织责任

结论：

- 广播链路以后必须只负责“发最近结果”

## 3. 不是绝对错误，但边界没写清的地方

### 3.1 私有 `inflight` 不是一律错误

例子：

- `apps/host/src/config/opencode-base-url-resolver.ts`
- `apps/host/src/modules/provider/codex-model-options.ts`
- `apps/host/src/modules/workbench/workspace-panel-snapshot-service.ts`

现状：

- 这些地方用私有 Promise 去重复用短生命周期结果

为什么不能一刀切：

- 其中一些只是同资源、同进程、短 TTL 的缓存填充
- 真把它们全塞进 `TaskManager`，代码反而会变得更蠢

需要补的不是“禁止”，而是边界：

- 什么时候局部 `inflight` 合理
- 什么时候已经长成散装任务系统

### 3.2 请求内同步文件读写也不是一律错误

例子：

- `apps/host/src/modules/file/file-content-service.ts`

现状：

- 单文件读
- 单文件写
- 单文件版本校验

这类动作的特点：

- 用户当前请求必须立刻拿结果
- 资源边界明确
- 体量小

结论：

- 不该把这类小动作也强行后台化
- 真正该盯的是跨目录、跨仓库、跨大量记录的同步重活

## 4. 第一批必须处理的对象

### 4.1 `WorkbenchService.getSnapshot()`

原因：

- 读接口带副作用
- 是很多工作台链路的入口

### 4.2 `WorkbenchWsHub`

原因：

- 私有刷新状态过多
- 定时器和订阅组织逻辑集中在这里

### 4.3 `WorkspaceFileWatcher`

原因：

- 整仓库 watcher 句柄成本高
- 已在真实运行实例里暴露出明显压力

### 4.4 Git 面板刷新链路

原因：

- 现有 `snapshot aborted` 说明刷新抖动还没完全稳住

### 4.5 `workspaceStateRefreshInflight`

原因：

- 说明刷新状态模型还没真正统一

## 5. 这份盘点的结论

当前仓库不是没有规则，而是规则还没统一成仓库级标准。

已经有一批正例：

- 摘要优先
- helper 承接重扫描
- 后台任务统一调度

也还有一批稳定风险：

- 读接口带副作用
- 广播链路承担刷新组织
- 整仓库 watcher
- 散装刷新状态

`spec001.2.1` 后面的工作，就是把这些经验收成统一标准，然后按标准去改第一批高风险链路。

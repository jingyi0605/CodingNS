# spec001.6-客户端与服务端统一更新机制

## 当前定位

这是 `spec001` 下的新子 Spec。

它只解决一件事：
把现在分散、半成品、平台各干各的更新方式，收口成一套能真正交付给用户的更新机制。

这次要定住的不是“设置页再多一个按钮”，而是下面这些真问题：

- macOS / Windows 客户端怎么检测新版本、下载并安装
- Android 客户端怎么用 `APK` 直装方式更新，而不是假装自己能静默升级
- 服务端怎么检测全局 NPM 包有新版本，并在用户点击后自动执行全局更新
- 更新完以后哪些场景可以立即生效，哪些场景必须明确要求重启
- 发布流水线到底要产出什么元数据和签名文件，客户端才能放心装

一句人话：
这次做的是“真正能用的更新链路”，不是“查到一个版本号然后让用户自己去网页下载”。

## 计划覆盖

- macOS / Windows 桌面端更新检查、下载、安装与回退边界
- Android `APK` 直装更新检查、下载、校验与系统安装器唤起
- 服务端全局 NPM 包更新检查、后台执行、结果回写与重启提示
- 更新元数据、版本比较、发布通道和校验信息的统一模型
- 设置页里的统一更新入口、状态展示和错误提示
- 桌面端与 Android 发布流水线需要补齐的产物和签名信息

## 本阶段明确不做

- 不做 iOS 更新链路
- 不做 Android 静默安装或 Root/企业签名方案
- 不做 Homebrew、Winget、Mac App Store、Google Play 多渠道同时接入
- 不做服务端自动回滚第一版
- 不把“更新检查”继续写成前端、Rust、Host 各自一份不一致逻辑

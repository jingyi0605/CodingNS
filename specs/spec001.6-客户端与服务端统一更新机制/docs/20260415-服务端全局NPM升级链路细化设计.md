# 20260415-服务端全局 NPM 升级链路细化设计

这份文档只回答一个问题：

- 服务端“检查 npm 包更新并一键升级”到底该怎么接进现在的 Host，而不是继续停留在界面里展示一条命令。

一句人话：
这不是“再加一个按钮”，这是把升级动作变成正式后台任务。

---

## 1. 目标

第一版服务端升级链路只做下面这些事：

1. 返回受管包列表，而不是单个包的半成品展示
2. 提供安装接口，点击后真正触发升级
3. 通过 `TaskManager` 管理升级任务
4. 把“包已升级”和“当前进程已生效”明确区分开

这次明确不做：

- 自动回滚
- 自动操控 `pm2/systemd`
- 多条升级任务并发调度编排

---

## 2. 当前实现的硬缺口

### 2.1 只有检查，没有安装

当前 Host 只有：

- `GET /api/client/service-update`

对应文件：

- [client-controller.ts](/Users/jackson/Code/CodingNS/apps/host/src/modules/client/client-controller.ts)
- [client-service.ts](/Users/jackson/Code/CodingNS/apps/host/src/modules/client/client-service.ts)
- [client.ts](/Users/jackson/Code/CodingNS/apps/host/src/routes/client.ts)

它只会：

1. 查 npm registry
2. 比较当前版本和最新版本
3. 返回一条命令字符串

它不会：

- 执行安装
- 记录任务状态
- 告诉前端“现在正在跑”
- 告诉前端“已经升级，但还没重启”

### 2.2 `TaskManager` 还没给 `external_process` 准备正式执行器

当前 `TaskManager` 只显式创建了 `helper_process` 执行器：

- [task-lane-executors.ts](/Users/jackson/Code/CodingNS/apps/host/src/modules/tasks/task-lane-executors.ts)

也就是说：

- 任务类型可以声明成 `external_process`
- 但如果不补执行器，最终仍会走 `definition.run()` 本地执行

这就是典型的假分层：

- `lane` 写得像外部进程
- 重活还是留在 Host 进程里

这次必须明确补上，不然服务端全局升级链路会从设计上就歪掉。

## 3. 第一版目标接口

### 3.1 `GET /api/client/service-update`

第一版从“单包返回”升级成“列表返回”，即使暂时只有一个包，也不要再把结构写死。

建议返回：

```json
{
  "channel": "stable",
  "packages": [
    {
      "packageName": "@jingyi0605/codingns",
      "displayName": "CodingNS Host",
      "currentVersion": "0.3.0",
      "latestVersion": "0.4.0",
      "hasUpdate": true,
      "checkStatus": "succeeded",
      "checkErrorMessage": null,
      "packagePageUrl": "https://www.npmjs.com/package/@jingyi0605/codingns",
      "installCommand": "npm install -g @jingyi0605/codingns@latest",
      "restartRequired": false,
      "activeInstallTask": null
    }
  ]
}
```

### 3.2 `POST /api/client/service-update/install`

建议输入：

```json
{
  "packageName": "@jingyi0605/codingns",
  "channel": "stable"
}
```

建议返回：

```json
{
  "task": {
    "taskId": "task_xxx",
    "taskType": "service.npm_global_update_install",
    "packageName": "@jingyi0605/codingns",
    "targetVersion": "latest",
    "status": "queued",
    "restartRequired": false
  }
}
```

### 3.3 `GET /api/client/service-update/tasks/:taskId`

建议用途：

- 前端安装后轮询
- 页面刷新后恢复任务状态

建议返回：

```json
{
  "task": {
    "taskId": "task_xxx",
    "taskType": "service.npm_global_update_install",
    "packageName": "@jingyi0605/codingns",
    "targetVersion": "latest",
    "status": "running",
    "summary": null,
    "restartRequired": false,
    "startedAt": "2026-04-15T10:00:00.000Z",
    "finishedAt": null
  }
}
```

## 4. 建议的服务拆分

### 4.1 `ClientService`

继续保留它做轻量数据聚合：

- 列出受管包
- 查 registry
- 读取当前全局已安装版本
- 合并当前任务状态

它不负责：

- 执行 `npm install -g`
- 管理长任务生命周期

### 4.2 `ServiceUpdateTaskService`

建议新建独立服务，职责只做三件事：

1. 注册后台任务类型
2. 触发安装任务
3. 查询任务状态并转换成前端 DTO

这样可以避免把 `ClientService` 写成一坨。

### 4.3 `NpmGlobalPackageService`

建议再拆一层纯命令执行器，负责：

- 检查本机 `npm` 是否可用
- 读取全局包当前版本
- 执行 `npm install -g`
- 收集 stdout/stderr 摘要

这样做的好处很直接：

- 后面如果要换成 `pnpm add -g` 或用户自定义 npm 路径，不会把 `ClientService` 搅成垃圾

## 5. 后台任务设计

### 5.1 新增任务类型

建议在 [task-types.ts](/Users/jackson/Code/CodingNS/apps/host/src/modules/tasks/task-types.ts) 里新增：

- `serviceNpmGlobalUpdateInstall: "service.npm_global_update_install"`

第一版 `check` 不强制任务化，因为当前只是单包 registry 查询，够轻。
但 `install` 必须任务化。

### 5.2 去重 key

建议：

```text
<packageName>:<channel>
```

例如：

```text
@jingyi0605/codingns:stable
```

这样可以保证：

- 同一个包同一通道不会并发装两次
- `stable` 和 `beta` 不会误去重

### 5.3 执行位点

必须声明成：

```text
external_process
```

但这里要补一句硬规则：

- 不是把 `executionLane` 写成 `external_process` 就完了
- 必须真的补一个 `external_process` 执行器，把升级命令发到外部子进程去跑

### 5.4 超时和并发

第一版建议：

- `timeoutMs: 300000`
- `concurrency: 1`
- 不配自动重试

理由很简单：

- 全局安装包是重操作
- 失败后盲重试只会把机器弄得更乱

---

## 6. 命令执行建议

### 6.1 标准命令

统一使用：

```bash
npm install -g <packageName>@<resolvedTagOrVersion>
```

例如：

```bash
npm install -g @jingyi0605/codingns@latest
npm install -g @jingyi0605/codingns@beta
```

### 6.2 不建议的做法

不要直接用：

```bash
npm update -g <packageName>
```

原因：

- 它依赖当前全局安装的 semver 范围
- 结果不如显式安装目标 tag 可控

### 6.3 结果摘要

第一版不要把全量 stdout/stderr 都塞给前端。

建议保留：

- 退出码
- 最后几行 stdout
- 最后几行 stderr
- 错误摘要

一句话：
前端要的是可读状态，不是命令行录屏。

## 7. “需要重启”判断

这是服务端升级里最容易自欺欺人的地方。

### 7.1 判断逻辑

如果升级的包就是当前 Host 自己，例如 `@jingyi0605/codingns`：

- 全局安装成功
- 但当前进程还在旧版本上运行

那就必须返回：

- `restartRequired: true`

### 7.2 第一版不要撒谎

第一版先做到：

- 能明确告诉用户“包已经装好了”
- 能明确告诉用户“当前服务还没切到新版本”

先不要吹“系统会自动完成重启”，除非后面真的把 supervisor 控制做好。

---

## 8. 前端变化建议

### 8.1 `ServiceUpdatePanel`

当前只有：

- 检查
- 打开 npm 页面

第一版应补成：

- 检查更新
- 安装更新
- 展示进行中状态
- 展示任务结果
- 展示“需要重启”

### 8.2 状态文案

至少区分：

- 检查失败
- 有新版本
- 正在安装
- 安装失败
- 包已升级，等待重启生效
- 已是最新版本

---

## 9. 实现顺序建议

1. 先把 `GET /api/client/service-update` 改成列表模型
2. 再补 `POST /api/client/service-update/install`
3. 再补 `GET /api/client/service-update/tasks/:taskId`
4. 接着补 `external_process` 执行器
5. 最后再补前端按钮和任务状态展示

不要反过来。

如果先改前端，只会得到一堆假按钮。

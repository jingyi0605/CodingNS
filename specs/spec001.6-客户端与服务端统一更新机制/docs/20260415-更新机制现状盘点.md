## 1. 桌面端现状

### 1.1 已有能力

- 设置页已经有桌面更新面板：
  - [ReleasePanel.tsx](/Users/jackson/Code/CodingNS/apps/user-app/src/settings/ReleasePanel.tsx)
- 前端已经有桌面桥接入口：
  - [platform-adapter.ts](/Users/jackson/Code/CodingNS/apps/user-app/src/platform/platform-adapter.ts)
  - [release-manager.ts](/Users/jackson/Code/CodingNS/apps/user-app/src/platform/desktop/release-manager.ts)
- Tauri Rust 侧已经暴露桌面更新命令：
  - `check_for_update`
  - `install_update`
  - `rollback_to_previous_version`
  - 对应文件：[lib.rs](/Users/jackson/Code/CodingNS/apps/desktop/src-tauri/src/lib.rs)

### 1.2 当前实现方式

当前桌面端不是走 Tauri 官方 updater，而是自己写了一套：

1. 调 GitHub Releases API
2. 选中 `.dmg/.msi/.exe`
3. 下载到本地更新目录
4. 计算 `sha256`
5. 校验通过后直接打开安装包

对应实现：

- [updater.rs](/Users/jackson/Code/CodingNS/apps/desktop/src-tauri/src/updater.rs)

### 1.3 现有问题

- Rust 依赖里没有 `tauri-plugin-updater`：
  - [Cargo.toml](/Users/jackson/Code/CodingNS/apps/desktop/src-tauri/Cargo.toml)
- Tauri 配置里没有 updater 配置块，也没有公钥、端点等正式 updater 配置：
  - [tauri.conf.json](/Users/jackson/Code/CodingNS/apps/desktop/src-tauri/tauri.conf.json)
- 当前 CI 只上传 `.dmg/.msi/.exe`，没有稳定产出 updater 所需的元数据和签名文件：
  - [desktop-release.yml](/Users/jackson/Code/CodingNS/.github/workflows/desktop-release.yml)
- 现有测试也默认允许 `signature: null`，这说明当前发布链路没有把“可安装更新”当成强约束：
  - [ReleasePanel.test.tsx](/Users/jackson/Code/CodingNS/apps/user-app/src/settings/ReleasePanel.test.tsx)

### 1.4 可复用部分

- 设置页入口和交互结构可以保留
- `DesktopReleaseState`、`ReleaseManifest` 这些前端状态模型可以继续演进，不必推倒重来
- `rollback` 相关逻辑可评估保留，但不能继续绑死在当前私有下载器上

### 1.5 结论

- 桌面端不是从零开始
- 但它现在是“私有下载器 + 设置页按钮”，还不是正式桌面更新链路

### 2.2 当前缺口

- 前端没有 Android 更新面板
- 平台适配层没有任何 “检查 Android 更新 / 下载 APK / 唤起安装器” 的桥接命令

- 当前打包脚本只负责构建 APK，不负责发布清单、校验文件和下载地址生成：
  - [build-android.sh](/Users/jackson/Code/CodingNS/scripts/build-android.sh)

### 2.3 结论

- Android 更新链路现在不是半成品，而是基本没开始做
- 唯一明确可复用的是：
  - 已有壳工程
  - 已有 release 签名和 `versionCode/versionName` 同步基础
  - 已有 `FileProvider`

## 3. 服务端现状

### 3.1 已有能力

- 设置页已经有服务端更新面板：
  - [ServiceUpdatePanel.tsx](/Users/jackson/Code/CodingNS/apps/user-app/src/settings/ServiceUpdatePanel.tsx)
- Host 已经能读取：
  - 发布通道
  - `releaseManifestRoot`
  - `serverUpdatePackageName`
  - `npmRegistryBaseUrl`
  - 对应文件：[env.ts](/Users/jackson/Code/CodingNS/apps/host/src/config/env.ts)
- Host 已经能查询 npm registry 并比较版本：
  - [client-service.ts](/Users/jackson/Code/CodingNS/apps/host/src/modules/client/client-service.ts)

### 3.2 当前实现方式

当前服务端更新逻辑只做了两件事：

1. 查一个受管包的当前版本和 registry 最新版本
2. 返回一个更新命令字符串给前端展示

### 3.3 现有问题

- 只支持单包展示，不是受管包列表
- 没有“安装更新”的后端接口
- 没有 `TaskManager` 任务类型
- 没有后台执行 `npm install -g`
- 没有“升级成功但需要重启”的状态模型
- 当前返回给前端的命令少了 `-g`：
  - 代码里是 `npm install ${packageName}@latest`
  - 这不符合“全局升级”的真实目标
- registry 请求失败时直接回成 `latestVersion: null + hasUpdate: false`
  - 这会把“检查失败”和“没有新版本”混淆

### 3.4 可复用部分

- Host 环境配置口子可以保留
- 版本比较逻辑可以保留
- 设置页服务端更新卡片可以保留，但必须补安装按钮、任务状态和重启提示

### 3.5 结论

- 服务端更新链路已经有“检查版本”的雏形
- 但“执行更新”这一步还完全没接进系统

## 5. 盘点结论

### 5.1 能复用的

- 桌面端和服务端设置页入口
- 桌面端当前版本状态模型
- Host 的更新相关环境配置
- npm 包现有发布链路
- Android 壳、签名和 `FileProvider`

### 5.2 必须重做或补齐的

- 桌面端底层更新执行链路
- Android 更新链路全部主体
- 服务端全局升级后台任务
- 三端统一的“检查失败 / 有更新 / 执行中 / 需要重启”状态模型
- 桌面端和 Android 的正式更新元数据产物

### 5.3 下一步该做什么

1. 先把统一的数据模型和状态模型定死
2. 桌面端先切正式 updater
3. Android 再补 `APK` 直装
4. 服务端最后补 `TaskManager` 全局升级闭环

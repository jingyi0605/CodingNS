# spec016.1-事务视图文档库与索引HOST集成

## 这份 Spec 现在解决什么问题

`spec016` 已经把“代码 / 事务”双工作台骨架立起来了，但事务视图里的文档库现在还是假数据。

一句人话：

- 现在事务视图里的“文档库”并没有接真实文件和真实索引
- 它只是拿工作区会话列表临时拼出来的占位结果
- 收藏、标签、路径、对象详情也都不是真的文档库数据

这会直接带来三个问题：

1. 用户进事务视图后，看到的不是自己要管理的资料库
2. 前端没法围绕真实文档对象做收藏、标签、详情和助手联动
3. 后面就算继续补待办、自动化和插件，底下的对象模型还是歪的

所以这份子 Spec 只做一件事：

**把真实文档库和索引能力正式接进事务视图，并把索引运行收口到本项目 HOST 的统一后台任务体系里。**

## 这次计划覆盖什么

- 事务视图首次进入时的文档库路径绑定流程
- 工作区级文档库配置落点
- 事务视图读取真实文档、真实标签、真实收藏的方式
- `doc-semantic-index-node` 能力集成到 `apps/host` 的方式
- 索引初始化、配置应用、重扫、标签重算、导出刷新等后台任务的统一接法
- 前端 `apps/user-app` 文档库状态模型和事务视图对象模型调整
- Host API / DTO / 刷新状态 / 订阅快照
- 首阶段性能边界：不把重扫描、重 SQLite、重导出塞回主线程

## 这次明确不做什么

- 不把整个 `/Users/jackson/SynologyDrive/index.html` 原样搬进 `user-app`
- 不在第一阶段就重做全文搜索、语义检索、复杂推荐和所有高级筛选
- 不在第一阶段支持任意第三方索引器接入
- 不重写 `doc-semantic-index-node` 全部 CLI 结构
- 不为了接文档库再长一套独立后台任务系统

## 为什么要单独起 spec016.1

因为这件事已经不是单纯前端页面接线了，而是横跨三层：

1. `apps/user-app` 的事务视图对象模型
2. `apps/host` 的文档库/索引服务封装
3. 后台任务、watcher、导出、状态快照的统一治理

如果继续混在 `spec016` 里，最后一定会变成：

- 前端想接真数据，但后端还没定义正式能力
- 后端能跑 CLI，但没有统一任务状态和快照
- watcher、apply-config、重扫、recompute-tags 又各长一套私活

这种垃圾必须提前掐死。

## 硬边界先写死

### 边界 1：事务视图文档库必须接真实对象，不再拿会话假扮文档

- 文档列表必须来自真实索引结果
- 标签必须来自真实标签树/标签列表
- 收藏必须来自文档库自己的收藏模型
- 路径必须是可回到真实文件系统的路径

### 边界 2：索引服务必须进 HOST，不准继续当外部孤岛页面能力

- `apps/host` 必须提供正式文档库读取与刷新能力
- 前端只读 HOST 暴露的数据，不直接自己拼 CLI
- 事务视图不能长期依赖静态 HTML 页面当正式实现

### 边界 3：所有重活统一走 TaskManager / worker，不准开私活

- 重扫描、重算标签、导出刷新、索引配置应用都要有正式 `taskType`
- 真正重活必须跑在 `helper_process` 或 `external_process`
- 读接口只读缓存和最近结果，不顺手开重活
- watcher 只打脏标记，不直接同步现算

### 边界 4：先把主链路做对，再谈高级能力

首阶段先保证：

- 绑定文档库路径
- 看到真实文件视图
- 看到真实收藏
- 看到真实标签
- 右侧详情和助手能围绕真实文档对象工作

先不扩成一整个搜索平台。

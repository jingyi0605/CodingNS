# 会话订阅性能基线与验收口径

日期：2026-08-15

## 这份记录是干什么的

这不是性能结论报告，也不是拿几个数字装样子。

它记录启动 spec002.1.1 时已经确认的源码事实，以及后续实现必须提供的对比证据。没有真实长会话回放或生产采样的项目，必须明确写成未验证，不能假装已经达标。

## 已确认的当前路径

1. SessionHistoryService 的订阅使用固定 300ms 定时器拉取历史页。
2. CodexAdapter 在来源 mtime 或 size 变化时失去 historyCache 命中。
3. 未命中时，CodexAdapter 会调用 readJsonLines；该函数同步读取完整文件、按行切分并解析。
4. 历史页 cursor 在完整消息集合构造之后才生效，因此小 delta 仍可能触发全文件读取。
5. WebSocket 发送 session.delta 后，当前实现会把多种会话事件带入 workbench snapshot 广播。

这些事实来自当前源码走查，不等于已经完成 CPU 火焰图采样。

## 本 Spec 的验收场景

### 场景 A：正常追加

准备同一份有效 Codex JSONL 的短文件和长文件版本，在两个文件末尾追加同样的一组完整记录。

要记录：

- 来源文件总字节数。
- 本次新增字节数。
- helper bytesRead。
- helper recordsParsed。
- helper tailWindowBytes。
- Host 合并耗时。
- session.delta payload 字节数。
- workbench snapshot 广播次数。

验收标准：

- 两个文件的新增内容相同时，正常追加的 helper bytesRead 和 recordsParsed 应接近。
- Host 不应出现订阅链路同步读取完整来源文件。
- 摘要不变时 workbench snapshot 广播次数为 0。

### 场景 B：半行与尾部补全

先写入一条不完整 JSONL 行，再补齐；再写入会影响最近工具状态的后续记录。

验收标准：

- 不完整行不会变成错误消息。
- 补齐后消息只出现一次。
- 尾部状态更新能覆盖旧版本，但不会重放整份历史。

### 场景 C：文件重置

模拟 size 缩小、文件替换或 helper checkpoint 丢失。

验收标准：

- reader 返回明确恢复模式。
- 客户端保留最近可用消息，随后通过可信历史补偿收敛。
- 不伪造运行状态，不静默丢弃更新。

### 场景 D：同源多订阅

为同一 sourceKey 建立两个 WebSocket 订阅，并触发一次来源变化。

验收标准：

- 只有一个 session.history_delta_read 真正执行。
- 两个订阅者都收到相同的可信 delta 或 snapshot。
- 最后一个订阅关闭后 watcher、quiet timer、fallback timer 和任务取消句柄均被释放。

### 场景 E：工作台广播门禁

分别模拟正文变化、工具输出变化、标题变化、消息计数变化和运行状态变化。

验收标准：

- 前两类只推会话 delta。
- 后三类可触发一次合并后的工作台广播。
- 工作台广播失败不影响会话 delta 已投递。

## 必须保留的观测字段

| 分类 | 字段 |
| --- | --- |
| 来源 | sourceKey、provider、rawStoreRef 摘要、文件版本 |
| helper | readMode、bytesRead、recordsParsed、tailWindowBytes、parseMs |
| 调度 | taskId、deduped、waitMs、runMs、cancelled、timeout |
| Host 收尾 | mergeMs、summarySignatureMs、serializeMs |
| 广播 | workbenchBroadcasted、workbenchBroadcastMs、原因 |
| 恢复 | resetRequired、replayMode、helperRestarted |

## 未验证项

- 真实生产 Codex JSONL 是否存在会在历史中段改写记录的样本。
- 不同平台上的文件 watcher 对替换和 rename 的实际事件组合。
- 低频兜底间隔与用户可感知延迟的最终平衡。
- tailWindow 的最终字节和消息数量上限。

这些问题在没有回放样本前不能写成已解决。

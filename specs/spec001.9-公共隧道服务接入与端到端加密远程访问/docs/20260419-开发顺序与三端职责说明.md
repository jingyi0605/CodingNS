# 20260419-开发顺序与三端职责说明

这份文档只回答两个问题：

1. 客户端、Host、公共隧道服务站点三端各自负责什么
2. 这个能力应该按什么顺序开发，才不会一上来就把系统做成一坨

一句人话：
先把职责和顺序定住，后面实现才不会边写边推翻。

---

## 1. 三端职责

### 1.1 客户端负责什么

这里的客户端包含两类：

- 官方桌面端 / 移动端
- 从固定可信域名加载的官方 H5

客户端的职责不是“代理请求”，而是：

1. 发现自己要访问哪个 Host
2. 根据三级域名或绑定信息去控制面拿 Host 的公开资料
3. 连到公共隧道服务的数据面
4. 和 Host 完成端到端加密握手
5. 把业务 HTTP / WebSocket 数据封成加密帧发出去
6. 在加密通道里继续走现有 CodingNS 业务登录

客户端需要实现的具体能力：

- 根据 `tunnelDomain` 查询目标 Host 绑定信息
- 获取 Host 公钥和指纹
- 生成客户端临时会话密钥
- 发起 E2EE 握手
- 握手成功后，建立隧道传输层
- 把现有 `/api/*` 和 `/ws` 请求改走隧道传输层
- 展示 Host 指纹、连接状态、配额状态和错误信息

客户端明确不负责：

- 保存 Host 私钥
- 决定三级域名怎么分配
- 决定套餐、支付和流量发放
- 充当中继节点

### 1.2 Host 负责什么

Host 是真正的业务终点。

公共隧道打开后，Host 负责两件核心事情：

1. 证明“我是谁”
2. 解密后把请求送到本地真实业务服务

Host 需要实现的具体能力：

- 保存实例级公共隧道配置
- 保存绑定状态、三级域名、最近错误和流量状态快照
- 首次启用时生成长期身份密钥对
- 保存 Host 公钥和指纹
- 启动 Host 侧隧道客户端并连到数据面
- 与客户端完成端到端加密握手
- 解密加密帧
- 把解密后的业务请求转给本地 Host
- 把本地响应重新封成加密帧回传
- 管理长连接、自动重连和启动恢复
- 在未初始化时阻止公网暴露

Host 明确不负责：

- 云端账号系统
- 套餐、订单和支付回调
- 三级域名池管理
- 公网边缘中继

一句话：
Host 是“加密终点 + 本地业务入口”，不是“云控制台”。

### 1.3 公共隧道服务站点负责什么

这里其实不是一个单体站点，而是两块：

- 控制面
- 数据面

#### 控制面负责什么

控制面负责“管理”和“计费”：

- 用户账号
- Host 绑定
- 三级域名分配
- Host 公钥登记
- 绑定状态查询
- 流量钱包
- 套餐、订单、支付
- 超额、停用、封禁等配额状态

#### 数据面负责什么

数据面负责“盲中继”：

- 接受客户端连接
- 接受 Host 连接
- 按会话转发密文帧
- 统计上下行字节数
- 在超额时拒绝新连接或中断现有连接

数据面明确不负责：

- 解密业务内容
- 读取 HTTP 请求体
- 读取 WebSocket 消息正文
- 接管 CodingNS 业务登录

一句话：

- 控制面管“谁能用、用了多少、该不该收费”
- 数据面管“把密文转过去”

## 2. 三端接入与配置顺序

### 2.1 Host 管理员的配置顺序

管理员在 Host 侧的操作顺序应该固定成这样：

1. 打开设置页“远程访问”
2. 选择“公共隧道”
3. Host 检查当前实例是否已完成初始化
4. 若未初始化，直接阻断，不允许继续启用
5. 若 Host 还没有身份密钥，则先生成长期密钥对，并保存公钥指纹
6. 管理员登录公共隧道服务账号
7. Host 向控制面提交当前实例资料、公钥和指纹
8. 控制面完成绑定，并分配三级域名
9. Host 保存 `bindingId / tunnelDomain / hostPublicKey / fingerprint`
10. Host 启动隧道客户端，连到数据面
11. 设置页开始展示状态、三级域名、指纹、流量余量和最近错误

### 2.2 远程用户的访问顺序

远程用户真正访问 Host 时，顺序应该是：

1. 用户拿到三级域名或分享入口
2. 官方客户端或官方 H5 去控制面查询目标 Host 的公开绑定信息
3. 客户端拿到 Host 公钥和指纹
4. 客户端连到数据面
5. 客户端和 Host 通过中继完成端到端加密握手
6. 握手成功后，业务请求才开始传输
7. 客户端把 HTTP / WebSocket 数据封成加密帧发给 Host
8. Host 解密后转发给本地真实业务服务
9. 本地响应再经 Host 加密，通过数据面回传
10. 用户在这条加密通道里继续走现有业务登录

### 2.3 H5 的特殊顺序

H5 需要单独强调一条边界：

1. 用户可以通过三级域名进入入口
2. 但真正业务 H5 代码必须从固定可信域名加载
3. H5 代码加载后，再根据 `tunnelDomain` 去建隧道

不要做成：

1. 用户打开三级域名
2. 三级域名直接返回整套业务 H5
3. 然后还声称中继绝对看不到内容

这种说法前后矛盾，不能用。

## 3. 推荐开发顺序

### 3.1 总原则

推荐顺序只有一条：

- 先打通最小闭环
- 再补计量
- 最后接支付

不要反过来。

如果一开始就先做支付，再回头补协议和隧道，最后一定重做。

### 3.2 阶段一：先把边界和协议定死

这一步先不追求功能跑通，先把边界定死：

- 主仓库只做什么
- 独立子仓库做什么
- 控制面接口大概有哪些
- 数据面只转发什么
- 客户端、Host 如何握手
- Host 公钥、指纹、临时会话密钥怎么用

这一步做完以后，后面所有人都不会再拿“是不是顺便把站点写进主仓库”这种问题反复扯皮。

### 3.3 阶段二：先做最小控制面

控制面第一阶段只要能做这些：

- 登录账号
- 绑定 Host
- 分配三级域名
- 查询绑定信息
- 登记 Host 公钥和指纹

先不要急着做：

- 套餐
- 支付
- 复杂运营后台

因为没有绑定和三级域名，后面根本没法联调。

### 3.4 阶段三：再做最小数据面

数据面第一阶段只要做到：

- 客户端能连
- Host 能连
- 能按会话转发密文帧
- 能记录字节数

先别做花哨功能。

一句话：
先把“中继只转密文”这个地基立起来。

### 3.5 阶段四：实现 Host 侧隧道客户端

这一步优先做 Host，因为 Host 是整个链路的终点。

先实现这些：

- 实例级配置和状态表
- Host 长期身份密钥
- 绑定状态机
- Host 到数据面的长连接
- 自动重连
- 启动恢复
- 解密后桥接本地 HTTP / WebSocket
- 未初始化实例阻断

这一步打通后，Host 才算准备好。

### 3.6 阶段五：接客户端

先接官方客户端，再接官方 H5。

原因很简单：

- 官方客户端的信任边界更简单
- 不需要先处理 H5 加载域名的复杂问题
- 更适合先打通 E2EE 和工作台联调

客户端先做到：

- 查询绑定信息
- 校验指纹
- 建立握手
- 通过隧道访问 `/api/*`
- 通过隧道访问 `/ws`

### 3.7 阶段六：再接官方 H5

H5 放到客户端之后做，原因不是它不重要，而是它更容易把信任模型搞脏。

H5 第一阶段只做：

- 从可信固定域名加载
- 读取 `tunnelDomain`
- 建立隧道
- 跑通核心访问链路

先不要做用户三级域名下的整站业务托管。

### 3.8 阶段七：补流量计量和限额

这一步开始做运营能力，但还是不碰支付。

先做：

- 双向字节统计
- 套餐余量查询
- 超额拒绝新连接
- 必要时断开现有连接
- Host 和客户端展示超额原因

只有这一步站稳了，支付才有意义。

### 3.9 阶段八：最后接支付

支付永远后置。

推荐顺序：

1. 先手工加量，验证账本正确
2. 再接订单创建
3. 再接支付回调
4. 再验证支付到账和流量到账一致

不要在隧道链路都没打通时就开始接支付 SDK，那是纯浪费时间。

---

## 4. 推荐的最小可用闭环

真正的最小可用闭环不是“用户已经能付款”，而是：

1. 没有公网地址的 Host 可以绑定一个三级域名
2. Host 可以稳定连到数据面
3. 客户端可以拿到 Host 公钥和指纹
4. 客户端和 Host 可以完成端到端加密握手
5. 现有 `/api/*` 和 `/ws` 能通过隧道正常工作
6. 中继只能看到密文和字节数

只要这 6 条没打通，后面的套餐和支付都只是空壳。

---

## 5. 一句话结论

推荐顺序就是：

1. 先分仓和定协议
2. 再做控制面最小绑定
3. 再做数据面盲中继
4. 再做 Host 隧道客户端
5. 再做官方客户端接入
6. 再做官方 H5 接入
7. 再做流量计量和限额
8. 最后做支付

这条顺序的目的只有一个：

先把“能安全连通”做成真，再去做“怎么收费”。

# spec014-通讯平台接入与助手会话桥接

## 这份 Spec 现在解决什么问题

`CodingNS` 现在已经有会话系统、Butler 控制会话、项目会话、终端、工作台，但还没有一条正式的“外部通讯平台 -> 助手会话”链路。

结果就是：

- 想在钉钉、飞书、Telegram、Slack、Discord、个人微信里和助手聊，当前没入口
- 就算后端以后临时接一个 webhook，也很容易接错对象，最后把消息塞到普通终端、普通 REST 路由，或者做成另一套散装聊天系统
- 一旦方向没先说死，后面实现时就会把 `FamilyClaw` 那套多成员、多绑定、多会话桥接原样搬进来，跟 `CodingNS` 的单用户代码助手模型不匹配

一句人话：

这份 Spec 先把一件事定死：

**通讯平台对接的对象，是本项目的助手会话。**

不是普通终端，不是 Git 提交通知，不是家庭成员消息路由，也不是另起一套聊天系统。

## 这次计划覆盖什么

- 定义 6 个通讯平台的接入边界：
  - 钉钉
  - 飞书
  - 个人微信（claw）
  - Telegram
  - Slack
  - Discord
- 定义统一的通道账号、外部会话、入站事件、出站回发模型
- 定义“外部消息进来以后，怎么命中或创建助手会话”
- 定义 webhook、polling、延迟回发、轮询调度这些后端链路该怎么挂到 `CodingNS`
- 定义第一阶段要交付的 Host API、存储、后台任务和回归口径

## 这次明确不做什么

- 不把消息直接接到普通 provider 会话列表，绕开助手层
- 不做 `FamilyClaw` 式家庭成员绑定、多成员路由
- 不做一套新的前端聊天页面
- 不在第一阶段支持所有平台的所有高级能力，比如群权限管理、富媒体、文件收发、联系人同步
- 不要求第一阶段就把微信个人号 transport 内嵌进 `CodingNS` 主进程；桥接模式允许先留

## 为什么现在就要立这个 Spec

因为这类需求一旦直接开写，最容易出现三种偏差：

1. 先接 webhook，后面发现消息落错对象
2. 先接平台 SDK，后面发现后台任务和主线程边界不对
3. 先做“能收能发”，后面发现审计、会话映射、回复等待全是散的

这不是后面补两张表能收回来的事，得先定模型。

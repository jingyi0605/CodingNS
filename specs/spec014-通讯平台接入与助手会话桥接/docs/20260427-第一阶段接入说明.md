# spec014 第一阶段接入说明

这份说明只回答三个问题：

1. 现在 Host 已经接通了什么
2. 每个平台账号最少要配什么
3. 现在还不能指望它做什么

## 1. 现在已经接通的范围

第一阶段已经完成这些事：

- Host 里有正式 `channels` 模块
- 平台账号、外部线程、入站事件、回发记录都能落库
- 外部消息会按 `channel_account_id + external_conversation_key` 映射到 Butler control session
- 同一个外部会话再次发消息时，会复用同一个 Butler control session
- webhook 入口已经挂到：
  - `GET /api/public/channel-gateways/:accountId/webhook`
  - `POST /api/public/channel-gateways/:accountId/webhook`
- polling / bridge 账号已经接入后台任务：
  - task type：`channel.account_poll`

一句人话：

外部平台现在已经不是“只落个表”，而是真的能进 Butler 控制会话，再把 Butler 的首条文本回复按平台规则记成回发记录。

## 2. 平台模式和最小配置

### 钉钉

推荐模式：

- `webhook`

最少配置：

- `token`：如果你要做 webhook token 校验
- `outboundWebhookUrl`：如果你想让 Butler 回复真正回到钉钉

当前实现方式：

- 入站先按文本消息解析
- challenge 会原样回
- 回发先走 `outboundWebhookUrl`

### 飞书

推荐模式：

- `webhook`

最少配置：

- `verificationToken`
- `outboundWebhookUrl`

当前实现方式：

- 支持 `challenge`
- 文本消息会从飞书事件体里抽出来
- 回发先走 `outboundWebhookUrl`

### 个人微信（claw）

推荐模式：

- `polling`

最少配置：

- 不走手填 transport 地址
- 先创建账号
- 再由 Host 发起二维码绑定

当前实现方式：

- Host 先生成微信 claw 绑定二维码
- 管理端轮询二维码绑定状态
- 绑定成功后，Host 保存 `botToken / baseUrl / boundUserId`
- 后续 polling 走真实 iLink API，而不是自定义 `/poll`、`/send` bridge

### Telegram

推荐模式：

- `polling`

最少配置：

- `botToken`

当前实现方式：

- probe 会调 `getMe`
- polling 会调 `getUpdates`
- 回发会调 `sendMessage`

### Slack

推荐模式：

- `webhook`

最少配置：

- 可选：`verificationToken`
- 可选：`outboundWebhookUrl`

当前实现方式：

- 支持 `url_verification`
- 支持最简单的 command / event 文本入口
- 如果 webhook 请求里带 `response_url`，优先用它回发
- 没有 `response_url` 时，会退回 `outboundWebhookUrl`

### Discord

推荐模式：

- `webhook`

最少配置：

- 可选：`verificationToken`
- 可选：`outboundWebhookUrl`

当前实现方式：

- interaction `type=1` 会回 pong
- command 文本会转成标准入站消息
- 如果 interaction 里自带 `application_id + token`，会优先走 Discord follow-up webhook 回发
- 否则退回 `outboundWebhookUrl`

## 3. 管理 API

当前可用的管理接口：

- `GET /api/channels/platforms`
- `GET /api/channels/accounts`
- `POST /api/channels/accounts`
- `PATCH /api/channels/accounts/:accountId`
- `POST /api/channels/accounts/:accountId/probe`
- `POST /api/channels/accounts/:accountId/poll`
- `GET /api/channels/accounts/:accountId/threads`
- `GET /api/channels/accounts/:accountId/events`
- `GET /api/channels/accounts/:accountId/deliveries`

## 4. 当前明确不承诺的事

下面这些，第一阶段不要当成已经完成：

- 图片、文件、语音、卡片、按钮交互
- Slack / Discord / 飞书 / 钉钉的完整官方签名体系
- 个人微信 transport 直接内嵌到 Host 主进程
- 所有平台都走官方 SDK 的完整协议细节

一句人话：

现在已经能打通“文本消息 -> Butler 控制会话 -> 文本回发记录”这条主链路，但还没到“六个平台全部生产级全能力”的程度。

## 5. 验证建议

最小验证顺序：

1. 先建一个账号
2. 调 `probe`
3. 对 webhook 平台打一次 `POST /api/public/channel-gateways/:accountId/webhook`
4. 对 polling 平台调一次 `POST /api/channels/accounts/:accountId/poll`
5. 看 `threads / events / deliveries` 三个接口是不是都有记录

看到这些结果，就说明第一阶段主链路已经通了：

- 有 thread 映射
- 有 inbound event
- Butler 回复后有 delivery

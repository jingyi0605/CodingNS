# spec016.4-事务文档库刷新阻塞治理与索引稳定性改造

## 这份 Spec 现在只解决什么

这份 Spec 只解决一件事：

**把事务文档库“看起来一直在刷新、排队很久、文件明明改了却迟迟不更新”的稳定性问题正式收口。**

一句人话：

- 现在这条链路不是单点 bug，而是调度、兜底刷新、helper 隔离和 Host 读链路一起发虚
- 用户看到的是“刷新中”“排队中”，但系统里可能根本没真正开始跑，或者结果已经旧了
- 如果不把这几层拆开收口，后面继续补搜索、更多标签、更多对象动作，只会越补越乱

所以这份 Spec 不追求“再多做几个功能”，只追求把现有文档库刷新和索引主链路做稳。

## 这次要交付什么

### 1. 双层兜底刷新

把当前“watcher + 单层周期兜底”改成两层：

- **30 到 60 秒轻量对账**：只检查状态、watermark、最近目录变化，不默认全量重建
- **10 分钟全库巡检**：先做全库对账，发现漂移后优先增量修复，只在必要时才触发全量重建

### 2. 排队等待超时和陈旧队列回收

把“任务已经 queued 很久但没人处理”从一个隐形坑，变成正式状态：

- Host 队列等待超时
- helper 内部排队超时
- 陈旧 queued 快照清理
- 前端可读状态区分

### 3. per-rootDir helper 隔离

把现在共享 helper 进程承载事务文档库重任务的模型，改成按 `rootDir` 隔离。

目标很直接：

- A 文档库卡住，不拖死 B 文档库
- 取消一个根目录任务时，不影响别的根目录
- helper 故障域从“全局”缩到“当前资料库”

### 4. Host 主线程去同步 I/O

把现在文档库读链路里那些重同步 I/O 收口：

- 大目录 live scan 不再长期压在 Host 主线程上
- Host 负责轻量组装和缓存，不负责同步扫大目录
- 目录大小大到一定程度时，先回快照，再异步补新

## 这次明确不做什么

- 不引入 Redis 作为事务文档库主索引真源
- 不把 SQLite 主索引替换成内存数据库
- 不把 10 分钟巡检做成“每次都全量重建”
- 不在这轮顺手重做全文搜索、语义搜索或标签系统
- 不把前端事务视图整页重画成另一套产品
- 不把办公目录之外的别的文件系统模型一起混进来

## 为什么这轮明确不引入 Redis

这件事要先说死，不然后面很容易跑偏。

原因很简单：

1. 当前主要问题不是“没有内存数据库”，而是调度和隔离做得不够稳
2. 文档库主索引现在已经是本地文件系统 + SQLite + 导出快照，强行再塞一层 Redis，只会多一份状态同步成本
3. Redis 适合做短期缓存、锁、队列和瞬时状态，不适合在这轮替代本地文档索引真源
4. rpm 是系统安装包，不是 npm 依赖；后续如果真要接 Redis，也应该是外部服务或 sidecar，不是“直接塞进 npm 包里”

这轮真正该做的，是把现有本地链路做稳，而不是再长一层新基础设施。

## 这次的硬边界

### 边界 1：10 分钟保底不是 10 分钟全量重建

- 10 分钟可以做全库对账
- 不能默认每 10 分钟都重写整个索引和导出
- 真正的 full rebuild 必须是“检测到严重漂移后的显式升级动作”

### 边界 2：队列状态必须说真话

- queued 只是“进了队”，不等于“真的在跑”
- 超时、饿死、被阻塞、被取消必须分开表达
- 不能继续用一个“刷新中”糊弄全部状态

### 边界 3：同一根目录串行，不同根目录隔离

- 同一 `rootDir` 的 apply-config / index / export 仍然要串行
- 不同 `rootDir` 之间允许并行
- 不能再让一个资料库的堵塞拖死全部资料库

### 边界 4：Host 主线程只保留轻读和组装

- 重目录扫描、重文件遍历、重导出解析要逐步下沉
- 读接口不能顺手变成同步重活执行器
- watcher 继续只打脏标记，不直接背重活

# 需求文档 - spec016-代码视图与事务视图双工作台重构

状态：Draft

## 简介

当前 `CodingNS` 的桌面端主界面，已经长出了两类完全不同的工作：

1. 代码开发工作
2. 通用事务工作

代码开发工作天然围着“会话”展开：

- 聊天消息
- 代码上下文
- Git
- 终端
- 工作区文件
- 并行会话

但通用事务工作不是这样。它更像围着“对象”和“结果”展开：

- 文档
- 标签
- 收藏
- 待办
- 自动化
- 插件
- 浏览器任务
- 文档导出
- 运维结果

如果继续把这两类工作硬塞进同一个会话工作台里，后面只会越来越乱。

所以这次要正式把前端主结构升级成：

- **代码视图**：会话主导
- **事务视图**：对象主导

这份 Spec 的重点不是视觉换皮，而是回答下面几件事：

1. 顶层视图到底怎么命名
2. 顶层视图和现有路由、工作区、会话之间是什么关系
3. 事务视图到底放哪些东西，哪些先不放
4. 文档库、待办、自动化、插件怎么进入事务视图
5. 两个视图下 AI 对话分别扮演什么角色
6. 现有助手能力怎么保留，并从代码类助手扩到通用事务助手

## 可实现性结论

### 结论

这件事 **值得做，而且必须按信息架构重构来做**。

### 原因

1. 现有代码工作台已经成熟，不值得推翻，但也不适合继续承载所有新能力。
2. `office.document.*`、`office.browser.*`、`office.ops.*`、文档库、待办、自动化这些能力已经说明，前端需要第二种主舞台。
3. 如果这次只改左上角按钮文案，不改顶层模型，后面复杂度只会翻倍。

### 当前已确认事实

1. 代码视图可以保留现有左中右结构，不需要这次重写内部主链路。
2. 事务视图第一优先对象是文档库，但最终必须覆盖待办、自动化和插件入口。
3. 事务视图的 AI 对话应该位于右侧辅助区，而不是继续占中间主舞台。
4. 第二个顶层视图的命名不能再用狭义“办公”，因为范围已经明显超出办公。
5. 当前助手功能和对应逻辑必须保留，但在事务视图里要转成通用 AI 助手，而不是继续只服务代码跟进。

## 术语表

- **System**：`CodingNS`
- **代码视图**：以会话、消息、代码上下文和开发工具为主舞台的工作台模式
- **事务视图**：以文档、待办、自动化、插件和对象文件为主舞台的工作台模式
- **顶层视图切换**：位于工作台主导航层级的模式切换，不等同于中心 tab 切换
- **主对象区**：事务视图中间区域，用来展示文档库、待办、自动化等核心对象
- **辅助面板**：事务视图右侧区域，用来展示对象详情、AI 对话和相关动作

## 范围说明

### In Scope

- 顶层“代码 / 事务”双视图命名与信息架构
- 桌面端双视图路由与布局骨架
- 代码视图零破坏迁移策略
- 事务视图左中右三栏布局
- 文档库作为事务视图默认首页的接入方案
- 待办、自动化、插件入口的布局位置与一级结构
- 事务视图下 AI 对话的职责定义
- 移动端与小屏降级规则

### Out of Scope

- 文档库全部功能的详细业务实现
- 新的待办系统业务模型从 0 到 1 的完整定义
- 自动化引擎本身的详细执行模型
- 所有事务插件的完整设计和逐个实现
- 本 Spec 之外的深度视觉动效打磨

## 需求

### 需求 1：系统必须提供正式的顶层双视图切换

**用户故事：** 作为使用者，我希望在同一个工作区里明确区分代码工作和事务工作，以便进入不同场景时不用继续挤在同一套布局里。

#### 验收标准

1. WHEN 用户进入桌面端主工作台 THEN System SHALL 提供正式的顶层视图切换，而不是仅提供中心内容 tab。
2. WHEN 用户切换顶层视图 THEN System SHALL 记住当前工作区下的视图选择，并在刷新后恢复。
3. WHEN 用户在代码视图和事务视图之间切换 THEN System SHALL 保留各自必要的局部状态，而不是每次重置整个界面。

### 需求 2：系统必须把第二个顶层视图正式定义为“事务”类视图

**用户故事：** 作为使用者，我希望第二个视图能覆盖办公、生活、学习、待办和自动化，而不是被“办公”这种过窄名称限制住。

#### 验收标准

1. WHEN System 展示顶层双视图名称 THEN 第二个视图 SHALL 使用能覆盖通用事务的正式命名。
2. WHEN 设计文档和前端文案描述第二个视图 THEN System SHALL 明确它不只服务办公文档，而是服务更广义的事务对象。
3. WHEN 后续功能接入第二个视图 THEN System SHALL 不要求这些功能必须属于狭义办公场景。

### 需求 3：系统必须保证代码视图零破坏迁移

**用户故事：** 作为现有用户，我希望升级后原来的代码工作方式还能保持稳定，而不是因为引入新视图把原来的开发体验打坏。

#### 验收标准

1. WHEN 用户进入代码视图 THEN System SHALL 保持现有左侧会话栏、中间会话消息、右侧工具栏主结构不变。
2. WHEN 用户使用现有代码会话、Git、终端、文件、Butler 等能力 THEN System SHALL 继续按原有主链路工作。
3. WHEN 系统实施顶层视图重构 THEN System SHALL 不把成熟代码工作台内部结构当成首轮大改对象。

### 需求 4：系统必须提供事务视图三栏布局

**用户故事：** 作为使用者，我希望事务视图围绕对象工作，而不是继续把聊天消息放在中间主舞台。

#### 验收标准

1. WHEN 用户进入事务视图 THEN System SHALL 提供左侧导航、中间主对象区、右侧辅助面板三栏结构。
2. WHEN 用户在事务视图里工作 THEN 中间区域 SHALL 作为主对象工作区，而不是继续展示代码会话消息流。
3. WHEN 右侧展示 AI 对话和详情 THEN System SHALL 把它们定义为辅助面板，而不是中心主舞台。

### 需求 5：系统必须让文档库成为事务视图第一优先对象

**用户故事：** 作为使用者，我希望事务视图一进来就能看到文档库，而不是只看到一个空壳。

#### 验收标准

1. WHEN 用户首次进入事务视图 THEN System SHALL 提供文档库作为默认主对象页或默认首页。
2. WHEN 文档库接入事务视图 THEN System SHALL 支持左侧标签、收藏和导航关系与中间主区联动。
3. WHEN 用户从事务视图打开文档对象 THEN System SHALL 在右侧展示对应详情和相关 AI 辅助区。

### 需求 6：系统必须给待办、自动化和插件保留正式入口

**用户故事：** 作为使用者，我希望事务视图不只是一页文档库，而是后续所有通用事务能力的正式容器。

#### 验收标准

1. WHEN 事务视图定义一级结构 THEN System SHALL 为待办、自动化和插件保留正式入口位置。
2. WHEN 后续能力继续接入事务视图 THEN System SHALL 不需要再从代码视图里临时找角落塞按钮。
3. WHEN 某项能力暂未完成 THEN System SHALL 可以先占位，但必须把归属位置定义清楚。

### 需求 7：系统必须定义事务视图顶部工具区

**用户故事：** 作为使用者，我希望事务视图里常用动作和插件入口容易找到，而不是全部埋在侧栏或详情里。

#### 验收标准

1. WHEN 用户处于事务视图 THEN System SHALL 提供顶部工具区或可展开工具区。
2. WHEN 用户需要使用新建、搜索、筛选、插件快捷入口等动作 THEN System SHALL 能从顶部工具区进入。
3. WHEN 顶部工具区展开或收起 THEN System SHALL 不破坏中间主对象区的基本可用性。


### 需求 7.1：系统必须保证双视图共享同一套 UI 语言

**用户故事：** 作为使用者，我希望代码视图和事务视图看起来属于同一套产品，而不是一切换就像换了应用。

#### 验收标准

1. WHEN 用户位于代码视图或事务视图 THEN System SHALL 始终显示统一的左上角顶层视图切换组件。
2. WHEN 用户位于代码视图或事务视图 THEN System SHALL 始终显示统一的顶部通用工具按钮区域。
3. WHEN 事务视图展示中间主工作区和右侧详情/AI 区 THEN System SHALL 保持它们顶部工具栏的高度与代码视图标题栏高度一致。
4. WHEN 用户在两个视图之间切换 THEN System SHALL 让颜色、间距、标题栏、工具栏和面板节奏保持同一产品语言，而不是像切到另一个应用。

### 需求 8：系统必须定义两个视图下 AI 对话的不同职责

**用户故事：** 作为使用者，我希望 AI 在代码工作和事务工作里各司其职，而不是到处都抢同一个主舞台。

#### 验收标准

1. WHEN 用户处于代码视图 THEN System SHALL 继续把会话消息作为主舞台。
2. WHEN 用户处于事务视图 THEN System SHALL 把 AI 对话定义为右侧辅助能力，而不是中心主舞台。
3. WHEN AI 在事务视图里执行动作 THEN System SHALL 能明确它是围绕当前对象提供帮助，而不是脱离上下文的独立闲聊。


### 需求 8.1：系统必须保留现有助手能力，并把它扩成通用事务助手

**用户故事：** 作为使用者，我希望现在已经能用的助手能力不要因为双视图重构被删掉，同时我也希望它在事务视图里不再只会管代码。

#### 验收标准

1. WHEN 系统实施双视图重构 THEN System SHALL 保留现有助手功能和底层运行逻辑。
2. WHEN 用户处于事务视图 THEN System SHALL 允许助手围绕文档、标签、待办、自动化、浏览器、运维等通用对象工作。
3. WHEN 用户在事务视图里需要 AI 辅助 THEN System SHALL 不要求用户必须跳转到独立 Butler 页面才能使用助手。

### 需求 9：系统必须提供移动端和小屏降级方案

**用户故事：** 作为移动端或小屏用户，我希望双视图重构后仍然能用，而不是桌面三栏直接压到小屏上。

#### 验收标准

1. WHEN 屏幕尺寸不足以承载事务视图三栏布局 THEN System SHALL 提供抽屉、切页或分段式降级方案。
2. WHEN 用户在移动端进入代码视图或事务视图 THEN System SHALL 明确两者的导航和返回路径。
3. WHEN 后续继续扩事务视图能力 THEN System SHALL 不要求移动端完全复刻桌面三栏结构。

## 非功能需求

### 非功能需求 1：兼容性

1. WHEN 顶层视图重构落地 THEN System SHALL 保证现有代码工作流的主要入口和核心操作不被破坏。
2. WHEN 老路由、老状态或老书签仍然存在 THEN System SHALL 提供兼容迁移或明确跳转规则。

### 非功能需求 2：可维护性

1. WHEN 后续新增事务对象或插件 THEN System SHALL 能复用事务视图既有骨架，而不是再长第三套工作台。
2. WHEN 后续调整顶部导航或侧栏结构 THEN System SHALL 有明确的顶层视图状态模型和布局模块边界。

### 非功能需求 2.1：视觉一致性

1. WHEN 用户在代码视图和事务视图之间切换 THEN System SHALL 保持统一的顶层导航、工具按钮布局和标题栏节奏。
2. WHEN 事务视图新增局部工具栏 THEN System SHALL 与代码视图对应区域保持一致的高度、边距和层级关系。

### 非功能需求 3：性能与体验

1. WHEN 用户在两个顶层视图之间来回切换 THEN System SHALL 在可接受时间内恢复主要界面状态。
2. WHEN 事务视图接入文档库、标签和详情面板 THEN System SHALL 避免因为布局切换造成明显卡顿或整页闪烁。

## 成功定义

- 桌面端正式出现“代码 / 事务”双视图，而不是继续用旧中心 tab 假装升级
- 代码视图在主要开发流程上保持稳定可用
- 事务视图能以文档库为默认主对象页跑通第一条主链路
- 后续待办、自动化、插件接入时，有明确位置，不再继续挤代码工作台

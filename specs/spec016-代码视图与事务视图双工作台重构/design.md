# 设计文档 - spec016-代码视图与事务视图双工作台重构

状态：Draft

## 1. 概述

### 1.1 目标

- 把当前前端主工作台从“单一代码会话工作台”升级成“代码 / 事务”双视图骨架
- 保持代码视图零破坏迁移，不拿成熟链路做无意义重写
- 双视图共享同一套 UI 语言和布局节奏，避免切换后像换了应用
- 为事务视图建立长期可扩展的对象工作台结构，让文档库、待办、自动化、插件能逐步接入同一套容器
- 明确两个视图下 AI 对话的职责差异，避免主舞台冲突
- 保留现有 Butler / 助手底层能力，并把它从代码类助手扩成事务视图里的通用 AI 助手

### 1.3 技术约束

- 前端：`apps/user-app` React 工作台
- 路由：现有 workspace / session / butler / tools 导航体系
- i18n：必须走统一字典，不允许硬编码视图名称和新文案
- 桌面端样式：必须复用现有工作台布局能力，不另起一套窗口壳
- 移动端：必须参考 `spec009`、`spec009.1` 的导航和密度规则

### 1.4 视觉约束

- 左上角顶层视图切换组件是代码视图和事务视图共享的正式壳层组件
- 顶部通用工具按钮区域是代码视图和事务视图共享的正式壳层组件
- 事务视图中间主工作区顶部栏高度必须和代码视图标题栏高度一致
- 事务视图右侧详情 / AI 助手顶部栏高度也必须和代码视图标题栏高度一致
- 事务视图可以换内容，但不能换产品语言；颜色、间距、圆角、阴影、分割和栏位节奏必须延续现有工作台体系

## 2. 架构

### 2.1 系统结构

这次重构不推翻现有工作台，而是在它上面再加一层正式的“顶层模式”。

新的结构分三层：

1. **顶层模式层**
   - 代码
   - 事务
2. **视图内部骨架层**
   - 代码视图骨架
   - 事务视图骨架
3. **对象与工具层**
   - 会话、终端、Git、文件、Butler
   - 文档库、待办、自动化、插件、详情、AI 辅助

关键点：

- 旧的 center tab 只是代码视图内部能力切换，不再承担顶层模式职责
- 顶层模式决定整个主工作区的布局骨架
- 事务视图要围绕对象工作，不再复用“消息占中间”的旧假设

### 2.2 模块职责

| 模块 | 职责 | 输入 | 输出 |
| --- | --- | --- | --- |
| `WorkbenchShellMode` | 维护当前顶层模式 | 当前路由、工作区、用户选择 | 当前模式、恢复状态 |
| `CodeWorkbenchView` | 承载现有代码工作台骨架 | 工作区、会话、工具状态 | 代码视图主界面 |
| `AffairsWorkbenchView` | 承载事务视图三栏骨架 | 工作区、事务对象状态 | 事务视图主界面 |
| `AffairsNavigationPanel` | 承载标签、收藏、入口列表 | 当前工作区、对象导航状态 | 左侧导航区 |
| `AffairsPrimaryStage` | 展示文档库、待办、自动化、插件等主对象 | 当前对象类型、筛选条件 | 中间主对象区 |
| `AffairsAuxiliaryPanel` | 展示详情和 AI 辅助 | 当前选中对象、辅助上下文 | 右侧详情与 AI 面板 |
| `AffairsSharedTopBar` | 事务视图中间主区和右侧面板共享的顶部栏规范 | 当前分区、当前对象、动作配置 | 统一高度和布局节奏的顶部栏 |
| `UniversalAssistantBridge` | 复用现有 Butler/助手底层能力，为事务视图提供通用 AI 助手上下文 | 当前工作区、当前对象、office 能力上下文 | 事务视图助手状态与动作 |

### 2.3 关键流程

#### 2.3.1 顶层模式切换

1. 用户点击顶层“代码 / 事务”切换按钮
2. 系统读取当前工作区的模式偏好和路由上下文
3. 系统决定进入代码视图或事务视图
4. 系统恢复该视图上一次保存的局部状态

#### 2.3.2 事务视图进入文档库

1. 用户进入事务视图
2. 系统默认选中文档库作为主对象页
3. 左侧显示标签、收藏和对象入口
4. 中间显示文档库主区
5. 右侧显示对象详情和 AI 辅助区
6. 右侧 AI 辅助区复用现有助手底层能力，但产品定位切成通用事务助手

#### 2.3.3 从事务视图切回代码视图

1. 用户点击“代码”
2. 系统恢复上一次代码视图的工作区、会话和面板状态
3. 不重置代码视图内部消息流和工具栏结构

### 3.3 接口契约

覆盖需求：1、5、6、7、8、9

#### 3.3.1 视图状态持久化接口

- 类型：前端本地状态 + 账户/工作区偏好扩展点
- 路径或标识：待实现时在 `local-ui-preference-store` 或对应 workspace 视图快照中落地
- 输入：工作区 ID、模式、局部布局状态
- 输出：恢复后的顶层模式和局部视图状态
- 校验：工作区切换时不能串状态
- 错误：状态缺失时回退默认值

#### 3.3.2 文档库主对象数据接口

- 类型：HTTP / 现有工作区能力桥接
- 路径或标识：首阶段允许走现有文档库接入层，后续收口正式事务对象接口
- 输入：工作区 ID、筛选条件、标签、排序、分页
- 输出：对象列表、标签树、收藏列表、详情对象
- 校验：只允许当前工作区作用域
- 错误：未准备好时返回明确空态和错误状态

## 4. 数据与状态模型

### 4.1 数据关系

顶层关系如下：

- 一个 `workspace` 下有一个当前顶层 `mode`
- `mode=code` 时，核心关系仍然是 `workspace -> session -> timeline/tools`
- `mode=affairs` 时，核心关系变成 `workspace -> navigation node -> primary object -> auxiliary context`

也就是说：

- 代码视图主索引是“会话”
- 事务视图主索引是“对象”

这是这次重构最重要的数据关系变化。

### 4.2 状态流转

| 状态 | 含义 | 进入条件 | 退出条件 |
| --- | --- | --- | --- |
| `code` | 代码视图激活 | 用户点击代码、代码路由恢复 | 用户切到事务 |
| `affairs` | 事务视图激活 | 用户点击事务、事务路由恢复 | 用户切到代码 |
| `library` | 文档库为事务主区 | 首次进入事务视图或手动选择文档库 | 切到待办/自动化/插件 |
| `todo` | 待办为事务主区 | 用户进入待办分区 | 切到其他分区 |
| `automation` | 自动化为事务主区 | 用户进入自动化分区 | 切到其他分区 |
| `plugins` | 插件为事务主区 | 用户进入插件分区 | 切到其他分区 |

## 5. 错误处理

### 5.1 错误类型

- `mode_restore_failed`：顶层模式恢复失败
- `affairs_state_invalid`：事务视图局部状态无效
- `affairs_object_load_failed`：事务主对象加载失败
- `affairs_context_mismatch`：右侧详情与当前对象不同步

### 5.2 错误响应格式

```json
{
  "detail": "事务视图状态恢复失败，已回到默认布局。",
  "error_code": "affairs_state_invalid",
  "field": "primarySection",
  "timestamp": "2026-05-29T00:00:00Z"
}
```

### 5.3 处理策略

1. 顶层模式状态缺失：默认回到代码视图或按明确产品规则进入事务视图默认首页
2. 事务对象加载失败：保留布局，显示空态和错误提示，不把整个工作台打回代码视图
3. 左中右上下文不同步：优先清理辅助区选择状态，避免显示错对象详情
4. 移动端布局不足：主动切抽屉或单列模式，不硬挤三栏

## 6. 正确性属性

### 6.1 属性 1：代码视图零破坏

*对于任何* 已存在的代码工作流，系统都应该满足：顶层双视图改造不会要求代码视图重写其主消息区、左侧会话区和右侧工具区才能继续工作。

**验证需求：** 需求 3

### 6.2 属性 2：事务视图主舞台是对象

*对于任何* 事务视图场景，系统都应该满足：中间区域优先展示对象工作区，而不是继续展示代码会话消息作为主舞台。

**验证需求：** 需求 4、需求 5、需求 8

### 6.3 属性 3：两个顶层视图的状态不串线

*对于任何* 工作区内的模式切换，系统都应该满足：代码视图和事务视图都能恢复各自局部状态，而不是相互覆盖。

**验证需求：** 需求 1、需求 9

### 6.4 属性 4：助手能力保留但职能扩展

*对于任何* 双视图重构后的助手入口，系统都应该满足：现有 Butler/助手底层逻辑仍然保留，但事务视图里的助手已经能服务通用事务对象，而不是继续只会处理代码跟进。

**验证需求：** 需求 8、需求 8.1

## 8. 风险与待确认项

### 8.1 风险

- 现有 `WorkbenchLayout` 过大，顶层模式抽层时容易一边拆一边把旧逻辑缠死
- 如果事务视图第一阶段只接一张静态页面，后面可能再次形成孤岛
- 桌面端先做完、移动端迟迟不补，会导致双视图能力只在大屏成立
- 代码视图和事务视图共享太多状态时，容易出现恢复错乱

### 8.2 待确认项

- 顶层模式是否直接进入独立路由，还是先保留在同一路由下按状态切换
- 文档库首阶段是直接嵌现有静态能力，还是先抽成 `user-app` 原生容器再接数据
- 事务视图右侧 AI 面板是复用现有会话组件，还是做轻量上下文助手壳
- 顶部工具区常驻项和展开项的最终划分

## 9. 视觉一致性约束

### 9.1 顶层共享壳层

下面这些东西在两个视图里都必须稳定存在，而且位置不漂：

1. 左上角 `代码 / 事务` 切换组件
2. 顶部通用工具按钮区
3. 主工作区与侧栏的统一外边距节奏

### 9.2 局部顶部栏高度统一

事务视图至少有两块局部顶部栏必须和代码视图标题栏对齐：

1. 中间主对象工作区顶部栏
2. 右侧详情 / AI 助手顶部栏

这里的“对齐”不是大概差不多，而是要求：

- 统一高度
- 统一垂直居中方式
- 统一内边距节奏
- 统一分割线和背景层级

### 9.3 可变化的只有内容，不是应用壳

事务视图允许变化的是：

- 左侧导航内容
- 中间主对象类型
- 右侧详情和 AI 的具体内容

不允许变化的是：

- 主壳层结构
- 导航节奏
- 标题栏语言
- 工具栏高度体系

### 9.4 验证要求

- 代码 / 事务切换后，第一眼仍能看出这是同一个工作台
- 截图对比时，共享壳层位置稳定
- 中间和右侧顶部栏与代码视图标题栏高度一致

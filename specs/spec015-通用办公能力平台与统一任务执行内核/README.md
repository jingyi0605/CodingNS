# spec015-通用办公能力平台与统一任务执行内核

## 这份 Spec 现在解决什么问题

`CodingNS` 现在已经有一套很强的 AI 编码底座：

- 工作区
- 会话
- 文件
- Git
- 终端
- 进程
- 助手能力门面
- 自动化基础

但这些能力大多还是围着“代码开发”转。

现在要解决的新问题不是“再多加几个工具按钮”，而是把 `CodingNS` 正式扩成一套**完整办公执行平台**，让它除了开发，还能稳定承载下面四类真实工作：

1. 浏览器操作
2. 专业文档产出
3. SSH 与浏览器运维
4. 重复事务自动化

一句人话：

这份 Spec 要把 `CodingNS` 从“AI 编码 IDE”推进成“带统一任务模型的通用办公执行平台”。

## 这次计划覆盖什么

- 定义平台级统一任务模型，不再让任务散在会话、终端、页面和脚本里
- 定义浏览器执行内核，覆盖标签页、会话、DOM、截图/OCR、表单、上传下载、登录态隔离、失败重试
- 定义专业文档内核，覆盖大纲、模板、引用、版本历史、批注协作和 `docx/pdf/md` 导出
- 把“指定 `doct` 模板”写成强约束，不允许样式靠模型即兴生成
- 定义系统运维内核，第一阶段聚焦 `SSH` 命令执行和浏览器运维
- 定义重复事务自动化内核，覆盖触发器、步骤、条件分支、重试、暂停恢复、幂等和失败补偿
- 定义统一资源连接器模型，把浏览器、文档、系统和外部办公平台都挂到同一套接口下
- 定义 Host API、CLI、助手能力面和后续前端入口的统一暴露方式

## 这次明确不做什么

- 不把 `Codex` / `Claude Code` 自带浏览器能力当平台核心执行层
- 不把文档样式交给模型自由发挥
- 不做“什么系统都能全自动接管”的无限运维平台
- 不在第一阶段支持任意脚本表达式驱动的自动化 DSL
- 不为了“统一”把现有工作区、终端、Butler、自动化全部一次性推翻重写

## 为什么现在就要立这个 Spec

因为如果不先把模型说死，后面一定会长出四套各自为政的东西：

1. 浏览器自己一套动作模型
2. 文档自己一套导出模型
3. 运维自己一套审批模型
4. 自动化自己一套状态机

这四套东西一旦分家，最后就会变成：

- 审计对不上
- 权限对不上
- 产物对不上
- 回放对不上
- 失败补偿对不上

这不是后面再补两张表能救回来的。

## 硬边界先写死

### 浏览器

- 核心执行层：`Playwright`
- 浏览器目标：真实 `Google Chrome Stable`、真实 `Microsoft Edge`
- 默认方式：独立持久化 `Profile`
- 高级方式：`CDP` 接管运行中的浏览器
- 插件角色：桥接和人工接管，不是核心执行引擎

### 文档

- 最终样式必须来自指定 `doct` 模板
- AI 负责内容，不负责最终版式真相
- 导出必须走真实模板渲染，而不是“看起来差不多”的模拟

### 运维

- 第一阶段以 `SSH` 和浏览器运维为主
- 高风险动作必须经过审批、审计、回滚和权限分级

### 自动化

- 必须挂到平台级任务模型
- 不能再散落成私有定时器、私有状态机和 prompt 递归

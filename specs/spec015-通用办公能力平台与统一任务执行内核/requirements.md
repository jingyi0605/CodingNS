# 需求文档 - spec015-通用办公能力平台与统一任务执行内核

状态：Draft

## 简介

当前 `CodingNS` 的强项是 AI 编码协作，但你这次要的不是“把编码工具做得更满”，而是把它扩成一套完整办公解决方案。

这次需要正式纳入平台核心的能力有 6 类：

1. 浏览器执行内核
2. 专业文档内核
3. 系统运维内核
4. 重复事务自动化内核
5. 统一任务模型
6. 资源连接器

这里最关键的一句边界是：

**所有办公能力都必须回到统一任务模型和统一连接器体系，而不是各长一套私有流程。**

## 可实现性结论

### 结论

这件事 **值得做，而且必须按平台级能力来做**。

### 原因

1. `CodingNS` 已经有工作区、终端、任务调度、助手能力门面、自动化基础，地基不算空。
2. 现在缺的不是单点工具，而是统一的执行面、审计面和任务面。
3. 如果继续按“哪个需求急就给哪个页面塞功能”去做，后面一定烂成散装系统。

### 当前已确认事实

1. 浏览器能力不能押在 `Codex` / `Claude Code` 自带网页操作上，平台必须自己掌控执行层。
2. 文档产出必须使用指定 `doct` 模板，保证样式是真实生产环境样式。
3. 运维主需求不是“全能系统控制”，而是 `SSH` 命令执行和浏览器化运维。
4. 自动化需要正式支持触发器、步骤、分支、重试、暂停恢复、幂等和失败补偿。
5. 平台后续还会继续接更多办公对象，所以连接器必须标准化。

## 术语表

- **System**：`CodingNS`
- **统一任务模型**：平台级任务、步骤、审批、产物、回执、事件的统一结构
- **浏览器执行内核**：负责真实浏览器操作的正式执行层
- **文档模板**：受控的 `doct` 模板及其字段映射规则
- **运维目标**：可被平台执行运维动作的主机、环境、控制台或站点
- **连接器**：对浏览器、文档、系统和外部平台的统一能力封装
- **产物**：任务执行过程中生成或引用的文件、截图、文档、日志、导出件、记录等对象

## 范围说明

### In Scope

- 平台级统一任务模型
- 浏览器执行内核与真实浏览器控制
- `doct` 模板驱动的专业文档内核
- `SSH` 与浏览器运维内核
- 正式自动化工作流模型
- 统一资源连接器协议
- 审批、审计、回滚和权限分级

### Out of Scope

- 第一阶段覆盖所有办公 SaaS 的完整深度适配
- 让模型自由定义任意格式文档样式
- 任意脚本表达式驱动的自动化 DSL
- 一次性重写现有所有助手、工作区、终端主流程

## 技术边界

### 边界 1：浏览器核心执行层必须平台自管

- 浏览器执行层必须由 `CodingNS` 自己掌控
- `Codex` / `Claude Code` 浏览器能力只允许作为上层策略或辅助兜底
- 核心执行目标是真实 `Chrome Stable` 和真实 `Edge`

### 边界 2：文档最终样式必须来自 `doct` 模板

- 模型不能直接决定最终交付样式
- 模板是样式真相源
- 导出产物必须可验证来自指定模板

### 边界 3：运维第一阶段只做最有价值的能力

- 第一阶段以 `SSH` 和浏览器运维为主
- 不做无限扩张的“全系统控制台”

### 边界 4：所有执行都必须进统一任务模型

- 任务、步骤、审批、产物、回执必须结构化
- 不允许继续散在终端、聊天消息和页面按钮后面

### 边界 5：自动化必须纳入正式后台任务体系

- 新增自动化执行、重试、补偿、轮询都必须走正式后台链路
- 不允许私长新的 `inflight`、私有定时器和私有重试队列

## 需求

### 需求 1：系统必须提供平台级统一任务模型

**用户故事：** 作为平台维护者，我希望浏览器、文档、运维和自动化都挂到同一套任务模型上，以便统一审计、回放和排障。

#### 验收标准

1. WHEN 任意办公能力被触发 THEN System SHALL 创建正式任务对象，而不是只执行一段临时命令。
2. WHEN 任务运行过程中存在多个阶段 THEN System SHALL 把每个阶段记录为正式步骤对象。
3. WHEN 任务产生文档、截图、日志、导出件或回执 THEN System SHALL 把它们记录为正式产物或回执对象。
4. WHEN 任务需要人工确认 THEN System SHALL 创建正式审批对象，而不是只在聊天里提示一句。

### 需求 2：系统必须提供浏览器执行内核

**用户故事：** 作为使用者，我希望平台能稳定操作真实浏览器，而不是只会打开网页或依赖模型临时点点页面。

#### 验收标准

1. WHEN 用户或助手发起浏览器任务 THEN System SHALL 支持真实 `Chrome Stable` 或真实 `Edge` 执行。
2. WHEN 浏览器任务运行 THEN System SHALL 支持标签页、会话、导航、点击、输入、DOM 读取、截图和上传下载。
3. WHEN 浏览器任务需要失败恢复 THEN System SHALL 记录失败步骤、支持重试并保留必要快照。
4. WHEN 平台未启用模型浏览器能力 THEN System SHALL 仍能通过自有浏览器执行层完成主流程。

### 需求 3：系统必须支持浏览器登录态隔离与复用

**用户故事：** 作为使用者，我希望不同浏览器任务既能复用登录态，又不会把我的日常浏览环境搞坏。

#### 验收标准

1. WHEN 平台创建浏览器运行环境 THEN System SHALL 默认使用独立持久化 `Profile`。
2. WHEN 不同任务或不同目标需要隔离 THEN System SHALL 支持按用户、工作区或目标对象分离浏览器 `Profile`。
3. WHEN 用户显式请求接管运行中的浏览器 THEN System SHALL 支持通过 `CDP` 连接真实浏览器，但必须明确标记为高级模式。
4. WHEN 用户不使用高级模式 THEN System SHALL 不直接污染用户日常浏览器 `Profile`。

### 需求 4：系统必须提供专业文档内核

**用户故事：** 作为使用者，我希望平台能产出正式可交付文档，而不是只给我一份 Markdown 草稿。

#### 验收标准

1. WHEN 用户创建文档任务 THEN System SHALL 提供正式文档对象，而不是只生成一段文本。
2. WHEN 用户编辑文档 THEN System SHALL 支持大纲、结构化段落和章节层级。
3. WHEN 用户引用材料 THEN System SHALL 记录引用来源，并能在导出时保留引用关系。
4. WHEN 用户查看文档历史 THEN System SHALL 支持版本历史和变更追踪。

### 需求 5：系统必须强制使用指定 `doct` 模板输出正式文档

**用户故事：** 作为文档交付者，我希望输出文档严格使用指定模板，以便最终样式和生产环境一致。

#### 验收标准

1. WHEN 文档进入正式导出 THEN System SHALL 使用指定 `doct` 模板渲染。
2. WHEN 模型生成内容 THEN System SHALL 只负责内容填充，不得绕过模板直接决定最终样式。
3. WHEN 用户导出 `docx/pdf/md` THEN System SHALL 明确记录使用的模板、模板版本和导出时间。
4. WHEN 用户选择不兼容模板的结构或字段 THEN System SHALL 返回明确校验失败，而不是静默导出错误样式。

### 需求 6：系统必须提供文档协作与导出能力

**用户故事：** 作为团队成员，我希望文档不仅能写，还能评论、追历史并导出成正式产物。

#### 验收标准

1. WHEN 用户对文档内容提出意见 THEN System SHALL 支持批注或评论对象。
2. WHEN 文档被修改 THEN System SHALL 记录修订版本。
3. WHEN 文档需要交付 THEN System SHALL 支持导出 `docx`、`pdf` 和 `md`。
4. WHEN 导出完成 THEN System SHALL 把导出件记录为任务产物。

### 需求 7：系统必须提供受控的运维内核

**用户故事：** 作为运维使用者，我希望平台既能执行真实运维动作，又不会变成无审计的危险后门。

#### 验收标准

1. WHEN 用户发起运维任务 THEN System SHALL 支持 `SSH` 执行和浏览器运维两类正式动作。
2. WHEN 运维动作涉及命令、主机、环境和凭据 THEN System SHALL 使用正式目标模型和凭据模型，而不是靠自由文本拼接。
3. WHEN 运维任务执行 THEN System SHALL 记录命令、输出摘要、退出状态和相关产物。
4. WHEN 运维任务失败 THEN System SHALL 保留错误详情和可回放记录。

### 需求 8：系统必须支持审批、审计、回滚和权限分级

**用户故事：** 作为维护者，我希望高风险动作能被拦住、能追责、能回滚，而不是谁都能一把梭。

#### 验收标准

1. WHEN 任务命中高风险策略 THEN System SHALL 进入待审批状态。
2. WHEN 审批通过或拒绝 THEN System SHALL 记录审批人、审批时间和审批结论。
3. WHEN 任务完成后需要回滚信息 THEN System SHALL 能记录明确回滚计划或补偿动作。
4. WHEN 不同角色调用同一类能力 THEN System SHALL 按权限分级决定可见范围和可执行范围。

### 需求 9：系统必须提供正式的重复事务自动化内核

**用户故事：** 作为使用者，我希望把重复工作交给平台持续做，而不是每次都手工重新操作。

#### 验收标准

1. WHEN 用户定义自动化 THEN System SHALL 支持触发器、步骤、条件分支和目标动作。
2. WHEN 自动化执行失败 THEN System SHALL 支持重试、暂停、恢复、取消和失败补偿。
3. WHEN 自动化重复触发同一业务对象 THEN System SHALL 支持幂等控制。
4. WHEN 自动化依赖外部事件 THEN System SHALL 支持事件订阅或轮询驱动的正式触发方式。

### 需求 10：系统必须提供统一资源连接器模型

**用户故事：** 作为平台维护者，我希望以后新增浏览器、文档、系统或外部平台能力时，不需要每次再造一套新协议。

#### 验收标准

1. WHEN 系统接入浏览器、文档、系统或外部平台 THEN System SHALL 通过统一连接器接口暴露能力。
2. WHEN 上层任务调用底层资源 THEN System SHALL 通过连接器能力描述决定可执行动作，而不是直接写死具体实现。
3. WHEN 新增连接器 THEN System SHALL 不要求上层任务模型发生结构性变化。

### 需求 11：系统必须提供统一入口给 Host API、CLI 和助手能力面

**用户故事：** 作为调用方，我希望浏览器、文档、运维和自动化能力都能通过正式入口调用，而不是只能点某个页面。

#### 验收标准

1. WHEN 平台暴露办公能力 THEN System SHALL 提供正式 Host API。
2. WHEN 用户从命令行调用 THEN System SHALL 提供对应 CLI 入口。
3. WHEN 助手需要代理调用 THEN System SHALL 通过统一能力面访问这些能力，而不是直接硬编码底层路由。

### 需求 12：系统第一阶段不能破坏现有编码主链路

**用户故事：** 作为维护者，我希望新增办公能力后，原来的工作区、终端、会话、Git 和助手链路不被打断。

#### 验收标准

1. WHEN 用户完全不使用新办公能力 THEN System SHALL 保持现有编码主流程不变。
2. WHEN 新办公能力出现失败 THEN System SHALL 把影响限制在该任务和相关对象内。
3. WHEN 平台逐步接入新连接器 THEN System SHALL 不要求现有终端、工作区和会话对象整体迁移重构。

## 非功能需求

### 非功能需求 1：可靠性

1. WHEN 浏览器、文档导出、SSH 或自动化依赖外部系统 THEN System SHALL 提供明确超时、失败、重试和错误记录。
2. WHEN 平台异常中断后恢复 THEN System SHALL 能依据正式状态对象恢复未完成任务的可见状态。

### 非功能需求 2：可观测性

1. WHEN 任务执行 THEN System SHALL 记录任务事件、步骤事件、审批事件和产物事件。
2. WHEN 维护者排查问题 THEN System SHALL 能按任务、目标、连接器和时间范围检索执行记录。

### 非功能需求 3：可扩展性

1. WHEN 平台新增浏览器动作、文档模板、运维目标或连接器 THEN System SHALL 复用统一模型扩展，而不是复制一套新结构。
2. WHEN 后续接更多办公平台 THEN System SHALL 不要求重做统一任务模型和连接器协议。

## 成功定义

- 平台能正式承载浏览器、文档、运维和自动化四类办公任务
- 高风险动作有审批、审计和回滚记录
- 文档导出可证明使用指定 `doct` 模板
- 新办公能力接入后不破坏现有编码主链路

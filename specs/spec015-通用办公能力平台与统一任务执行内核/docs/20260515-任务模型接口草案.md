# spec015 任务模型接口草案

状态：Draft

## 1. 目标

这份草案只回答一个问题：

`office_tasks` 这一组平台对象，实际写代码时应该暴露什么服务接口，哪些状态能改，哪些字段只能系统写，哪些地方必须校验。

一句话版本：

**先把任务模型怎么读、怎么写、怎么推进说死，再让浏览器、文档、运维和自动化往里挂。**

## 2. 核心对象

平台级统一任务对象最少包括：

- `OfficeTask`
- `OfficeTaskStep`
- `OfficeArtifact`
- `OfficeApproval`
- `OfficeReceipt`

其中：

- `OfficeTask` 是总对象
- `OfficeTaskStep` 是执行过程
- `OfficeArtifact` 是过程产物
- `OfficeApproval` 是人为放行
- `OfficeReceipt` 是执行回执

## 3. 服务边界

### 3.1 `office-task-service`

职责：

- 创建任务
- 读取任务
- 推进任务状态
- 更新当前步骤
- 取消任务
- 重试任务
- 记录结束态

不该做：

- 不直接执行浏览器动作
- 不直接执行 SSH
- 不直接渲染模板
- 不直接处理复杂权限校验

### 3.2 `office-task-step-service`

职责：

- 创建步骤
- 标记步骤开始
- 标记步骤结束
- 标记步骤失败
- 推进下一步

### 3.3 `office-artifact-service`

职责：

- 记录截图、OCR、导出件、日志、下载文件、DOM 快照
- 绑定到任务或步骤

### 3.4 `office-approval-service`

职责：

- 创建审批
- 处理审批回复
- 查询待审批列表

### 3.5 `office-receipt-service`

职责：

- 记录执行结果摘要
- 记录回执载荷
- 供上层 UI / CLI / 助手查询

## 4. 仓储接口建议

### 4.1 `OfficeTaskRepository`

建议暴露：

- `create(task)`
- `getById(taskId)`
- `list(filters)`
- `update(taskId, patch)`
- `updateStatus(taskId, status)`
- `assignCurrentStep(taskId, stepId)`
- `findByIdempotencyKey(userId, key)`

### 4.2 `OfficeTaskStepRepository`

建议暴露：

- `create(step)`
- `getById(stepId)`
- `listByTaskId(taskId)`
- `update(stepId, patch)`
- `updateStatus(stepId, status)`

### 4.3 `OfficeArtifactRepository`

建议暴露：

- `create(artifact)`
- `listByTaskId(taskId)`
- `listByStepId(stepId)`

### 4.4 `OfficeApprovalRepository`

建议暴露：

- `create(approval)`
- `getById(approvalId)`
- `list(filters)`
- `updateStatus(approvalId, status)`

### 4.5 `OfficeReceiptRepository`

建议暴露：

- `create(receipt)`
- `listByTaskId(taskId)`
- `listByStepId(stepId)`

## 5. 状态流转规则

### 5.1 任务状态

| 状态 | 含义 | 谁能改 |
| --- | --- | --- |
| `draft` | 草稿 | 创建者或系统 |
| `pending_approval` | 待审批 | 系统 |
| `ready` | 可执行 | 系统 |
| `running` | 运行中 | 系统 |
| `paused` | 暂停 | 用户或系统 |
| `waiting_external` | 等待外部 | 系统 |
| `succeeded` | 成功 | 系统 |
| `failed` | 失败 | 系统 |
| `cancelled` | 已取消 | 用户或系统 |
| `rolled_back` | 已回滚 | 系统 |

### 5.2 步骤状态

| 状态 | 含义 | 谁能改 |
| --- | --- | --- |
| `pending` | 待执行 | 系统 |
| `running` | 执行中 | 系统 |
| `waiting_approval` | 等审批 | 系统 |
| `waiting_external` | 等外部结果 | 系统 |
| `succeeded` | 成功 | 系统 |
| `failed` | 失败 | 系统 |
| `cancelled` | 已取消 | 用户或系统 |
| `skipped` | 已跳过 | 系统 |

### 5.3 任务状态推进原则

1. 任务创建后先是 `draft`
2. 如果需要人工确认，先进入 `pending_approval`
3. 审批通过后才进入 `ready`
4. 开始执行后进入 `running`
5. 任务结束后只能进入终态

不要允许：

- 直接从 `failed` 偷偷跳回 `running`
- 已经终止的任务再当正常任务继续推进

## 6. 幂等规则

### 6.1 幂等键

`idempotency_key` 只应该用于：

- 避免同一用户重复提交同一个任务
- 避免自动化触发器重复拉起同一业务动作

### 6.2 幂等策略

1. 同一用户同一幂等键，只能命中一个活跃任务
2. 任务已终态后，重复提交应返回明确可识别结果
3. 自动化触发也必须带稳定幂等键，不允许短时间内无限并发重入

## 7. 审批规则

### 7.1 什么时候必须审批

默认建议：

- 高风险 SSH 命令
- 运行中浏览器接管
- 对外系统执行破坏性操作
- 任何明确标记为高风险的任务步骤

### 7.2 审批对象应该记录什么

至少记录：

- 审批策略
- 目标任务
- 目标步骤
- 审批人
- 审批结论
- 审批说明

## 8. 产物规则

### 8.1 产物类型

第一阶段建议先支持：

- 截图
- OCR 结果
- DOM 快照
- 下载文件
- 文档导出件
- 命令日志
- 审批回执

### 8.2 产物必须可追溯

每个产物至少要能追到：

- 属于哪个任务
- 属于哪个步骤
- 什么时候产生
- 存到哪

## 9. 接口契约建议

### 9.1 创建任务

输入：

- 任务类型
- 标题
- 工作区
- 连接器
- 目标引用
- 风险等级
- 输入参数

输出：

- 任务对象
- 当前状态
- 是否需要审批

### 9.2 推进步骤

输入：

- 任务 ID
- 步骤类型
- 输入载荷

输出：

- 步骤对象
- 产物引用
- 下一步建议

### 9.3 查询任务

输入：

- 任务 ID

输出：

- 任务基本信息
- 步骤列表
- 审批状态
- 产物摘要
- 回执摘要

## 10. 失败处理

### 10.1 任务失败

失败后必须保存：

- 错误摘要
- 失败步骤
- 最后更新时间
- 是否可重试

### 10.2 步骤失败

步骤失败时：

- 当前步骤标记 `failed`
- 任务根据策略进入 `failed`、`paused` 或 `waiting_external`

### 10.3 回滚或补偿

如果任务定义了补偿动作，就要把补偿也写成步骤，不允许只在日志里写一句“已回滚”。

## 11. 后续实现时最容易犯的错

1. 只做任务表，不做步骤表
2. 只做步骤表，不做审批和产物
3. 任务状态太多，最后没人敢改
4. 把浏览器动作直接塞进任务表 JSON，后面无法查询
5. 把文档模板和导出结果混成一张表

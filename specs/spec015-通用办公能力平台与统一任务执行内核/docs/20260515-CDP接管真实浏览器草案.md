# spec015 CDP 接管真实浏览器草案

状态：Draft

## 1. 目标

这份草案只解决一件事：

把“接管运行中的真实 Chrome/Edge”这件事说死，避免后面把高级模式做成默认模式，或者把用户日常浏览器搞坏。

一句话版本：

**CDP 接管只能是显式授权的高级模式，不是默认执行方式。**

## 2. 核心原则

### 2.1 默认模式和接管模式必须分开

默认模式是：

- 平台自己起独立 `Profile`
- 平台自己启动真实浏览器
- 平台自己控制上下文

接管模式是：

- 用户显式授权
- 平台连接现成浏览器
- 平台只能在受控边界里继续执行

### 2.2 接管模式必须可见

接管中必须让人一眼知道：

- 这是接管模式
- 接管的是哪个引擎
- 接管的是哪个 endpoint
- 谁授权的
- 什么时候开始的

### 2.3 不允许静默接管

不允许：

- 偷偷连到用户正在用的浏览器
- 不提示就读登录态
- 不留审计就操作页面

## 3. 接管对象

### 3.1 接管的是运行中的真实浏览器

允许接管：

- 真实 `Google Chrome Stable`
- 真实 `Microsoft Edge`

不允许：

- 默认把自带 Chromium 当作“真实浏览器接管目标”

### 3.2 接管的最小输入

接管请求至少要有：

- 浏览器引擎
- `CDP endpoint`
- 显式名称
- 授权来源

### 3.3 接管成功后应该得到什么

接管成功后，平台应该得到：

- 一个可用的运行时会话
- 一个明确标记为高级模式的 Profile 关联
- 可继续执行的页面和动作能力

## 4. 服务边界

### 4.1 `browser-bridge-service`

职责：

- 接收接管请求
- 校验是否允许接管
- 连接 `CDP endpoint`
- 标记接管模式

### 4.2 `browser-runtime-service`

职责：

- 挂接接管后的运行时
- 继续管理页面和动作
- 结束后释放接管状态

### 4.3 `browser-audit-service`

职责：

- 记录接管开始和结束
- 记录授权者
- 记录接管的浏览器引擎和 endpoint

## 5. 审计要求

接管模式至少要审计：

- 谁发起接管
- 谁批准接管
- 接管的是哪个浏览器
- 接管的是哪个 endpoint
- 接管开始和结束时间
- 接管过程中发生了什么关键动作

## 6. 风险控制

### 6.1 高风险默认提示

接管模式默认应当被当作高风险动作处理。

### 6.2 不可默认为全局共享

接管模式不应该把整个系统的浏览器状态都当成共享资源。  
它应该和普通独立 Profile 模式隔开。

### 6.3 失败后要能退回

如果接管失败：

- 记录失败原因
- 释放接管状态
- 不污染普通 Profile 运行链路

## 7. 最容易做烂的地方

1. 把接管模式偷偷做成默认模式
2. 不记录授权来源
3. 接管后无法区分普通 Profile 和高级模式
4. 失败后不释放连接
5. 把用户当前浏览器里的东西当平台公共状态

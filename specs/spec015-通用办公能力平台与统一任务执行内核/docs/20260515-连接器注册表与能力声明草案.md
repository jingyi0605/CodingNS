# spec015 连接器注册表与能力声明草案

状态：Draft

## 1. 目标

这份草案只解决一件事：

把浏览器、文档、运维和后续外部办公平台，都收进同一套连接器注册表和能力声明模型。

一句话版本：

**连接器不是随便写一个适配器，而是平台正式资源。**

## 2. 核心原则

### 2.1 连接器先回答“能做什么”

连接器最重要的不是“内部怎么实现”，而是：

- 它支持哪些动作
- 它需要什么授权
- 它会产出什么
- 它能不能订阅事件

这些都要对上层明确可见。

### 2.2 上层任务只认连接器，不认底层实现细节

上层任务应该看到：

- `browser.playwright`
- `document.doct`
- `ops.ssh`

而不是直接看到：

- Playwright 具体类名
- doct 内部桥接脚本
- SSH 客户端库细节

### 2.3 连接器能力声明必须稳定

能力声明不能今天一个字段，明天一个字段。

不然上层路由、CLI、助手能力面都会跟着抖。

## 3. 核心对象

### 3.1 `OfficeConnector`

`OfficeConnector` 是平台里的正式连接器对象。

建议最少字段：

- `id`
- `connectorKey`
- `kind`
- `displayName`
- `capabilityJson`
- `status`
- `createdAt`
- `updatedAt`

### 3.2 `ConnectorCapability`

`capabilityJson` 至少要表达：

- 支持的动作列表
- 支持的资源类型
- 需要的授权类型
- 支持的产物类型
- 是否支持订阅
- 是否支持长连接
- 是否支持回调或回执

## 4. 统一接口

所有连接器第一阶段至少要提供：

- `describeCapabilities`
- `authorize`
- `connect`
- `execute`
- `listArtifacts`
- `subscribe`
- `disconnect`

### 4.1 `describeCapabilities`

职责：

- 返回稳定能力声明
- 告诉上层这个连接器到底能做什么

### 4.2 `authorize`

职责：

- 校验当前调用方和目标资源是否允许使用
- 返回授权上下文

### 4.3 `connect`

职责：

- 建立一次正式执行上下文
- 返回连接句柄或上下文对象

### 4.4 `execute`

职责：

- 在连接上下文里执行正式动作
- 产出结果、产物和回执

### 4.5 `listArtifacts`

职责：

- 列出本次执行过程中生成的正式产物

### 4.6 `subscribe`

职责：

- 提供事件订阅入口
- 让工作流和自动化可以监听外部变化

### 4.7 `disconnect`

职责：

- 释放连接
- 清理上下文
- 结束订阅

## 5. 注册表模型

### 5.1 `office-connector-registry`

注册表至少要管：

- 注册连接器
- 按 `connectorKey` 查连接器
- 读取能力声明
- 判断连接器状态
- 按任务类型选默认连接器

### 5.2 注册表不该做什么

不该做：

- 在注册表里直接执行业务动作
- 在注册表里写一堆 if/else 硬编码业务逻辑
- 把所有鉴权都塞进注册表

注册表只管发现、声明和选路。

## 6. 选路规则

### 6.1 按任务类型选连接器

第一阶段建议按下面方式选：

- 浏览器任务 -> `browser.playwright`
- 文档任务 -> `document.doct`
- SSH 运维 -> `ops.ssh`
- 浏览器运维 -> `ops.browser_console`
- 工作区文件 -> `file.workspace`

### 6.2 允许显式指定连接器

如果用户或工作流显式指定连接器，就优先按指定走。

前提是：

- 连接器存在
- 连接器状态可用
- 能力声明覆盖该任务动作

### 6.3 不允许静默降级

如果目标连接器不可用，不要偷偷换另一个实现糊弄过去。

要返回明确错误，让调用方知道：

- 连接器不可用
- 不支持该动作
- 授权不足

## 7. 第一批标准连接器

### 7.1 `browser.playwright`

职责：

- 真实 Chrome / Edge 浏览器执行
- Profile、页面、动作、截图、下载

### 7.2 `document.doct`

职责：

- 模板注册
- 字段校验
- `docx/pdf/md` 正式导出

### 7.3 `ops.ssh`

职责：

- SSH 目标连接
- 参数化命令执行
- 命令产物、日志、回执

### 7.4 `ops.browser_console`

职责：

- 控制台目标登录
- 浏览器运维动作
- 页面证据留痕

### 7.5 `file.workspace`

职责：

- 工作区文件读写
- 文件落点、附件引用、产物归档

### 7.6 `external.channel`

职责：

- 给后续邮件、IM、工单、知识库这类外部平台预留统一入口

第一阶段不要求把外部 SaaS 全接完，但接口必须先留正。

## 8. 能力声明样例

### 8.1 `browser.playwright`

建议最少声明：

- `supportedTaskTypes`: `["browser", "ops"]`
- `supportedActions`: `["goto", "click", "fill", "upload", "download", "read_dom", "screenshot"]`
- `supportedArtifacts`: `["screenshot", "ocr_result", "downloaded_file", "dom_snapshot"]`
- `supportsSubscription`: `false`

### 8.2 `document.doct`

建议最少声明：

- `supportedTaskTypes`: `["document"]`
- `supportedActions`: `["validate_template", "render_docx", "render_pdf", "render_md"]`
- `supportedArtifacts`: `["document_export"]`
- `supportsSubscription`: `false`

### 8.3 `ops.ssh`

建议最少声明：

- `supportedTaskTypes`: `["ops"]`
- `supportedActions`: `["run_command", "collect_log"]`
- `supportedArtifacts`: `["command_log", "custom"]`
- `supportsSubscription`: `false`

### 8.4 `ops.browser_console`

建议最少声明：

- `supportedTaskTypes`: `["ops"]`
- `supportedActions`: `["login_console", "goto", "click", "fill", "download", "screenshot"]`
- `supportedArtifacts`: `["screenshot", "dom_snapshot", "downloaded_file"]`
- `supportsSubscription`: `false`

## 9. 与统一任务模型的关系

### 9.1 任务对象里必须记连接器

每个 `OfficeTask` 都必须记：

- `connectorId`
- `targetRefKind`
- `targetRefId`

这样后面排障时才能知道：

- 这任务是通过谁执行的
- 打到了哪个目标

### 9.2 连接器不替代任务模型

连接器回答“怎么连、怎么做”。

任务模型回答“这件事是什么、做到了哪、产出了什么”。

不要把两者揉成一层。

## 10. 最容易做烂的地方

1. 把连接器注册表做成 if/else 大杂烩
2. 能力声明不稳定，今天一个格式明天一个格式
3. 上层直接绕过连接器去碰底层实现
4. 连接器失败时静默切换到别的实现
5. 把注册表当执行器，把职责搅烂

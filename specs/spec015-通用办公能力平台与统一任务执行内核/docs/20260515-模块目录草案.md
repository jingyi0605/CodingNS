# spec015 模块目录草案

状态：Draft

## 1. 目标

这份草案回答一个很实际的问题：

`spec015` 真开始写代码时，`apps/host/src`、`apps/user-app/src`、`packages/codingns` 到底该怎么落，不至于一开工就把目录拆成一堆没人愿意维护的碎片。

先说结论：

**第一阶段继续沿用当前仓库“按业务域平铺”的现实风格，不引入为了看起来高级而高级的深层目录树。**

## 2. 现有代码库风格判断

当前可以看到的宿主端模式很稳定：

- 路由层：`apps/host/src/routes/*.ts`
- 业务模块：`apps/host/src/modules/<domain>/*.ts`
- 存储仓储：`apps/host/src/storage/repositories/*-repository.ts`

当前前端模式也很清楚：

- 页面和业务组件按 `features/*` 切
- 跨域共享放 `shared/`、`platform/`、`config/`

所以 `spec015` 不应该突然长出一套很深的 DDD 目录树。

### 4.2 为什么前端也不要一开始拆太深

如果一开始就搞：

- `domain/model/usecase/viewmodel/component/presenter`

这种目录树，结果通常只有一个：

- 目录看起来很“架构”
- 但所有人都在来回跳文件，效率很差

当前仓库既有前端不是这么写的，那这里也别装。

## 6. 文件职责草案

### 6.1 `office-controller.ts`

职责：

- 接收 `/api/office/...` 请求
- 参数校验
- 调用各 service
- 组装 DTO

不该做：

- 直接写 SQL
- 直接调 Playwright
- 直接执行 SSH
- 直接拼复杂审批逻辑

### 6.2 `office-task-service.ts`

职责：

- 创建、读取、取消、重试任务
- 推进任务状态
- 协调步骤、审批、产物和回执

### 6.3 `browser-profile-service.ts`

职责：

- 创建浏览器 Profile
- 锁定和回收 Profile
- 管理 `persistent` 和 `cdp_attached` 模式

### 6.4 `browser-action-service.ts`

职责：

- 导航、点击、输入、上传、下载、截图、DOM 读取
- 统一浏览器动作执行语义

### 6.5 `document-template-service.ts`

职责：

- 注册和查询 `doct` 模板
- 字段校验
- 模板版本选择

### 6.6 `document-export-service.ts`

职责：

- 调用真实导出链路
- 生成 `docx/pdf/md`
- 把导出件挂到任务产物

### 6.7 `ssh-run-service.ts`

职责：

- 执行参数化 SSH 命令
- 记录退出码、日志摘要和失败信息

### 6.8 `ops-browser-run-service.ts`

职责：

- 把运维目标和浏览器执行内核接起来
- 在控制台页面完成正式运维步骤

### 6.9 `workflow-run-service.ts`

职责：

- 管理一次工作流运行
- 推进分支、重试和补偿

### 6.10 `office-connector-registry.ts`

职责：

- 注册平台可用连接器
- 暴露能力声明
- 统一解析连接器状态

## 7. 推荐实现顺序对应目录

第一轮建议按这个顺序长代码：

1. `office/`
2. `storage/repositories/*office*`
3. `browser-runtime/`
4. `document-runtime/`
5. `ops-runtime/`
6. `workflow-runtime/`
7. `user-app/src/features/office*`
8. `packages/codingns/src/office-*`

理由很简单：

- 不先把任务对象立起来，后面所有目录都会返工
- 不先把平台层立起来，浏览器、文档、运维和自动化都会各写各的入口

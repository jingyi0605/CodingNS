# spec015 浏览器运行时草案

状态：Draft

## 1. 目标

这份草案只解决一件事：

把 `Playwright + 真实 Chrome/Edge` 这套浏览器执行层说清楚，让平台后面真的能去开标签页、读 DOM、截图、上传下载、保登录态、做重试。

一句话版本：

**浏览器执行不是“能打开网页”，而是一个正式的运行时。**

## 2. 核心原则

### 2.1 真正的执行对象不是页面，是运行时会话

浏览器任务不是靠一条脚本直接跑完。  
它应该先落到一个正式的浏览器运行时会话，再在会话里管理页面和动作。

### 2.2 默认必须隔离

第一阶段默认要做的是：

- 独立 `Profile`
- 独立 `BrowserContext`
- 独立任务会话

不要一开始就直接碰用户日常浏览器的原始 Profile。

### 2.3 真实浏览器优先

平台默认目标是：

- `Google Chrome Stable`
- `Microsoft Edge`

而不是自带 Chromium 伪装成浏览器。

### 2.4 模型浏览器能力只做辅助

`Codex` / `Claude Code` 可能会提供浏览器相关操作能力，但在平台里只能是：

- 辅助策略
- 人工接管
- 兜底

不能做核心执行层。

## 3. 核心对象

### 3.1 `BrowserProfile`

用于保存浏览器身份、目录和接管方式。

它回答的是：

- 用哪个浏览器引擎
- 用哪个 Profile
- 是独立持久化还是 CDP 接管
- 归谁管

### 3.2 `BrowserRuntimeSession`

用于表示一次真实浏览器运行。

它回答的是：

- 这次运行属于哪个任务
- 用了哪个 Profile
- 当前运行状态是什么
- 最后一个活动页面是什么

### 3.3 `BrowserPage`

用于表示一个标签页或页面上下文。

它回答的是：

- 当前打开哪个 URL
- 页面处于什么状态
- 页面上一次操作是什么

### 3.4 `BrowserAction`

用于表示一次正式执行动作。

它回答的是：

- 导航
- 点击
- 输入
- 选择
- 上传
- 下载
- 读取 DOM
- 截图

### 3.5 `BrowserArtifact`

用于表示截图、OCR、下载文件、DOM 快照等产物。

## 4. 服务边界

### 4.1 `browser-profile-service`

职责：

- 创建浏览器 Profile
- 锁定 Profile
- 回收 Profile
- 标记 `persistent` 或 `cdp_attached`

### 4.2 `browser-runtime-service`

职责：

- 启动和关闭真实浏览器
- 管理运行时会话
- 绑定任务、Profile 和浏览器引擎

### 4.3 `browser-page-service`

职责：

- 打开和关闭标签页
- 切换活动页面
- 记录页面上下文

### 4.4 `browser-action-service`

职责：

- 执行浏览器动作
- 记录动作结果
- 挂接产物

### 4.5 `browser-artifact-service`

职责：

- 保存截图
- 保存 OCR
- 保存 DOM 快照
- 保存下载文件引用

### 4.6 `browser-bridge-service`

职责：

- 接收插件桥接
- 接收人工接管
- 标记高级模式浏览器上下文

## 5. 运行时模型

### 5.1 运行时状态

| 状态 | 含义 | 进入条件 | 退出条件 |
| --- | --- | --- | --- |
| `created` | 刚创建 | 收到启动请求 | 成功启动或失败 |
| `starting` | 启动中 | 正在拉起浏览器 | 运行成功或失败 |
| `running` | 运行中 | 浏览器已可用 | 关闭、失败、暂停 |
| `paused` | 暂停 | 人工暂停或等待外部结果 | 恢复或关闭 |
| `closing` | 收尾中 | 主动关闭 | 成功关闭 |
| `closed` | 已关闭 | 收尾完成 | 终态 |
| `failed` | 启动或运行失败 | 异常发生 | 终态或重试 |

### 5.2 页面状态

| 状态 | 含义 |
| --- | --- |
| `opening` | 页面打开中 |
| `active` | 当前活动页面 |
| `idle` | 暂无动作 |
| `blocked` | 被弹窗、登录或权限挡住 |
| `closed` | 已关闭 |

## 6. 浏览器动作模型

### 6.1 动作类型

第一阶段建议先支持：

- `goto`
- `click`
- `fill`
- `press`
- `select`
- `upload`
- `download`
- `read_dom`
- `screenshot`
- `wait`
- `extract_text`

### 6.2 动作记录最少要保存什么

每个动作最少记录：

- 所属任务
- 所属运行时会话
- 所属页面
- 动作类型
- 输入参数
- 输出摘要
- 是否成功
- 耗时
- 错误信息

### 6.3 为什么要把动作和任务分开

因为一个任务里可能有很多动作。  
如果把所有动作都塞回任务表里，后面就没法按页面、产物或失败点查询。

## 7. 登录态与 Profile 规则

### 7.1 默认模式

默认模式是：

- 每个用户或工作区有自己的独立 Profile
- 任务优先复用同一个 Profile
- 不主动碰用户日常浏览器目录

### 7.2 高级模式

高级模式是：

- 用户显式授权
- 通过 `CDP` 连接运行中的真实浏览器
- 必须清楚标记这是“接管模式”

### 7.3 不允许的事

不允许：

- 未授权接管用户日常 Profile
- 未记录审计就改登录态
- 把运行中浏览器当匿名一次性临时窗口乱用

## 8. 失败与重试

### 8.1 浏览器运行失败

如果浏览器启动失败：

- 记录失败原因
- 记录当前引擎和 Profile
- 允许任务重试，但重试要走正式任务状态

### 8.2 动作失败

如果动作失败：

- 保存失败动作
- 保存必要的截图或 DOM 快照
- 标记步骤状态

### 8.3 重试规则

建议默认：

- 可重试的网络类错误允许重试
- 登录态缺失、权限拒绝、目标页面结构变化，要明确返回失败，不要无限重试

## 9. 产物规则

浏览器任务的产物至少包括：

- 页面截图
- OCR 结果
- DOM 快照
- 下载文件
- 活动页面记录

产物必须能追到：

- 属于哪个任务
- 属于哪个步骤
- 来自哪个页面

## 10. 与任务模型的关系

### 10.1 任务启动时

浏览器任务启动后，平台要先创建 `OfficeTask`，再创建 `BrowserRuntimeSession`，最后进入页面和动作执行。

### 10.2 执行过程中

每个动作都应映射成：

- 一个 `OfficeTaskStep`
- 一个或多个 `OfficeArtifact`

### 10.3 结束时

运行结束后必须回写：

- 任务状态
- 最后步骤
- 最后产物
- 失败原因或成功摘要

## 11. 最容易做烂的地方

1. 把“浏览器任务”理解成一条脚本
2. 把“标签页”只当临时变量
3. 把登录态放在不受控的全局目录里
4. 把截图和日志混成一锅
5. 把 CDP 接管当默认模式

# spec015 工作流对象、触发器、幂等与补偿草案

状态：Draft

## 1. 目标

这份草案只解决一件事：

把重复事务自动化升级成平台级工作流对象，而不是继续散在计时器、会话和 prompt 递归里。

一句话版本：

**自动化不是“到点执行一下”，而是一个可追踪、可暂停、可补偿的正式工作流。**

## 2. 核心原则

### 2.1 先复用调度经验，不再重造一套

这里要复用：

- `spec001.2` 的 `TaskManager` 规则
- `spec013.3` 的触发器、运行记录和调度经验

但不能直接拿助手自动化冒充平台工作流。

原因很简单：

- 助手自动化主要围绕会话和 Butler
- 平台工作流要驱动浏览器、文档、运维和连接器

### 2.2 工作流是正式对象

工作流至少要能回答：

- 这条自动化到底要做什么
- 由什么触发
- 分几步
- 每步失败后怎么办
- 有没有补偿动作
- 现在跑到哪了

### 2.3 不做任意脚本 DSL

第一阶段不做：

- 任意脚本语言
- 任意表达式执行器
- 用户自己写无限复杂逻辑

先把固定模型和有限步骤做稳。

## 3. 核心对象

### 3.1 `WorkflowDefinition`

用于定义一条正式工作流。

建议最少字段：

- `id`
- `userId`
- `workspaceId`
- `title`
- `description`
- `status`
- `triggerType`
- `triggerConfigJson`
- `entryTaskType`
- `entryConnectorId`
- `idempotencyScope`
- `createdAt`
- `updatedAt`

### 3.2 `WorkflowStepDefinition`

用于定义工作流里的步骤。

建议最少字段：

- `id`
- `workflowId`
- `stepSeq`
- `stepType`
- `title`
- `inputTemplateJson`
- `branchConfigJson`
- `retryPolicyJson`
- `compensationJson`
- `createdAt`
- `updatedAt`

### 3.3 `WorkflowRun`

用于表示一次真实运行。

建议最少字段：

- `id`
- `workflowId`
- `triggeredBy`
- `triggerSnapshotJson`
- `status`
- `currentStepId`
- `officeTaskId`
- `idempotencyKey`
- `startedAt`
- `finishedAt`
- `createdAt`
- `updatedAt`

### 3.4 `WorkflowRunStep`

用于表示某次运行中的具体步骤。

建议最少字段：

- `id`
- `workflowRunId`
- `definitionStepId`
- `stepSeq`
- `status`
- `inputJson`
- `outputJson`
- `retryCount`
- `errorMessage`
- `startedAt`
- `finishedAt`
- `createdAt`
- `updatedAt`

## 4. 触发器模型

### 4.1 第一阶段正式触发器

先只支持：

- `manual`
- `once`
- `interval`
- `cron`
- `event`
- `condition`

### 4.2 触发器边界

触发器只负责回答：

- 什么时候该跑
- 为什么会跑
- 本次触发上下文是什么

不要把业务执行逻辑塞进触发器。

### 4.3 触发快照

每次运行都要保存触发快照，至少记录：

- 触发类型
- 触发时间
- 触发来源
- 条件结果或事件载荷

## 5. 步骤和分支模型

### 5.1 步骤类型

第一阶段先支持：

- `create_task`
- `wait_task`
- `branch`
- `pause`
- `notify`
- `complete`

### 5.2 分支规则

分支先只支持有限判断：

- 上一步是否成功
- 某个字段是否存在
- 某个状态是否命中

不要在第一阶段上复杂表达式语言。

### 5.3 步骤和平台任务的关系

平台工作流本身不是替代 `OfficeTask`。

正确关系应该是：

- `WorkflowRun` 管编排
- `OfficeTask` 管具体浏览器、文档、运维、外部动作

也就是说：

- 工作流步骤可以创建一个或多个 `OfficeTask`
- 工作流只管何时触发、怎样推进、失败后如何补偿

## 6. 重试与幂等

### 6.1 幂等键

每次运行必须有稳定 `idempotencyKey`。

它至少要能防住：

- 同一事件重复投递
- 同一计划任务重复扫描
- 同一业务对象短时间内多次并发执行

### 6.2 重试规则

第一阶段建议只支持：

- 固定次数
- 固定间隔
- 从失败步骤继续

不默认支持：

- 无限重试
- 整条工作流从头无脑重跑

### 6.3 什么情况不该自动重试

以下情况默认不该自动重试：

- 权限拒绝
- 审批被拒
- 模板校验失败
- 页面结构已变
- 凭据失效且需要人工处理

## 7. 补偿与回滚

### 7.1 补偿不是装饰

如果一个步骤可能造成外部副作用，就必须明确：

- 有补偿动作
- 没有补偿动作但明确标注不可补偿

### 7.2 补偿动作怎么挂

补偿动作应该挂在 `WorkflowStepDefinition.compensationJson` 或对应正式对象里。

补偿执行后还必须：

- 生成 `WorkflowRunStep`
- 生成 `OfficeTaskStep`
- 记录 `OfficeRollbackRecord`

### 7.3 补偿触发时机

建议第一阶段只支持：

- 某一步失败后立即补偿
- 用户手动请求补偿

先不做复杂 Saga 编排引擎。

## 8. 与现有自动化的关系

### 8.1 不破坏现有助手自动化

`spec013.3` 现有助手自动化继续存在。

但在平台层应该把它视为：

- 一个已有自动化子系统
- 一个后续可以挂进平台工作流的兼容入口

### 8.2 平台工作流和助手自动化的边界

助手自动化主要管：

- 控制会话
- 助手提示
- 临时沙箱

平台工作流主要管：

- 浏览器任务
- 文档任务
- 运维任务
- 外部连接器任务

不要把两层揉成一团。

## 9. 与后台任务体系的关系

### 9.1 必须走 `TaskManager`

以下动作默认应进 `TaskManager`：

- 到期工作流扫描
- 事件触发消费
- 条件检查
- 延迟重试
- 补偿任务

### 9.2 不允许再长私有队列

不允许在工作流模块里重新长出：

- 私有 `setTimeout`
- 私有重试队列
- 私有全局扫描器

这类东西已经在前置 Spec 里被判过死刑了。

## 10. 最容易做烂的地方

1. 把工作流直接等同于计时器
2. 把工作流和 `OfficeTask` 混成一个对象
3. 重试时整条流程从头乱跑
4. 有外部副作用却没有补偿
5. 在模块里再长一套私有调度器

# spec015 平台对象与表结构草案

状态：Draft

## 1. 目标

这份草案只解决一件事：

把 `spec015` 里的统一任务模型、浏览器、文档、运维、自动化、连接器这些核心对象，压成可以落到当前宿主端 SQLite 的第一版表结构。

一句话版本：

**先把平台自己的权威对象立住，再让浏览器、文档、运维和自动化往上挂。**

## 2. 设计原则

### 2.1 先统一任务对象，再接具体能力

这轮的主对象不是：

- 浏览器命令
- SSH 命令
- 文档导出脚本

而是：

- 任务
- 步骤
- 审批
- 产物
- 回执

### 2.2 能做一等列就别全塞 JSON

像状态、类型、时间、引用关系这种后面一定会查的字段，直接拆成列。  
只有变化快、结构弱、又不适合频繁联表查询的内容，才进 `json` 文本列。

### 2.3 平台对象和底层执行对象分开

平台对象回答：

- 这件事是什么
- 属于谁
- 做到了哪一步
- 需要谁批准
- 产出了什么

底层执行对象回答：

- 浏览器怎么开
- SSH 怎么连
- 模板怎么渲染

不要把两层糊在一张表里。

## 3. 与现有表的关系

### 3.1 直接复用的现有表

- `workspaces`
  - 继续作为任务和资源的工作区归属根对象
- 现有认证、账户、终端、会话表
  - 继续做底层宿主数据源，不在办公平台层重复造一份

### 3.2 新表与现有表的关系

- 一个 `workspace` 下可以有多个 `office_tasks`
- 一个 `office_task` 下可以有多个 `office_task_steps`
- 一个 `office_task` 下可以有多个 `office_artifacts`
- 一个 `office_task` 下可以有多个 `office_approvals`
- 一个用户可以拥有多个 `browser_profiles`
- 一个用户可以拥有多个 `ops_targets`
- 一个文档可以关联多个 `document_revisions`

## 4. 建议新表

### 4.1 `office_tasks`

用途：平台级办公任务主表。

建议字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | `TEXT PRIMARY KEY` | 任务 ID |
| `user_id` | `TEXT NOT NULL` | 归属用户 |
| `workspace_id` | `TEXT` | 所属工作区，可空 |
| `task_type` | `TEXT NOT NULL` | `browser / document / ops / workflow` |
| `title` | `TEXT NOT NULL` | 标题 |
| `description` | `TEXT` | 描述 |
| `connector_id` | `TEXT NOT NULL` | 连接器 ID |
| `target_ref_kind` | `TEXT` | 目标对象类型 |
| `target_ref_id` | `TEXT` | 目标对象 ID |
| `input_json` | `TEXT NOT NULL` | 任务输入 |
| `status` | `TEXT NOT NULL` | 任务状态 |
| `risk_level` | `TEXT NOT NULL` | `low / medium / high` |
| `approval_policy_id` | `TEXT` | 审批策略引用 |
| `current_step_id` | `TEXT` | 当前步骤 |
| `idempotency_key` | `TEXT` | 幂等键 |
| `started_at` | `TEXT` | 开始时间 |
| `finished_at` | `TEXT` | 结束时间 |
| `created_at` | `TEXT NOT NULL` | 创建时间 |
| `updated_at` | `TEXT NOT NULL` | 更新时间 |

约束与索引：

- `FOREIGN KEY (workspace_id) REFERENCES workspaces(id)`
- `CHECK (task_type IN ('browser', 'document', 'ops', 'workflow'))`
- `CHECK (risk_level IN ('low', 'medium', 'high'))`
- `CHECK (status IN ('draft', 'pending_approval', 'ready', 'running', 'paused', 'waiting_external', 'succeeded', 'failed', 'cancelled', 'rolled_back'))`
- 索引：
  - `idx_office_tasks_user_id`
  - `idx_office_tasks_workspace_id`
  - `idx_office_tasks_status`
  - `idx_office_tasks_task_type`

### 4.2 `office_task_steps`

用途：任务步骤主表。

建议字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | `TEXT PRIMARY KEY` | 步骤 ID |
| `task_id` | `TEXT NOT NULL` | 所属任务 |
| `step_seq` | `INTEGER NOT NULL` | 步骤序号 |
| `step_type` | `TEXT NOT NULL` | 步骤类型 |
| `title` | `TEXT NOT NULL` | 步骤标题 |
| `input_json` | `TEXT` | 步骤输入 |
| `output_json` | `TEXT` | 步骤输出 |
| `status` | `TEXT NOT NULL` | 步骤状态 |
| `retry_count` | `INTEGER NOT NULL DEFAULT 0` | 重试次数 |
| `started_at` | `TEXT` | 开始时间 |
| `finished_at` | `TEXT` | 结束时间 |
| `error_message` | `TEXT` | 错误摘要 |
| `created_at` | `TEXT NOT NULL` | 创建时间 |
| `updated_at` | `TEXT NOT NULL` | 更新时间 |

约束与索引：

- `FOREIGN KEY (task_id) REFERENCES office_tasks(id)`

- `CHECK (status IN ('pending', 'running', 'waiting_approval', 'waiting_external', 'succeeded', 'failed', 'cancelled', 'skipped'))`

## 5. 第一阶段不建议先落的表

下面这些对象第一阶段先不要急着实体化，不然容易过度设计：

- 细粒度模板字段值实例表
- 浏览器每次 DOM 节点级快照表
- 工作流图节点定义表
- 复杂组织级审批流模板表

第一阶段先让任务、步骤、产物、审批、Profile、模板、文档、运维目标、连接器这几张主表稳定下来。

# spec015 文档对象、大纲、修订、批注草案

状态：Draft

## 1. 目标

这份草案只解决一件事：

把专业文档内核的“文档本体”说清楚，先建立正式文档对象、大纲、修订和批注模型，再谈模板导出。

一句话版本：

**文档不是一段文本，而是一个有结构、有历史、有评论的正式对象。**

## 2. 核心原则

### 2.1 文档内容和文档样式分开

文档对象首先负责内容结构和修订历史。  
样式真正怎么长，后面再交给 `doct` 模板。

### 2.2 文档要有结构，不只是一坨富文本

至少要能知道：

- 标题
- 大纲层级
- 段落
- 表格
- 图片
- 引用
- 批注位置

### 2.3 修订必须可追溯

每一次正式修改都应该能追到：

- 谁改的
- 改了哪一版
- 哪些内容变了
- 改动摘要是什么

### 2.4 批注不是正文

批注是围绕正文的附属对象，不应该污染正文主内容。

## 3. 核心对象

### 3.1 `Document`

用于表示一篇正式文档。

它回答的是：

- 文档标题是什么
- 属于谁
- 属于哪个工作区
- 当前用哪个模板
- 当前处于什么状态

建议最少字段：

- `id`
- `userId`
- `workspaceId`
- `title`
- `templateId`
- `templateVersion`
- `status`
- `currentRevisionId`
- `sourceTaskId`
- `createdAt`
- `updatedAt`

### 3.2 `DocumentOutline`

用于表示文档的大纲结构。

它回答的是：

- 文档分几级标题
- 每节的顺序是什么
- 这一页或这一段属于哪一节

建议最少字段：

- `id`
- `documentId`
- `parentId`
- `level`
- `title`
- `orderIndex`
- `anchorKey`
- `blockStartId`
- `blockEndId`
- `createdAt`
- `updatedAt`

大纲不要只做成 UI 树。
它必须是正式对象，不然后面修订、评论、导出都会乱。

### 3.3 `DocumentRevision`

用于表示一次修订版本。

它回答的是：

- 当前版本号是多少
- 这个版本的正文是什么
- 相对上一版改了什么

建议最少字段：

- `id`
- `documentId`
- `revisionSeq`
- `baseRevisionId`
- `contentJson`
- `outlineJson`
- `changeSummary`
- `createdBy`
- `createdAt`

修订的作用只有一个：

- 保留可追溯历史

修订不是把旧内容覆盖掉再嘴上说“我记得改过了”。

### 3.4 `DocumentComment`

用于表示批注和评论。

它回答的是：

- 批注挂在哪个位置
- 谁提的
- 说了什么
- 是否已解决

建议最少字段：

- `id`
- `documentId`
- `revisionId`
- `anchorType`
- `anchorKey`
- `body`
- `status`
- `createdBy`
- `resolvedBy`
- `createdAt`
- `resolvedAt`

批注只挂锚点，不挂空气。
如果不能精确定位到正文位置，这个批注就没法落地。

### 3.5 `DocumentCitation`

用于表示引用来源。

它回答的是：

- 引用来自哪里
- 引用了哪一段
- 用在文档中的哪个位置

建议最少字段：

- `id`
- `documentId`
- `sourceKind`
- `sourceTitle`
- `sourceRef`
- `quoteText`
- `targetAnchorKey`
- `createdAt`

引用不是备注。
引用必须能回溯到来源，否则就是装样子。

## 4. 服务边界

### 4.1 `document-service`

职责：

- 创建、读取、更新文档
- 维护文档状态
- 协调大纲、修订、批注和引用

### 4.2 `document-outline-service`

职责：

- 生成和更新大纲
- 维护章节层级
- 支持重排标题结构

### 4.3 `document-revision-service`

职责：

- 创建修订
- 读取历史版本
- 比较版本差异

### 4.4 `document-comment-service`

职责：

- 创建批注
- 关闭批注
- 查询批注列表

### 4.5 `document-citation-service`

职责：

- 记录引用来源
- 校验引用位置
- 给导出阶段保留引用信息

### 4.6 `document-block-service`

职责：

- 管理正文块
- 插入、移动、删除和重排内容块
- 让编辑器直接操作结构化内容，而不是整篇文本

### 4.7 `document-lock-service`

职责：

- 控制编辑锁
- 处理多人同时编辑的冲突
- 防止同一文档被多个写入面乱改

## 5. 文档状态模型

### 5.1 文档状态

| 状态 | 含义 |
| --- | --- |
| `draft` | 草稿 |
| `reviewing` | 审阅中 |
| `published` | 已发布 |
| `archived` | 已归档 |

### 5.2 批注状态

| 状态 | 含义 |
| --- | --- |
| `open` | 打开 |
| `resolved` | 已解决 |
| `archived` | 已归档 |

## 6. 文档结构模型

### 6.1 大纲层级

文档大纲至少应该支持：

- 一级标题
- 二级标题
- 三级标题
- 小节内段落

### 6.2 内容块

第一阶段建议先支持：

- 标题
- 段落
- 列表
- 表格
- 图片
- 引用块

### 6.3 为什么不一开始就做复杂富文本编辑器

因为这里的目标不是复制一个办公套件，而是先把文档作为正式对象立起来。  
太复杂的富文本能力只会把规则冲散。

### 6.4 编辑器边界

编辑器只做这几件事：

- 展示大纲
- 编辑正文块
- 挂批注
- 生成修订
- 发起导出

编辑器不该做的事：

- 把 Markdown 当最终真相源
- 把样式逻辑写死在前端
- 绕开模板直接拼最终 `docx/pdf`

## 7. 修订规则

### 7.1 每次保存不等于每次修订

可以先在编辑态里改很多次，只有正式提交时才创建新修订。

### 7.2 修订必须带摘要

每个修订至少要有：

- 修订序号
- 修订摘要
- 创建人
- 创建时间

### 7.3 不允许静默覆盖历史

不能只保留当前正文，不保留版本历史。  
文档如果没有版本历史，后面根本没法审阅和回滚。

## 8. 批注规则

### 8.1 批注必须挂锚点

批注不是一条无位置的评论。  
它必须能挂到：

- 某个段落
- 某个标题
- 某个表格单元格
- 某个图片或页面区域

### 8.2 批注要能关闭

批注至少有：

- 打开
- 已解决
- 归档

### 8.3 批注不要污染正文

批注内容要单独存，不要混在正文里。

## 9. 与任务模型的关系

### 9.1 文档任务还是统一任务

专业文档能力最终仍然应该落到 `OfficeTask`。

### 9.2 文档编辑过程

编辑器里的操作应该尽量形成：

- 一个任务
- 多个步骤
- 多个修订
- 多个批注
- 最终产物

### 9.3 文档对象不是导出对象

这轮只定义文档对象本身。  
模板导出后面单独补。

### 9.4 文档任务和编辑任务要分开

- 编辑过程可以频繁保存草稿
- 只有正式提交、发布、导出，才算进入平台任务流
- 普通输入动作不要每次都变成任务，不然任务模型会被噪音淹没

## 10. 最容易做烂的地方

1. 把文档直接等同于一段富文本
2. 不保留修订历史
3. 批注混进正文
4. 大纲只是 UI 树，不是正式对象
5. 编辑器直接绕开结构化模型
5. 引用来源不留记录

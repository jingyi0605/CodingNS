# 20260426-provider启用控制回归清单

## 这份清单是干什么的

以后只要有人改了 provider 启用态、provider catalog、会话入口过滤、Butler / Skill / Fork / 并行会话这些地方，至少要按这份清单回归一遍。

目标只有一个：

别再出现“设置页已经关了，但某个角落还能继续用”的低级漏口。

## 最小回归范围

### 1. 设置页

要确认的事：

1. 设置页能正常读出所有 provider
2. 能看到启用数、禁用数、总数
3. 每个 provider 都有能力矩阵
4. 开关切换成功后，状态文案会立刻更新

自动化入口：

- `pnpm --filter user-app exec vitest run src/settings/ProviderManagementPanel.test.tsx`
- `pnpm --filter user-app exec vitest run src/features/settings/pages/SettingsPage.test.tsx`

### 2. 会话创建和前端入口过滤

要确认的事：

1. 新建会话 provider 列表不会再显示 disabled provider
2. 选区新会话动作不会再显示 disabled provider
3. 并行会话弹窗不会再显示 disabled provider
4. Fork 目标 provider 不会再显示 disabled provider

自动化入口：

- `pnpm --filter user-app exec vitest run src/features/conversation/components/SessionProviderPicker.test.tsx`
- `pnpm --filter user-app exec vitest run src/features/conversation/components/ConversationSelectionActions.test.tsx`
- `pnpm --filter user-app exec vitest run src/features/conversation/components/ParallelSessionCreateModal.test.tsx`
- `pnpm --filter user-app exec vitest run src/features/conversation/components/ComposerPanel.test.tsx`

### 3. 前端缓存失效

要确认的事：

1. 切换 provider 启用态后，`SessionProviderPicker` 不会继续吃旧能力缓存
2. 重新启用后，创建入口可以重新看到 provider

自动化入口：

- `pnpm --filter user-app exec vitest run src/settings/ProviderManagementPanel.test.tsx src/features/conversation/components/SessionProviderPicker.test.tsx`

### 4. Skill 和 Butler

要确认的事：

1. Skill 新目标选择会过滤 disabled provider
2. Butler 当前支持的 provider 会跟着 catalog 一起收口
3. 已禁用 provider 的旧绑定和旧记录仍然能解释，不会直接变空白

自动化入口：

- `pnpm --filter user-app exec vitest run src/settings/SkillManagementPanel.test.tsx`
- `pnpm --filter user-app exec vitest run src/features/conversation/components/SessionButlerActionButton.test.tsx src/features/butler/pages/ButlerPage.test.tsx`
- `pnpm --filter host test -- --run tests/integration/skill-add-service.test.ts tests/integration/skill-import-service.test.ts tests/integration/skill-routes.test.ts`
- `pnpm --filter host test -- --run tests/integration/assistant-capability-service.test.ts tests/integration/butler-profile-service.test.ts tests/integration/butler-control-session-service.test.ts`

### 5. 后端门禁

要确认的事：

1. disabled provider 不参与发现
2. disabled provider 的旧会话不会出现在正常列表
3. start / resume / send / fork / assistant follow-up / skill 新动作会被统一拒绝
4. 错误码稳定为 `PROVIDER_DISABLED`

自动化入口：

- `pnpm --filter host test -- --run tests/integration/provider-control-session-history.test.ts`
- `pnpm --filter host test -- --run tests/integration/provider-discovery-runtime.test.ts`
- `pnpm --filter host test -- --run tests/integration/provider-discovery-helper-client.test.ts`
- `pnpm --filter host test -- --run tests/integration/session-routes.test.ts`
- `pnpm --filter host test -- --run tests/integration/assistant-capability-routes.test.ts`

## 手工验收最少要点

如果这次改动要发给真实用户，除了自动化以外，至少手点下面几步：

1. 在设置页禁用一个 provider，确认它立刻从新建会话、Fork、并行会话、选区新会话入口里消失
2. 再重新启用，确认这些入口立刻恢复
3. 禁用 `codex` 或 `claude-code` 后，Butler 页面和 Butler 动作同步变化
4. 禁用一个支持 Skill 的 provider 后，Skill 新建目标不再可选
5. 重新启用后，旧会话重新回到正常列表

## 这次明确不靠什么回归

下面这些做法都不算回归：

1. 只看设置页开关有没有切过去
2. 只跑一个 provider picker 测试就说“前端都好了”
3. 只看前端隐藏，不看后端门禁
4. 不验证重新启用后的恢复路径

# 20260426-provider入口与门禁现状盘点

这份文档只回答一个问题：

现在仓库里到底哪些地方在决定 provider 是否显示、是否可用、是否还能继续参与业务链路。

如果这一步不先盘清楚，后面做启用控制一定会漏门禁。

## 1. 现状判断

当前系统已经有 provider 能力抽象，但“provider 是否启用”还不是正式模型。

现状更接近这样：

- `session-sync-core` 负责声明 provider 原生 capability
- Host 负责做部分能力增强和 CLI 可用性降级
- 前端在多个组件里各自维护 provider 列表
- Skill 和 Butler 还有自己的目标范围或白名单

这意味着：

- 单纯在设置页加一个开关，没有任何意义
- 如果没有统一 catalog 和后端门禁，禁用一定会漏

## 2. 后端关键门禁点

### 2.1 会话主链路

最关键的文件是：

- `apps/host/src/modules/sessions/session-history-service.ts`

当前它直接负责：

- 工作区会话发现
- provider capability 查询
- 会话创建
- 会话继续
- 会话 Fork
- 会话列表输出

这也是 provider 启用控制必须先收口的地方。

如果这里只改一半，前端隐藏入口也没用，因为直接请求还是能打通。

### 2.2 provider 路由

当前 provider 路由主要是：

- `apps/host/src/routes/providers.ts`
- `apps/host/src/modules/provider/provider-controller.ts`

现状问题：

- 只有单 provider capability 接口
- 没有 provider catalog 总览接口
- 设置页如果想拼能力矩阵，只能自己挨个扫接口

### 2.3 后台任务与发现链路

当前 provider 会话发现和 capability refresh 已经接入后台任务体系。

相关位置：

- `apps/host/src/modules/sessions/session-history-service.ts`
- `apps/host/src/modules/provider/provider-discovery-runtime.ts`
- `apps/host/src/modules/tasks/*`

这说明启用控制不能做成“只影响前端”的轻逻辑，必须在后台任务入口就过滤。

### 2.4 Skill 链路

关键位置：

- `apps/host/src/modules/skills/skill-manager-service.ts`

现状问题：

- Skill 目标有固定范围
- 但没有 provider enabled 这一层判定
- 如果 provider 被关掉，Skill 新同步目标仍可能继续把它当成合法选项

### 2.5 Butler / 助手链路

关键位置：

- `apps/host/src/modules/butler/*`
- `apps/host/src/modules/assistant-capability/*`

现状问题：

- Butler 当前只正式支持 `codex` 和 `claude-code`
- 但这套支持范围是自己维护的，不知道 provider 是否被用户禁用

## 3. 前端关键入口

### 3.1 provider metadata 和静态列表

关键位置：

- `apps/user-app/src/features/conversation/capability/provider-ui.ts`

当前这里维护：

- provider 名称
- 图标
- 显示顺序
- 若干静态默认能力
- `REGISTERED_PROVIDER_IDS`
- `SESSION_PROVIDER_PICKER_IDS`

问题不是它不该存在，而是它现在同时承担了“元数据”和“动态可见性”两种职责。

后面要拆成：

- 静态 metadata 继续留
- 动态可见性改成读 provider catalog

### 3.2 会话创建与 provider picker

关键位置：

- `apps/user-app/src/features/conversation/components/SessionProviderPicker.tsx`
- `apps/user-app/src/features/conversation/components/ConversationSelectionActions.tsx`
- `apps/user-app/src/features/conversation/components/ParallelSessionCreateModal.tsx`

问题：

- 这些地方当前依赖静态 provider 列表
- 只要不收口，禁用 provider 后仍可能继续出现在创建入口

### 3.3 Fork 入口

关键位置：

- `apps/user-app/src/features/conversation/components/ComposerPanel.tsx`

这里当前自己维护：

- `FORK_PROVIDER_IDS`
- `NATIVE_FORK_PROVIDERS`
- `RECONSTRUCTED_FORK_TARGET_PROVIDERS`

这就是典型的“功能上线时先写死，后面越来越难改”。

### 3.4 Butler 跟进入口

关键位置：

- `apps/user-app/src/features/conversation/components/SessionButlerActionButton.tsx`
- `apps/user-app/src/features/butler/*`

问题：

- 当前 follow-up provider 还是静态范围
- provider 禁用后，这里必须同步收口

### 3.5 Skill 设置页

关键位置：

- `apps/user-app/src/settings/SkillManagementPanel.tsx`

当前这里维护：

- `SKILL_TARGET_OPTIONS`
- `ASSISTANT_UPLOAD_TARGET_OPTIONS`

这两个列表后面必须和 provider enabled 联动。

## 4. 当前最危险的点

### 4.1 启用态如果做成用户偏好，会和后台任务去重打架

当前工作区发现任务按 `workspaceId` 去重和缓存。

如果把 provider enabled 做成每个用户自己的偏好，就会出现这类问题：

- 用户 A 关了 `gemini`
- 用户 B 没关
- 后台发现任务到底该不该扫 `gemini`
- 同一个 `workspaceId` 的缓存应该信谁

这就是为什么第一版必须把 provider 启用态定成 Host 全局。

### 4.2 旧会话不能删，只能隐藏

如果禁用 provider 直接删：

- 重新启用后数据回不来
- 测试和用户都很难理解这是“禁用”还是“清空”

所以这次只能做：

- 查询结果层隐藏
- 后端动作层拒绝

## 5. 本轮 Spec 必须覆盖的收口范围

至少要覆盖：

1. provider 启用态存储
2. provider catalog 总览接口
3. SessionHistoryService 主门禁
4. Skill 新目标门禁
5. Butler / 助手 provider 入口门禁
6. 前端 provider picker / Fork / 并行会话 / 设置页收口

如果这六块里漏一块，这次启用控制都不算真的做完。

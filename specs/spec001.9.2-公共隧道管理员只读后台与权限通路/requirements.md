# 需求文档 - spec001.9.2 公共隧道管理员只读后台与权限通路

状态：Draft

## 简介

`spec001.9.1` 已经把公共隧道的用户控制台基本补起来了：

1. 用户可以注册、登录、找回密码
2. 用户可以查看自己的绑定、钱包、grant、订单和激活码兑换结果
3. `control-api` 已经有正式数据库、支付事件表和 relay usage 事件表

但现在有个很现实的问题还没解决：

- 管理员没有入口
- 账号模型没有角色字段
- 后端只有“是否登录”的判断，没有“是否管理员”的判断
- 前端只有 `/dashboard`，没有 `/admin/*`
- 运营要看全局账号、设备、激活码、支付事件、relay usage，只能直接查库或跑脚本

这不是小毛病，这是数据结构没长出来。

这次要解决的事情很明确：

1. 给账号补角色模型
2. 给后端补管理员鉴权
3. 给控制面补独立管理员只读接口
4. 给前端补独立管理员路由和只读后台页面
5. 保证现有用户控制台语义不变

## 2026-04-20 二期补记

一期已经把只读后台做完。二期不另起炉灶，继续沿用现有管理员通路，只补最小写操作：

1. 管理员解绑任意设备绑定
2. 管理员停用未兑换激活码
3. 管理员重新启用未兑换激活码
4. 管理员在线批量生成激活码

这次还是守一条铁律：
不碰用户 `/api/v1/*` 语义，不做手工加量、封禁账号和复杂 RBAC。

## 术语表

- **用户控制台**：当前 `console-web` 里的注册、登录、绑定、钱包、订单、激活码页面
- **管理员后台**：这次新增的 `/admin/*` 前端页面和 `/api/admin/*` 后端接口
- **角色模型**：账号上的 `role` 字段，第一版只允许 `user` 和 `admin`
- **管理员鉴权**：在已登录基础上再判断 `role === "admin"`
- **只读后台**：第一版只允许查询，不允许后台改数据

## 范围说明

### In Scope

- `accounts.role` 字段和老数据兼容迁移
- `AccountProfile` 及相关登录/查询契约补 `role`
- `control-api` 新增 `requireAdmin()` 和 `/api/admin/*`
- 管理员只读查询接口：
  - 账号列表
  - 绑定列表
  - 激活码列表
  - 支付事件日志
  - relay usage 日志
- 管理员最小写操作接口：
  - 解绑任意设备绑定
  - 停用未兑换激活码
  - 重新启用未兑换激活码
  - 在线批量生成激活码
- `console-web` 新增 `/admin` 路由壳、只读列表页和最小写操作按钮
- 管理员登录后的路由跳转与旧 session 兼容补齐

### Out of Scope

- 复杂 RBAC、权限组、资源级授权
- 管理员注册、邀请和审批流
- 后台写操作，例如手工加量、手工封禁、账号角色审批
- 运营审计中心、行为审计报表
- 独立第二套管理员站点域名
- 在后台列表里长期展示完整激活码明文

## 需求

### 需求 1：账号必须有角色模型

**用户故事：** 作为系统维护者，我希望账号自身带有明确角色，这样系统才能区分普通用户和管理员，而不是靠脚本、邮箱白名单或临时约定。

#### 验收标准

1. WHEN 管理员后台需求落地 THEN System SHALL 在 `accounts` 表增加 `role` 字段，且第一版只允许 `user` 与 `admin`
2. WHEN 旧账号迁移到新版本 THEN System SHALL 默认把旧数据视为 `user`，不得让旧用户失去登录能力
3. WHEN 登录、查询当前账号或读取账号资料 THEN System SHALL 在返回的账号资料里带上 `role`

### 需求 2：管理员权限必须走独立鉴权通路

**用户故事：** 作为维护者，我希望管理员接口和普通用户接口明确分开，这样不会把用户控制台语义越改越乱。

#### 验收标准

1. WHEN 请求进入管理员接口 THEN System SHALL 先校验登录态，再校验账号角色为 `admin`
2. WHEN 未登录用户访问管理员接口 THEN System SHALL 返回 `401`
3. WHEN 已登录但不是管理员的用户访问管理员接口 THEN System SHALL 返回 `403`
4. WHEN 普通用户继续访问 `/api/v1/*` THEN System SHALL 保持现有语义不变

### 需求 3：管理员必须能看全局账号和设备数据

**用户故事：** 作为管理员，我希望在后台查看所有账号和设备绑定，而不是只能看当前登录账号自己的数据。

#### 验收标准

1. WHEN 管理员访问账号列表 THEN System SHALL 返回全局账号列表，并提供最小摘要信息
2. WHEN 管理员查看账号摘要 THEN System SHALL 能看到账号邮箱、角色、创建时间，以及与该账号相关的绑定数、订单数和剩余流量摘要
3. WHEN 管理员访问绑定列表 THEN System SHALL 返回全局绑定列表，并支持按账号筛选

### 需求 4：管理员必须能看激活码和核心事件日志

**用户故事：** 作为运营者，我希望能在后台直接看激活码状态、支付事件和 relay usage，而不是靠查数据库拼数据。

#### 验收标准

1. WHEN 管理员访问激活码列表 THEN System SHALL 返回批次、规格、状态、兑换人和兑换时间等最小信息
2. WHEN 管理员访问支付事件日志 THEN System SHALL 返回事件 ID、订单 ID、交易 ID、事件类型和处理时间
3. WHEN 管理员访问 relay usage 日志 THEN System SHALL 返回 usage ID、账号、绑定、上下行字节数和观察时间

### 需求 5：前端必须有独立管理员视图，而不是污染用户控制台

**用户故事：** 作为管理员，我希望进入后台后看到的是独立的管理页面，而不是和普通用户共用一张越堆越乱的 Dashboard。

#### 验收标准

1. WHEN 管理员登录成功 THEN System SHALL 把管理员默认导向 `/admin` 路由，而不是普通用户 `/dashboard`
2. WHEN 管理员访问后台 THEN System SHALL 提供独立管理员路由和导航
3. WHEN 普通用户登录成功 THEN System SHALL 继续进入原有 `/dashboard`
4. WHEN 旧浏览器 session 里还没有 `role` THEN System SHALL 能通过补拉当前账号信息完成兼容，而不是强制全部重新登录

### 需求 6：第一期必须先把只读后台做稳

**用户故事：** 作为项目维护者，我希望第一版先把查询链路做稳，不要一上来把写操作、细权限和复杂流程全部混进去。

#### 验收标准

1. WHEN 第一期交付 THEN System SHALL 只提供只读后台查询能力
2. WHEN 后续需要后台写操作 THEN System SHALL 先复用现有角色模型和 `/api/admin/*` 通路，不得回头污染用户接口

### 需求 7：第二期只允许最小写操作

**用户故事：** 作为管理员，我希望先得到几项风险最低、边界最清楚的后台动作，这样能处理设备解绑和激活码停用问题，但不会把后台一次做成什么都能改的垃圾站。

#### 验收标准

1. WHEN 管理员解除设备绑定 THEN System SHALL 允许管理员解绑任意绑定，且不要求切换到目标用户账号
2. WHEN 管理员停用激活码 THEN System SHALL 只允许停用未兑换且未过期的激活码
3. WHEN 管理员重新启用激活码 THEN System SHALL 只允许重新启用未兑换且未过期、当前处于停用状态的激活码
4. WHEN 管理员尝试修改已兑换或已过期激活码 THEN System SHALL 返回明确错误，不得静默成功
5. WHEN 这些管理员写操作落地 THEN System SHALL 继续不改动现有用户 `/api/v1/*` 接口语义

### 需求 8：管理员必须能在线批量生成激活码

**用户故事：** 作为管理员，我希望直接在后台生成一批指定规格的激活码，这样不用再切回脚本环境手工跑命令。

#### 验收标准

1. WHEN 管理员在后台提交生成请求 THEN System SHALL 允许指定生成数量、流量规格、批次标签和可选的码过期天数
2. WHEN 激活码生成成功 THEN System SHALL 在当前页面一次性返回完整激活码结果，便于管理员立即复制保存
3. WHEN 新生成的激活码写入后台列表 THEN System SHALL 继续只展示掩码，不在长期列表里暴露完整明文
4. WHEN 普通用户或未登录用户调用该能力 THEN System SHALL 分别返回 `403` 或 `401`

## 非功能需求

### 非功能需求 1：向后兼容

1. WHEN 老用户继续使用控制台 THEN System SHALL 保持注册、登录、绑定、钱包、订单、激活码兑换链路不变
2. WHEN 新增管理员角色字段后 THEN System SHALL 不破坏现有数据库迁移顺序

### 非功能需求 2：可维护性

1. WHEN 后续继续做管理员写操作或更细粒度权限 THEN System SHALL 基于明确角色模型和独立 `/api/admin/*` 扩展，而不是重写现有用户接口
2. WHEN 管理员查询继续增多 THEN System SHALL 优先在独立读模型里扩展，不把用户 store 改成一锅粥

### 非功能需求 3：可观测性

1. WHEN 管理员查看日志类页面 THEN System SHALL 返回足够的追踪字段，便于查支付、扣量和兑换问题
2. WHEN 管理员鉴权失败 THEN System SHALL 返回明确错误，不返回模糊的失败信息

## 成功定义

- 账号模型正式带有 `role`
- `control-api` 新增独立管理员鉴权和只读接口
- `control-api` 新增最小管理员写接口，支持解绑设备和切换激活码状态
- `control-api` 新增管理员在线生成激活码接口
- `console-web` 新增独立管理员路由、页面和最小写操作按钮
- 普通用户控制台行为不变
- 管理员能直接看全局账号、绑定、激活码、支付事件和 relay usage
- 管理员能直接解绑设备并停用或重新启用未兑换激活码
- 管理员能直接在线生成激活码，并在当前页拿到一次性完整结果

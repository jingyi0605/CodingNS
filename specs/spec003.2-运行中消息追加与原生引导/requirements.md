# 需求文档 - spec003.2 运行中消息追加与原生引导

状态：Draft

## 简介

`spec003.1` 已经把“真实原生会话运行时”立起来了，但现在还差半口气：

- 会话一旦进入运行态，输入区基本就被禁掉
- Host 对同一 `sessionId` 只能保留一个 active run，新的发送会撞上 `ACTIVE_RUN_EXISTS`
- `Claude Code` 当前接法还是一轮一个 `claude -p` 进程，没有接住它原生支持的长连接流式输入
- `Codex` 当前接法是一轮一个 `runStreamed(...)`，没有对齐它当前公开可确认的 `queue/steer` 语义

这就导致一个很现实的问题：用户看到了“真实运行时”，却不能在运行过程中自然地追加指令、修正方向或补充上下文。

这次要解决的不是“再加一个按钮”，而是明确两件事：

1. 哪些 provider 真的支持运行中输入
2. 本项目怎样最小改动地按原生能力工作，而不是自己发明一套私有队列

## 术语表

- **运行中输入**：原生会话已经在执行时，用户继续提交新的文本指导、补充说明或修正意见
- **原生引导**：provider 自己认可的运行中输入方式，而不是本项目自己拼出来的假协议
- **流式引导**：当前运行尚未结束时，新的输入可以直接进入同一长连接会话
- **排队引导**：当前运行尚未结束时，新的输入先进入 provider 原生队列，等上一轮结束后再处理
- **能力矩阵**：不同 provider 对运行中输入能力的真实支持情况
- **Active Run**：项目内当前附着到某个原生会话的运行句柄

## 范围说明

### In Scope

- 新增运行中输入能力声明
- `Claude Code` 运行时切换为长连接 `stdin/jsonl` 输入
- `Codex` 运行时对齐当前公开可确认的原生 `queue/steer` 语义
- 复用现有 `messages/live` 路由承接运行中输入
- 前端输入区依据 provider 能力选择“追加指导”“加入队列”或禁用
- 统一运行中输入相关错误码和状态回传

### Out of Scope

- 新增项目私有排队服务
- 保证 `Codex` 支持“当前 turn 立刻吸收修正”
- 重新设计消息持久化格式
- 重写完整前端对话页
- 新增多端协同或多人同时控制同一会话

## 需求

### 需求 1：系统必须明确暴露运行中输入能力，而不是混成一个笼统的“能发消息”

**用户故事：** 作为开发者，我希望在进入会话前就知道当前 provider 是否支持运行中追加输入，以及它到底是即时引导还是排队引导，以便我不会被 UI 误导。

#### 验收标准

1. WHEN 前端读取 provider 或 session 能力 THEN System SHALL 返回明确的运行中输入模式，而不是让前端猜。
2. WHEN provider 不支持运行中输入 THEN System SHALL 明确返回禁用状态和限制说明。
3. WHEN provider 支持的语义不同 THEN System SHALL 保留这种差异，不得强行包装成同一种行为。

### 需求 2：`Claude Code` 必须通过长连接流式输入支持运行中追加指导

**用户故事：** 作为开发者，我希望在 `Claude Code` 正在执行时继续补充指导，而不用中断当前会话重来，以便我的工作流更接近原生体验。

#### 验收标准

1. WHEN `Claude Code` 会话开始运行 THEN System SHALL 维持同一长连接进程，而不是每次新消息重新拉起一个 `claude -p` 子进程。
2. WHEN 用户在运行中追加指导 THEN System SHALL 通过 `stdin/jsonl` 输入送入同一会话，而不是新建第二个 active run。
3. WHEN `Claude Code` 返回后续流式事件 THEN System SHALL 继续沿用现有实时事件模型和会话绑定，不得分叉出第二条假会话。

### 需求 3：`Codex` 必须只对齐当前可确认的原生 `queue/steer` 语义

**用户故事：** 作为开发者，我希望 `Codex` 在本项目里的行为和它原生一致，即使能力有限也要说实话，以便我不会被假的“即时引导”坑住。

#### 验收标准

1. WHEN 当前 `Codex` 接入层没有稳定暴露运行中排队能力 THEN System SHALL 保持禁用，而不是自行实现项目私有队列。
2. WHEN 当前 `Codex` 接入层已稳定暴露原生排队能力 THEN System SHALL 只按“排队引导”语义接入，不得声称能立即打断并吸收新消息。
3. WHEN 前端显示 `Codex` 运行中输入状态 THEN 文案 SHALL 反映真实行为，例如“加入队列”，而不是“继续引导中”。

### 需求 4：运行中输入必须复用现有 active run，而不是制造第二条执行链

**用户故事：** 作为系统维护者，我希望运行中的同一会话仍然只有一个执行真相，以便后端不会同时跑两条互相打架的链路。

#### 验收标准

1. WHEN 同一 `sessionId` 已存在 active run 且支持运行中输入 THEN System SHALL 把新输入提交到该 active run，而不是再次调用 start/continue。
2. WHEN 同一 `sessionId` 已存在 active run 但不支持运行中输入 THEN System SHALL 返回明确能力错误，而不是落成模糊的 provider I/O 错误。
3. WHEN 运行中输入提交成功 THEN System SHALL 保持同一会话映射、同一运行状态和同一订阅链路。

### 需求 5：前端输入区必须按真实能力降级，而不是运行中统一禁用

**用户故事：** 作为开发者，我希望输入区在运行中仍然可用，但前提是它的行为和 provider 真相一致，以便我知道这次提交到底会立即生效、排队还是根本不支持。

#### 验收标准

1. WHEN 当前会话运行中且 provider 支持流式引导 THEN 前端 SHALL 允许继续输入并显示“追加指导”一类文案。
2. WHEN 当前会话运行中且 provider 只支持排队引导 THEN 前端 SHALL 允许继续输入并显示“加入队列”一类文案。
3. WHEN 当前会话运行中且 provider 不支持运行中输入 THEN 前端 SHALL 保持禁用，并展示清楚的原因。

### 需求 6：系统必须保持向后兼容，不破坏现有实时对话主链路

**用户故事：** 作为维护者，我希望引入运行中输入后，已有的新建会话、继续会话、中断和历史同步都不能被搞坏，以便不会为了一个高级交互把基础链路炸掉。

#### 验收标准

1. WHEN 会话未运行时 THEN 现有 `start-live` 与 `messages/live` 主链路 SHALL 保持原有行为。
2. WHEN 用户执行中断 THEN 现有中断接口和状态流转 SHALL 继续可用。
3. WHEN 前端或 Host 不支持新的运行中输入能力字段 THEN 系统 SHALL 安全退化为当前的禁用行为。

## 非功能需求

### 非功能需求 1：最小改动

1. System SHALL 优先复用现有 HTTP 路由、运行时注册表、WS 通道和消息模型。
2. System SHALL 避免为了 `Codex` 增加新的持久化队列表或第二套会话状态机。

### 非功能需求 2：可观察性

1. WHEN 运行中输入被接受、排队、拒绝或失败 THEN System SHALL 返回结构化结果和明确原因。
2. WHEN 排查 provider 差异问题 THEN System SHALL 能明确区分是能力不支持、项目未接入，还是 provider 原生行为如此。

## 成功定义

- `Claude Code` 在本项目中可以运行中追加指导，并保持同一原生会话真相。
- `Codex` 在本项目中不再被误报成支持它其实没有的运行中即时引导能力。
- 输入区和 Host 运行时行为与 provider 原生能力一致，不再是一刀切禁用。
- 现有实时对话主链路不被破坏。

# 需求文档 - spec003.2 运行中消息追加与原生引导

状态：Draft

## 简介

`spec003.1` 已经把“真实原生会话运行时”立起来了，但现在还差半口气：

- 会话一旦进入运行态，输入区基本就被禁掉
- Host 对同一 `sessionId` 只能保留一个 active run，新的发送会撞上 `ACTIVE_RUN_EXISTS`
- `Claude Code` 当前接法还是一轮一个 `claude -p` 进程，没有接住它原生支持的长连接流式输入
- `Codex` 之前接法是一轮一个 `runStreamed(...)`，没有对齐 CLI app-server 当前已公开的 `turn/steer` 语义

这就导致一个很现实的问题：用户看到了“真实运行时”，却不能在运行过程中自然地追加指令、修正方向或补充上下文。

这次要解决的不是“再加一个按钮”，而是明确两件事：

1. 本项目怎样维护统一发送队列，让会话在上一条结束后自动继续跑下一条
2. provider 原生能力在项目里到底是“直发优化”还是“唯一依赖”

## 术语表

- **运行中输入**：原生会话已经在执行时，用户继续提交新的文本指导、补充说明或修正意见
- **原生引导**：provider 自己认可的运行中输入方式，而不是本项目自己拼出来的假协议
- **流式引导**：当前运行尚未结束时，新的输入可以直接进入同一长连接会话
- **排队引导**：当前运行尚未结束时，新的输入先进入 provider 原生队列，等上一轮结束后再处理
- **能力矩阵**：不同 provider 对运行中输入能力的真实支持情况
- **Active Run**：项目内当前附着到某个原生会话的运行句柄

## 范围说明

### In Scope

- 新增会话级统一发送队列
- 运行中可向同一会话连续加入多条待发送消息
- 队列按照先进先出顺序，在上一条完成后自动发送下一条
- 支持删除仍处于等待中的队列项
- `Claude Code` 保留当前运行中直发能力，并增加项目队列能力
- `Codex` 在项目内既支持原生运行中 steer，也继续保留统一队列作为续跑兜底
- 复用现有 `messages/live` 主发送入口，必要时新增队列查询/删除接口
- 前端展示等待中的队列项，并提供删除入口

### Out of Scope

- 不把旧版 CLI 误报成支持 `turn/steer`
- 重新设计 provider 原始消息持久化格式
- 重写完整前端对话页
- 新增多端协同或多人同时控制同一会话

## 需求

### 需求 1：系统必须明确暴露会话发送队列能力，而不是只暴露“能不能发”

**用户故事：** 作为开发者，我希望在进入会话前就知道当前 provider 是否支持运行中追加输入，以及它到底是即时引导还是排队引导，以便我不会被 UI 误导。

#### 验收标准

1. WHEN 前端读取 provider 或 session 运行时状态 THEN System SHALL 返回当前会话的队列能力、等待项和是否允许删除等待项。
2. WHEN provider 不支持运行中直发 THEN System SHALL 仍可通过项目队列承接后续消息，而不是直接让用户卡死。
3. WHEN provider 支持的运行中直发语义不同 THEN System SHALL 保留这种差异，但队列语义必须统一。

### 需求 2：系统必须支持项目内统一发送队列，并保证同一会话按顺序串行执行

**用户故事：** 作为开发者，我希望在一条消息还没跑完时就提前排入多条后续消息，让系统在上一条结束后自动继续，以便我不用盯着界面一条条手动续发。

#### 验收标准

1. WHEN 用户向同一会话连续加入多条待发送消息 THEN System SHALL 按先进先出顺序保存这些队列项。
2. WHEN 当前 active run 完成、失败或被中断后 THEN System SHALL 自动尝试发送队列中的下一条等待消息。
3. WHEN 队列中存在多条等待消息 THEN System SHALL 始终只启动一条下一轮运行，不得并发拉起多条执行链。
4. WHEN 服务重启后 THEN System SHALL 仍能从持久化状态恢复等待队列，而不是把待发消息丢掉。

### 需求 3：用户必须能删除仍处于等待中的队列项

**用户故事：** 作为开发者，我希望在后续消息真正发送前撤回它，以便修正排队内容而不用等它错着跑出去。

#### 验收标准

1. WHEN 队列项仍处于等待状态 THEN System SHALL 允许删除该队列项。
2. WHEN 队列项已经开始发送 THEN System SHALL 拒绝删除，并返回明确原因。
3. WHEN 队列项被删除 THEN 前端 SHALL 立即刷新列表，不再显示该等待项。

### 需求 4：`Claude Code` 必须继续保留当前运行中直发能力，并与项目队列并存

**用户故事：** 作为开发者，我希望在 `Claude Code` 正在执行时继续补充指导，而不用中断当前会话重来，以便我的工作流更接近原生体验。

#### 验收标准

1. WHEN `Claude Code` 会话开始运行 THEN System SHALL 维持同一长连接进程，而不是每次新消息重新拉起一个 `claude -p` 子进程。
2. WHEN 用户在运行中追加指导 THEN System SHALL 通过 `stdin/jsonl` 输入送入同一会话，而不是新建第二个 active run。
3. WHEN `Claude Code` 返回后续流式事件 THEN System SHALL 继续沿用现有实时事件模型和会话绑定，不得分叉出第二条假会话。
4. WHEN 用户选择加入项目队列而不是立即直发 THEN System SHALL 把消息排入队列，并在当前轮结束后继续发送。

### 需求 5：`Codex` 必须对齐 CLI app-server 的 steer 能力，并保留项目队列兜底

**用户故事：** 作为开发者，我希望 `Codex` 在本项目里的行为和 CLI 原生一致：能 steer 的时候就直发，steer 不可用或当前轮已结束时也别把消息弄丢。

#### 验收标准

1. WHEN `Codex CLI app-server` 暴露 `turn/steer` THEN System SHALL 把运行中追加消息送入同一个 active run，而不是新建第二个执行链。
2. WHEN `turn/steer` 因当前轮刚好结束而失败 THEN System SHALL 安全丢弃陈旧 active run，并用同一会话自动续跑这一条消息。
3. WHEN 当前轮 `Codex` 执行结束且仍有等待项 THEN System SHALL 自动启动下一条队列消息，而不要求用户手动再点一次发送。
4. WHEN 前端显示 `Codex` 运行中输入状态 THEN 文案 SHALL 反映真实行为，例如“追加指导”；若当前环境不支持 steer，则必须退回明确的队列或不支持提示。

### 需求 6：队列续跑必须复用现有会话，不得制造第二条执行链

**用户故事：** 作为系统维护者，我希望运行中的同一会话仍然只有一个执行真相，以便后端不会同时跑两条互相打架的链路。

#### 验收标准

1. WHEN 同一 `sessionId` 已存在 active run 且用户选择排队 THEN System SHALL 仅创建队列项，而不是再次调用 start/continue。
2. WHEN 当前 active run 结束并开始处理下一条队列消息 THEN System SHALL 复用同一 `sessionId` 与已有 provider 会话映射。
3. WHEN 队列消息自动续跑成功 THEN System SHALL 保持同一会话映射、同一订阅链路和正确的运行状态流转。

### 需求 7：前端必须展示并管理等待中的队列项

**用户故事：** 作为开发者，我希望输入区在运行中仍然可用，但前提是它的行为和 provider 真相一致，以便我知道这次提交到底会立即生效、排队还是根本不支持。

#### 验收标准

1. WHEN 当前会话运行中且支持项目队列 THEN 前端 SHALL 允许继续输入并显示“加入队列”一类文案。
2. WHEN 队列中存在等待项 THEN 前端 SHALL 展示等待顺序、内容摘要和删除入口。
3. WHEN 队列项已被删除或已自动发送 THEN 前端 SHALL 及时刷新显示，不得残留幽灵项。

### 需求 8：系统必须保持向后兼容，不破坏现有实时对话主链路

**用户故事：** 作为维护者，我希望引入运行中输入后，已有的新建会话、继续会话、中断和历史同步都不能被搞坏，以便不会为了一个高级交互把基础链路炸掉。

#### 验收标准

1. WHEN 会话未运行时 THEN 现有 `start-live` 与 `messages/live` 主链路 SHALL 保持原有行为。
2. WHEN 用户执行中断 THEN 现有中断接口和状态流转 SHALL 继续可用。
3. WHEN 队列能力未被前端消费 THEN 系统 SHALL 安全退化为当前的单条发送行为。

## 非功能需求

### 非功能需求 1：最小改动

1. System SHALL 优先复用现有 HTTP 路由、运行时注册表、WS 通道和消息模型。
2. System SHALL 只增加会话级发送队列表，不新增第二套 provider 会话状态机。

### 非功能需求 2：可观察性

1. WHEN 运行中输入被接受、排队、拒绝或失败 THEN System SHALL 返回结构化结果和明确原因。
2. WHEN 排查 provider 差异问题 THEN System SHALL 能明确区分是能力不支持、项目未接入，还是 provider 原生行为如此。

## 成功定义

- `Claude Code` 和 `Codex` 在本项目中都可以把后续消息接进现有运行链路或统一发送队列。
- 队列会在上一条结束后自动续跑下一条，不需要用户手工续发。
- 用户可以删除等待中的队列项。
- 输入区和 Host 运行时行为不再是一刀切禁用，`Codex` 的能力声明也和 CLI 真相一致。
- 现有实时对话主链路不被破坏。

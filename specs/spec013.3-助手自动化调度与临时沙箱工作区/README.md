# spec013.3-助手自动化调度与临时沙箱工作区

## 当前定位

`spec013.2` 已经把 Butler 的内部能力面和代理执行入口补出来了，但现在还卡着两个明显缺口：

- 助手自动化只有一次性 `timer`，本质上只是“到点补发一条消息”
- 助手临时会话还得绑在现有项目 / 工作区上，缺少真正独立的沙箱空间

这两个问题表面上分开，实际上是同一个毛病：

- 调度模型太弱，只能靠补丁串逻辑
- 执行上下文太死，助手没法安全地起临时活

一句人话：

这一步要把 Butler 从“会定个闹钟、会借别人的工作区做事”，补成“有正式自动化能力、也有自己临时工作台”的助手。

## 计划覆盖

- 把现有一次性 `timer` 升级成正式的助手自动化模型
- 支持单次触发、定时循环、条件循环三类触发方式
- 保留现有 `timers.create` 兼容入口，不把已上线链路打断
- 给助手补独立的临时沙箱工作区模型，而不是强迫绑定现有工作区
- 让真实会话启动入口支持 `project / workspace / sandbox` 三种目标
- 定义自动化调度、条件检查、审计、清理和 UI/CLI 映射

## 依赖关系

- 前置依赖：`spec013`、`spec013.1`、`spec013.2`
- 规则依赖：`spec001.2` 后台任务调度规范
- 直接影响：`apps/host`、`apps/user-app`、`packages/codingns`
- 后续受益：仓库巡检通知、延后跟进、临时调试会话、一次性分析沙箱、未来受控自动化

## 本阶段明确不做

- 不做一个什么都想接的通用流程引擎
- 不支持任意脚本表达式条件，条件触发只允许白名单能力
- 不让沙箱默认变成正式项目，也不自动加入所有工作区主导航
- 不把现有 `PatrolPlan`、`ButlerControlTimer`、项目工作区一次性重写成一套大一统模型
- 不开放“自动化直接改项目代码”这种高风险动作

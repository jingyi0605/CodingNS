# 20260417-旧计时器到自动化模型兼容映射说明

这份文档只回答一个问题：

- 现有 `timers.*` 怎么在不打断线上链路的前提下，过渡到新的助手自动化模型

一句人话：

别一边说“要升级”，一边把已经能跑的助手链路直接砸掉。

## 1. 当前旧模型到底是什么

现有 `ButlerControlTimer` 本质上是一次性延时投递：

- 记录一段 `content`
- 记录一个 `dueAt`
- 到点后给控制会话发消息
- 然后把自己标成 `completed / failed / cancelled`

它没有下面这些东西：

- 循环触发
- 条件触发
- 正式的执行记录
- 下一次触发时间推进
- 动作类型扩展

所以兼容的正确方向不是继续补字段，而是：

1. 新建正式自动化模型
2. 让旧 `timers.*` 变成这个新模型的兼容入口

## 2. 兼容原则

### 2.1 用户侧行为不破

下面这些体验在迁移后必须继续成立：

- `codingns assistant timers create ...` 还能用
- Butler 页面里旧“计时器”仍然能看到
- 旧接口查出的对象，至少还能读到标题、目标、到点时间、状态

### 2.2 内部实现不再以旧表为核心

迁移后真正的权威对象应该是：

- `AssistantAutomationTask`
- `AssistantAutomationRun`

旧 `timer` 只保留为：

- CLI 兼容命令组
- Host API 兼容视图
- 前端兼容 DTO

### 2.3 一次只迁一层，不做大爆破

建议按下面顺序走：

1. 先落新表和新服务
2. 再让 `timers.create` 改为创建 `triggerType=once` 的自动化
3. 再让 `timers.list / get / cancel` 走兼容映射
4. 最后再决定旧表是保留只读、迁移归档，还是彻底下线

## 3. 字段映射

## 3.1 创建时映射

旧输入：

```ts
interface CreateButlerControlTimerInput {
  userId: string
  controlSessionId?: string | null
  projectId?: string | null
  targetSessionId?: string | null
  title?: string | null
  content: string
  dueAt?: string | null
  afterSeconds?: number | null
}
```

新模型建议映射：

```ts
AssistantAutomationTask {
  userId,
  controlSessionId,
  projectId,
  title,
  triggerType: "once",
  triggerConfigJson: {
    dueAt: resolvedDueAt
  },
  actionType: "send_control_message",
  actionConfigJson: {
    content,
    includeTriggerContext: false,
    targetSessionId
  },
  status: "active",
  nextRunAt: resolvedDueAt
}
```

说明：

- `afterSeconds` 先在兼容层解成 `resolvedDueAt`
- `targetSessionId` 先放进 `actionConfigJson`，方便后面做更细动作扩展
- 旧模型没有的 `nextRunAt`，在这里直接等于 `dueAt`

## 3.2 读取时映射

兼容 `timer` DTO 时，建议这样反推：

| 旧字段 | 新来源 |
| --- | --- |
| `id` | `automation.id` |
| `controlSessionId` | `automation.controlSessionId` |
| `sessionId` | 从关联控制会话读 |
| `userId` | `automation.userId` |
| `projectId` | `automation.projectId` |
| `targetSessionId` | `actionConfigJson.targetSessionId` |
| `title` | `automation.title` |
| `content` | `actionConfigJson.content` |
| `dueAt` | `triggerConfigJson.dueAt` |
| `status` | 由自动化状态和最近 run 状态折算 |
| `triggeredAt` | 最近成功或失败 run 的 `startedAt/finishedAt` |
| `lastError` | `automation.lastError` 或最近 run 的 `error` |
| `createdAt` | `automation.createdAt` |
| `updatedAt` | `automation.updatedAt` |
| `cancelledAt` | `automation.cancelledAt` |

## 3.3 状态折算规则

因为旧 `timer` 只有：

- `active`
- `completed`
- `cancelled`
- `failed`

所以兼容视图必须收窄新状态：

| 新状态 | 旧兼容状态 |
| --- | --- |
| `active` | `active` |
| `paused` | `active` |
| `completed` | `completed` |
| `cancelled` | `cancelled` |
| `failed` | `failed` |

说明：

- `paused` 在旧世界里没有对应状态
- 为了不炸旧前端，兼容视图先按“还没结束的等待项”处理
- 但新页面必须明确显示它其实是暂停，不是正常等待

## 4. 路由和 CLI 兼容策略

### 4.1 Host API

现有兼容入口保持不动：

- `GET /api/assistant/timers`
- `GET /api/assistant/timers/:timerId`
- `POST /api/assistant/timers`
- `POST /api/assistant/timers/:timerId/cancel`

内部改成：

- 调 `assistant-automation-service`
- 返回兼容过的 timer DTO

同时新增正式入口：

- `GET /api/assistant/automations`
- `POST /api/assistant/automations`

### 4.2 CLI

现有：

```bash
codingns assistant timers create
codingns assistant timers list
codingns assistant timers get
codingns assistant timers cancel
```

迁移后：

- 继续保留
- help 文案写明“兼容入口，只支持一次性触发”
- 新功能统一走 `codingns assistant automations ...`

## 5. 前端兼容策略

### 5.1 旧 Butler 计时器区域

迁移后先不要强迫它理解全部自动化类型。

第一阶段建议：

- 继续只展示 `triggerType=once` 的兼容视图
- 新自动化区域再展示完整自动化列表

这样做的原因很直接：

- 不会把旧页面一下子搞成一团乱码
- 也不会为了兼容旧区块，把新模型重新压回一次性计时器思维

### 5.2 新 Butler 自动化区域

新区域应该直接认正式模型，至少区分：

- 单次触发
- interval
- cron
- condition

## 6. 建议迁移步骤

### 第一步：落新表和新服务

结果：

- 新代码可以开始围着正式自动化模型工作
- 旧 timer 还继续跑

### 第二步：`timers.create` 改接新服务

结果：

- 新创建出来的“一次性计时器”其实已经是新自动化对象
- 旧接口外观不变

### 第三步：`timers.list / get / cancel` 改走兼容映射

结果：

- 旧 CLI 和旧页面开始真正读取新模型

### 第四步：评估旧表去留

只有在下面三件事都稳定后，才讨论旧表下线：

1. 新自动化对象已经覆盖所有旧 timer 场景
2. 旧前端和 CLI 已经切到兼容映射
3. 线上不存在依赖旧表直接读写的旁路代码

## 7. 明确不做

- 不做一次性全量历史迁移脚本，第一阶段优先保证新建对象走新模型
- 不为了旧前端完全无感，把新模型能力硬压成旧四个字段
- 不把 `interval / cron / condition` 伪装成“特殊 timer”

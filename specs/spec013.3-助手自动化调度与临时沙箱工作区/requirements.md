# 需求文档 - spec013.3-助手自动化调度与临时沙箱工作区

状态：Draft

## 简介

当前 Butler 已经能做两件事：

- 通过控制会话和用户持续沟通
- 通过内部能力面去查项目、会话、终端，并代理推进真实执行

但一到“稍后继续”“每小时巡检”“发现条件满足再通知”“先开个临时地方跑一轮分析”这种真实助手工作，现状就开始露馅：

1. 现在的 `timer` 只有一次性触发，没有正式的循环和条件模型
2. 现在的临时会话启动必须选已有项目，或者先手工建工作区再绕一圈
3. 控制面已经有独立工作目录，但真实执行还没有独立的临时沙箱
4. 调度和上下文绑定太松，最后只能靠 prompt 硬记基线、硬续下一次

这不是小瑕疵，是助手能力边界没补完整。

真正需要的是两套正式模型：

- 一套负责“什么时候继续做事”的自动化模型
- 一套负责“在哪里安全地做临时活”的沙箱模型

## 可实现性结论

### 结论

这个能力 **值得做，而且现在就该做**。

不做的话，后面 Butler 相关需求会继续烂成一堆临时计时器、手工续建消息和借来的工作区。

### 已确认事实

1. 当前助手能力面已经有 `timers.list / get / create / cancel`，但 `create` 只支持 `dueAt` 或 `afterSeconds`。
2. 当前 `ButlerControlTimer` 数据结构只有一次性投递语义，没有循环触发、条件触发、运行记录和下一次调度规则。
3. 当前仓库已有 `PatrolPlan`，并且已经支持 `manual / interval / cron` 触发模型，说明平台并不是完全没有周期调度基础。
4. 当前控制面会话已经有独立工作目录 `workspacePath`，而且明确禁止直接复用项目仓库目录。
5. 当前真实项目会话启动仍然绑定 `project.workspaceId`，没有“直接在指定 workspace 或 assistant sandbox 上开会话”的正式入口。
6. 当前助手能力面已经能创建目录、导入工作区、克隆仓库，但这些工作区能力还没有和“临时会话启动”连成直接可用的链路。
7. 后台任务规则已经明确要求：跨请求、可延后、要去重、要观测的任务应该进入 `TaskManager`，不能再长私有队列和新一套散装定时逻辑。

### 平台判断

- ✅ 值得做：这是 Butler 从“补发消息”升级成“正式自动化”的关键一步
- ✅ 能落地：工作区、会话、控制面、CLI、调度基础都已经有了
- ❌ 不能继续拿一次性 `timer` 冒充 cron
- ❌ 不能继续让临时会话寄生在现有工作区上

## 术语表

- **Assistant Automation（助手自动化）**：由 Butler 创建和管理的自动触发任务，负责在未来某个时间或某个条件满足后继续动作
- **Automation Trigger（自动化触发器）**：决定何时触发自动化的规则，第一阶段支持 `once / interval / cron / condition`
- **Automation Action（自动化动作）**：触发后执行的受控动作，第一阶段默认回到 Butler 控制会话继续工作
- **Automation Run（自动化执行记录）**：一次自动化真正触发后的执行结果，用于审计、回放和排错
- **Assistant Sandbox Workspace（助手沙箱工作区）**：由 Butler 自己创建和管理的临时工作区，用来承载一次性分析、临时调试或临时执行会话
- **Temporary Session（临时会话）**：绑定到 `workspace` 或 `sandbox` 的真实会话，不属于现有正式项目
- **Sandbox Promotion（沙箱晋升）**：把临时沙箱从“助手私有临时空间”转成正式保留的工作区或项目入口
- **Condition Watch（条件监听）**：由系统白名单条件驱动的轮询检查，不允许执行任意脚本表达式

## 范围说明

### In Scope

- 定义正式的助手自动化任务和执行记录模型
- 定义 `once / interval / cron / condition` 四类触发器
- 定义现有 `timers.*` 到新自动化模型的兼容映射
- 定义助手沙箱工作区模型、生命周期和清理规则
- 定义会话启动目标从 `project` 扩展到 `workspace / sandbox`
- 定义 CLI、Host API、Butler 页面上的自动化和沙箱入口
- 定义调度、条件检查、审计和失败隔离规则

### Out of Scope

- 不实现任意 DSL、JS 表达式或用户自定义脚本条件
- 不实现自动化直接执行高风险写代码动作
- 不把所有现有后台调度器一次性合并成一张超级表
- 不重做整个 Butler 页面信息架构
- 不在第一阶段支持跨主机分布式调度

## 技术边界

### 边界 1：自动化不是 prompt 递归

- 不能靠“消息里提醒自己下次再建 timer”冒充循环调度
- 调度规则必须落正式结构化字段
- 下一次运行时间必须由系统算，不由 prompt 硬记

### 边界 2：条件循环只允许白名单条件

- 第一阶段只支持平台能稳定计算的条件
- 不允许用户塞一段 shell、JS 或正则脚本让系统自己跑
- 条件检查必须有轮询间隔、过期时间和最大重试边界

### 边界 3：沙箱是助手私有执行空间，不等于正式项目

- 沙箱默认是临时的、可回收的、可隐藏的
- 不能因为起了一个临时会话，就污染正式项目模型
- 只有用户或明确动作确认后，沙箱才能晋升成长期保留对象

### 边界 4：兼容比“理论完美”重要

- 现有 `timers.create` 不能直接废掉
- 现有项目会话入口不能被新沙箱模型打断
- 旧前端如果只认一次性计时器，也必须还能显示最小可读信息

### 边界 5：后台执行必须纳入正式任务体系

- 新增自动化执行、条件检查、清理任务必须走 `TaskManager`
- 不允许再长新的私有 `inflight`、私有定时器队列和隐式重试链
- 调度扫描、触发执行、结果回写要可观测、可去重、可限流

## 需求

### 需求 1：系统必须提供正式的助手自动化模型

**用户故事：** 作为使用者，我希望助手创建的“稍后继续”“每小时检查”“条件满足再通知”都是正式对象，而不是一条一次性消息补丁。

#### 验收标准

1. WHEN 用户或 Butler 创建自动化 THEN System SHALL 持久化正式自动化对象，而不是只写一条一次性 timer 记录。
2. WHEN 自动化被创建 THEN System SHALL 至少记录触发器、动作、目标控制会话、状态、下一次触发时间和创建时间。
3. WHEN 自动化被取消、完成或失败 THEN System SHALL 保留明确状态和原因。

### 需求 2：系统必须支持单次、定时循环、条件循环三类核心触发方式

**用户故事：** 作为使用者，我希望同一套能力既能处理“1 小时后继续”，也能处理“每小时检查一次”，还能处理“发现新 tag 才通知我”。

#### 验收标准

1. WHEN 创建单次触发任务 THEN System SHALL 支持按绝对时间或相对延迟执行。
2. WHEN 创建定时循环任务 THEN System SHALL 支持 `interval` 和 `cron` 两类周期规则。
3. WHEN 创建条件循环任务 THEN System SHALL 支持白名单条件检查，并在条件满足时触发动作。

### 需求 3：系统必须保留现有 `timers.*` 兼容入口

**用户故事：** 作为维护者，我希望升级自动化能力时，不把当前已经可用的助手链路直接打坏。

#### 验收标准

1. WHEN 旧入口调用 `timers.create` THEN System SHALL 仍然可创建一个一次性自动化任务。
2. WHEN 旧页面读取计时器 THEN System SHALL 能映射到新模型中的兼容视图。
3. WHEN 新模型落地 THEN System SHALL 不要求现有调用方立即全部迁移。

### 需求 4：系统必须把自动化调度、条件检查和执行回写纳入正式后台任务体系

**用户故事：** 作为维护者，我希望这套自动化不是又一套散装循环，而是能统一观测、去重和限流。

#### 验收标准

1. WHEN 自动化进入待执行状态 THEN System SHALL 通过正式后台任务体系安排检查和执行。
2. WHEN 同一自动化在短时间内被重复触发 THEN System SHALL 能按稳定 key 去重或拒绝并发冲突。
3. WHEN 自动化执行、条件检查或清理失败 THEN System SHALL 记录任务结果和错误原因。

### 需求 5：系统必须为每次自动化触发保留执行记录

**用户故事：** 作为维护者，我希望知道某条自动化什么时候触发过、成功没有、当时带了什么上下文。

#### 验收标准

1. WHEN 自动化被真正触发 THEN System SHALL 创建一条执行记录。
2. WHEN 执行动作成功、失败、取消或跳过 THEN System SHALL 把结果写回执行记录。
3. WHEN 用户查看历史 THEN System SHALL 能看到最近执行时间、结果摘要和错误信息。

### 需求 6：系统必须提供助手私有的沙箱工作区模型

**用户故事：** 作为使用者，我希望助手临时做事时，有自己的安全空间，而不是总要借我的正式工作区。

#### 验收标准

1. WHEN 用户或 Butler 请求创建临时沙箱 THEN System SHALL 创建一个助手拥有的独立工作区对象。
2. WHEN 沙箱创建成功 THEN System SHALL 记录来源方式、目录路径、可见性、过期时间和当前状态。
3. WHEN 沙箱过期或被用户清理 THEN System SHALL 能安全回收其入口和关联临时资源。

### 需求 7：系统必须允许真实会话绑定到 `project / workspace / sandbox` 三种目标

**用户故事：** 作为使用者，我希望既能在正式项目里起会话，也能在普通工作区或助手沙箱里起一个临时会话。

#### 验收标准

1. WHEN 助手启动真实会话 THEN System SHALL 支持以 `projectId`、`workspaceId` 或 `sandboxId` 作为目标，但三者只能选一个。
2. WHEN 目标是沙箱 THEN System SHALL 在沙箱对应工作区中启动真实会话，而不是强行关联某个正式项目。
3. WHEN 目标不存在或状态不可用 THEN System SHALL 返回明确错误，而不是悄悄退回默认项目。

### 需求 8：系统必须支持沙箱晋升和保留

**用户故事：** 作为使用者，我希望某个临时沙箱做得不错时，可以把它留下来，而不是永远只能当临时垃圾箱。

#### 验收标准

1. WHEN 用户确认保留某个沙箱 THEN System SHALL 支持把它晋升为长期保留的工作区入口。
2. WHEN 用户需要把沙箱纳入正式项目管理 THEN System SHALL 提供明确迁移路径，而不是要求手工重新导入。
3. WHEN 沙箱未被晋升 THEN System SHALL 继续按临时资源规则管理和清理。

### 需求 9：系统必须在 CLI、Host API 和 Butler 页面上暴露自动化与沙箱能力

**用户故事：** 作为使用者，我希望不管是通过 CLI、Butler 页面还是内部能力面，都能看到同一套自动化和沙箱对象。

#### 验收标准

1. WHEN 平台暴露自动化能力 THEN System SHALL 提供 Host API、CLI 和 Butler 页面入口。
2. WHEN 平台暴露沙箱能力 THEN System SHALL 提供创建、查看、清理和晋升入口。
3. WHEN CLI 启动会话 THEN System SHALL 能显式选择 `--project`、`--workspace` 或 `--sandbox`。

### 需求 10：系统必须保证失败隔离和向后兼容

**用户故事：** 作为维护者，我希望自动化和沙箱出问题时，影响只停留在助手控制面，不把普通项目链路打断。

#### 验收标准

1. WHEN 自动化执行失败 THEN System SHALL 不影响普通项目会话和普通工作区功能。
2. WHEN 沙箱创建或清理失败 THEN System SHALL 把影响限制在该沙箱对象和对应入口。
3. WHEN 用户完全不使用自动化和沙箱 THEN System SHALL 保持现有 Butler、会话、工作区主流程不变。

# 需求文档 - spec007-进程管理与启动器

状态：Draft

## 简介

这个 Spec 解决的是一个很现实的问题：用户远程连进工作区后，不能只“看代码”，还要“把项目跑起来、停下来、看日志、看端口”。

如果进程管理只是几个零散按钮，后面一定会变成事故现场：谁启动的、用什么命令启动的、为什么端口冲突、日志去哪了，全都说不清。

所以 `spec007` 的目标很明确：

- 把启动配置做成模型（`LauncherProfile`），不是一堆按钮
- 把进程管理做成独立服务，不挂靠终端
- 所有进程操作默认受鉴权保护
- 让桌面端、H5、移动端都能读取同一份进程状态真相

## 术语表

- **System**：`CodingNS Host` 与客户端协作的整体系统
- **Workspace（工作区）**：进程、终端、会话、文件、Git 的统一归属边界
- **LauncherProfile（启动配置）**：可复用的启动模板，定义命令、参数、目录、环境变量、端口预期等信息
- **ProcessInstance（进程实例）**：某次实际启动出来的进程运行记录
- **TerminalLink（终端关联）**：进程实例和终端实例的弱关联关系
- **Protected API（受保护接口）**：必须登录后才能访问的接口

## 范围说明

### In Scope

- `LauncherProfile` 模型设计与管理
- 进程发现、启动、停止、重启
- 进程日志查看与日志滚动读取
- 端口识别与端口占用状态展示
- 常见项目启动模板（前端/后端/全栈）
- 进程与工作区、终端的关系定义
- 进程 API 与 WebSocket 事件的鉴权保护

### Out of Scope

- 分布式调度
- 容器编排
- 企业级运维平台能力
- 跨机器集群进程编排
- 复杂审批流与多级权限流

## 需求

### 需求 1：启动配置必须模型化

**用户故事：** 作为开发者，我希望把常用启动命令保存成可复用的配置，以便每次不再手敲命令和参数。

#### 验收标准

1. WHEN 用户创建启动配置 THEN System SHALL 以 `LauncherProfile` 结构持久化 `cwd`、`command`、`args`、`env`、`ports` 等字段。
2. WHEN 用户查看工作区启动配置 THEN System SHALL 返回该工作区下可用的配置列表，并支持标记默认配置。
3. WHEN 用户修改或删除启动配置 THEN System SHALL 保持配置版本一致，不影响已运行的历史进程实例记录。

### 需求 2：进程管理必须是独立服务，不挂靠终端

**用户故事：** 作为维护者，我希望进程状态不依赖某个终端 tab 是否还在，以便断线后仍能管理进程。

#### 验收标准

1. WHEN 终端会话断开 THEN System SHALL 继续维护进程实例状态，不把进程误判为已退出。
2. WHEN 用户通过进程面板执行停止或重启 THEN System SHALL 直接作用于 `ProcessInstance`，而不是要求先找到某个终端。
3. WHEN 进程与终端有关联 THEN System SHALL 只记录 `TerminalLink`，不把终端当进程主数据来源。

### 需求 3：进程生命周期操作必须完整可用

**用户故事：** 作为用户，我希望在同一工作区里完成进程发现、启动、停止、重启，以便不必切回本地终端处理。

#### 验收标准

1. WHEN 用户打开进程列表 THEN System SHALL 返回工作区内当前运行与最近运行的进程实例。
2. WHEN 用户执行启动 THEN System SHALL 按选定的 `LauncherProfile` 启动进程并返回实例状态。
3. WHEN 用户执行停止或重启 THEN System SHALL 更新实例状态并返回可读的执行结果与失败原因。

### 需求 4：日志与端口信息必须可追踪

**用户故事：** 作为调试者，我希望快速看到进程日志和端口占用，以便判断服务是否真的启动成功。

#### 验收标准

1. WHEN 进程运行中 THEN System SHALL 持续采集日志，并支持按游标滚动读取。
2. WHEN 进程启动后绑定端口 THEN System SHALL 返回端口列表与占用状态。
3. WHEN 进程异常退出 THEN System SHALL 保留最近日志片段和退出码，便于排障。

### 需求 5：常见项目启动模板必须内置

**用户故事：** 作为新用户，我希望开箱就有常见启动模板，以便不用从零配置每个项目。

#### 验收标准

1. WHEN 新工作区首次初始化进程模块 THEN System SHALL 提供常见模板，例如 `npm run dev`、`pnpm dev`、`next dev`、`node server.js`。
2. WHEN 用户选中模板创建配置 THEN System SHALL 自动填充命令、参数、默认端口建议。
3. WHEN 模板不适配当前项目 THEN System SHALL 允许用户在创建后立即编辑保存。

### 需求 6：所有进程相关操作默认受鉴权保护

**用户故事：** 作为管理员，我希望未登录用户不能查看或控制进程，以便防止远程误操作和信息泄漏。

#### 验收标准

1. WHEN 客户端访问进程与启动器 API 且未携带有效登录态 THEN System SHALL 返回未授权错误。
2. WHEN 客户端订阅进程日志 WebSocket 且鉴权失败 THEN System SHALL 拒绝订阅。
3. WHEN 系统新增进程相关接口 THEN System SHALL 默认归入受保护接口，除非明确声明为公开。

## 非功能需求

### 非功能需求 1：性能

1. WHEN 用户请求进程列表 THEN System SHALL 在正常负载下 1 秒内返回首屏结果。
2. WHEN 用户滚动读取日志 THEN System SHALL 支持增量拉取，避免一次性返回超大日志导致界面卡顿。

### 非功能需求 2：可靠性

1. WHEN Host 重启 THEN System SHALL 能恢复最近进程状态快照和日志读取位置，不丢失关键状态。
2. WHEN 进程操作失败 THEN System SHALL 返回明确错误码与可读提示，不允许静默失败。

### 非功能需求 3：可维护性

1. WHEN 新增启动模板 THEN System SHALL 通过模板注册机制扩展，不改核心执行链路。
2. WHEN 排查“进程和终端状态不一致”问题 THEN System SHALL 能通过实例 ID、终端关联 ID、日志引用快速定位。

### 非功能需求 4：安全性

1. WHEN 执行启动命令 THEN System SHALL 校验 `cwd` 必须位于工作区边界内，拒绝越权路径执行。
2. WHEN 写入日志缓存 THEN System SHALL 不把超长日志全文持续写入 SQLite，而是按文件缓存与索引结合存储。

## 成功定义

- 用户可以在工作区内完成“启动、停止、重启、看日志、看端口”的完整闭环操作
- 进程真相独立于终端真相，终端断开不会破坏进程管理
- 启动配置从“按钮集合”升级为可复用、可维护的 `LauncherProfile`
- 所有进程接口和日志订阅都走鉴权保护，不存在未登录可访问口子

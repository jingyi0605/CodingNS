# 20260515 Windows 安装链路与原生依赖现状盘点

## 这份盘点是干什么的

这份文档只做一件事：把当前 Windows 安装到底卡在哪、哪些地方受控、哪些地方根本不受控，先说清楚。

后面不管是改 `install.sh`，还是做 `@codingns/node-pty` fork，都应该先回来看这份盘点，不要靠聊天记录和记忆拼图。

## 一、当前 Windows 安装主链路

按现在仓库里的逻辑，Windows 安装大致分成 5 段：

1. `install.sh` 检查当前机器是否有 `node`、`npm`
2. `install.sh` 只按 Node/NPM 主版本做最低门槛判断
3. `install.sh` 直接使用当前系统里的 `node`、`npm`、全局 prefix 执行 `npm install -g @jingyi0605/codingns`
4. npm 安装 `better-sqlite3`、`node-pty` 等依赖
5. `packages/codingns/scripts/postinstall.mjs` 再校验并补装 Codex SDK 与平台二进制

这条链最大的毛病很简单：

- 前半段靠系统环境
- 中间段靠第三方原生包是否正好命中预编译
- 后半段还有 `postinstall` 二次修复

用户看到的是“一次安装”，实际上里面串了三层不同来源的失败点。

## 二、`install.sh` 现在实际做了什么

### 2.1 现在有的判断

从 `install.sh` 当前实现看，Windows 相关逻辑主要只有这些：

- Node 主版本小于 22：直接报错
- npm 主版本小于 10：直接报错
- 没检测到 Visual Studio Build Tools：给 warning
- 当前是 Windows + Node 24 及以上：给 warning，建议优先 Node 22
- npm 安装失败后，如果日志里出现 Visual Studio 或 prebuild 下载报错，再补一段诊断提示

也就是说，现在脚本知道“这台机器可能会炸”，但它还没有能力在安装前把这件事真正收住。

### 2.2 现在没有的判断

当前脚本明确缺这些能力：

- 没有 `better-sqlite3` / `node-pty` 的受管支持矩阵
- 没有基于 `process.versions.modules` 或 Node ABI 的判断
- 没有“系统 Node 不合适时切私有 Node”的能力
- 没有私有 npm prefix
- Windows 不支持自动准备运行时
- Windows 也不支持自动安装前置环境，`supports_automatic_prerequisite_install()` 只支持 `Darwin` 和 `Linux + apt-get`

结论很直接：当前脚本只是“提示用户环境可能有问题”，不是“替用户解决环境问题”。

## 三、当前服务包里的两个原生依赖

### 3.1 `better-sqlite3`

当前服务包和 Host 都直接依赖 `better-sqlite3`。

现状：

- 它有预编译下载逻辑
- 安装脚本是 `prebuild-install || node-gyp rebuild --release`
- 命中预编译时，Windows 用户可以免本机编译
- 一旦预编译下载失败、网络超时、ABI 不命中，就会回退到本机编译

这意味着它不是完全受控，只是“有机会不编译”。

### 3.2 `node-pty`

当前服务包和 Host 也都直接依赖 `node-pty@^1.0.0`。

现状：

- 当前 1.0.0 包的安装入口是 `node-gyp rebuild`
- 包里没有现成的 Windows 预编译随包发布策略
- 对 Windows 普通用户来说，默认路径就是本机编译

这不是偶发风险，这是默认行为。

## 四、`node-pty` 在项目里不是可选依赖

这包现在是终端主链路的一部分，不是“有最好，没有也行”的附属件。

当前明确使用点包括：

- `apps/host/src/modules/terminal/runtime/pty-runtime-manager.ts`
- `apps/host/src/modules/terminal/runtime/pty-host-attachment-manager.ts`
- `apps/host/src/modules/terminal/runtime/pty-broker-agent-process.ts`
- `apps/host/src/modules/terminal/runtime/conpty-session-agent-process.ts`

Host 现在直接依赖它的这些能力：

- `spawn`
- `write`
- `resize`
- `kill`
- `onData`
- `onExit`

所以这次不能靠“禁用终端功能绕过去”。那是换问题，不是解决问题。

## 五、当前安装失败点清单

### 5.1 系统 Node 不受控

当前安装脚本直接吃系统 Node。

问题：

- 用户可能正好装了 Node 24+
- 用户可能切过 nvm、fnm、Volta，实际运行 Node 不稳定
- 即使版本号满足 `>=22`，也不代表当前 ABI 一定命中原生预编译

### 5.2 `better-sqlite3` 预编译下载失败会回退本机编译

当前真实安装日志已经证明：

- prebuild 下载可能因为 `ECONNRESET`、超时等原因失败
- 失败后会直接进入 `node-gyp rebuild`
- Windows 上一旦进 `node-gyp`，就要求本机有 Visual Studio Build Tools

### 5.3 `node-pty` 当前默认就是本机编译

这不是网络偶发问题，而是发布策略本身决定的。

只要还在用官方 `node-pty@1.0.0`，Windows 用户就很难真正免编译。

### 5.4 `postinstall.mjs` 是第二层失败点

即使两个原生包都没炸，`packages/codingns/scripts/postinstall.mjs` 还会继续做这些事：

- 校验 `@openai/codex-sdk` 入口
- 校验 `codex` CLI 入口
- 校验平台二进制是否存在且可执行
- 如果缺失，则在包目录内再跑一次 `npm install`

这意味着安装链路不是“原生依赖过了就结束”，而是后面还有一层 Codex 运行时修复。

这层之前已经修过真实 bug，所以不能假装它不存在。

## 六、当前支持矩阵初稿

这不是最终发布矩阵，只是第一阶段盘点后能落地的受管判断起点。

| 包名 | 当前来源 | Windows 免编译现状 | 第一阶段判断 |
| --- | --- | --- | --- |
| `better-sqlite3` | 上游包 | 可能命中预编译，也可能回退编译 | 继续复用上游，允许 `allow-build`，但要提前提示风险 |
| `node-pty` | 上游官方包 | 默认本机编译 | 不适合作为正式免编译方案 |
| `@codingns/node-pty` | 计划新增 fork | 第一版目标是随包提供 Windows x64 + Node 22 预编译 | 作为受管核心依赖，未命中时优先明确失败 |

## 七、当前 `install.sh` 的关键缺口

如果只看这次 Spec 要解决的问题，当前脚本至少缺 4 件关键东西：

### 7.1 没有安装前的命中判断

脚本现在不会在安装前回答：

- 当前 Node ABI 能不能装 `better-sqlite3`
- 当前 Node ABI 能不能装 `node-pty`
- 哪个包会落回本机编译

### 7.2 没有私有 Node

脚本现在只能“建议你换 Node 22”，不能“给 CodingNS 自己准备一份 Node 22”。

这就等于把成功率交给用户自己折腾系统环境。

### 7.3 没有私有 npm prefix

当前仍然走系统全局 npm prefix。

问题：

- 容易受系统权限、已有全局配置影响
- 不利于把 CodingNS 和系统其他 npm 包隔离开
- 后续 PM2 和升级链路也难以完全受控

### 7.4 Windows 没有自动准备运行时

现在脚本在 macOS、Linux 至少会尝试自动补 Node 或构建工具。

Windows 这里没有对应能力，只有 warning。

## 八、第一阶段已经能确认的现实边界

这一步必须说人话，不然后面一定越做越歪。

### 8.1 先做什么

第一阶段先只收两件事：

1. 给 CodingNS 准备私有 Node 22 LTS，不碰系统 Node
2. 接管 `node-pty` 的 Windows x64 + Node 22 预编译发布

### 8.2 先不做什么

第一阶段明确不做这些事：

- 不承诺一次覆盖 macOS、Linux、Windows arm64
- 不承诺立刻把 `better-sqlite3` 也变成自维护 fork
- 不承诺自动给 Windows 安装 Visual Studio Build Tools
- 不重写终端架构，不拿“先禁用 PTY”这种偷懒方案冒充解决问题

### 8.3 现实约束

第一阶段要接受这些现实：

- `better-sqlite3` 仍然是上游包，极端情况下还是可能回退编译
- `postinstall.mjs` 仍然是安装链路的一部分，不能只测 native install 不测 postinstall
- `@codingns/node-pty` 第一版就算只支持 `win32 + x64 + Node 22`，也比“表面支持很多，实际上全靠本机编译”强

## 九、后续设计输入清单

这份盘点完成后，后面的设计和实现必须回答下面这些具体问题：

1. 私有 Node 22 下载地址、校验值和目录结构放哪
2. 安装脚本怎样判断“当前系统 Node 能不能直接继续”
3. 私有 Node 安装后，怎样切换 npm prefix、PM2 启动命令和后续升级入口
4. `@codingns/node-pty` 的包结构到底是“随包内置 `build/Release`”还是“安装时再拉 release 产物”
5. `@codingns/node-pty` 第一版未命中时，是直接失败，还是保留显式开关允许编译
6. `better-sqlite3` 如果在私有 Node 22 上仍然因为网络拿不到 prebuild，安装脚本该怎么报错和定位
7. `postinstall.mjs` 在私有 Node + 私有 prefix 场景下，是否还会遇到额外路径问题

## 十、结论

当前 Windows 安装失败，不是一个点坏了，而是三层问题叠在一起：

- 系统 Node 不受控
- `node-pty` 发布策略不适合免编译目标
- `postinstall` 还会再引入一层运行时修复风险

所以这次 Spec 先收口环境，再收口 `node-pty`，这是对的。先把最脆的链路拿回来，别再继续赌用户机器。

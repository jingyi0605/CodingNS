# 20260515 Windows 私有 Node 策略取舍

## 这份文档回答什么

第二阶段真正要先决定的，不是“Node 下载地址放哪”，而是更前面的事：

Windows 安装时，CodingNS 到底要不要继续允许“命中就用系统 Node，不命中再切私有 Node”。

这是根分叉。这里选错，后面脚本、日志、升级、PM2、排障都会变脏。

## 一、两个可选方案

### 方案 A：条件切换

做法：

- 先检查当前系统 Node 是否命中 `better-sqlite3` 和 `@codingns/node-pty` 支持矩阵
- 命中就继续用系统 Node
- 不命中再下载私有 Node 22

看起来省下载，其实会把运行时分成两套。

### 方案 B：Windows 一律使用私有 Node 22

做法：

- Windows 安装时始终准备并复用 CodingNS 自己的私有 Node 22
- 系统 Node 最多只拿来做诊断提示
- 正式 npm 安装、PM2 启动、升级、回滚全部绑定私有运行时

这才叫“受控运行时”。

## 二、按 Linus 的方式拆这个问题

### 2.1 数据结构

方案 A 的真实数据结构是两套环境：

- 系统 Node + 系统 npm prefix
- 私有 Node + 私有 npm prefix

这会把后面所有东西都变成双分支：

- 服务装在哪
- PM2 用哪个 Node 拉起
- 升级时复用哪套环境
- 日志里该打印哪套路径
- postinstall 在哪套 `node_modules` 里修复

方案 B 的数据结构只有一套：

- CodingNS Runtime Home

这就对了。好代码先把数据结构收简单。

### 2.2 特殊情况

方案 A 会天然长出这些特殊情况：

- 系统 Node 22 命中，直接安装
- 系统 Node 24 不命中，切私有 Node
- 系统 Node 22 命中 `better-sqlite3`，但不命中 `@codingns/node-pty`
- 第一次安装走系统 Node，后续升级又切到私有 Node
- PM2 当前进程是系统 Node，升级后想切私有 Node

这堆 if/else 没一个是业务价值，全是自己造出来的复杂度。

方案 B 直接把这些分支砍掉：

- Windows 上 CodingNS 永远跑私有 Node 22

### 2.3 破坏性

两种方案都可以做到“不改系统 Node”，这一点没区别。

但方案 A 更容易破坏已有安装：

- 同一台机器上，不同时间可能装进不同 prefix
- 升级逻辑要判断旧安装到底跑在哪套 Node 上
- 用户一旦手工改系统 Node，下一次升级行为可能变掉

方案 B 更稳：

- 系统环境怎么变，CodingNS 自己的运行时不变
- 回滚时也只需要回到私有运行时目录里的上一版本

### 2.4 实用性

方案 A 的唯一好处是：

- 有时候能少下一次 Node 压缩包

这点收益太小，不值得换来长期维护成本。

方案 B 的代价是：

- Windows 首次安装多一份私有 Node 22 占用

这点磁盘成本是现实世界里最便宜的成本。和安装失败、升级错乱、排障分支相比，根本不值一提。

## 三、核心判断

### 【核心判断】

✅ 值得做：Windows 下让 CodingNS 一律使用私有 Node 22，系统 Node 只做诊断，不参与正式运行时。

### 【关键洞察】

- 数据结构：保持一套 `Runtime Home`，比同时维护系统/私有两套运行时干净得多。
- 复杂度：把“命中就用系统 Node”的分支去掉，能直接消灭升级、PM2、prefix、postinstall 的一大片特殊情况。
- 风险点：首次安装会多下载一份 Node，但这比维护双运行时简单太多。

## 四、推荐落地方式

推荐第二阶段按下面这个顺序设计：

1. Windows 安装启动后，先确定目标正式运行时固定为私有 Node 22。
2. 系统 Node 如果存在，只做两件事：
   - 打印当前系统 Node 版本和 ABI，作为诊断信息
   - 在极端情况下辅助脚本执行少量探测命令
3. 正式安装前，检查的是“目标私有 Node 22 环境”是否命中受管原生包支持矩阵，而不是检查完系统 Node 就直接拿它继续跑。
4. `npm install`、`postinstall`、PM2、升级、回滚全部绑定私有 Node 和私有 npm prefix。

## 五、这不等于放弃支持矩阵检查

这里容易误解，所以要单独说。

“Windows 一律使用私有 Node 22”不等于“不检查支持矩阵”。

真正应该检查的是：

- 目标平台是不是 `win32`
- 目标架构是不是 `x64`
- 目标运行时是不是 Node 22
- 目标 ABI 是否命中 `better-sqlite3` 和 `@codingns/node-pty`

也就是说，检查依然要做，但检查对象应该是正式运行时，而不是用户系统里那套我们不打算长期依赖的环境。

## 六、如果暂时不愿意彻底切到方案 B

那至少要承认方案 A 的代价：

- 安装脚本要维护两套执行上下文
- PM2 和升级要处理历史安装分流
- 文档和排障要解释更多特殊情况

如果团队不想吃这些复杂度，别犹豫，直接选方案 B。

## 七、结论

方案 A 看起来灵活，实际上是在给后续每一步埋分支。

方案 B 才是“把 CodingNS 的 Windows 运行时真正收回来”。

这不是过度设计，恰恰相反，这是把不必要的特殊情况砍掉。

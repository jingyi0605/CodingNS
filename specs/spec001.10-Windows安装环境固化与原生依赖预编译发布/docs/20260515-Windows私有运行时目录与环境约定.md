# 20260515 Windows 私有运行时目录与环境约定

## 这份文档解决什么问题

前面已经决定了两件事：

1. Windows 下，CodingNS 正式运行时统一走私有 Node 22。
2. npm 安装、PM2、升级、回滚都不能再依赖系统 Node。

但如果这里只停在“私有 Node”四个字，后面实现时还是会乱。

真正需要钉死的是：

- 目录怎么摆
- 哪些路径是稳定入口
- 进程环境变量怎么传
- PM2 和升级链路到底吃哪套上下文

这份文档就是把这些东西写成人话，避免后面边写边猜。

## 一、目录设计原则

先说原则，不然路径名字换一次就乱一次。

### 1.1 只保留一套正式运行时根目录

Windows 下，CodingNS 所有正式运行时文件都收口到：

- `<dataDir>/runtime/`

不要一部分放 `dataDir`，一部分放 npm 默认 prefix，一部分再借系统 `%APPDATA%`。那不是设计，那是扩散。

### 1.2 稳定路径和版本目录分开

好代码要同时解决两件事：

- 运行中的命令能有稳定路径
- 升级和回滚时又不能把版本信息抹掉

所以应该分成两层：

- 稳定入口路径：脚本和 PM2 固定引用
- 真实版本目录：具体某个 Node 22.x.y 实体

### 1.3 不依赖 Windows 符号链接

Windows 上用 symlink/junction 看起来很酷，实际会引入权限和兼容问题。

第一版不要靠它。目录切换应该用：

- 明确的元数据文件
- 安装脚本自己解析真实目录

别把运行时切换建立在系统权限彩票上。

## 二、建议目录结构

建议第一版采用下面这套结构：

```text
<dataDir>/
  runtime/
    node-22/
      versions/
        node-v22.x.y-win-x64/
      active.json
    npm-global/
      node_modules/
      package.json
      package-lock.json
    cache/
      downloads/
      npm/
    logs/
      install/
      runtime/
    pm2/
    service/
      install-state.json
      install-state.previous.json
      launch-env.json
```

## 三、每个目录到底放什么

### 3.1 `runtime/node-22/versions/`

这里放真实解压出来的 Node 发行目录。

例如：

- `<dataDir>/runtime/node-22/versions/node-v22.16.0-win-x64/`

里面包含：

- `node.exe`
- `npm.cmd`
- `npx.cmd`
- Node 自带运行时文件

这个目录一旦解压完成，就尽量视为只读版本目录，不要在里面混入业务状态文件。

### 3.2 `runtime/node-22/active.json`

这是私有 Node 的稳定入口元数据，不是摆设。

建议至少记录：

- `version`
- `platform`
- `arch`
- `nodeDir`
- `nodeExe`
- `npmCmd`
- `npxCmd`
- `installedAt`
- `sourceUrl`
- `sha256`

示例：

```json
{
  "version": "22.16.0",
  "platform": "win32",
  "arch": "x64",
  "nodeDir": "C:/Users/.../.codingns/runtime/node-22/versions/node-v22.16.0-win-x64",
  "nodeExe": "C:/Users/.../.codingns/runtime/node-22/versions/node-v22.16.0-win-x64/node.exe",
  "npmCmd": "C:/Users/.../.codingns/runtime/node-22/versions/node-v22.16.0-win-x64/npm.cmd",
  "npxCmd": "C:/Users/.../.codingns/runtime/node-22/versions/node-v22.16.0-win-x64/npx.cmd",
  "installedAt": "2026-05-15T09:00:00Z",
  "sourceUrl": "https://nodejs.org/dist/v22.16.0/node-v22.16.0-win-x64.zip",
  "sha256": "..."
}
```

安装脚本和升级脚本都只认这份文件，不要到处扫目录猜哪份 Node 才是当前活动版本。

### 3.3 `runtime/npm-global/`

这是 CodingNS 私有 npm prefix。

这里放：

- `@jingyi0605/codingns`
- `pm2`
- 后续必须跟随私有运行时管理的全局 npm 包

这里不应该放：

- 用户自己其他项目的全局包
- 系统 npm 共享状态

第一版建议把这份 prefix 明确当成 CodingNS 专用空间。

### 3.4 `runtime/cache/`

拆成两类：

- `downloads/`：Node 压缩包、校验文件等下载缓存
- `npm/`：npm cache

这样做的好处很简单：

- 重复安装不必重复下载
- 出问题时能清理 cache，而不用动正式运行时

### 3.5 `runtime/logs/`

至少拆两层：

- `install/`：安装、升级、修复日志
- `runtime/`：服务启动或运行期辅助日志

错误日志别再丢到系统临时目录里让用户自己猜。

### 3.6 `runtime/pm2/`

这里直接当 `PM2_HOME`。

原因很现实：

- 不污染系统默认 PM2 状态
- 不跟用户已有 PM2 进程打架
- 升级和回滚能明确知道自己在管哪一组进程

### 3.7 `runtime/service/`

这是安装状态和服务元数据目录。

第一版建议至少保留：

- `install-state.json`
- `install-state.previous.json`
- `launch-env.json`

它们解决的是三个不同问题：

- 当前到底装了什么
- 上一版是什么，便于回滚
- 启动时到底使用了哪些关键环境变量

## 四、稳定路径约定

后面脚本不要各自拼路径，统一认下面这些逻辑名称。

| 逻辑名 | 建议路径 | 用途 |
| --- | --- | --- |
| `RUNTIME_HOME` | `<dataDir>/runtime` | 私有运行时总根目录 |
| `NODE_RUNTIME_ROOT` | `<dataDir>/runtime/node-22` | Node 22 运行时根目录 |
| `NODE_ACTIVE_META` | `<dataDir>/runtime/node-22/active.json` | 当前活动 Node 元数据 |
| `NPM_GLOBAL_PREFIX` | `<dataDir>/runtime/npm-global` | 私有 npm prefix |
| `NPM_CACHE_DIR` | `<dataDir>/runtime/cache/npm` | 私有 npm 缓存 |
| `DOWNLOAD_CACHE_DIR` | `<dataDir>/runtime/cache/downloads` | 下载缓存 |
| `PM2_HOME_DIR` | `<dataDir>/runtime/pm2` | 私有 PM2 HOME |
| `SERVICE_STATE_DIR` | `<dataDir>/runtime/service` | 安装/回滚元数据 |
| `INSTALL_LOG_DIR` | `<dataDir>/runtime/logs/install` | 安装日志目录 |

## 五、进程环境变量约定

第一版要避免一件蠢事：到处 `npm config set prefix`、改全局配置文件、污染用户 shell。

正确做法是：只在当前安装进程和 PM2 启动上下文里注入环境变量。

### 5.1 安装阶段必须显式注入的环境变量

建议至少包括：

- `CODINGNS_DATA_DIR=<dataDir>`
- `CODINGNS_RUNTIME_ROOT=<dataDir>/runtime`
- `CODINGNS_RUNTIME_NODE_VERSION=22.x.y`
- `PM2_HOME=<dataDir>/runtime/pm2`
- `npm_config_prefix=<dataDir>/runtime/npm-global`
- `npm_config_cache=<dataDir>/runtime/cache/npm`
- `npm_config_userconfig=<dataDir>/runtime/npm-global/npmrc`

如果要给 `PATH` 预置，顺序应该是：

1. 私有 Node 目录
2. 私有 npm prefix
3. 系统原始 PATH

不要反过来。反过来就又把系统命令抢回来了。

### 5.2 服务启动阶段必须保留的环境变量

PM2 启动 CodingNS 时，至少应显式传入：

- `CODINGNS_DATA_DIR`
- `CODINGNS_PM2_PROCESS_NAME`
- `PM2_HOME`
- 私有运行时 PATH

必要时可以继续传：

- `CODINGNS_NPM_REGISTRY_BASE_URL`
- `CODINGNS_RELEASE_CHANNEL`

但核心原则不变：服务进程必须能在脱离当前用户交互 shell 的情况下独立启动。

## 六、安装上下文约定

### 6.1 `npm install` 应该怎么跑

不要依赖系统 `npm`，也不要依赖系统 prefix。

正式安装上下文应该等价于：

```text
PATH=<private-node>;<private-prefix>;<system-path>
PM2_HOME=<dataDir>/runtime/pm2
npm_config_prefix=<dataDir>/runtime/npm-global
npm_config_cache=<dataDir>/runtime/cache/npm
<private-node>/npm.cmd install -g @jingyi0605/codingns
```

如果用户选择 PM2，也应该安装到同一个私有 prefix：

```text
<private-node>/npm.cmd install -g pm2
```

这点要写死。不然你最后还是会落回系统 PM2。

### 6.2 `codingns` 命令的真实来源

第一版不要再用“系统里能找到哪个 `codingns` 就用哪个”的逻辑。

Windows 正式安装后，应该认定 `codingns` 的有效命令来自：

- `<dataDir>/runtime/npm-global/codingns.cmd`

对应脚本和包目录来自私有 npm prefix，不再依赖系统全局 npm 目录。

### 6.3 `pm2` 命令的真实来源

如果启用 PM2，应该认定它来自：

- `<dataDir>/runtime/npm-global/pm2.cmd`

而不是系统 `%APPDATA%\\npm\\pm2.cmd`。

这和前面一样，目的是彻底切断系统环境漂移。

## 七、PM2 启动约定

当前脚本已经是这种思路：

- `pm2 start <node> --interpreter none -- <codingns-script> start ...`

第一版继续沿用这个模型，但把路径全部换成私有运行时。

建议等价命令：

```text
<private-prefix>/pm2.cmd start <private-node>/node.exe --name codingns --cwd <dataDir> --interpreter none -- <private-prefix>/node_modules/@jingyi0605/codingns/bin/codingns.mjs start --host 0.0.0.0 --port <port> --data-dir <dataDir>
```

这里有两个关键点：

1. `node.exe` 必须是私有 Node。
2. `codingns.mjs` 必须来自私有 prefix 的包目录。

不要出现“私有 PM2 拉起系统 Node”或者“私有 Node 跑系统 prefix 的 codingns”这种混搭。那种方案非常垃圾，排障时谁都想骂人。

## 八、升级约定

升级时不要重新发明流程。

第一版建议升级复用和首次安装同一套上下文：

1. 读取 `active.json`
2. 读取 `install-state.json`
3. 校验私有 Node 仍然存在且可执行
4. 用私有 Node + 私有 prefix 执行新的 npm 安装
5. 更新 `install-state.previous.json`
6. 写入新的 `install-state.json`
7. 再做 PM2 reload/restart

升级流程里如果发现活动 Node 丢了，不应该偷偷退回系统 Node，而应该直接报错并要求修复运行时。

## 九、回滚约定

第一版回滚先别追求花哨，只追求清楚。

建议最小回滚模型：

- `install-state.json`：当前状态
- `install-state.previous.json`：上一版状态

状态文件至少记录：

- `packageName`
- `packageVersion`
- `packageSpec`
- `nodeVersion`
- `nodeExe`
- `npmPrefix`
- `pm2Home`
- `installedAt`
- `registry`

回滚时只做两件事：

1. 用上一版状态里记录的私有 Node 和私有 prefix 恢复服务包
2. 重启私有 PM2 进程

别搞“自动猜上一版在哪”。既然是受控运行时，就该有明确状态文件。

## 十、明确不做什么

这一阶段先不做下面这些复杂活：

- 不做多版本 Node 并行切换 UI
- 不做自动清理所有历史 Node 版本
- 不做跨机器同步 runtime 目录
- 不做系统级 PATH 永久写入
- 不做系统级 npm config 永久改写

第一版重点只有一个：让本机安装、升级、回滚全都围绕私有运行时这一个中心转。

## 十一、结论

真正需要被“固化”的不是 Node 22 这个名字，而是整套安装上下文。

如果只是下载一份私有 Node，但：

- npm 还用系统 prefix
- PM2 还用系统 HOME
- `codingns` 还从系统全局命令解析

那等于什么都没收住。

所以第二阶段必须一起收 4 个东西：

1. 私有 Node
2. 私有 npm prefix
3. 私有 PM2 HOME
4. 私有服务状态元数据

少一个，后面都会重新漏回系统环境。

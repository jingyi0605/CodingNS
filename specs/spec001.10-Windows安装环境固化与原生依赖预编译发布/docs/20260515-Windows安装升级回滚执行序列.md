# 20260515 Windows 安装升级回滚执行序列

## 这份文档回答什么

前面已经把私有运行时目录和环境变量定下来了，但还有一个问题不能含糊：

- 第一次安装怎么落盘
- 升级时先改什么，后改什么
- 失败时回滚到哪一层

如果这块不先说清楚，后面实现时最容易出现两种垃圾状态：

1. 包已经换了一半，PM2 还是旧进程
2. Node 是新的，prefix 是旧的，状态文件还是假的

这份文档就是为了把执行顺序写死，别让安装脚本临场自由发挥。

## 一、基本原则

### 1.1 先准备新状态，再切换正式状态

安装和升级都不应该一边改正式状态，一边希望自己别失败。

正确顺序应该是：

1. 先准备候选运行时和候选安装结果
2. 确认成功后再写正式状态
3. 最后再切 PM2 进程

### 1.2 状态文件必须是单一真相来源

不要让下面这些东西分别自说自话：

- 实际装在哪个 prefix
- 当前用哪个 Node
- PM2 进程拉起的到底是哪套脚本

第一版必须认 `runtime/service/install-state.json` 是单一真相来源。

### 1.3 回滚只回滚正式状态，不回滚下载缓存

缓存不是正式状态。

回滚应该管：

- 当前服务包版本
- 当前私有 Node 指向
- 当前 PM2 进程启动入口

不应该管：

- `cache/downloads`
- `cache/npm`

## 二、状态文件约定

### 2.1 `install-state.json`

代表“当前正式生效状态”。

建议至少包含：

```json
{
  "schemaVersion": 1,
  "packageName": "@jingyi0605/codingns",
  "packageVersion": "0.7.4",
  "packageSpec": "@jingyi0605/codingns",
  "registry": "https://registry.npmjs.org",
  "nodeVersion": "22.16.0",
  "nodeExe": "C:/Users/.../.codingns/runtime/node-22/versions/node-v22.16.0-win-x64/node.exe",
  "npmCmd": "C:/Users/.../.codingns/runtime/node-22/versions/node-v22.16.0-win-x64/npm.cmd",
  "npmPrefix": "C:/Users/.../.codingns/runtime/npm-global",
  "pm2Home": "C:/Users/.../.codingns/runtime/pm2",
  "codingnsCommand": "C:/Users/.../.codingns/runtime/npm-global/codingns.cmd",
  "pm2Command": "C:/Users/.../.codingns/runtime/npm-global/pm2.cmd",
  "dataDir": "C:/Users/.../.codingns",
  "port": 3002,
  "processName": "codingns",
  "installedAt": "2026-05-15T09:30:00Z"
}
```

### 2.2 `install-state.previous.json`

代表“上一个正式可回滚状态”。

规则很简单：

- 每次正式升级成功前，先把旧 `install-state.json` 复制到这里
- 如果当前是首次安装，可以不存在

### 2.3 `launch-env.json`

这是 PM2 真正启动时使用的关键环境快照。

建议至少保留：

- `PATH`
- `PM2_HOME`
- `CODINGNS_DATA_DIR`
- `CODINGNS_RUNTIME_ROOT`
- `npm_config_prefix`
- `npm_config_cache`

它不是给程序运行时读的，主要是给排障和回放看的。

## 三、首次安装执行序列

建议第一版按下面 10 步走：

1. 校验输入参数
2. 准备私有 Node 22
3. 组装私有安装环境
4. 校验目标支持矩阵
5. 用私有 npm prefix 安装 `@jingyi0605/codingns`
6. 如果用户启用 PM2，用同一私有 prefix 安装 `pm2`
7. 校验 `codingns.cmd`、`pm2.cmd`、`codingns.mjs`、私有 `node.exe` 都可解析
8. 写入新的 `install-state.json`
9. 写入 `launch-env.json`
10. 启动或重建 PM2 服务

这里有一个关键点：

首次安装成功的定义不是“npm install 结束了”，而是“正式状态已写入，并且服务能按这份状态启动”。

## 四、升级执行序列

升级时最容易犯的错误是：刚下载完新包就直接覆盖当前状态。

第一版不要这么做。

建议升级顺序：

1. 读取当前 `install-state.json`
2. 校验当前私有 Node 和 prefix 仍然存在
3. 准备目标包安装
4. 在同一私有 prefix 中完成 npm 升级
5. 校验升级后的 `codingns` 入口和 `postinstall` 结果
6. 把当前 `install-state.json` 复制为 `install-state.previous.json`
7. 写入新的 `install-state.json`
8. 更新 `launch-env.json`
9. `pm2 restart` 或 `pm2 reload`
10. 验证进程已按新入口拉起

注意：

- 升级默认不切系统 Node
- 升级默认不切系统 PM2
- 升级默认不从系统 PATH 重新解析 `codingns`

否则你等于升级一次就重新赌一次环境。

## 五、失败回滚策略

### 5.1 哪些失败可以直接中止，不需要正式回滚

如果失败发生在正式状态切换前，只要退出就行。

例如：

- 私有 Node 下载失败
- 支持矩阵检查失败
- npm 安装失败
- `postinstall` 修复失败

这种情况不要碰 `install-state.json`。

### 5.2 哪些失败需要正式回滚

如果失败发生在写入新状态之后，就必须考虑回滚。

例如：

- 新状态写入成功，但 PM2 启动失败
- PM2 拉起成功，但健康检查失败

这时候建议顺序：

1. 读取 `install-state.previous.json`
2. 用上一版记录的私有 Node 和私有 prefix 恢复服务入口
3. 重写 `install-state.json` 为上一版内容
4. 用上一版环境重启 PM2

### 5.3 回滚失败怎么办

第一版不要装英雄。

如果自动回滚也失败，脚本必须明确输出：

- 当前失败阶段
- 当前 `install-state.json` 路径
- 当前 `install-state.previous.json` 路径
- 私有 Node 路径
- 私有 npm prefix 路径
- PM2 HOME 路径

至少要让人类维护者能接手，不要把现场再抹一遍。

## 六、PM2 切换规则

升级和回滚都必须遵守同一个规则：

- PM2 进程启动入口永远来自私有运行时

也就是：

- `node.exe` 来自私有 Node
- `codingns.mjs` 来自私有 npm prefix
- `PM2_HOME` 来自私有 runtime

不能出现这些混搭：

- 系统 PM2 + 私有 Node
- 私有 PM2 + 系统 Node
- 私有 PM2 + 私有 Node + 系统 `codingns.cmd`

这三种状态都是脏状态，都不该被文档承认。

## 七、建议的最小健康检查

第一版不用搞复杂 orchestration，但至少要有最小健康检查。

建议包含：

1. 目标 `codingns` 命令可解析
2. 目标 `node.exe` 可执行
3. PM2 进程存在
4. 服务端口开始监听

这四个都过了，才算切换成功。

## 八、明确不做什么

这一阶段先不做：

- 灰度升级
- 多版本并行服务切换
- 自动数据库结构回滚
- 跨主版本 Node 热切换

第一版先把“单机单实例单私有运行时”做稳，这才是正路。

## 九、结论

安装、升级、回滚这三件事本质上不是三个系统，而是一套状态切换规则。

真正要守住的只有一句话：

- 任何时候，正式运行状态都必须能被一份明确的状态文件完整描述。

只要这个前提守住，脚本就不会越写越像玄学。

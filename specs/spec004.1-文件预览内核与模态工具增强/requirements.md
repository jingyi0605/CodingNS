# 需求文档 - spec004.1-文件预览内核与模态工具增强

状态：Draft

## 简介

`spec004` 已经把文件管理主链路跑起来了，但预览体验还有几个明显短板：

- 常用二进制文件还是“不能预览”
- HTML 走特殊通道，别的格式没有统一模型
- 预览模态框尺寸固定，大文件、大图、大 PDF 都挤
- 工具按钮没有按格式分化，用户看图片、看 PDF、改文本时拿到的是同一套壳

这些问题都不是“以后再优化”的小毛病，它们已经直接影响文件管理是否真的能用。

如果继续把 `TXT / PDF / 图片` 这种高频格式丢给外部 H5 工具，问题只会更多：

- 文件可能要出网
- 离线和弱网直接退化
- 第三方服务挂了，预览也跟着挂
- 同一个文件在不同平台、不同网络条件下行为不一致

所以这次边界先说死：

1. `TXT / PDF / 图片` 走内置预览
2. 预览模态框要能调尺寸
3. 工具按钮按文件格式切换
4. `Office` 明确留到后续，不混进这次范围

## 可实现性结论

### 结论

这个能力 **值得做，而且应该作为 `spec004` 的直接增强项尽快推进**。

### 已确认事实

1. 当前前端已经有 `FileViewerModal`，说明预览壳已经存在，不需要从零再造一层页面系统。
2. 当前后端已经有 `file-preview-service` 和 `file-preview-link-service`，说明服务端预览链路已经有底子。
3. 当前预览模型只够覆盖文本和 HTML，无法稳定承接图片和 PDF。
4. 当前项目已经明确：`TXT / PDF / 图片` 不走外部 H5 在线工具主方案，`Office` 留待未来。

## 术语表

- **Builtin Preview（内置预览）**：由当前应用自身完成渲染或展示，不依赖第三方在线服务
- **Preview Kind（预览类型）**：预览链路识别出的文件展示类型，如 `text`、`image`、`pdf`
- **Viewer Tools（查看工具按钮）**：根据文件格式切换的一组操作按钮，例如缩放、翻页、切换编辑态
- **Resizable Modal（可调尺寸模态框）**：支持在查看过程中调整宽高或切换尺寸档位的预览弹层
- **Preview Provider（预览提供者）**：负责决定某个文件由哪种内置能力渲染的实现单元

## 范围说明

### In Scope

- 统一文件预览结果模型，明确 `text / image / pdf / html / unsupported` 等类型
- 对现有文本预览和编辑能力做兼容增强，不破坏已有文本工作流
- 为图片提供正式内置预览
- 为 PDF 提供正式内置预览
- 支持文件预览模态框调整尺寸
- 支持根据文件格式展示不同工具按钮
- 为未来 `Office / 插件化预览` 预留扩展接口，但不实现其具体预览器

### Out of Scope

- `doc / docx / xls / xlsx / ppt / pptx` 等 Office 文件预览实现
- 第三方在线 H5 预览服务接入
- 重型代码编辑器能力扩展
- 文件批注、协同评论、多人同步查看

## 技术边界

### 边界 1：高频格式必须内置

- `TXT / Markdown / 代码文本 / 图片 / PDF` 必须由当前应用内置处理
- 不允许把这些格式的主链路外包给第三方在线 H5 服务

### 边界 2：模态框增强不能破坏现有编辑链路

- 文本文件现有的打开、编辑、保存、冲突保护逻辑必须继续可用
- 新增预览类型不能把文本编辑能力搞坏

### 边界 3：工具按钮必须按格式分组，而不是继续一刀切

- 图片、PDF、文本文件要允许不同按钮集合
- 但整体交互结构要统一，不能每种类型都长一套完全不同的弹层

### 边界 4：这次只给未来插件化留接口，不实现 Office 预览

- 未来可以扩 `Preview Provider Registry`
- 但这次不为了“以后可能有 Office”把范围做炸

### 边界 5：预览链路默认不出网

- 本地工作区文件预览默认只走本地 Host + 当前应用
- 不允许默认上传文件到外部服务换取预览

## 需求

### 需求 1：系统必须为常用格式提供稳定的内置预览

**用户故事：** 作为文件管理用户，我希望在当前应用里直接查看 `TXT / PDF / 图片` 等常用格式，而不是频繁碰到“不支持预览”。

#### 验收标准

1. WHEN 用户打开文本类文件 THEN System SHALL 提供稳定的内置文本预览，并保持原有基础编辑能力可用。
2. WHEN 用户打开图片文件 THEN System SHALL 提供稳定的内置图片预览。
3. WHEN 用户打开 PDF 文件 THEN System SHALL 提供稳定的内置 PDF 预览。
4. WHEN 文件类型当前仍不支持 THEN System SHALL 返回明确原因，而不是静默失败。

### 需求 2：系统必须提供统一但可扩展的预览类型模型

**用户故事：** 作为维护者，我希望后端和前端都能明确知道“这是什么预览”，这样后续加新格式时不用继续堆特殊分支。

#### 验收标准

1. WHEN 服务端返回预览结果 THEN System SHALL 明确返回预览类型，而不是只区分文本和二进制。
2. WHEN 前端接收预览结果 THEN System SHALL 按预览类型选择对应查看器，而不是继续用文件扩展名硬编码到处判断。
3. WHEN 未来新增 `Office` 或其他格式 THEN System SHALL 可以在不推翻当前模型的前提下扩展。

### 需求 3：文件预览模态框必须支持调整尺寸

**用户故事：** 作为查看大文件、大图和 PDF 的用户，我希望预览弹层尺寸能调整，而不是永远被固定大小卡死。

#### 验收标准

1. WHEN 用户打开文件预览 THEN System SHALL 提供合理默认尺寸，保证常用场景开箱可看。
2. WHEN 用户需要更大或更小的查看区域 THEN System SHALL 支持调整模态框尺寸。
3. WHEN 用户切换不同文件 THEN System SHALL 维持一致的尺寸交互规则，不允许某些格式能调、某些格式完全不能调。

### 需求 4：系统必须根据文件格式展示不同工具按钮

**用户故事：** 作为用户，我希望看文本、看图片、看 PDF 时拿到真正有用的工具，而不是一堆无关按钮。

#### 验收标准

1. WHEN 用户查看文本类文件 THEN System SHALL 展示与编辑、刷新、切换视图相关的工具按钮。
2. WHEN 用户查看图片 THEN System SHALL 展示与缩放、适配视图、打开原图相关的工具按钮。
3. WHEN 用户查看 PDF THEN System SHALL 展示与分页、缩放、适配视图、外部打开相关的工具按钮。
4. WHEN 某个工具当前格式不支持 THEN System SHALL 不显示该按钮，或明确置灰并说明原因。

### 需求 5：系统不能破坏现有文件查看和保存行为

**用户故事：** 作为现有用户，我希望这次增强不会把已经能用的文本查看、编辑、保存流程搞坏。

#### 验收标准

1. WHEN 用户继续打开文本文件 THEN System SHALL 保持现有预览、编辑、保存能力可用。
2. WHEN 用户保存文本文件 THEN System SHALL 继续使用既有版本冲突保护链路。
3. WHEN 新增图片和 PDF 预览后 THEN System SHALL 不影响现有 HTML、Markdown 和代码文本的基本行为。

### 需求 6：系统必须为未来扩展预留预览提供者接口

**用户故事：** 作为后续维护者，我希望未来加 Office 或插件化预览时，不需要再推翻这一轮设计。

#### 验收标准

1. WHEN 定义本轮预览架构 THEN System SHALL 预留预览提供者扩展点。
2. WHEN 后续新增新格式 THEN System SHALL 可以通过增加 provider 或 viewer 的方式接入。
3. WHEN 当前不实现某个格式 THEN System SHALL 在设计上清楚标明未来接入位置。

### 需求 7：系统必须维持本地预览的安全边界和性能下限

**用户故事：** 作为维护者，我希望预览增强后不会把本地文件默认送出网，也不会在常见场景下慢到不可用。

#### 验收标准

1. WHEN 预览本地工作区文件 THEN System SHALL 默认只走本地受控链路，不依赖第三方在线服务。
2. WHEN 用户打开常见大小的文本、图片、PDF 文件 THEN System SHALL 在可接受时延内展示首屏内容。
3. WHEN 文件超出当前支持上限 THEN System SHALL 给出明确提示和可理解退路。

## 非功能需求

### 非功能需求 1：兼容性

1. WHEN 本轮增强上线 THEN System SHALL 兼容当前 `spec004` 的文件查看和保存接口，不强迫前后端同时推翻重写。
2. WHEN 桌面端和 H5 复用同一套文件查看器 THEN System SHALL 保持核心交互一致。

### 非功能需求 2：可维护性

1. WHEN 后续继续扩更多格式 THEN System SHALL 能在预览类型模型和工具注册表上继续扩展。
2. WHEN 排查预览问题 THEN System SHALL 能从日志或错误码看出是哪类预览、哪条链路出错。

### 非功能需求 3：安全性

1. WHEN 处理本地文件预览 THEN System SHALL 保持工作区路径边界校验不变。
2. WHEN 未来接插件化预览 THEN System SHALL 能区分本地内置预览和可能出网的外部预览。

## 成功定义

- 用户在文件管理里能直接预览 `TXT / PDF / 图片` 这些高频格式。
- 预览模态框不再是固定死尺寸，而是真能根据内容调整查看空间。
- 工具按钮不再一刀切，而是按文件格式提供更合适的操作。
- 本轮增强不破坏现有文本编辑和保存链路。
- `Office` 预览虽然还没做，但扩展入口已经留好，不需要下一轮再推翻架构。

# 需求文档 - spec013.1-代码管家控制面对话与聚合上下文

状态：Draft

## 简介

`spec013` 已经把代码管家的项目、会话、记忆、巡视、验证这些平台层对象立起来了，但还缺最关键的一层：

- 谁来把这些事实串起来
- 谁来用“管家”的身份和用户持续沟通
- 谁来决定是解释项目现状、续接某个项目会话，还是发起巡视和验证

如果这层没有单独建模，最后会退化成两种垃圾方案：

1. 前端加一个“管家”按钮，背后其实还是普通项目会话
2. 把几张表直接糊进 prompt，当成“全局管家”

这两种方案都不行。

真正需要的是一个独立的控制面会话：

- 它有自己的工作目录
- 它有自己的 `AGENTS.md`
- 它有用户手动设置的人格、说话方式、汇报重点和工作边界
- 它读的是平台聚合后的项目上下文，不是某个项目会话的局部视角
- 它能以“管家”的身份去解释、调度、续接项目工作

## 可实现性结论

### 结论

这个能力 **值得做，而且必须单独做**。

它不能靠复用现有项目会话接口硬拼，因为项目执行会话和管家控制会话的职责完全不同。

### 已确认事实

1. 当前 `apps/host` 已经有 `ButlerProject`、`ButlerSession`、`ProjectMemory`、`PatrolPlan`、`PatrolRun`、`VerificationRun` 等权威对象。
2. 当前 `apps/host` 已经有 butler 路由，但没有独立的控制面聊天 API。
3. 当前 `apps/user-app` 还没有“管家”主入口，也没有独立的 butler 工作台页面。
4. 当前会话前端和 Host runtime 已经具备创建会话、发送消息、续接会话的基础链路，可以复用到控制面会话实现。

### 平台判断

- ✅ 值得做：这是代码管家真正“像管家”的核心补全，不是装饰性 UI
- ✅ 能落地：`spec013` 已把事实层对象和后端底座铺好了
- ❌ 不能偷懒：不能把某个项目会话直接包装成管家聊天

## 术语表

- **ButlerProfile（管家档案）**：代码管家自身的初始化配置，包含 provider、工作目录、指令文件、人格、沟通偏好、工作重点等
- **ButlerWorkspace（管家工作目录）**：管家控制会话使用的独立目录，不等于某个项目仓库目录
- **ButlerControlSession（管家控制会话）**：独立于项目执行会话的对话会话，负责汇总、解释、调度和续接
- **ButlerContextSnapshot（管家上下文快照）**：按固定分层聚合后的项目状态、会话状态、记忆、巡视、验证摘要
- **ContextAggregator（上下文聚合器）**：负责把底层平台对象加工成适合管家会话消费的分层上下文
- **Control Action（控制动作）**：管家控制会话允许触发的明确动作，如续接项目会话、创建巡视、创建验证、读取项目详情

## 范围说明

### In Scope

- 定义 `ButlerProfile` 初始化模型与初始化流程
- 定义 `ButlerControlSession` 生命周期与独立聊天接口
- 定义 `ButlerContextSnapshot` 的分层聚合结构
- 定义控制面可触发的动作协议
- 定义管家工作台前端入口、页面结构和 provider 切换规则
- 定义 provider 切换清空当前控制会话上下文的规则

### Out of Scope

- 直接实现浏览器验证与视觉验证执行器细节
- 直接实现自动写代码审批流
- 让管家控制会话替代现有 `ButlerSession`
- 把项目执行日志完整镜像到控制会话消息里

## 技术边界

### 边界 1：管家控制会话不是项目执行会话

- 项目执行会话负责具体开发、巡视、验证
- 管家控制会话负责汇总、解释、调度、续接
- 两者可以关联，但不能混为一个表对象

### 边界 2：管家上下文必须先聚合，再注入会话

- 不能把数据库原始记录直接拼成大 prompt
- 必须先做事实层、摘要层、行动层的分层聚合

### 边界 3：管家初始化必须手动完成

- provider、工作目录、`AGENTS.md`、人格、工作重点这些配置必须显式设置
- 系统不能在未初始化时偷偷使用默认值直接开跑

### 边界 4：provider 切换等于控制会话切换

- 当前控制会话与当前 provider 强绑定
- 切换 provider 后，原控制会话上下文必须清空，防止把 `Codex` 和 `Claude Code` 的控制链路混在一起

### 边界 5：不能破坏现有 butler 事实模型

- 新能力是压在 `spec013` 之上的控制层
- 不能推翻现有项目、记忆、巡视、验证模型

## 需求

### 需求 1：系统必须提供代码管家初始化能力

**用户故事：** 作为使用者，我希望第一次启用代码管家时，可以手动设置它的 provider、工作目录、`AGENTS.md`、沟通风格和工作重点，这样它才真的是“我的管家”，不是一个无人格的默认助手。

#### 验收标准

1. WHEN 用户第一次启用代码管家 THEN System SHALL 要求完成初始化，而不是直接创建聊天会话。
2. WHEN 用户完成初始化 THEN System SHALL 持久化 `ButlerProfile`，至少记录 `providerId`、工作目录、`AGENTS.md` 内容或引用、人格配置、沟通偏好、工作重点和更新时间。
3. WHEN 用户未完成初始化 THEN System SHALL 拒绝启动控制会话，并返回明确原因。

### 需求 2：系统必须提供独立的管家控制会话

**用户故事：** 作为使用者，我希望和“管家”对话时，对方知道的是整个代码管家平台的状态，而不是某一个项目会话的局部上下文。

#### 验收标准

1. WHEN 用户启动管家对话 THEN System SHALL 创建或续接 `ButlerControlSession`，而不是直接创建普通项目会话。
2. WHEN 管家控制会话启动 THEN System SHALL 在独立的管家工作目录中运行，并使用管家自己的指令上下文。
3. WHEN 用户发送消息 THEN System SHALL 将消息路由到控制会话，而不是默认发送到某个项目执行会话。

### 需求 3：系统必须按分层结构聚合代码管家上下文

**用户故事：** 作为使用者，我希望管家回答项目情况时是有条理的，而不是把一堆原始记录原封不动倒给我。

#### 验收标准

1. WHEN 系统构造管家上下文 THEN System SHALL 分层聚合项目、会话、记忆、巡视、验证信息。
2. WHEN 管家需要解释项目情况 THEN System SHALL 优先使用聚合后的摘要层，而不是直接扫描原始表记录。
3. WHEN 用户明确追问某个项目、某个会话或某次巡视验证 THEN System SHALL 能下钻到对应事实层详情。

### 需求 4：系统必须支持以“管家”身份解释项目、会话、记忆、巡视、验证状态

**用户故事：** 作为使用者，我希望直接问“现在哪个项目最危险”“这个项目卡在哪”“最近验证为什么失败”，管家就能回答，而不是让我自己切五个页面去找。

#### 验收标准

1. WHEN 用户询问全局状态 THEN System SHALL 能回答项目优先级、主要风险、阻塞项和最近动作。
2. WHEN 用户询问项目状态 THEN System SHALL 能回答该项目的会话、记忆、巡视、验证和下一步建议。
3. WHEN 信息不足 THEN System SHALL 明确指出缺口，而不是编造状态。

### 需求 5：系统必须支持管家身份下的控制动作

**用户故事：** 作为使用者，我希望在和管家对话时，不只是听总结，还能让它继续做事，比如续接某个项目会话、发起巡视或发起验证。

#### 验收标准

1. WHEN 用户要求续接某个项目会话 THEN System SHALL 通过控制动作调用对应 butler 会话续接入口。
2. WHEN 用户要求发起巡视或验证 THEN System SHALL 通过控制动作调用对应 butler 运行入口。
3. WHEN 控制动作执行完成 THEN System SHALL 把结果回写到控制会话时间线和相关 butler 对象。

### 需求 6：系统必须限制控制会话 provider 为 `codex` 或 `claude-code`

**用户故事：** 作为维护者，我希望第一阶段只允许两家已经正式支持的 provider 参与管家控制会话，避免能力边界继续扩散。

#### 验收标准

1. WHEN 用户选择控制会话 provider THEN System SHALL 只允许 `codex` 或 `claude-code`。
2. WHEN 用户尝试使用其他 provider THEN System SHALL 返回明确的不支持错误。
3. WHEN provider 能力缺失 THEN System SHALL 明确提示，而不是静默降级成未知行为。

### 需求 7：系统必须在 provider 切换时清空当前管家对话上下文

**用户故事：** 作为使用者，我希望切换 `Codex` 和 `Claude Code` 时，旧的控制会话不会残留，避免不同 provider 的上下文、策略和历史混在一起。

#### 验收标准

1. WHEN 用户切换控制会话 provider THEN System SHALL 清空当前前端对话视图状态。
2. WHEN 用户切换控制会话 provider THEN System SHALL 不复用上一个 provider 的控制会话上下文。
3. WHEN 用户再次开始对话 THEN System SHALL 基于新 provider 创建新的控制会话。

### 需求 8：系统必须在前端工作台提供正式的“管家”入口和工作台

**用户故事：** 作为使用者，我希望在主工作台左侧能直接进入“管家”，并在一个地方完成对话和查看管家全局信息。

#### 验收标准

1. WHEN 桌面工作台渲染左侧导航 THEN System SHALL 在“终端”和“搜索”之间展示“管家”入口。
2. WHEN 用户进入“管家”页面 THEN System SHALL 在中间主区域同时提供对话区和管家信息区。
3. WHEN 管家信息区渲染 THEN System SHALL 能查看项目、会话、记忆、巡视、验证五类信息。

### 需求 9：系统必须保留审计与兼容边界

**用户故事：** 作为维护者，我希望新增控制会话后，仍然能知道谁触发了什么动作，而且不把现有主项目流程打坏。

#### 验收标准

1. WHEN 控制会话创建、续接、发送消息或触发动作 THEN System SHALL 记录审计事件。
2. WHEN 用户不进入“管家”模块 THEN System SHALL 维持现有工作区、会话、巡视、验证主链路不变。
3. WHEN 控制会话或聚合失败 THEN System SHALL 将影响限制在管家控制面范围内。

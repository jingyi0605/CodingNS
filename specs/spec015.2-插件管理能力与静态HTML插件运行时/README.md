# spec015.2-插件管理能力与静态HTML插件运行时

## 这份 Spec 现在解决什么问题

`CodingNS` 现在已经有：

- 工作区
- Host API
- CLI
- 助手能力面
- `office.browser`
- `desktop` 桌面壳桥接
- HTML 预览能力
- 后台任务与自动化基础

但现在缺一块正式能力：

**插件系统。**

这里说的插件，不是“再塞几个前端页面”，也不是“给 HTML 预览多开几个按钮”，而是：

1. 允许一个插件提供静态 HTML 前端
2. 允许插件可选提供 Node.js 后端脚本
3. 允许插件被动态注册、启用、禁用
4. 允许插件把能力以正式 API / CLI / 自动化任务的方式暴露给系统
5. 保证插件运行时有明确的工作区边界和权限边界

一句人话：

这份 Spec 要把 `CodingNS` 从“有零散 HTML 预览和桌面桥的系统”，推进成“**有正式插件管理能力和受控插件运行时的系统**”。

## 这次计划覆盖什么

- 定义插件的正式对象模型：清单、启用状态、权限、动作、调度、运行记录
- 定义静态 HTML 插件前端运行时，与普通 HTML 预览严格区分
- 定义 Node.js 插件后端动作模型，默认按需拉起，不常驻
- 定义 Host 层统一插件网关，而不是让每个插件私长路由和私长命令
- 定义插件调度与自动化接入方式，复用现有后台任务体系
- 定义插件安全模型：工作区隔离、权限声明、CSP、iframe sandbox、桌面能力收口、审计
- 定义前端插件容器、插件管理界面和插件调用协议
- 明确 `apps/desktop`、`apps/host`、`apps/user-app`、`packages/codingns` 的职责边界

## 这次明确不做什么

- 不把普通 HTML 文件预览直接等同于插件运行时
- 不允许插件直接拿到 `Tauri` 原生特权
- 不允许插件前端直接调用本地脚本或本地绝对路径
- 不把插件系统的核心放进 `apps/desktop` Rust 壳里
- 不为每个插件真的动态注册一堆不可控的 Fastify 路由和 CLI 子树
- 第一阶段不支持“任意第三方 npm 包在线安装后立即执行”的开放市场模式
- 第一阶段不默认支持插件常驻守护进程

## 为什么现在就要立这个 Spec

因为如果不先把边界写死，后面一定会烂成这样：

1. HTML 预览页偷偷变成插件页
2. 插件页偷偷拿到桌面壳能力
3. 不同插件各自长私有 API、私有脚本入口、私有定时器
4. 跨工作区文件读取和路径越权慢慢漏出来
5. Host、Desktop、前端三边各自加一层临时判断，最后没人说得清权限边界

这不是“后面再加安全策略”能补救的。必须先把模型定死。

## 硬边界先写死

### 插件前端

- 插件前端可以是静态 HTML
- 静态 HTML 可以是“仅前端插件”
- 但插件前端不是普通文档，不得直接复用普通 HTML 预览安全模型
- 插件前端必须运行在受控插件容器中

### 插件后端

- 插件后端默认是 Node.js 脚本动作
- 默认按需拉起，执行完成即退出
- 非必要不常驻
- 只有显式声明且被系统允许时，才可进入守护模式

### 插件管理落点

- 插件注册、启用/禁用、权限、动作、调度、审计必须落在 Host 层
- `desktop` 只提供受控桌面桥接，不承担插件业务中枢
- CLI 只提供统一插件命令入口，不为每个插件写死命令树

### 工作区边界

- 静态 HTML 插件只能访问当前工作区
- 决不允许跨工作区查看或操作文件
- 插件不得自由指定 `workspaceId`
- 所有文件访问最终都必须经过正式工作区路径守卫

### 安全边界

- 插件前端不能直接访问 `window.__TAURI_INTERNALS__`
- 插件前端不能直接访问 `window.CodingNSDesktop`
- 插件前端只能通过受控插件桥或 Host API 请求能力
- 插件权限必须显式声明，默认最小权限

# 需求文档 - spec015.2-插件管理能力与静态HTML插件运行时

状态：Draft

## 简介

当前 `CodingNS` 已经具备 HTML 预览、桌面壳桥接、Host API、CLI、后台任务和自动化基础，但仍缺少正式的插件管理与插件运行时。

这次新增需求不是“给 HTML 页面加几个后门接口”，而是建立一套正式插件体系：

1. 插件前端可以是静态 HTML
2. 插件可以只有前端，也可以附带 Node.js 后端
3. 插件后端默认按需执行，不常驻
4. 插件能力通过正式 Host API / CLI / 自动化任务统一暴露
5. 插件必须严格受工作区边界和安全边界约束

这里最关键的一句边界是：

**静态 HTML 插件前端是受控插件程序，不是普通 HTML 文件预览。**

## 可实现性结论

### 结论

这件事 **值得做，而且必须做成 Host 主导、Desktop 收口、前端受控的插件体系**。

### 原因

1. `CodingNS` 已经有 Host API、后台任务、自动化、文件访问守卫、工作区会话和桌面桥基础，不是从零开始。
2. 当前真实需求已经出现：静态 HTML 需要受控运行，并且要能调用系统能力。
3. 如果继续把插件能力散落在 HTML 预览、桌面桥和脚本入口里，后面一定会出现权限边界混乱和跨工作区越权。

### 当前已确认事实

1. `apps/desktop` 当前更适合作为桌面能力壳与桥，不适合作为插件业务中枢。
2. `apps/host` 已经是系统 API、任务和服务注册的中心，适合承载插件管理主逻辑。
3. 当前 HTML 预览能力允许脚本执行，但它不是正式的插件安全沙箱。
4. 当前系统已经存在工作区范围的认证、路径守卫和能力作用域概念，可复用到插件系统。
5. 当前桌面端已实现打开本地文件、打开所在目录等能力，但这些能力必须在插件场景下进一步收口。

## 术语表

- **System**：`CodingNS`
- **插件（Plugin）**：由清单、前端资源、可选后端动作、权限声明和运行配置组成的扩展单元
- **插件清单（Plugin Manifest）**：描述插件标识、版本、前端入口、后端动作、权限和调度声明的结构化文件
- **静态 HTML 插件前端**：在受控插件容器中运行的 HTML/CSS/JavaScript 前端程序
- **插件动作（Plugin Action）**：由插件后端暴露的一个正式执行入口
- **插件网关（Plugin Gateway）**：Host 提供的统一 API / CLI 分发层
- **插件权限（Plugin Permission）**：插件显式声明并被系统裁决后的能力集合
- **插件运行记录（Plugin Run）**：插件动作或调度执行产生的正式记录
- **普通 HTML 预览**：面向文件查看的受限渲染能力，不等同于插件运行时

## 范围说明

### In Scope

- 插件清单模型与插件注册表
- 插件启用 / 禁用机制
- 静态 HTML 插件前端运行时
- 支持“仅前端插件”和“前端 + Node.js 后端插件”
- 插件统一 API / CLI 网关
- 插件动作执行、结果回执、运行记录
- 插件自动化调度与正式后台任务接入
- 插件权限模型与工作区隔离模型
- 插件资源托管、插件容器、插件桥接协议
- 桌面能力在插件场景下的受控暴露

### Out of Scope

- 第一阶段开放任意第三方远程插件市场
- 第一阶段支持插件直接安装任意系统依赖
- 直接把普通 HTML 预览页升级成高权限插件页
- 第一阶段支持插件自定义原生桌面命令
- 第一阶段支持插件长期常驻多进程编排
- 第一阶段支持跨工作区联合读写

## 技术边界

### 边界 1：插件系统必须由 Host 统一管理

- 插件注册、启用/禁用、动作分发、调度、审计必须由 Host 层统一管理
- `desktop` 只负责受控桌面桥接和本地壳能力
- 不允许把插件运行时核心逻辑下沉到 `Tauri Rust` 层

### 边界 2：静态 HTML 插件前端不等于普通 HTML 预览

- 普通 HTML 预览是文件查看能力
- 静态 HTML 插件前端是受控应用能力
- 两者必须使用不同的资源托管、不同的权限模型和不同的安全策略

### 边界 3：插件前端不能直接拿宿主高权限

- 插件前端不能直接访问 `Tauri` 原生桥
- 插件前端不能直接访问宿主登录态、内部 token、私有存储或桌面桥对象
- 插件前端只能通过受控插件桥或受控 Host API 请求能力

### 边界 4：插件后端默认按需拉起，不常驻

- 插件后端默认以 Node.js 脚本动作为基本单位
- 调用时拉起进程，完成后退出
- 守护进程模式必须显式声明，并由系统额外批准

### 边界 5：插件只能访问当前工作区

- 插件运行上下文必须绑定当前工作区
- 插件不得自行指定其他 `workspaceId`
- 插件所有文件查看、预览、打开、导出、操作都仅允许作用于当前工作区
- 所有路径解析必须经过正式工作区路径守卫

### 边界 6：动态能力通过稳定网关分发，不通过动态改系统结构实现

- API 层使用稳定插件网关路由
- CLI 层使用稳定插件命令入口
- 不通过“为每个插件动态热插 Fastify 路由树和命令树”的方式实现动态能力

## 需求

### 需求 1：系统必须提供正式插件清单与注册表

**用户故事：** 作为维护者，我希望每个插件都有正式描述和正式注册状态，而不是靠约定俗成的文件夹和脚本拼接。

#### 验收标准

1. WHEN 系统发现插件目录 THEN System SHALL 读取正式插件清单，而不是猜测目录结构。
2. WHEN 插件被注册 THEN System SHALL 记录插件标识、版本、前端入口、动作定义、权限声明和状态。
3. WHEN 插件清单非法或不完整 THEN System SHALL 拒绝注册，并返回明确错误原因。
4. WHEN 插件被列出 THEN System SHALL 返回正式注册信息与当前启用状态。

### 需求 2：系统必须支持插件动态启用与禁用

**用户故事：** 作为维护者，我希望插件可以动态启用和禁用，而不是每次都靠改代码或重启整个系统切换。

#### 验收标准

1. WHEN 维护者启用插件 THEN System SHALL 将插件状态切换为已启用，并允许其前端和动作被访问。
2. WHEN 维护者禁用插件 THEN System SHALL 拒绝该插件后续动作调用，并停止其调度任务。
3. WHEN 插件被禁用 THEN System SHALL 不要求删除插件文件。
4. WHEN 插件状态变更 THEN System SHALL 记录操作者、时间和结果。

### 需求 3：系统必须支持静态 HTML 插件前端运行时

**用户故事：** 作为插件开发者，我希望插件可以只提供一个静态 HTML 前端，并在 `CodingNS` 内被正式运行，而不是被当成普通 HTML 文件胡乱预览。

#### 验收标准

1. WHEN 插件声明静态 HTML 前端入口 THEN System SHALL 在正式插件容器中加载它。
2. WHEN 插件只有前端没有后端 THEN System SHALL 仍允许该插件被注册、启用和展示。
3. WHEN 插件前端运行 THEN System SHALL 使用插件专用资源托管与运行时隔离策略。
4. WHEN 插件前端请求宿主能力 THEN System SHALL 通过受控插件桥或正式 Host API 处理，而不是直接暴露宿主全权限对象。

### 需求 4：系统必须支持 Node.js 插件后端动作

**用户故事：** 作为插件开发者，我希望插件可以提供一个或多个 Node.js 脚本动作，供前端、CLI 或自动化调用。

#### 验收标准

1. WHEN 插件声明后端动作 THEN System SHALL 能按清单定义执行对应 Node.js 入口脚本。
2. WHEN 插件动作被调用 THEN System SHALL 默认按需拉起进程，执行完成后退出。
3. WHEN 插件动作执行 THEN System SHALL 记录输入摘要、输出结果、退出状态和错误信息。
4. WHEN 插件动作超时或失败 THEN System SHALL 返回正式错误，不得静默失败。

### 需求 5：系统必须通过统一插件网关暴露动态能力

**用户故事：** 作为维护者，我希望插件能力通过统一网关暴露，而不是每个插件都偷偷改系统路由和命令分发。

#### 验收标准

1. WHEN 前端调用插件能力 THEN System SHALL 通过正式插件 API 网关路由处理。
2. WHEN CLI 调用插件能力 THEN System SHALL 通过正式插件 CLI 入口分发。
3. WHEN 插件新增动作 THEN System SHALL 无需为该插件手写独立系统级路由和命令模块。
4. WHEN 插件被禁用 THEN System SHALL 统一网关层拒绝其调用。

### 需求 6：系统必须支持插件自动化与定期执行

**用户故事：** 作为使用者，我希望插件可以接入 `CodingNS` 的自动化体系，定期生成数据或执行受控任务，而不是自己偷偷长私有定时器。

#### 验收标准

1. WHEN 插件声明定时动作 THEN System SHALL 将其注册到正式后台任务与调度体系。
2. WHEN 调度触发插件动作 THEN System SHALL 生成正式运行记录。
3. WHEN 插件被禁用 THEN System SHALL 停止其后续调度触发。
4. WHEN 插件需要重试或失败补偿 THEN System SHALL 复用正式后台任务策略，而不是私长新的调度循环。

### 需求 7：系统必须强制插件只作用于当前工作区

**用户故事：** 作为维护者，我希望插件绝不允许跨工作区查看或操作文件，避免插件把工作区边界打穿。

#### 验收标准

1. WHEN 插件运行于某工作区上下文 THEN System SHALL 将其能力范围绑定到该工作区。
2. WHEN 插件请求文件查看、预览、打开、导出或脚本动作 THEN System SHALL 只允许访问当前工作区资源。
3. WHEN 插件试图指定其他 `workspaceId` 或越出当前工作区 THEN System SHALL 拒绝请求并记录审计日志。
4. WHEN 插件请求桌面文件操作 THEN System SHALL 只允许处理解析后位于当前工作区内的受控路径。

### 需求 8：系统必须为插件提供正式权限模型与最小授权机制

**用户故事：** 作为维护者，我希望每个插件的能力边界是声明式、可审计、默认最小权限的，而不是先放开再补洞。

#### 验收标准

1. WHEN 插件被注册 THEN System SHALL 读取并校验其权限声明。
2. WHEN 插件未声明某项能力 THEN System SHALL 默认拒绝该能力。
3. WHEN 插件请求高风险能力 THEN System SHALL 要求显式授权或直接拒绝。
4. WHEN 插件能力被执行 THEN System SHALL 能关联到对应权限声明和审计记录。

### 需求 9：系统必须对静态 HTML 插件前端实施运行时安全限制

**用户故事：** 作为维护者，我希望静态 HTML 插件前端即使运行脚本，也只能在受控沙箱里活动，不能借机拿走宿主权限或外发敏感数据。

#### 验收标准

1. WHEN 插件前端被加载 THEN System SHALL 使用受控 iframe sandbox、CSP 和消息通道校验策略。
2. WHEN 插件前端运行 THEN System SHALL 不直接暴露宿主桌面桥、原生桥或内部 token。
3. WHEN 插件前端需要调用宿主能力 THEN System SHALL 通过受控插件桥转发并执行权限校验。
4. WHEN 插件前端尝试越权访问受限资源 THEN System SHALL 阻止该访问。

### 需求 10：系统必须提供插件相关桌面能力的受控中介

**用户故事：** 作为使用者，我希望插件在必要时可以调用“打开文件”“打开所在目录”等桌面动作，但这些动作必须受系统控制，而不是前端直接调用本地 API。

#### 验收标准

1. WHEN 插件请求桌面动作 THEN System SHALL 通过 Host 或受控插件桥中介执行。
2. WHEN 插件请求打开文件或目录 THEN System SHALL 对目标路径执行当前工作区边界校验。
3. WHEN 插件无相应权限 THEN System SHALL 拒绝桌面动作调用。
4. WHEN 桌面动作执行成功或失败 THEN System SHALL 记录正式调用结果。

### 需求 11：系统必须区分普通 HTML 预览与插件运行时

**用户故事：** 作为维护者，我希望普通 HTML 文件预览继续存在，但不能因为引入插件系统而被隐式升级成高权限运行时。

#### 验收标准

1. WHEN 用户打开普通 HTML 文件预览 THEN System SHALL 继续使用普通预览链路，而不是自动当成插件运行。
2. WHEN 插件前端运行 THEN System SHALL 使用独立的插件资源托管和运行时链路。
3. WHEN 两类链路都存在 THEN System SHALL 明确区分其权限、CSP、sandbox 与能力暴露方式。
4. WHEN 插件系统上线 THEN System SHALL 不破坏现有普通文件预览和文件查看主流程。

### 需求 12：系统必须提供插件运行的可观测性与审计能力

**用户故事：** 作为维护者，我希望插件出了问题时能知道是谁启用了什么、跑了什么动作、读了什么范围、为什么失败。

#### 验收标准

1. WHEN 插件被注册、启用、禁用、执行动作或触发调度 THEN System SHALL 记录正式事件与时间线。
2. WHEN 插件动作失败 THEN System SHALL 保留错误详情、退出状态和必要运行日志。
3. WHEN 发生越权或越界请求 THEN System SHALL 记录拒绝原因和上下文。
4. WHEN 维护者查看插件详情 THEN System SHALL 可查看插件状态、权限、最近运行记录和调度状态。

## 非功能需求

### 非功能需求 1：安全性

1. WHEN 插件前端运行 THEN System SHALL 默认遵守最小权限原则。
2. WHEN 插件后端执行脚本 THEN System SHALL 实施超时、工作目录、环境变量和可访问路径控制。
3. WHEN 插件请求跨工作区访问 THEN System SHALL 拒绝，而不是靠前端自觉。

### 非功能需求 2：可维护性

1. WHEN 新增插件动作类型 THEN System SHALL 优先复用插件清单与统一网关，不得新增第二套插件模型。
2. WHEN 新增插件安全策略 THEN System SHALL 能通过统一权限层和统一运行时生效，而不是逐插件打补丁。

### 非功能需求 3：零破坏接入

1. WHEN 插件系统接入 THEN System SHALL 不破坏现有 HTML 预览主流程。
2. WHEN 插件系统接入 THEN System SHALL 不破坏现有 `office.browser`、桌面桥、工作区和自动化主链路。
3. WHEN 用户完全不使用插件系统 THEN System SHALL 保持现有体验不变。

## 成功定义

- `CodingNS` 具备正式插件清单、注册、启用/禁用和运行记录能力
- 静态 HTML 可作为正式插件前端运行，而不是滥用普通预览页
- Node.js 插件后端可按需执行并通过统一网关暴露给前端、CLI 和自动化
- 插件运行严格绑定当前工作区，不允许跨工作区文件访问或操作
- 插件前端无法直接拿到宿主高权限，桌面动作与 Host 能力通过受控中介暴露
- 现有普通 HTML 预览与现有主链路保持可用

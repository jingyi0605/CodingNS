# 工作区会话 MCP 人工验证链

这份文档只回答一件事：怎么确认工作区会话里挂上的 `office.document.* / office.browser.* / office.ops.*` 不是“写在说明里”，而是真的已经作为 MCP 工具对运行时可见。

## 先看结论

如果下面 4 件事同时成立，基本就说明这条链是通的：

1. 工作区会话对应的专用 runtime 目录已经生成
2. runtime 目录里已经写出了对应 CLI 的 MCP 配置
3. 当前工作区会话实际跑在这个 runtime 目录里
4. 真实提问时，模型能直接列出或调用 `office_*` MCP 工具，而不是再回答“当前没有浏览器能力”

## 一、先找到当前工作区会话的 runtime 目录

工作区会话的专用 runtime 目录现在统一放在 CodingNS 全局数据目录下，固定形态是：

```text
~/.codingns/host/workspace-session-runtime/<workspaceId>/<sessionId>/
```

例如一个真实会话目录会长成：

```text
/Users/你的用户名/.codingns/host/workspace-session-runtime/616060c6-fabc-49da-b69b-5606808aa87e/fa24d6a7-64cd-404b-99b1-2cef317082e5/
```

注意：

- 这里不再往工作区目录里写 `.codingns/workspace-session-runtime`
- 工作区目录现在只读 `AGENTS.md` 这类项目规则文件，不承载会话 runtime / MCP 资产

至少要看到这些文件之一：

- `WORKSPACE_SESSION_AUTH.json`
- `WORKSPACE_SESSION_COMPOSED.md`
- `config.toml`
- `.claude.json`
- `opencode.json`

如果这个目录都没有生成，后面的 MCP 就不用看了，说明工作区会话 runtime 根本没落下来。

## 二、确认配置文件里真的写了 MCP

### 1. Codex

看：

```text
<runtimeHomeDir>/config.toml
```

至少应包含：

- `[mcp_servers.codingns-workspace-office]`
- `workspace-office`
- `--auth-file`

### 2. Claude Code

看：

```text
<runtimeHomeDir>/.claude.json
```

至少应包含：

- `mcpServers.codingns-workspace-office`
- `workspace-office`

### 3. OpenCode

看：

```text
<runtimeHomeDir>/opencode.json
```

至少应包含：

- `mcp.codingns-workspace-office`
- `type: "local"`
- `command`
- `CODINGNS_OFFICE_MCP_AUTH_FILE`

这里的 `opencode.json` 不是摆设。现在 Host 在拉起托管 `opencode serve` 时，会直接把这份 JSON 读出来，塞进 `OPENCODE_CONFIG_CONTENT`。

## 三、确认工作区会话实际跑在这个 runtime 目录里

这一步很关键。只写配置文件不够，运行时如果继续读全局 home，一样等于没接。

### 1. Codex / Claude

直接检查工作区会话里生成的说明文件是否也在同一个 runtime 目录：

- `WORKSPACE_SESSION_COMPOSED.md`
- 或 `WORKSPACE_SESSION_ASSISTANT.md`

如果说明文件和 MCP 配置文件都在同一个 `<runtimeHomeDir>` 下，说明 Host 至少已经把这条工作区会话的专用 runtime 落出来了。

### 2. OpenCode server/baseUrl 模式

这一步要额外确认：

- 当前会话如果走的是托管 `opencode serve`
- 它不再只按 `workspacePath` 复用
- 而是按 `workspaceId + runtimeHomeDir` 隔离

也就是说：

- 同一个工作区的两个不同工作区会话
- 各自有不同 `runtimeHomeDir`
- 就会各自得到自己的托管 `opencode serve`

这样 scoped token 才不会串会话。

## 四、在工作区会话里做最小人工验证

下面这些验证要直接在“工作区普通会话”里问，不要在 Butler 助手会话里问。

### 验证 1：先确认工具是否可见

直接提问：

```text
请列出你当前可用的 office 相关 MCP 工具名称，只列工具名。
```

期望结果：

- 模型直接列出工具名
- 至少能看到这类名字：
  - `office_document_create`
  - `office_browser_profile_list`
  - `office_browser_task_create`
  - `office_ops_target_list`
  - `office_ops_ssh_task_create`

不符合预期的表现：

- 回答“当前没有浏览器能力”
- 回答“我需要先从源码里查 API”
- 只重复系统说明，不列工具名

这三种都说明工具还没真的进入当前 runtime。

### 验证 2：真实网页任务是否会优先走 office.browser

直接提问：

```text
请打开 https://example.com ，读取页面 DOM 结构摘要。
```

期望结果：

- 模型优先调用 `office_browser_profile_list`
- 没有可复用 Profile 时，再调用 `office_browser_profile_create`
- 然后调用 `office_browser_task_create`

不符合预期的表现：

- 一上来就说“没有浏览器能力”
- 退回去翻源码、猜接口、猜 payload
- 直接改用 Codex 自带 Browser 打真实站点

如果用户问的是 `localhost / 127.0.0.1 / ::1` 本地调试，这时优先走 Codex Browser 才是对的。

### 验证 3：运维工具是否可见

直接提问：

```text
请列出当前可用的运维工具名称，并说明哪个是查看主机、哪个是创建 SSH 任务。
```

期望结果：

- 能直接点出：
  - `office_ops_target_list`
  - `office_ops_target_create`
  - `office_ops_ssh_task_create`
  - `office_ops_task_get`
  - `office_ops_task_execute`

### 验证 4：文档工具是否可见

直接提问：

```text
请列出当前可用的文档工具名称，并说明创建文档和导出文档分别用哪个。
```

期望结果：

- 能直接点出：
  - `office_document_create`
  - `office_document_update`
  - `office_document_export`
  - `office_document_task_get`

## 五、如果是 OpenCode 托管模式，再补一条人工检查

如果当前 provider 是 `opencode`，再加一条检查：

1. 先找到本会话的 `<runtimeHomeDir>/opencode.json`
2. 确认里面存在 `codingns-workspace-office`
3. 再让工作区会话执行一个真实网页任务
4. 如果模型能直接列出或调用 `office_browser_*`，说明托管 `opencode serve` 已经吃到了这份运行时配置

这里最核心的判断标准不是“文件存在”，而是：

- 工作区会话不再回答“没有浏览器能力”
- 而是直接把 `office_browser_*` 当正式工具来用

## 六、失败时优先排查什么

按顺序查：

1. 是否真的进入了工作区普通会话，而不是助手会话
2. 当前会话的 runtime 目录是否存在
3. runtime 目录里的 MCP 配置文件是否存在
4. 当前 provider 是否真的跑在这个 runtime 目录下
5. 如果是 OpenCode，是否命中了旧的非工作区托管 server

只要第 4 或第 5 步没过，前面配置文件写得再漂亮也没用。

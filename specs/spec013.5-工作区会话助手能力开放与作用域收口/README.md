# spec013.5-工作区会话助手能力开放与作用域收口

## 当前定位

`spec013.2` 已经把 `codingns assistant ...` 和 `/api/assistant/*` 这套助手能力门面做出来了，`spec013.4` 也已经把“谁算助手运行时”这件事收口到正式调用者身份上。

但现在还有一个更现实的问题没解决：

- 工作区里的普通会话，已经越来越需要调用一部分正式助手能力
- 用户明确希望把文档、浏览器、运维、工作树、当前工作区终端这些能力开放给工作区会话
- 但如果直接把整套 `codingns assistant` 全放进去，工作区会话就会顺手拿到不该拿的跨工作区、跨会话、审批回执、自动化编排和高风险执行入口
- 最后就会重新回到老路：能力看起来都在，边界全靠 prompt 撑着

一句人话：

这一步不是“让工作区会话也能随便调助手”，而是把该开放的能力正式开放，把不该开放的能力明确挡住，并且让工作区会话拿到的是带作用域的受控入口。

## 计划覆盖

- 定义 `workspace_session` 这种新的调用者档位
- 定义工作区会话默认能用、条件能用、暂不开放的助手能力清单
- 给工作区会话下发带 `workspaceId / projectId / capabilityProfile` 的 scoped token
- 让 `/api/assistant/capabilities` 和真实执行入口都按作用域过滤，而不是只给文案提示
- 给工作区会话补一层能力说明，让模型知道什么时候该调用哪些 `assistant office` / `assistant terminal` / `assistant worktree` 能力
- 补 `terminals.create`，把“只能列终端、不能新建终端”的缺口补上

## 本阶段明确不做

- 不把所有 `codingns assistant` 命令无差别开放给工作区会话
- 不把工作区会话升级成 Butler 控制面替身
- 不在这一轮重写整套全局登录和权限系统
- 不靠“给提示词多写几段说明”冒充权限控制
- 不在这一轮做复杂 UI 编排，只先把 Host API、CLI、工作区会话提示和权限边界打通

# 开发版 Tag 与版本号规则

## 这份说明是干什么的

这份文档把稳定版和开发版的 tag 规则正式定死，让所有维护者知道：

- 开发版 tag 长什么样
- 开发版怎么递增
- 什么时候转正
- 哪些写法明确不推荐

## 核心规则

### 稳定版 tag

```
vX.Y.Z
```

例子：

- `v0.9.7`
- `v1.2.0`

触发条件：`VERSION` 文件里写的是纯 `X.Y.Z`，不带预发布标记。

### 开发版 tag

```
vX.Y.Z-beta.N
```

例子：

- `v0.9.8-beta.1`
- `v0.9.8-beta.2`
- `v0.9.8-beta.3`

触发条件：`VERSION` 文件里写的是 `X.Y.Z-beta.N`。

## 递增规则

当你准备下一个版本（比如 `v0.9.8`），按这个顺序发：

1. 先把 `VERSION` 改成 `0.9.8-beta.1`，跑 `sync-version.mjs`，推送 tag `v0.9.8-beta.1`
2. 修完反馈后，改成 `0.9.8-beta.2`，推送 tag `v0.9.8-beta.2`
3. 继续迭代 `beta.3`、`beta.4`，直到验证通过
4. 确认可以发稳定版后，改成 `0.9.8`，推送 tag `v0.9.8`

一句话：**同一个目标版本的 beta 序号递增，不跨版本号复用。**

## 通道判断规则

代码层面的判断是：

- tag 中包含 `-beta.` 的，归开发版
- 不带预发布标记的，归稳定版

这条规则决定了：

1. **稳定版用户检查更新时**：忽略带 `beta` 的 tag，只看不带预发布标记的正式版本
2. **开发版用户检查更新时**：可以收到更高的 `beta.N` 版本，也能收到后续正式版

先把“也能收到后续正式版”说成人话，别再靠猜：

- **服务端 npm 更新**：开发版通道现在会同时比较 `dist-tags.beta` 和 `dist-tags.latest`，哪个 semver 更高就选哪个。所以如果当前是 `1.0.0-beta.2`，远端同时有 `1.0.0-beta.3` 和 `1.0.0`，会选 `1.0.0`。
- **桌面客户端更新**：当前 `beta` 还复用 `stable` 的 `latest.json`，所以开发版桌面客户端也能看到后续正式版。但这不是因为桌面端已经有独立 beta 元数据源，而是因为现在两边还没拆开。
- **Android APK 更新**：现在 Host 只同步 `stable/android-apk.json`。如果后面真做 Android beta 通道，要补独立清单和同步逻辑，别假装已经有。

## 明确不推荐的写法

这些写法虽然 semver 规范部分允许，但在本项目里不推荐：

| 不推荐 | 原因 |
| --- | --- |
| `v0.9.8-beta1` | 少了点号，不统一 |
| `v0.9.8-beta-1` | 额外连字符，没必要 |
| `v0.9.8-dev` | 无法表达第几个预览版 |
| `beta-v0.9.8` | 不利于统一解析和排序 |
| `v2026.06.12-beta` | 把日期塞进主版本，后面维护会越来越乱 |

统一用 `vX.Y.Z-beta.N`，没有例外。

## 与发布工作流的关系

### GitHub Actions 桌面端发布

当前桌面端发布工作流的 tag 触发规则是：

```text
v*
```

这个规则已经覆盖 `v0.9.8-beta.1` 这类 tag。

**开发版 tag 推送后会触发同样的桌面端构建和 Release 发布流程**。这意味着：

- 开发版也会生成 GitHub Release
- 用户可以在 GitHub 上看到开发版产物
- 但稳定版用户不会收到开发版更新推送（因为通道过滤）

### `sync-version.mjs` 版本同步

`sync-version.mjs` 的版本校验正则已经接受 `-beta.N` 格式：

```js
/^\d+\.\d+\.\d+(?:-[0-9A-Za-z.-]+)?(?:\+[0-9A-Za-z.-]+)?$/
```

不需要修改 `sync-version.mjs`，现有的 `isValidSemver` 函数能正确校验 `0.9.8-beta.1` 这类版本号。

当前不做的事：

- 不给 `sync-version.mjs` 单独加 `-beta.N` 专用校验（通用 semver 校验已经够用）
- 不做 GitHub Release 对 beta tag 的特殊标记或隐藏（第一版先保持一致流程）

## Android 版本号规则

Android 的 `versionCode` 由 `sync-version.mjs` 从 semver 主版本号自动计算：

```
versionCode = major * 1_000_000 + minor * 1_000 + patch
```

当版本号是 `0.9.8-beta.1` 时：

- 主版本号部分取 `0.9.8`
- `versionCode = 0 * 1_000_000 + 9 * 1_000 + 8 = 9008`

注意：`beta.N` 不参与 `versionCode` 计算，同一个目标版本的多个 beta 在 Android 上会有相同的 `versionCode`。如果需要区分，后续再单独处理，第一版先不引入额外复杂性。

## 常见问题

### 开发版发现问题后是补 `beta.N+1` 还是直接提主版本号？

补 `beta.N+1`。例如 `v0.9.8-beta.1` 发现问题 → 修 → 发 `v0.9.8-beta.2`。

只有确认稳定版发布后才提主版本号。不要在 beta 阶段就把 `0.9.8` 提前占掉。

### 如果当前稳定版已经是 `v0.9.7`，下一个开发版应该叫什么？

如果下一版目标版本号是 `v0.9.8`，开发版就从 `v0.9.8-beta.1` 开始。

如果下一版目标版本号是 `v0.10.0`，开发版就从 `v0.10.0-beta.1` 开始。

规则：**开发版的目标版本号就是下一个计划中的稳定版版本号。**

### 开发版 tag 推送后，稳定版用户会收到更新吗？

不会。客户端和服务端更新检查都会根据用户设置的 `releaseChannel` 过滤版本。稳定版用户只会看到不带 `-beta.` 标记的 tag。

### 如果当前已经装的是 `v1.0.0-beta.2`，后面发了 `v1.0.0`，会不会提示更新？

分链路说，别混：

- **服务端 npm 更新**：会。现在开发版通道会在 `beta` 和 `latest` 之间选 semver 更高的那个，`1.0.0` 高于 `1.0.0-beta.2`，所以会提示并安装稳定版。
- **桌面客户端更新**：会。当前桌面端 beta 仍复用 stable 的 `latest.json`，所以也会看到 `v1.0.0`。
- **Android APK 更新**：当前文档不承诺这个能力，因为 Android beta 清单链路还没正式补齐。

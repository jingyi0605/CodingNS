# 设计文档 - spec001.12-更新通道与预览版本更新体验

状态：Draft

## 1. 概述

### 1.1 目标

- 把现有 `releaseChannel` 从内部字段补成用户可见、可理解、可切换的正式能力
- 保持通道模型简单，只保留 `stable / beta`
- 把开发版版本号和 tag 规则定成可以长期执行的发布纪律
- 把更新日志展示接进现有更新管理面板和模态框体系

### 1.2 覆盖需求

- `requirements.md` 需求 1：用户必须能在设置页明确选择更新通道
- `requirements.md` 需求 2：切换到开发版前必须先看风险说明并显式同意
- `requirements.md` 需求 3：开发版 tag 和版本号规则必须正式定下来
- `requirements.md` 需求 4：检查更新时如果目标版本带有更新内容，必须能查看更新日志
- `requirements.md` 需求 5：更新日志展示必须兼容客户端、Android 和服务端更新信息

### 1.3 技术约束

- 前端只改 `apps/user-app`
- 更新管理里的模态框必须遵守 `DesktopModal / MobileSheet` 和 `ModalAtoms` 规范
- 现有 `releaseChannel` 类型暂时仍为 `stable | beta`
- 现有更新检查主链路不重写，只在结果模型和设置交互上增量改造
- 现有 manifest 要继续兼容旧字段，不能因为新增说明字段把旧发布产物全部打坏

## 2. 架构

### 2.1 核心判断

这次不要重做更新机制，直接围绕已经存在的 `releaseChannel` 补三层东西：

1. **配置层**：让用户真的能改 `releaseChannel`
2. **发布层**：把 `beta` tag 的版本纪律定死
3. **展示层**：把更新日志接进现有更新面板

这才是最短路径。

### 2.2 模块职责

| 模块 | 职责 | 输入 | 输出 |
| --- | --- | --- | --- |
| `client-config-service` | 保存更新通道和开发版风险同意状态 | 本地运行时配置 patch | 持久化配置 |
| `settings software-update section` | 在设置页展示和切换更新通道 | 当前 runtime config | 通道设置 UI |
| `beta-channel-consent-modal` | 承载切换开发版前的说明和确认 | 目标通道 | 用户确认结果 |
| `release-manifest dto` | 扩展更新日志展示字段 | 发布清单 JSON | 客户端可读 manifest |
| `update-notes-modal` | 展示更新内容 | 版本号、标题、时间、正文 | 模态框 UI |
| `release publishing convention` | 定义稳定版 / 开发版 tag 规则 | 目标版本、发布阶段 | 统一 tag 命名 |

### 2.3 数据流

#### 2.3.1 更新通道切换流程

1. 设置页读取当前 `runtimeConfig.releaseChannel`
2. 用户选择目标通道
3. 如果目标是 `stable`，直接写入配置
4. 如果目标是 `beta`，先打开说明模态框
5. 用户显式同意后，再写入 `releaseChannel=beta`
6. 后续桌面端、Android、服务端检查更新时继续读取这个统一字段

#### 2.3.2 更新日志展示流程

1. 更新检查结果返回目标版本 manifest 或服务端目标版本元信息
2. 面板判断是否存在可展示的更新说明
3. 存在则显示“查看更新内容”按钮
4. 用户点击后打开统一更新日志模态框
5. 模态框展示标题、版本号、发布时间、正文

## 3. 数据与状态模型

### 3.1 客户端运行时配置扩展

现有 `ClientRuntimeConfig` 已有：

- `releaseChannel: "stable" | "beta"`

这次建议新增：

#### 3.1.1 `betaChannelConsentAcceptedAt`

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `betaChannelConsentAcceptedAt` | `string \| null` | 否 | 用户最近一次同意开发版风险说明的时间 |

设计要点：

- 这不是安全凭证，只是 UI 行为记录
- 第一版只保存在客户端本地运行时配置里，不做账户级同步
- 作用是避免用户每次已经在 `beta` 通道里还反复被弹确认

#### 3.1.2 为什么不单独再做复杂同意版本表

没必要。

这次真正要解决的是：

- 从稳定版切开发版前必须显式看说明

不是要做法律条款系统。

所以一个 `acceptedAt` 足够。再长更多状态就是垃圾复杂度。

### 3.2 统一更新说明模型

建议抽一个统一展示模型给前端 UI 使用：

#### 3.2.1 `UpdateNotesSummary`

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `version` | string | 是 | 目标版本号 |
| `title` | string | 否 | 更新标题，优先来自 release title |
| `publishedAt` | string | 否 | 发布时间 |
| `content` | string | 否 | 更新正文，支持纯文本或 markdown 字符串 |
| `channel` | `stable \| beta` | 是 | 对应更新通道 |
| `source` | `desktop \| android \| service` | 是 | 来源类型 |

前端面板不要直接耦合不同 manifest 结构，先在 manager 层规整成这一个东西。

### 3.3 现有 manifest / DTO 扩展

#### 3.3.1 客户端 manifest

现有 `ReleaseManifest` 已有：

- `title`
- `notes`
- `publishedAt`

桌面端这块基本够用，主要问题不是字段缺失，而是 UI 没有正式展示入口。

#### 3.3.2 Android manifest

现有 `AndroidApkManifest` 已有：

- `notes`
- `publishedAt`
- `htmlUrl`

Android 也有基础字段，重点同样是 UI 层统一展示。

#### 3.3.3 服务端更新 DTO

现有 `ManagedServicePackageInfo` 没有更新日志字段，建议补：

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `latestTitle` | `string \| null` | 否 | 目标版本标题 |
| `latestNotes` | `string \| null` | 否 | 目标版本说明 |
| `latestPublishedAt` | `string \| null` | 否 | 目标版本发布时间 |

为什么服务端要补：

- 否则更新日志只能客户端能看，服务端更新仍然是黑箱
- 第一版允许拿不到这些字段，但 DTO 结构先留出来

## 4. 交互设计

### 4.1 设置页更新通道入口

建议放在设置页 `software-update` 分组，和自动检查更新、自动下载更新并列，而不是藏到别的页面。

桌面 / 移动端都遵守同一条规则：

- 标题：更新通道
- 说明：决定你会收到稳定版还是开发版更新
- 当前值：稳定版 / 开发版
- 切换控件：优先用单选或分段选择，不要搞花哨下拉

### 4.2 开发版切换说明模态框

#### 4.2.1 组件规则

- 桌面端：`DesktopModal`
- 移动端：`MobileSheet`
- 内容结构：`ModalSection + ModalActions`

#### 4.2.2 必须讲清楚的内容

至少要有这三句人话：

1. 开发版会比稳定版更早拿到新功能
2. 开发版可能包含尚未完全验证的变更
3. 你可能遇到未知 bug、兼容问题或稳定性下降

再加一个显式同意勾选：

- “我已了解开发版可能不稳定，仍要切换到开发版”

### 4.3 更新日志按钮与模态框

#### 4.3.1 按钮出现条件

只要最近一次检查结果里存在：

- `notes` 非空
- 或服务端 `latestNotes` 非空

就显示“查看更新内容”按钮。

#### 4.3.2 模态框内容顺序

1. 标题
2. 版本号与通道
3. 发布时间
4. 更新正文
5. 如无正文，展示空态说明

### 4.4 文案原则

别写工程黑话。

例如：

- 不要写“切换至 beta 通道路由”
- 要写“切换到开发版”
- 不要写“预发布构建可能存在未知回归”
- 要写“开发版可能有未知 bug 或不稳定情况”

## 5. 版本号与 Tag 设计

### 5.1 行业常见做法

行业里最稳的做法还是 semver 预发布标记：

- 稳定版：`v1.4.0`
- 开发版：`v1.5.0-beta.1`
- 后续开发版：`v1.5.0-beta.2`、`v1.5.0-beta.3`
- 转正后：`v1.5.0`

这套规则的好处很现实：

- 工具链认识它
- 版本比较好做
- 用户也容易看懂
- 不需要自己再发明 `dev-20260612` 这种半吊子规则

### 5.2 本项目推荐规则

#### 稳定版

- tag：`vX.Y.Z`
- 例子：`v0.9.7`

#### 开发版

- tag：`vX.Y.Z-beta.N`
- 例子：`v0.9.8-beta.1`

#### 递增规则

- 当你准备下一个稳定版 `v0.9.8` 时，先发：
  - `v0.9.8-beta.1`
  - `v0.9.8-beta.2`
  - `v0.9.8-beta.3`
- 验证完成后，再发：
  - `v0.9.8`

#### 明确不推荐的写法

- `v0.9.8-beta1`：少了点号，不统一
- `v0.9.8-beta-1`：额外连字符，没必要
- `v0.9.8-dev`：无法表达第几个预览版
- `beta-v0.9.8`：不利于统一解析和排序
- `v2026.06.12-beta`：把日期塞进主版本，后面维护会越来越乱

### 5.3 通道判断规则

- tag 中包含 `-beta.` 的，归开发版
- 不带预发布标记的，归稳定版

用户口头上说“tag 包含 beta 就算开发版”没问题，但落到正式规则里，建议精确成：

- **开发版 tag 使用 semver 预发布标记 `-beta.N`**

这样不会把 `v1.0.0-betafix` 这种垃圾字符串误判成合法版本。

## 6. 兼容与风险

### 6.1 兼容策略

- 旧客户端没有 `betaChannelConsentAcceptedAt` 时，按 `null` 处理
- 旧 manifest 没有扩展字段时，继续只用现有 `title / notes / publishedAt`
- 服务端拿不到 release notes 时，更新按钮不显示，不阻断检查

### 6.2 风险点

1. 服务端 npm 更新日志来源可能暂时不稳定
2. 前端如果直接写死 `beta` 判断，后续扩展通道会更难收口
3. 更新日志正文如果直接吃 GitHub 原始 markdown，样式要控制，别把模态框撑烂

### 6.3 方案取舍

- 不做账户级同步：先把单端体验做对
- 不做第三通道：先把 `stable / beta` 做扎实
- 不做发布系统大改：先把现有 tag 和 manifest 规则补齐

## 7. 测试策略

### 7.1 单元测试

- 更新通道默认值与持久化
- 稳定版切开发版的确认逻辑
- 更新日志按钮显隐逻辑
- `beta` tag / semver 解析规则

### 7.2 集成测试

- 设置页更新管理区域的桌面 / 移动分支展示
- 切换通道后更新检查请求参数变化
- 模态框展示更新日志正文

### 7.3 人工验证

- 从稳定版切到开发版，确认必须先同意
- 切回稳定版可以直接完成
- 检查到带说明的新版本时，可以正常查看更新内容
- 没有说明时，不会出现空白日志弹窗

### 7.4 验证映射

| 需求 | 设计章节 | 验证方式 |
| --- | --- | --- |
| 需求 1 | §3.1、§4.1 | 设置页定向测试 + 手工走查 |
| 需求 2 | §4.2、§6.1 | 模态框交互测试 |
| 需求 3 | §5.1、§5.2、§5.3 | 版本规则单测 + 发布文档走查 |
| 需求 4 | §3.2、§4.3 | 更新日志按钮与模态框测试 |
| 需求 5 | §3.3、§4.3 | 多来源说明字段兼容测试 |

## 8. 风险与待确认项

### 8.1 风险

- 服务端更新日志如果第一版拿不到，需要先允许客户端 / Android 先落地
- GitHub Release 现有产物里 title / notes 的生成质量，会直接影响展示效果

### 8.2 待确认项

- 服务端更新说明第一版是直接查 npm dist-tag 对应 release，还是先允许为空
- 更新日志正文第一版是否按纯文本展示，还是支持受控 markdown 渲染

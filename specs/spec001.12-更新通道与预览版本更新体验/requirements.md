# 需求文档 - spec001.12-更新通道与预览版本更新体验

状态：Draft

## 简介

当前系统已经有 `releaseChannel: "stable" | "beta"` 这个基础字段，也能按通道读 manifest、查服务端更新。

但从用户视角看，这套能力还是缺口很大：

- 没有正式的更新通道选择入口
- 没有“为什么切开发版有风险”的确认说明
- 没有一套清楚的开发版 tag / 版本号规则
- 没有把更新日志作为正式更新体验的一部分展示出来

所以这次要补的是完整的“更新通道体验层”和“开发版发布约束层”。

## 术语表

- **稳定版（Stable）**：默认更新通道，只接收正式发布版本，不接收带 `beta` 标记的预览版本。
- **开发版（Beta）**：预览更新通道，可以接收带 `beta` 标记的版本，用于提前体验新功能和变更。
- **更新通道（Update Channel）**：客户端保存的更新偏好，用于决定检查客户端更新、Android 清单和服务端 npm 包时应该取哪一类版本。
- **发布标签（Release Tag）**：Git tag，例如 `v1.2.3`、`v1.3.0-beta.2`。
- **更新日志（Release Notes）**：版本变更说明，用于告诉用户这个版本修了什么、加了什么、有哪些已知注意事项。

## 范围说明

### In Scope

- 设置页“更新管理”分组新增更新通道设置
- 默认稳定版
- 从稳定版切到开发版前的风险说明和显式同意流程
- 开发版 tag 含 `beta` 的规则正式化
- 开发版版本号与 tag 设计方案
- 客户端检查更新后展示更新日志按钮
- 使用模态框展示更新内容
- manifest / DTO / 前端状态模型补齐更新日志展示字段

### Out of Scope

- 新增 `alpha`、`nightly`、`rc` 等更多通道
- 强制更新或最低版本拦截
- 对 GitHub Release 页面样式做深度运营化改造
- 服务端多包不同通道独立配置
- 用户账户级跨设备同步更新通道偏好

## 需求

### 需求 1：用户必须能在设置页明确选择更新通道

**用户故事：** 作为用户，我希望在设置—更新管理里明确看到自己当前是稳定版还是开发版，这样我才能知道自己接收的是什么版本。

#### 验收标准

1. WHEN 用户进入设置页的更新管理区域 THEN System SHALL 展示当前更新通道。
2. WHEN 用户首次使用或本地没有已保存通道 THEN System SHALL 默认使用稳定版。
3. WHEN 用户切换更新通道 THEN System SHALL 立即保存到当前客户端运行时配置，并用于后续更新检查。
4. WHEN 当前平台不支持客户端自更新但支持服务端更新检查 THEN System SHALL 仍然展示更新通道，因为它会影响服务端更新检查目标版本。

### 需求 2：切换到开发版前必须先看风险说明并显式同意

**用户故事：** 作为普通用户，我希望系统在切到开发版前讲清楚风险，而不是让我在不知情的情况下装上预览版本。

#### 验收标准

1. WHEN 用户从稳定版切到开发版 THEN System SHALL 先弹出说明模态框，而不是直接切换。
2. WHEN 说明模态框打开 THEN System SHALL 明确说明开发版可能包含预览功能、未知 bug 和稳定性风险。
3. WHEN 用户未勾选或未明确同意 THEN System SHALL 不得切换到开发版。
4. WHEN 用户明确同意 THEN System SHALL 完成切换并显示切换成功后的当前通道。
5. WHEN 用户从开发版切回稳定版 THEN System SHALL 允许直接切换，不要求再次确认风险。

### 需求 3：开发版 tag 和版本号规则必须正式定下来

**用户故事：** 作为维护者，我希望开发版版本号和 tag 有固定规则，这样发布、比较版本和排障都不会乱。

#### 验收标准

1. WHEN 维护者发布稳定版 THEN System SHALL 使用不带预发布标记的 semver tag，例如 `v1.4.0`。
2. WHEN 维护者发布开发版 THEN System SHALL 使用带 `beta.N` 预发布标记的 semver tag，例如 `v1.5.0-beta.1`。
3. WHEN 一个开发周期内连续发布多个开发版 THEN System SHALL 递增同一目标版本下的 `beta.N` 序号。
4. WHEN 稳定版用户检查更新 THEN System SHALL 忽略带 `beta` 的 tag。
5. WHEN 开发版用户检查更新 THEN System SHALL 可以接收更高的 `beta` 版本和后续正式版。

### 需求 4：检查更新时如果目标版本带有更新内容，必须能查看更新日志

**用户故事：** 作为用户，我希望看到这个版本到底改了什么，而不是只看到一个版本号。

#### 验收标准

1. WHEN 系统检查到新版本且目标 manifest 或更新结果包含更新日志 THEN System SHALL 展示“查看更新内容”按钮。
2. WHEN 用户点击“查看更新内容” THEN System SHALL 以模态框展示更新标题、版本号、发布时间和更新内容。
3. WHEN 当前没有新版本但最近一次检查结果里包含目标版本说明 THEN System SHALL 允许在合适位置继续查看这次检查到的更新内容。
4. WHEN 更新日志为空 THEN System SHALL 不展示空白模态框，而是明确提示“这个版本暂时没有附带更新说明”。

### 需求 5：更新日志展示必须兼容客户端、Android 和服务端更新信息

**用户故事：** 作为用户，我希望无论是桌面端、Android 还是服务端升级，只要有说明，就能用一致的方式查看更新内容。

#### 验收标准

1. WHEN 客户端 manifest 含有更新日志 THEN System SHALL 用统一展示结构展示。
2. WHEN Android manifest 含有更新日志 THEN System SHALL 用同一套更新日志展示模态框展示。
3. WHEN 服务端更新检查结果能拿到目标版本更新日志 THEN System SHALL 也能展示查看入口。
4. WHEN 某一类更新源暂时没有更新日志字段 THEN System SHALL 保持兼容，不因为缺字段导致更新检查失败。

## 非功能需求

### 非功能需求 1：兼容性

1. WHEN 旧配置里没有通道同意状态 THEN System SHALL 继续按稳定版运行，不破坏现有用户。
2. WHEN 旧 manifest 不带更新日志扩展字段 THEN System SHALL 继续兼容旧格式。

### 非功能需求 2：可维护性

1. WHEN 后续新增更新日志字段 THEN System SHALL 复用现有 manifest / DTO 模型，不允许桌面端、Android、服务端各长一套不同字段名。
2. WHEN 后续继续扩展发布通道 THEN System SHALL 优先在统一 `ReleaseChannel` 和版本规则上演进，而不是在页面里硬编码判断字符串。

### 非功能需求 3：可理解性

1. WHEN 用户看到开发版切换说明 THEN System SHALL 使用普通用户能看懂的人话，而不是工程术语。
2. WHEN 用户看到更新日志按钮和模态框 THEN System SHALL 明确告诉用户“这次更新带来了什么变化”，而不是只贴原始字段。

## 成功定义

- 设置页里能明确看到并切换稳定版 / 开发版
- 开发版切换前有明确的风险说明和用户同意动作
- 项目有一套固定的 `vX.Y.Z-beta.N` 开发版 tag 规则
- 检查到新版本时，用户可以直接在应用内查看更新内容

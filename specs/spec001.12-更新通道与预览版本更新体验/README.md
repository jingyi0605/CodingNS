# spec001.12-更新通道与预览版本更新体验

状态：Draft

## 这个 Spec 要解决什么问题

现在项目已经有统一更新机制，也已经有 `stable / beta` 两个通道字段，但这套东西还不算真正可交付，问题很直接：

- 用户看不到一个正式的“更新通道”设置入口
- `beta` 现在更像内部实现字段，不像用户能理解和切换的能力
- 预览版本到底怎么命名、怎么打 tag、怎么避免把稳定版用户带进测试版本，规范还不够清楚
- 检查到新版本以后，更新日志展示还不完整，用户只能看版本号，不知道这次到底改了什么

一句人话：
这次不是重做更新器，而是把“稳定版 / 开发版”的使用规则、版本发布规则和设置页交互补齐，让这套更新机制真正能给普通用户用。

## 为什么现在做

- 现有代码已经有 `releaseChannel`，但没有完整的用户切换链路，等于能力只做了一半。
- 没有正式的开发版版本号规范，后面发布越多，tag 越容易乱。
- 更新日志不展示，用户只能看到“有新版本”，却不知道值不值得更。
- 这件事继续拖着，稳定版和开发版会混在一起，最后不是体验问题，是发布纪律问题。

## 这次明确覆盖什么

- 设置页“更新管理”里的更新通道设置入口
- 默认稳定版、切到开发版前必须看说明并同意
- `beta` tag 与开发版通道的映射规则
- 行业常见做法下适合本项目的开发版 tag / 版本号设计
- 检查更新后展示更新日志按钮，并用模态框展示内容
- 发布清单和前端状态模型里补齐更新日志展示所需字段

## 这次明确不做什么

- 不新增第三种通道，比如 `alpha`、`nightly`、`canary`
- 不重做桌面端、Android、服务端三条更新主链路
- 不在这次把 GitHub Release 发布自动化整套重写
- 不做“强制更新”规则
- 不做多语言长篇发布公告编辑器

## 关联 Spec

- `spec001.6-客户端与服务端统一更新机制`
- `spec001.1-账户偏好入库与跨客户端同步`
- `spec008.2-桌面端与移动端模态框统一模板`

## 当前判断

这事值得做，而且应该单开一个子 Spec，而不是塞回 `spec001.6` 里继续长。

### 【核心判断】

✅ 值得做：这是现有更新机制的交付收口，不是空想功能。

### 【关键洞察】

- 数据结构：`releaseChannel` 已经存在，缺的是“谁能改、怎么改、改完影响哪些更新检查”。
- 复杂度：不要再发明 `preview/dev/experimental` 三四套通道，第一版就只保留 `stable / beta`。
- 风险点：如果版本号和 tag 规则不先定死，后面前端再怎么做通道切换，最终也会因为发布侧混乱而失效。

## 总体判断

这 5 份文件虽然都叫“HTML 单文件 PPT”，但结构并不完全一样。

共同点很明确：

- 都有稳定的“页”概念
- 每一页都有固定尺寸或固定比例
- 页面内容主要靠 `HTML + CSS` 排版，不依赖复杂运行时数据
- 交互脚本主要用于翻页、缩放、进度条和打印，不是业务逻辑

真正重要的差异在这里：

- 有的文档是“所有页直接竖向排开”
- 有的是“只显示当前页，其他页靠 `active` 切换”
- 有的是“整条 `deck` 横向平移”
- 有的动画和装饰非常重，适合展示，不适合第一阶段做稳定编辑

一句人话：

不是所有“能翻页的 HTML”都该进第一阶段编辑器。

## 分类结果

### A 类：优先支持

特点：

- 页面边界明确
- 每页主要内容是稳定容器
- 文字、卡片、图表、列表这些块状结构清楚
- 装饰脚本不决定内容结构

包含：

1. `20260327-合伙人佣金系统定制方案PPT.html`
2. `20260511-企业Agent平台建设技术方案PPT-1.html`
3. `化工行业AI培训/index.html`

### B 类：条件支持

特点：

- 页面边界明确
- 但动画、切换状态类、全局装饰层更多
- 内容可编辑，但必须先过滤掉大量展示态壳子

包含：

1. `20260426-AI模型贴脸对战.html`
2. `codingns-presentation.html`

### C 类：第一阶段不支持

当前这 5 份里，没有完全落到这一类的文件，但如果后续遇到下面这些情况，先不支持：

- 页面边界依赖运行时数据而不是固定 DOM
- 内容主要靠 `canvas` 绘制
- 核心布局严重依赖脚本逐帧计算
- 一页内部存在大量自由旋转、3D 透视、复杂滤镜联动
- 一保存就必须整份重生成，无法稳定回写

- 没有真正的翻页逻辑

资源特点：

- 存在外部图片引用，例如 `./assets/partner_graph.svg`

- 很高

原因：

- 页面边界最清楚
- 内容块都比较规整

- 很适合作为第一阶段输入基线

- 某些图表块和装饰块使用绝对定位

## 共同结构特征

### 1. 页面边界模式

这 5 份样板目前能归到这些模式：

| 模式 | 特征 | 样板 |
| --- | --- | --- |
| `section.slide` 纵向顺排 | 所有页直接在 DOM 中按顺序出现 | 合伙人佣金系统 |
| `section.slide + active` | 只显示当前页，其余页隐藏 | 企业 Agent 平台、AI 模型贴脸对战 |
| `deck translateX` 横向切页 | 整个容器平移切页 | 化工行业 AI 培训 |
| `div.slide + active` | 页面不是 `section`，而是普通块级容器 | codingns-presentation |

第一阶段应明确支持：

- `section.slide`
- `.slide`
- `[data-slide]`
- `[data-title]`

但前提是：

- 页节点在初始 DOM 中完整存在
- 不是运行时动态拼接

### 2. 内容组织模式

高频模式很统一：

- 标题：`h1 / h2 / h3`
- 正文：`p`
- 列表：`ul / li`
- 指标卡：`div.card / .metric / .mini-card`
- 栅格布局：`grid`
- 排列容器：`flex`
- 装饰图表：绝对定位块、简单条形图、内联 `svg`

这意味着第一阶段可编辑组件优先收敛成：

- 文本块
- 图片块
- 容器块
- 简单图形块

先不要碰：

- 复杂动画块
- 粒子背景
- 3D 透视切换
- 复杂 `svg` 语义化编辑

### 3. 脚本依赖模式

这些样板的脚本主要分 4 类：

1. 翻页控制
2. 响应式缩放
3. 进度条 / 页码 / 目录提示
4. 打印前缩放补丁

结论很明确：

- 这些脚本大多是“展示壳逻辑”
- 不是“内容数据逻辑”

所以导入时应该：

- 保留原始脚本源码
- 但编辑器内部不要依赖这些脚本驱动画布

## 第一阶段建议支持边界

### 直接支持

- 单文件 HTML
- 页节点在 DOM 里静态存在
- 每页有稳定根节点，例如 `section.slide`
- 主体内容以文本、卡片、图片、列表、表格、简单图形为主
- 布局主要依赖 `grid / flex / 常见 absolute`

### 条件支持

- 页切换依赖 `active / next / prev`
- 全局存在装饰动画层
- 存在简单内联 `svg`
- 存在局部外链图片

条件支持的意思是：

- 可以打开
- 但某些块只读或受限编辑

### 暂不支持

- 运行时动态生成页面
- 核心内容在 `canvas`
- 复杂 3D 透视和连续动画决定实际布局
- 页序、页边界本身不稳定

## 第一阶段导入规则建议

### 规则 1：先认页，再认块

先把页边界识别稳定，再把页内节点映射成组件。

不要一上来就深挖每个 DOM 节点，否则会把展示壳和内容壳混在一起。

### 规则 2：过滤展示态状态类

这些类默认不应进入编辑模型：

- `active`
- `next`
- `prev`
- 进度条宽度类或运行态类
- 纯展示动画类

### 规则 3：把全局装饰层和内容层分开

像这些层应先归为“页面装饰 / 只读背景”：

- 背景网格
- 发光层
- 粒子层
- 全局悬浮提示
- 翻页控制按钮

### 规则 4：复杂结构先锁定，不强编

这些内容第一阶段可以只读：

- 复杂内联 `svg`
- 深层绝对定位关系图
- 依赖脚本动态压缩的密集内容页

宁可先锁住，也不要给用户一个看起来能改、实际一保存就跑版的假能力。

## 对 `spec004.2` 的直接影响

### 对任务 1.2 的影响

页面模型里必须至少区分：

- 页面根节点
- 内容容器节点
- 文本节点
- 图片节点
- 只读装饰节点
- 受限复杂节点

### 对任务 2.1 的影响

导入器第一阶段至少要识别：

- `section.slide`
- `.slide`
- `[data-slide]`
- `[data-title]`

并且要能过滤：

- 翻页控制 DOM
- 全局装饰 DOM
- 运行态状态类

### 对任务 3.1 的影响

保存策略必须优先补丁式回写：

- 改文字就只改对应文本节点
- 改位置和尺寸就只改对应节点样式
- 不要因为改了一处文字，就把整份样板 HTML 洗成另一种结构

## 结论

第一阶段的正确做法不是“支持所有 HTML PPT”，而是：

1. 先稳定支持 `A 类样板`
2. 对 `B 类样板` 只做条件支持
3. 把全局展示壳和内容壳分开
4. 把复杂结构先标成只读

真正的问题不是“能不能把 HTML 打开”，而是“能不能在不把页面搞坏的前提下稳定保存和导出”。

先把这个边界钉死，后面开发才不会失控。

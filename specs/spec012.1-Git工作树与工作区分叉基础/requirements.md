# 需求文档 - spec012.1-Git工作树与工作区分叉基础

状态：Draft

## 简介

这份 Spec 不讨论“多个 AI 同时跑起来怎么比较”。

这一步先只做一件事：
把 `git worktree` 从 Git 技巧升级成系统内的正式能力。

用户真正需要的不是“多几个 branch”，而是：

- 能从一个工作区长出子工作树
- 能继续从子工作树再 fork
- 能清楚知道自己当前在根工作区还是子工作树里
- 能把子工作树改动合回直接父节点
- 跑完以后能安全清理掉，不把项目目录越搞越脏

## 术语表

- **根工作区**：当前已经存在的顶层 `workspace`
- **子工作树**：基于某个工作区或某个子工作树创建出来的 `git worktree`
- **工作树元数据**：描述子工作树血缘、分支、状态和展示信息的持久化记录
- **直接父节点**：创建当前子工作树时所使用的来源工作区
- **根工作树会话**：根工作区现有的会话列表，保持当前逻辑不变
- **子工作树区块**：工作台中新增的分组，用来展示当前根工作区下面的 worktree 树
- **上下文视觉标识**：用稳定颜色和提示文案提醒用户“当前在哪个工作树里工作”

## 范围说明

### In Scope

- 为子工作树建立正式元数据模型
- 创建、列出、继续 fork、删除、清理 `git worktree`
- 只支持“合并回直接父节点”
- 工作台中新增“子工作树”树状区块
- 父工作区与子工作树的视觉区分
- 失败恢复、残留检测和安全边界校验

### Out of Scope

- 多 provider 并行尝试
- 一键从父会话批量拉起多个子工作树
- 自动冲突解决
- 自动验证并给出结果评分
- 完整运行时隔离资源分配

## 需求

### 需求 1：系统必须把子工作树当成正式对象持久化

**用户故事：** 作为维护者，我希望子工作树不是临时目录，而是系统能追踪的对象，这样我才能继续 fork、合并和清理。

#### 验收标准

1. WHEN 用户创建子工作树 THEN System SHALL 持久化一条工作树元数据，至少记录 `workspaceId`、`rootWorkspaceId`、`parentWorkspaceId`、`branchName`、`baseRef`、`baseCommit`、`status`、`createdAt`。
2. WHEN 用户查看某个根工作区 THEN System SHALL 返回该根工作区下全部子工作树及其父子关系。
3. WHEN 某个顶层工作区没有任何子工作树 THEN System SHALL 保持当前工作区展示结构不变。

### 需求 2：系统必须支持从工作区创建子工作树

**用户故事：** 作为用户，我希望在当前项目下直接创建一个独立工作树，而不是自己手工敲 `git worktree add`。

#### 验收标准

1. WHEN 用户从根工作区发起创建 THEN System SHALL 创建新的分支和新的 `git worktree` 目录。
2. WHEN 系统创建子工作树 THEN System SHALL 把该目录注册成可访问的独立 `workspace`，但不在顶层工作区列表单独冒出来。
3. WHEN 来源工作区存在未提交改动 THEN System SHALL 明确拒绝创建，并说明原因，而不是偷偷丢状态。

### 需求 3：系统必须支持从子工作树继续 fork

**用户故事：** 作为调试者，我希望可以从子工作树继续长出孙工作树，这样我才能逐层试不同方向。

#### 验收标准

1. WHEN 用户从某个子工作树发起继续 fork THEN System SHALL 基于该工作树当前 `HEAD` 创建新的子节点。
2. WHEN 新节点创建成功 THEN System SHALL 记录直接父节点，而不是只记根工作区。
3. WHEN 工作台展示子工作树 THEN System SHALL 按真实父子关系树状显示，而不是拍平成列表。

### 需求 4：工作台必须在不破坏当前结构的前提下展示子工作树

**用户故事：** 作为长期用户，我希望新的工作树能力不要把现在已经工整的工作区列表打乱。

#### 验收标准

1. WHEN 根工作区没有子工作树 THEN System SHALL 继续按“当前主工作树会话 + 归档会话”的既有结构展示。
2. WHEN 根工作区已有子工作树 THEN System SHALL 在“当前主工作树会话”和“归档会话”之间新增“子工作树”区块。
3. WHEN 用户展开“子工作树”区块 THEN System SHALL 展示每个子工作树自己的会话列表，并支持继续展开其子节点。

### 需求 5：父工作区与子工作树必须有清晰视觉区分

**用户故事：** 作为用户，我希望一眼看出自己当前到底在根工作区还是某个子工作树里，避免改错地方。

#### 验收标准

1. WHEN 工作台展示子工作树节点 THEN System SHALL 用稳定的文字颜色或标识色区分该节点，不与根工作区混成一样。
2. WHEN 用户进入某个子工作树的聊天界面 THEN System SHALL 显示清晰的工作树上下文提示，包括来源关系和当前分支。
3. WHEN 用户查看右侧信息栏或辅助信息区 THEN System SHALL 通过背景色或强调样式提示当前工作树上下文，且不同工作树之间视觉可区分。

### 需求 6：系统必须支持仅合并回直接父节点

**用户故事：** 作为维护者，我希望第一阶段合并规则足够简单，别一上来就搞任意目标合并。

#### 验收标准

1. WHEN 用户请求合并 THEN System SHALL 只允许把当前子工作树合并回直接父节点。
2. WHEN 系统执行合并前 THEN System SHALL 提供预检结果，至少包含目标是否干净、是否存在冲突风险、来源与目标的引用信息。
3. WHEN 合并成功 THEN System SHALL 回写工作树状态，但不自动删除该子工作树目录。

### 需求 7：系统必须支持可控清理

**用户故事：** 作为维护者，我希望不用的工作树能被安全清掉，但不能误删还在用的东西。

#### 验收标准

1. WHEN 用户清理某个子工作树 THEN System SHALL 检查其是否仍有活跃会话、终端或其他占用。
2. WHEN 检查通过 THEN System SHALL 清理对应 `git worktree` 和相关元数据。
3. WHEN 清理失败 THEN System SHALL 保留残留信息和错误详情，不能假装成功。

### 需求 8：新能力不能破坏现有工作区主链路

**用户故事：** 作为现有系统维护者，我希望不使用工作树能力时，现有工作区、会话、文件、Git、终端体验都不变。

#### 验收标准

1. WHEN 用户不创建子工作树 THEN System SHALL 保持当前工作区列表、会话列表和路由行为不变。
2. WHEN 文件、Git、终端、聊天页切到子工作树 THEN System SHALL 继续复用现有 `workspaceId` 主链路，而不是复制一套平行实现。
3. WHEN 工作树功能失败 THEN System SHALL 将影响限制在目标工作树范围内，不拖垮其他工作区。

## 非功能需求

### 非功能需求 1：可维护性

1. WHEN 后续 `spec012` 接入多 provider 并行编排 THEN System SHALL 直接复用本 Spec 的工作树元数据和生命周期能力。
2. WHEN 排查问题 THEN System SHALL 能快速定位 `rootWorkspaceId`、`parentWorkspaceId`、`workspaceId`、`branchName` 和 `path` 的关系。

### 非功能需求 2：安全性

1. WHEN 系统创建或删除 `git worktree` THEN System SHALL 校验路径边界，拒绝越权目录。
2. WHEN 用户请求合并或清理 THEN System SHALL 校验当前工作树确实属于该根工作区树，不允许跨树乱操作。

### 非功能需求 3：易用性

1. WHEN 用户在子工作树内工作 THEN System SHALL 始终给出稳定、可见、不过度打扰的上下文提示。
2. WHEN 用户返回根工作区 THEN System SHALL 视觉上明显回到默认上下文，而不是保留子工作树提示造成误导。

## 成功定义

- 系统正式支持从工作区长出子工作树，并能继续 fork
- 工作台顶层结构基本不变，只是在展开区新增“子工作树”分组
- 用户能一眼看出当前会话属于哪个工作树
- 第一阶段只支持合并回直接父节点，规则清楚、不绕
- 这套 worktree 能力可以直接成为 `spec012` 的基础，而不是日后返工重写

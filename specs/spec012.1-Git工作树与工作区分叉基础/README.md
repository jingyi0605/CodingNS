# spec012.1-Git工作树与工作区分叉基础

## 当前定位

这个子 Spec 先解决一个更基础、也更硬的问题：

- 系统能不能把 `git worktree` 当成正式对象管理，而不是继续把“并行开发”理解成几条零散分支和几份手工复制目录。

一句人话：
先把工作树建对、管住、收干净，再谈并行会话组和更重的上层编排。

如果这一步不先做，后面的 `spec012` 很容易继续长歪：

- 会话可以 fork，但代码目录还是同一个，根本谈不上真正隔离
- 工作台里只能看到一层工作区，不知道谁是谁的子工作树
- 合并和清理只能靠人记目录、记分支、记来源
- UI 看上去像在一个项目里工作，实际上人已经切到另一个 worktree，特别容易误操作

所以 `spec012.1` 的目标很明确：

- 在不推翻现有 `workspace` 模型的前提下，补一层 `worktree meta`
- 先打通 `git worktree` 的创建、继续 fork、合并回直接父节点、清理
- 让工作台维持现有顶层结构，只在展开后新增“子工作树”区块
- 让父工作区和子工作树在列表、聊天页、右侧信息栏上有清晰视觉区分

## 计划覆盖

- 子工作树元数据模型与仓储
- `git worktree add/list/remove/prune` 生命周期管理
- 从根工作区创建子工作树
- 从子工作树继续 fork 出孙工作树
- 仅支持“合并回直接父节点”的预检与执行
- 工作台侧边栏的“当前主工作树会话 / 子工作树 / 归档会话”结构
- 父工作区与子工作树的最小视觉区分方案
- 资源清理、残留恢复与边界校验

## 本阶段明确不做

- 不做并行会话组和成员级临时隔离工作区编排
- 不做统一结果快照和多尝试对比
- 不做自动 merge 决策
- 不做端口块、缓存目录、数据库目录这类完整运行时隔离
- 不做“父会话一键开多个 worktree”的高级入口

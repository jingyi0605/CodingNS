# 需求文档 - spec008.2-桌面端与移动端模态框统一模板

状态：Draft

## 简介

当前项目里的模态框问题不是“看着不统一”这么简单，而是基础模型没收口。

已经确认的现状有几条：

1. 仓库里已经有 `WorkbenchModal`，但它只统一了桌面端弹窗外壳，没有统一尺寸档位、布局类型、底部操作区和滚动规则。
2. 代码里仍然有多处业务组件直接手写 `workbench-modal-layer` 结构，说明基础组件还没有形成硬约束。
3. 移动端也已经有多种 sheet，但 `ios-action-sheet-overlay` 这套结构仍在页面里重复拷贝，没有公共组件。
4. 当前样式文件已经有大量 modal token 和控件规则，但业务层还在继续补局部 class，说明“有样式”不等于“有模板”。

这会直接带来三个后果：

- 新建弹窗时，每次都要重新调宽度、布局、滚动和按钮位置
- 老弹窗越长越像特殊情况集合，后面谁都不敢改
- 桌面端和移动端的交互心智不稳定，用户每开一个弹窗都要重新适应

所以这次边界先说死：

1. 桌面端必须有统一 `DesktopModal`
2. 移动端必须有统一 `MobileSheet`
3. 尺寸、高度、布局都要用固定档位
4. 模态框里的常见控件区域要有统一模板
5. 历史弹窗必须允许渐进迁移，不能一刀切把主流程砍掉

## 可实现性结论

### 结论

这个能力 **值得做，而且必须尽快做**。

继续放任每个业务弹窗自己长，后面只会有更多例外和更多不敢动的垃圾代码。

### 已确认事实

1. 当前项目已经有桌面端模态框基础壳：`apps/user-app/src/features/conversation/components/WorkbenchModal.tsx`
2. 当前项目已经有统一 modal 样式基线：`apps/user-app/src/app/styles.css`
3. 当前仓库里 `WorkbenchModal` 已被使用，但仍有多处业务代码直接手写 `workbench-modal-layer`
4. 当前移动端 sheet 已经在多个页面重复使用相似结构，但没有正式的 `MobileSheet` 基础组件
5. 当前文件查看器已经独立长出了自己的尺寸档位，说明“固定档位 + 特例增强”是可行路线
6. 当前前端已经有 i18n、主题和平台适配基础，不需要为了做模态框模板再重建一套 UI 运行时

### 平台判断

- ✅ 值得做：这是明显真实存在的工程问题，不是空想出来的设计洁癖
- ✅ 能落地：现有代码里已经有桌面 modal 壳、移动端 sheet 壳和样式 token
- ❌ 不能继续靠业务组件自己手写 `portal + backdrop + card`
- ❌ 不能继续用“再加几个 className”假装完成统一

## 术语表

- **Desktop Modal（桌面端模态框）**：在桌面端或宽屏 Web 场景下居中显示的对话框容器
- **Mobile Sheet（移动端抽屉式弹层）**：在紧凑宽度下从底部弹出的操作层或表单层
- **Size Preset（尺寸档位）**：桌面端模态框的固定宽度档位，例如窄、中、宽、全屏
- **Height Preset（高度档位）**：移动端 sheet 的固定高度档位，例如半屏、四分之三屏、全屏
- **Layout Preset（布局类型）**：模态框内部结构类型，例如确认型、表单型、列表型、查看器型
- **Modal Atoms（模态框原子块）**：弹窗里的统一结构片段，例如字段区、分组区、按钮区、列表区、空态区
- **Migration Wrapper（迁移兼容层）**：为了不打断旧代码而保留的一层旧接口包装，例如让 `WorkbenchModal` 先代理到新的桌面端基础组件

## 范围说明

### In Scope

- 定义桌面端 `DesktopModal` 的统一组件模型
- 定义移动端 `MobileSheet` 的统一组件模型
- 定义固定尺寸档位、固定高度档位和固定布局类型
- 定义模态框内的字段、分组、按钮区、列表区、空态、标签等通用结构模板
- 给现有 `WorkbenchModal` 设计兼容过渡方案
- 首批迁移一组代表性弹窗，验证模板不是纸上谈兵
- 定义后续新增弹窗的开发约束和回归要求

### Out of Scope

- 重做全站设计系统
- 全量迁移所有历史弹窗
- 重写文件查看器内部业务逻辑
- 重写移动端导航、桌面多窗口、右侧面板等其它交互体系
- 新造一套完全独立于现有按钮和输入框体系的 UI 库

## 技术边界

### 边界 1：模板必须先统一“模型”，不是只统一皮肤

- 统一对象至少包括：壳层结构、尺寸档位、布局类型、底部操作区、滚动规则、关闭行为
- 只改颜色和圆角，不改结构模型，不能算完成

### 边界 2：桌面端和移动端必须各有自己的基础件

- 桌面端不能继续拿移动端 sheet 结构硬凑
- 移动端不能继续拿桌面端 modal 缩小后硬塞
- 两套基础件可以共用 token 和原子块，但不能强行共用同一个 DOM 模型

### 边界 3：历史兼容必须优先于理论完美

- 现有主流程弹窗不能因为这次统一而被打断
- `WorkbenchModal` 必须有过渡路径，不能突然全仓改接口
- 个别大型特例弹窗可以暂时保留增强能力，但必须接入统一尺寸和结构约束

### 边界 4：固定档位必须是真正可复用的有限集合

- 桌面端宽度必须收成有限几个档位
- 移动端高度必须收成有限几个档位
- 不允许继续让每个业务弹窗自己定义一组临时百分比

### 边界 5：新增弹窗不能再直接手写基础壳

- 后续新增业务弹窗默认必须基于统一基础组件
- 如果确实需要例外，必须明确写出原因和偏离点

### 边界 6：用户可见文案和交互仍然遵守现有前端规范

- 文案继续走统一 i18n 字典
- 桌面端和移动端的基础按钮、输入框、选择器样式继续沿用统一主题 token
- 不能为了弹窗模板收口把现有国际化和主题体系绕开

## 需求

### 需求 1：系统必须提供统一的桌面端模态框基础组件

**用户故事：** 作为前端开发者，我希望桌面端弹窗有正式的基础组件和固定结构，这样新增弹窗时不需要再从零拼壳。

#### 验收标准

1. WHEN 开发者新增桌面端弹窗 THEN System SHALL 提供统一的桌面端基础组件，而不是要求业务代码自己拼 `portal + backdrop + card`。
2. WHEN 桌面端弹窗展示标题、描述、头部操作区和关闭按钮 THEN System SHALL 提供固定结构位置。
3. WHEN 不同桌面端弹窗需要不同内容 THEN System SHALL 允许在统一结构内插入业务内容，而不是鼓励复制基础壳。

### 需求 2：系统必须提供统一的移动端 sheet 基础组件

**用户故事：** 作为前端开发者，我希望移动端动作面板、表单面板和选择面板都能基于同一个 sheet 模板，而不是每个页面自己复制一套。

#### 验收标准

1. WHEN 开发者新增移动端弹层 THEN System SHALL 提供统一的 `MobileSheet` 基础组件。
2. WHEN 移动端弹层需要标题、描述、底部取消区、拖拽手柄或安全区处理 THEN System SHALL 提供固定结构和默认行为。
3. WHEN 不同移动端弹层属于动作型、表单型或选择型 THEN System SHALL 支持在统一基础上切换布局类型。

### 需求 3：系统必须提供固定的尺寸档位、高度档位和布局类型

**用户故事：** 作为开发者，我希望弹窗大小和内部布局都能从固定档位里选，而不是每次再讨论这次到底 57% 还是 62%。

#### 验收标准

1. WHEN 开发者定义桌面端弹窗大小 THEN System SHALL 使用固定的尺寸档位集合。
2. WHEN 开发者定义移动端弹层高度 THEN System SHALL 使用固定的高度档位集合。
3. WHEN 开发者选择确认型、表单型、列表型、查看器型等场景 THEN System SHALL 提供对应的布局类型，而不是继续靠业务类名硬拼。

### 需求 4：系统必须统一模态框内的常见结构模板

**用户故事：** 作为开发者，我希望弹窗里的字段、标签、按钮区、列表区、空态区有统一模板，这样业务代码只关心内容，不再重复调间距和对齐。

#### 验收标准

1. WHEN 弹窗包含输入字段、下拉框、文本域和标签 THEN System SHALL 提供统一的模态框原子结构。
2. WHEN 弹窗包含底部操作按钮 THEN System SHALL 提供统一的按钮区模板和对齐规则。
3. WHEN 弹窗包含列表、分组、空态和危险操作区 THEN System SHALL 提供统一的结构模板，而不是每个弹窗自己写一套。

### 需求 5：系统必须支持渐进迁移，不破坏现有主流程

**用户故事：** 作为当前用户，我希望这次统一不会把现有弹窗全改坏；作为维护者，我希望旧代码可以分批迁移，而不是一刀切大爆炸。

#### 验收标准

1. WHEN 引入新的模态框基础组件 THEN System SHALL 为现有 `WorkbenchModal` 提供兼容或包装路径。
2. WHEN 首批业务弹窗迁移完成 THEN System SHALL 保持现有打开、关闭、确认、取消主流程不回退。
3. WHEN 还有历史弹窗未迁移 THEN System SHALL 允许分批推进，而不是要求一次性全改。

### 需求 6：系统必须统一基础交互和可访问性规则

**用户故事：** 作为用户，我希望不同弹窗的关闭、滚动、遮罩、键盘行为一致，不要每个弹窗都像不同人写的。

#### 验收标准

1. WHEN 用户点击遮罩、按 `Escape`、点击关闭按钮 THEN System SHALL 按统一规则处理关闭行为。
2. WHEN 弹窗处于 `busy`、不可关闭或危险确认状态 THEN System SHALL 支持显式禁用关闭，而不是每个弹窗自己补逻辑。
3. WHEN 弹窗打开后 THEN System SHALL 保持基本的对话框可访问性语义和焦点约束。

### 需求 7：系统必须迁移一批代表性弹窗来验证模板可用

**用户故事：** 作为维护者，我希望这套模板不是只停留在文档里，而是真正能覆盖确认弹窗、表单弹窗、列表弹窗、动作 sheet 和表单 sheet。

#### 验收标准

1. WHEN 完成首批迁移 THEN System SHALL 至少覆盖桌面端确认型、桌面端列表型、移动端动作型、移动端表单型四类代表场景。
2. WHEN 首批迁移完成 THEN System SHALL 证明新模板能承接现有真实业务，而不是只做演示组件。
3. WHEN 迁移完成后回归测试运行 THEN System SHALL 保持现有核心交互不回退。

### 需求 8：系统必须建立后续新增弹窗的收口规则和验证要求

**用户故事：** 作为维护者，我希望这次统一之后，后续新增弹窗不会马上重新长歪。

#### 验收标准

1. WHEN 后续新增业务弹窗 THEN System SHALL 默认要求使用统一基础组件。
2. WHEN 某个弹窗仍然需要手写壳层 THEN System SHALL 明确记录偏离原因。
3. WHEN 组件库和样式规则变更 THEN System SHALL 有对应测试或验收清单证明关键弹窗没有回退。

## 非功能需求

### 非功能需求 1：一致性

1. WHEN 用户在同一应用里打开不同桌面端弹窗 THEN System SHALL 看到一致的尺寸、头部、滚动和按钮区基线。
2. WHEN 用户在移动端打开不同 sheet THEN System SHALL 看到一致的标题区、底部安全区和关闭心智。

### 非功能需求 2：可维护性

1. WHEN 开发者新增弹窗 THEN System SHALL 能通过少量明确的 props 完成，而不是继续复制几十行壳层结构。
2. WHEN 维护者调整模态框样式基线 THEN System SHALL 能通过统一组件和统一 token 生效到多数弹窗。

### 非功能需求 3：兼容性

1. WHEN 统一模板上线 THEN System SHALL 不破坏现有桌面端、H5、iOS、Android 共享前端运行时。
2. WHEN 旧弹窗逐步迁移 THEN System SHALL 允许新旧实现并存一段时间，但行为规则不能分裂。

## 成功定义

- 新增桌面端弹窗时，不再需要重复手写基础壳和宽度规则。
- 新增移动端 sheet 时，不再需要复制 `overlay + card + cancel` 结构。
- 桌面端与移动端都具备固定档位和固定布局模型。
- 首批真实业务弹窗完成迁移，并通过回归测试。
- 后续新增弹窗如果继续手写基础壳，会成为明确的例外，而不是默认做法。

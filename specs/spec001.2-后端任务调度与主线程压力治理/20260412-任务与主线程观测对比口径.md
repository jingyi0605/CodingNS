# 任务与主线程观测对比口径

这份文档只回答一件事：

做完 `spec001.2` 之后，后端任务和主线程压力到底怎么看，优化前后到底拿什么比。

别再说“感觉快了一点”。这类说法没用。

## 1. 当前统一观测出口

当前 Host 已提供只读观测接口：

- `GET /api/observability/runtime`

返回三组快照：

1. `backgroundTasks`
   - 全局后台任务指标
   - 包含 `enqueue`、`dedupe`、`started`、`finished`、`failed`、`cancelled`、`timeout`、`wait_ms`、`run_ms`、`cache_hit`
2. `schedulers`
   - 巡检、跟进、摘要调度器的 tick / idle / taskCount / duration / nextDelay
3. `eventLoop`
   - Host 主线程事件循环延迟分布
   - 当前返回 `min / max / mean / stddev / p50 / p95 / p99`

## 2. 后台任务对比口径

先按任务类型比，不要先按模块名比。

当前首批重点任务只有两个：

- `workspace.discovery`
- `provider.capability_refresh`

每次对比至少看下面这些字段：

1. `enqueue`
   - 看入口到底触发了多少次后台刷新
2. `dedupe`
   - 看重复触发有没有被真正收口
3. `cache_hit`
   - 看请求是否真的优先命中缓存，而不是每次都现刷
4. `wait_ms.avg / wait_ms.max`
   - 看任务有没有在队列里堆住
5. `run_ms.avg / run_ms.max`
   - 看单次执行有没有明显长尾
6. `failed / timeout / cancelled`
   - 看系统有没有因为新调度逻辑引入新的不稳定性

最小判断规则：

- `dedupe` 上升，说明重复重活减少了
- `cache_hit` 上升，说明请求主链路更像“缓存优先”
- `run_ms.max` 下降，说明单次长任务被压短或挪走了
- `failed / timeout` 不能因为优化而明显变高

## 3. 调度器对比口径

调度器现在不是“有没有醒”，而是“醒来有没有干重活、空转有没有退让”。

当前统一看这几个字段：

1. `tickTotal`
   - 总共醒了多少次
2. `idleTickTotal`
   - 其中多少次只是空转判断
3. `taskCountTotal`
   - tick 期间真正命中的业务任务总数
4. `durationMs.avg / durationMs.max`
   - 单次 tick 实际消耗
5. `nextDelayMs`
   - 当前退让后的下一次调度间隔
6. `idleStreak`
   - 连续空转次数

最小判断规则：

- 长时间无任务时，`idleTickTotal` 会增加，但 `nextDelayMs` 也应该逐步变大
- 有真实任务进入后，`idleStreak` 应该回落，`nextDelayMs` 回到基础间隔
- `durationMs.max` 不应该在无任务场景下还出现明显高值

## 4. 主线程压力对比口径

现在先用 `eventLoop` 当代理指标，不假装已经有完整 profiler。

重点看：

1. `eventLoop.p95Ms`
2. `eventLoop.p99Ms`
3. `eventLoop.maxMs`

最小判断规则：

- 如果后台任务治理真的有效，`p95/p99/max` 不该在同类请求压力下继续恶化
- 如果 `workspace.discovery` 和 `provider.capability_refresh` 已被去重并挪到后台，主线程长尾应该更稳定

## 5. 推荐回归步骤

每次回归按下面顺序做，别乱。

1. 启动 Host，完成 setup/login
2. 连续触发以下入口：
   - 工作台刷新
   - 代码助手总览
   - provider 能力读取
3. 期间多次读取 `GET /api/observability/runtime`
4. 记录优化前后的以下字段：
   - `backgroundTasks.taskTypes["workspace.discovery"]`
   - `backgroundTasks.taskTypes["provider.capability_refresh"]`
   - `schedulers.schedulers.patrol`
   - `schedulers.schedulers.butler_follow_up`
   - `schedulers.schedulers.session_summary`
   - `eventLoop`

## 6. 这份口径明确不解决什么

- 不提供长期报表平台
- 不提供火焰图
- 不替代真实压测
- 不证明所有入口都已经绝对最优

它只解决一件事：

后续再做任务治理时，大家至少用同一把尺子说话。

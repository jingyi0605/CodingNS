# 20260413-终端卡顿治理补记

这份补记只回答三个问题：

- 这次 `tmux` 终端卡顿真正卡在哪
- 为什么前一轮“后台化”之后，Host 还是会阻塞
- 最后到底是怎么把卡顿打掉的

一句人话：
这次问题不是 `tmux` 自己慢，也不是前端渲染慢，而是 Host 主线程里还残留着几条“看起来异步，实际上仍在本地同步读文件 / SQLite / 大事务”的脏活。

---

## 1. 最后的结论

最终确认的根因顺序是这样的：

1. `tmux` 输入链路不是主因
2. 前端渲染不是主因
3. 终端日志 flush 最开始是阻塞源之一，但不是最后的最大头
4. `workspace.discovery` 的 Host 同步持久化曾经是明显阻塞源，但拆批以后已经不再是最大头
5. 最后真正命中的主犯，是 `workbench.sync_titles -> readSessionTitle`

具体一点说：

- `sync_titles` 虽然已经挂进 `TaskManager`
- 但它最早仍跑在 `host_background`
- 而 `readSessionTitle()` 内部会同步读 provider 本地文件或 SQLite
- 所以它本质上还是在 Host 主线程做重活

这就是为什么“任务看起来已经后台化了”，但终端输入还是会卡 2 到 3 秒。

---

## 2. 这次日志里真正有用的判断口径

这次排查里，有些值能信，有些值不能信。

### 2.1 能直接拿来判断的

- 前端：
  - `sendToAckMs`
  - `sendToOutputMs`
- 后端：
  - `wsToWriteMs`
  - `wsToAckMs`
  - `wsToOutputMs`
- Host：
  - `event_loop.lag`
  - `workspace.discovery.completed`
  - `workbench.sync_titles.completed`
  - `workbench.terminal_manager_snapshot.completed`

### 2.2 不能直接拿来判断网络慢不慢的

- `clientToWsMs`
- `clientToWriteMs`
- `clientToOutputMs`

原因很简单：
浏览器和 Node 不是同一个时钟基准，这几个跨端差值不能直接当真实网络耗时。

---

## 3. 这轮实际做了哪些改动

### 3.1 先补诊断埋点，别再靠猜

已恢复并补充这些调试能力：

- Host 侧终端调试开关：`CODINGNS_TERMINAL_DEBUG=1`
- 前端侧终端调试开关：`localStorage.setItem("codingns.terminal.debug","1")`
- `terminal_manager_snapshot` 分阶段耗时
- `workspace.discovery.completed` 分阶段耗时

新增的 `workspace.discovery.completed` 会拆出：

- `discoverMs`
- `persistPass1Ms`
- `persistPass1BatchCount`
- `persistPass1MaxBatchMs`
- `relationMapMs`
- `persistPass2Ms`
- `persistPass2BatchCount`
- `persistPass2MaxBatchMs`
- `cleanupMs`
- `listItemsMs`
- `refreshStateMs`

这样才能知道到底是 helper 发现慢，还是 Host 收尾慢。

### 3.2 先把终端日志 flush 挪出主线程

最早的一条明显阻塞源，是终端日志同步 flush。

这次把它改成了后台 writer 进程：

- Host 主线程不再同步 `appendFileSync + better-sqlite3`
- 终端输出落盘改走独立 writer 进程

这一刀去掉了一个阻塞源，但事实证明它不是最后的大头。

### 3.3 把 `TaskManager` 从“标签系统”补成真正执行位点

之前的一个关键架构问题是：

- `executionLane` 基本只是语义标签
- `helper_process` 不等于真的会自动走 helper
- 只要 `run()` 里写了同步重活，它照样堵主线程

这次补了统一 helper executor 以后：

- `helper_process` 有了真正统一的执行器
- 可以把本地重扫描和端口探测统一挪到 helper 进程
- 不再依赖每个 service 自己记得“再 fork 一次”

### 3.4 收掉工作台侧几条残留主线程重活

这次继续把下面几条链路挪到了更合理的位置：

- `workspaceManagement` 的代码类型扫描改走 helper
- `terminal_manager_snapshot` 的模板端口状态探测改走 helper
- `workspaceManagement` 的周期性自动刷新默认关闭，便于做 A/B

这一轮之后，`terminal_manager_snapshot` 日志已经从秒级回落到几十毫秒，说明它不再是主犯。

### 3.5 把 `workspace.discovery` 的 Host 收尾拆批

前一轮之后，`workspace.discovery` 虽然 discovery 本身已经在 helper 进程里跑，
但 helper 返回后，Host 还要做一整大块同步持久化和清理。

这次做了两件事：

1. 给 `workspace.discovery` 补分阶段埋点
2. 把大事务改成分批事务，中间 `delay(0)` 让出事件循环

同时把这些阶段一起分批 / 控体量：

- 第一轮基础落库
- 第二轮关系修正落库
- `cleanupStaleHiddenSessions()` 删除清理

后续日志证明这一步是有效的：

- `persistMs` 明显下降
- `persistPass1MaxBatchMs / persistPass2MaxBatchMs` 已经落到个位数毫秒

所以这条链后来不再是最终主犯。

### 3.6 最后一刀：把 `sync_titles` 的标题读取搬进 helper

最后真正打中卡顿的是这里：

- `workbench.sync_titles`
- `SessionHistoryService.syncSessionTitleFromProvider()`
- `SessionSyncService.readSessionTitle()`

不同 provider 的 `readSessionTitle()` 内部会做：

- 同步读 jsonl
- 同步读本地 SQLite
- 同步组装消息 / 元数据

这类逻辑只要还在 Host 进程，就会继续卡事件循环。

最后的修复方式是：

- 给 `provider-discovery-helper` 增加 `session_title_read` 请求类型
- `syncSessionTitleFromProvider()` 不再直接在 Host 主线程里读标题
- 标题读取统一搬到 helper 进程执行

卡顿最终消失，就是在这一刀之后。

## 4. 这次排查得到的架构经验

这次最重要的经验，不是“某个函数慢”，而是下面这几条：

### 4.1 `host_background` 不是免死金牌

只要任务还在 Host 进程里跑：

- 同步文件读写
- 同步 SQLite
- 大事务
- 大对象组装

照样会卡事件循环。

所以：

- `host_background` 只适合轻聚合、轻状态整理
- 一旦涉及本地重 I/O 或扫描，就该优先上 `helper_process`

### 4.2 helper 化只搬走前半段，不代表主线程没事

`workspace.discovery` 这次就是典型例子：

- helper 侧发现已经出去
- 但 Host 回来后的同步持久化仍可能卡几秒

所以“任务已经 helper 化”不能当验收结论，必须继续看：

- helper 返回后的 Host 收尾有多重
- 有没有同步大事务
- 有没有批间让出事件循环

### 4.3 WebSocket 广播链路不能现算重任务

`sync_titles` 这次暴露得非常明显：

- 只要在广播链路里现算
- 又正好碰到同步本地读
- 终端输入就会被一并拖住

以后工作台 / 侧边栏 / 广播链路应该遵守同一条规则：

- 广播链路只读缓存或最近结果
- 重算通过后台任务调度
- 重算完成后再广播更新

### 4.4 先补埋点再优化，少走很多弯路

如果没有这次新增的分阶段埋点：

- 很容易误以为 `tmux` 慢
- 很容易误以为 `terminal_manager_snapshot` 一定是主犯
- 很容易误以为“已经后台化了，就不可能再卡主线程”

事实证明：
没有阶段耗时，优化很容易打偏。

---

## 5. 最终结果

最终结果很简单：

- 终端输入卡顿消失
- `workspace.discovery` 的 Host 收尾不再是大段同步阻塞
- `sync_titles` 的本地标题读取不再堵在 Host 主线程
- `terminal_manager_snapshot` 回落到几十毫秒量级

一句人话：
这次不是靠“多加几个 async”解决的，而是把真正不该留在 Host 主线程里的活，真的搬走了。

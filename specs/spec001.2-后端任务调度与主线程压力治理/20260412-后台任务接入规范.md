# 20260412-后台任务接入规范

这份文档只回答一个问题：

- 后面再新增后台任务时，应该按什么规则接到当前 `TaskManager`，而不是再长出新的 `inflight`、`timer`、私有队列和散装状态。

一句人话：
以后谁再想加“跨请求、可延后、要去重、要观测”的后台活，就照这份文档来。不要重新发明一套。

---

## 1. 什么任务必须走当前任务系统

满足下面任意两条，就默认应该进 `TaskManager`：

- 跨请求复用，同一个资源会被多个入口反复触发
- 不是这次 HTTP 响应必须当场完成的工作
- 同一资源需要按 `taskType + key` 去重
- 需要超时、取消、重试、并发限制
- 需要统一指标和调试观测
- 真正执行发生在 `host_background`、`helper_process`、`external_process`

当前已接入的标准样板就是：

- `workspace.discovery`
- `provider.capability_refresh`

参考实现：

- [session-history-service.ts](/Users/jackson/Code/CodingNS/apps/host/src/modules/sessions/session-history-service.ts)

## 2. 什么任务不要硬塞进来

下面这些东西，不归全局后台任务系统管：

- 请求主链路必需的同步逻辑
- 普通 CRUD
- 单次参数校验、权限校验、DTO 组装
- 会话运行时内部重试，比如 `queueRetryTimers`
- 某个 WebSocket 连接自己的一次性短任务

判断标准很简单：

- 如果这次请求不做就没法返回结果，这不是后台任务
- 如果它只活在一个运行时实例内部，不需要跨请求复用，也别硬塞

## 3. 新任务接入步骤

### 3.1 先定 `taskType`

规则：

- 使用稳定字符串，不要拼随机值
- 命名风格用 `domain.action`，例如 `workspace.discovery`
- 同一类任务只保留一个 `taskType`，不要在不同服务里各起一套近义词

推荐做法：

- 先把公共任务类型放到 [task-types.ts](/Users/jackson/Code/CodingNS/apps/host/src/modules/tasks/task-types.ts)
- 如果某个模块后续任务明显变多，再拆自己的 `task-types.ts`

不要这样干：

- `taskType: "refresh"`
- `taskType: "workspace_1_refresh"`
- `taskType` 里混入用户 ID、时间戳、请求 ID

### 3.2 把 `key` 设计对

`key` 决定去重效果。核心规则只有一句：

- 同一个资源的同一种后台任务，必须落到同一个 key

推荐写法：

- 工作区级任务：`workspaceId`
- provider 能力刷新：`provider + workspacePath`
- 项目级巡检：`projectId`

不要这样干：

- 每次 enqueue 都用 `createId()`
- 把时间戳塞进 key，导致永远去不了重
- 用模糊 key，把本来不同资源错误合并

### 3.3 选对执行位点

直接按这个表选，别拍脑袋：

| 执行位点 | 什么时候用 | 不该放什么 |
| --- | --- | --- |
| `host_background` | 轻 CPU、轻 I/O、轻聚合 | 重扫描、同步本地 I/O、大对象构造 |
| `helper_process` | 本地重扫描、provider 会话发现、重 I/O | 必须依赖当前请求上下文的短逻辑 |
| `external_process` | CLI / provider 命令、模型探测 | 高频、低成本、本地内存就能解决的事 |
| `request_main_thread` | 只保留给类型定义或兼容场景，正常不要拿它当后台位点 | 新的后台任务 |

一句人话：

- 只要怀疑会拖 Host 事件循环，就别留在 `host_background`

### 3.4 在服务初始化阶段注册，不要边跑边注册

推荐模式：

```ts
private registerBackgroundTasks(): void {
  if (!this.taskManager.has(HOST_TASK_TYPES.workspaceDiscovery)) {
    this.taskManager.register<WorkspaceDiscoveryInput, SessionListItem[]>({
      taskType: HOST_TASK_TYPES.workspaceDiscovery,
      executionLane: "helper_process",
      timeoutMs: 30_000,
      run: async (input) => this.runDiscoverWorkspaceSessions(input)
    });
  }
}
```

规范：

- 注册放在 service 构造后的初始化路径里
- 用 `has()` 防止重复注册
- `run()` 只做真正执行，不要把缓存判断、入口兜底、请求层分支也塞进去

参考实现：

- [session-history-service.ts](/Users/jackson/Code/CodingNS/apps/host/src/modules/sessions/session-history-service.ts)

### 3.5 请求入口要先走缓存，再决定 enqueue

标准顺序：

1. 先读缓存或最近结果
2. 命中则 `recordCacheHit(taskType, key)`
3. 未命中或过期，再 `enqueue`
4. 如果是后台刷新，不要把刷新 Promise 强绑到接口返回

推荐模式：

```ts
if (cached && !expired) {
  this.taskManager.recordCacheHit(HOST_TASK_TYPES.providerCapabilityRefresh, cacheKey);
  return cached.value;
}

const task = this.taskManager.enqueue<Input, Output>(HOST_TASK_TYPES.providerCapabilityRefresh, {
  key: cacheKey,
  source: "session_history.provider_capability_refresh",
  input
});
```

这里最重要的是：

- 接口返回和后台刷新要分开
- 背景刷新失败要吃掉并打日志，别把整个入口一起带崩

### 3.6 `source` 命名要能看懂

`source` 是给观测和调试面板看的，别写成废话。

推荐格式：

- `service_name.action_name`
- `session_history.discover_workspace_sessions`
- `session_history.provider_capability_refresh`

不要这样写：

- `refresh`
- `background`
- `task`

### 3.7 超时、并发、重试要保守

第一版规则：

- 默认先不配重试，除非你能明确证明这是幂等且值得重试
- 默认要给超时，别让任务无限挂着
- 只有同类任务真的会互相打架时，再配 `concurrency`

建议起步值：

- `host_background`：`timeoutMs` 5s 到 15s
- `helper_process`：`timeoutMs` 15s 到 30s
- `external_process`：`timeoutMs` 20s 到 60s

如果你想加重试，先回答三个问题：

1. 这个任务是不是幂等
2. 失败是不是短暂性问题
3. 重试会不会把外部系统打爆

答不清就先别加。

### 3.8 指标和观测不要另起炉灶

接入 `TaskManager` 后，这些指标已经自动有了：

- `enqueue`
- `dedupe`
- `started`
- `finished`
- `failed`
- `cancelled`
- `timeout`
- `wait_ms`
- `run_ms`
- `cache_hit`

规范：

- 不要再为同一任务维护第二套近义指标
- 调试面板要看的最近活动记录，直接走当前观测接口
- 平时不要为了调试常驻开启高成本采样

也就是说：

- 观测默认轻量
- 打开调试窗口时才开启高成本采样

### 3.9 测试必须补到位

每接一个新任务，至少补下面三类验证：

1. 任务管理器级
   - 去重
   - 超时 / 取消 / 并发限制
2. 任务接入点级
   - 缓存命中时会不会直接返回并记录 `cache_hit`
   - 重复触发时会不会复用同一个任务
3. 观测级
   - 任务执行后能不能在 `backgroundTasks` 或最近活动记录里看到

## 4. 推荐代码模板

### 4.1 注册模板

```ts
if (!this.taskManager.has(MY_TASK_TYPES.exampleRefresh)) {
  this.taskManager.register<ExampleInput, ExampleOutput>({
    taskType: MY_TASK_TYPES.exampleRefresh,
    executionLane: "helper_process",
    timeoutMs: 30_000,
    run: async (input) => {
      return await this.runExampleRefresh(input);
    }
  });
}
```

### 4.2 请求入口模板

```ts
if (cached && !expired) {
  this.taskManager.recordCacheHit(MY_TASK_TYPES.exampleRefresh, cacheKey);
  return cached.value;
}

return this.taskManager.enqueue<ExampleInput, ExampleOutput>(MY_TASK_TYPES.exampleRefresh, {
  key: cacheKey,
  source: "example_service.example_refresh",
  input: {
    workspaceId,
    userId
  }
}).promise;
```

### 4.3 后台刷新模板

```ts
const task = this.taskManager.enqueue<ExampleInput, void>(MY_TASK_TYPES.exampleRefresh, {
  key: cacheKey,
  source: "example_service.background_refresh",
  input
});

if (!task.deduped) {
  void task.promise.catch((error) => {
    logPerformance("example.refresh_failed", 0, {
      error: error instanceof Error ? error.message : "unknown"
    });
  });
}
```

## 5. 明确禁止的反模式

- 新建一个 `xxxInflight = new Map()`
- 新建一个 `xxxTicking`，但又不接统一调度指标
- 任务已经可复用，却继续每次请求现跑一次
- 用随机 key 导致去重失效
- 背景刷新失败直接把接口打成 500
- 为了调试常驻开启 `event loop` 采样
- 把会话运行时内部重试硬塞成全局任务

## 6. 新任务接入前的检查清单

在提交代码前，把下面这些问题过一遍：

- 这真的是跨请求、可延后、值得进入全局任务系统的任务吗？
- `taskType` 是否稳定、可读、不会重复？
- `key` 是否真的代表同一个资源？
- 执行位点是否选对？
- 请求入口是否先走缓存？
- 缓存命中时是否调用了 `recordCacheHit()`？
- 后台刷新失败时是否只记日志、不破坏原入口？
- 是否补了去重 / 缓存 / 观测相关测试？

如果这些问题有两三个都答不清，那就别提交。先把任务模型想明白。

# 需求文档 - spec007.1-外部仓库调试进程端口编排与启动适配

状态：Draft

## 简介

这个 Spec 解决的是一个已经摆在眼前的真实问题：

- 用户会在同一台机器上，同时打开多个外部 Git 仓库
- 同一个仓库还可能 fork 出多个工作树并行开发
- 每个仓库的调试进程默认都想监听自己的“习惯端口”

如果平台只会“启动命令”，不会“编排端口和访问入口”，那它只能跑单仓库 demo，撑不起真正的并行开发。

所以 `spec007.1` 的目标不是发明容器平台，而是用最实用、跨 `macOS/Linux/Windows` 都能落地的方式，把这件事做成标准能力：

- 主工作区在进程管理里登记真实启动项，子工作区直接继承这些启动模板
- 端口编排围绕“已登记启动项”进行，框架分析只负责判断注入方式和服务联动
- 通过用户可配置的动态端口池，给子工作区分配不冲突的新端口
- 优先通过参数、环境变量、临时覆盖文件改端口
- 尽量不碰用户仓库里的 tracked 文件
- 只有前面几层都失败时，才允许 AI 兜底编辑

## 术语表

- **Managed Repository（受管仓库）**：被 `CodingNS` 纳入调试管理的外部 Git 仓库
- **Debug Target（调试目标）**：一个可被启动和观察的调试单元，通常对应某个仓库或某个工作树
- **Debug Service（调试服务）**：调试目标中的一个具体服务，例如前端、后端、API、Worker、Mock 服务
- **Service Role（服务角色）**：平台对服务的语义分类，例如 `frontend/backend/worker/mock`
- **Launch Adapter（启动适配器）**：负责识别技术栈，并决定如何给服务注入端口的适配逻辑
- **Port Lease（端口租约）**：平台给某个调试服务临时分配的端口记录
- **Runtime Binding（运行时绑定）**：某次启动后，服务角色和真实监听端口之间的绑定关系
- **Override Artifact（覆盖产物）**：平台为了不改源码而临时生成的覆盖文件或脚本
- **AI Fallback Edit（AI 兜底编辑）**：前几种非侵入方式都失败后，才允许执行的受限代码修改

## 范围说明

### In Scope

- 项目框架分析与兼容性判定
- 外部仓库调试运行时的统一数据模型
- 调试服务角色与运行时绑定建模
- 启动适配器分层与优先级规则
- 端口租约分配、冲突检测、释放、崩溃回收
- AI 兜底编辑的准入、审计、回滚协议
- 第一阶段可落地的技术栈覆盖边界

### Out of Scope

- Docker、Kubernetes、Dev Container 等容器方案
- 操作系统级网络隔离
- 跨机器分布式调试编排
- 自动修复任意项目的全部构建问题
- 发布环境、生产环境端口治理

## 需求

### 需求 1：项目框架必须先被分析，再决定是否自动注入端口

**用户故事：** 作为用户，我希望平台先判断当前仓库到底是什么框架、支持到什么程度，再决定是否自动改端口，而不是看见一个 `dev` 命令就盲目下注。

#### 验收标准

1. WHEN 用户把外部仓库纳入调试管理 THEN System SHALL 先输出框架分析结果，包括候选框架、置信度、服务角色建议和兼容等级。
2. WHEN 框架兼容等级为 `supported/conditional` THEN System SHALL 才允许进入自动端口注入链路。
3. WHEN 框架兼容等级为 `unsupported/unknown` THEN System SHALL 默认关闭自动端口注入，并明确说明原因与下一步可选动作。
4. WHEN 框架需要额外处理前后端发现、HMR 或回调地址 THEN System SHALL 在分析结果里显式标注，不允许隐式跳过。

### 需求 1.1：前端必须把“分析展示”和“启动执行”分开

**用户故事：** 作为用户，我希望前端继续把仓库分析和框架识别结果展示出来，但我不希望页面再拿这些结果去猜启动方式，最后反而和我在进程管理里登记的命令打架。

#### 验收标准

1. WHEN 前端展示调试信息 THEN System SHALL 保留仓库分析、框架识别、兼容等级和说明信息。
2. WHEN 前端决定“哪些服务可以启动、当前被什么阻断、运行态怎么显示” THEN System SHALL 只以进程管理里已注册的启动项和其端口运行态作为判断依据。
3. WHEN 仓库分析结果和进程管理登记项不一致 THEN System SHALL 把分析结果当信息展示，而不是覆盖或猜测登记启动命令。

### 需求 1.2：主工作区启动模板必须能复制到子工作区，并重新编排端口

**用户故事：** 作为用户，我会先在主工作区的进程管理里把前端、后端和其他服务登记清楚。之后我 fork 出多个子工作区并行开发时，我希望这些登记项自动继承过来，但端口要重新编排，不能继续抢主工作区的默认端口。

#### 验收标准

1. WHEN 基于主工作区创建子工作区 THEN System SHALL 把主工作区里已登记的启动项复制到子工作区。
2. WHEN 启动项被复制到子工作区 THEN System SHALL 保留命令、工作目录相对关系、运行时类型和代理等模板信息，但运行端口不得继续写死使用主工作区默认端口。
3. WHEN 子工作区生成启动方案 THEN System SHALL 优先从端口池里为各服务分配新的可用端口，而不是因为默认端口被占用就直接停止。
4. WHEN 前端和后端同时存在 THEN System SHALL 在编排后给前端补上指向编排后后端地址的联动信息，保证访问链路不断。

### 需求 2：外部仓库调试服务必须有统一数据模型

**用户故事：** 作为平台维护者，我希望不同技术栈的调试服务都能映射到同一套模型里，这样端口管理、状态展示、日志和代理入口才能复用。

#### 验收标准

1. WHEN 用户把外部仓库纳入调试管理 THEN System SHALL 以统一结构描述该仓库下的调试目标、服务角色、启动入口和默认端口期望。
2. WHEN 某个调试目标被启动 THEN System SHALL 记录本次运行实例、服务实例、运行时绑定和关联端口租约。
3. WHEN 前端、后端、Worker 属于同一调试目标 THEN System SHALL 能区分它们的角色、启动方式和端口需求，而不是把它们混成一条命令。

### 需求 3：启动适配必须分层，不允许默认直接改源码

**用户故事：** 作为用户，我希望平台优先用最小破坏的方式解决端口冲突，而不是一上来就把我的仓库改脏。

#### 验收标准

1. WHEN 平台准备启动调试服务 THEN System SHALL 先尝试 `CLI 参数覆盖`、`环境变量覆盖`、`运行时覆盖文件` 这些非侵入方式。
2. WHEN 已有非侵入方式可行 THEN System SHALL 不进入 AI 兜底编辑流程。
3. WHEN 适配器识别到技术栈 THEN System SHALL 返回所选注入方式、使用的端口字段、失败原因和下一层兜底路径。

### 需求 4：端口分配必须做成租约机制，而不是临时猜数字

**用户故事：** 作为系统维护者，我希望端口分配可追踪、可回收、可复用，而不是每次靠扫描和猜测。

#### 验收标准

1. WHEN 调试服务启动前申请端口 THEN System SHALL 为每个服务角色分配独立的 `Port Lease`，并记录归属目标、服务和过期状态。
2. WHEN 进程正常退出、启动失败或崩溃失联 THEN System SHALL 释放或标记失效租约，避免端口长期被脏占用。
3. WHEN 端口已被其他受管运行时持有 THEN System SHALL 拒绝重复分配，并返回明确冲突信息。
4. WHEN 用户在设置页修改端口池范围 THEN System SHALL 用新的范围参与后续子工作区编排，并校验范围是否合法且不重叠。

### 需求 5：AI 兜底编辑必须受严格约束

**用户故事：** 作为用户，我接受在极少数情况下让 AI 帮我改端口，但我不接受它随便改我的仓库。

#### 验收标准

1. WHEN 平台进入 AI 兜底编辑 THEN System SHALL 先记录触发原因、识别失败点、建议修改文件和目标端口。
2. WHEN AI 生成改动 THEN System SHALL 只允许触达端口相关配置文件和启动入口文件，不允许无边界扩散编辑。
3. WHEN AI 编辑完成 THEN System SHALL 保存补丁、回滚信息和受影响文件列表，并允许用户在提交前一键回退。

### 需求 6：第一阶段必须画清边界，先解决最值钱的 80%

**用户故事：** 作为负责人，我希望第一阶段能真正落地，而不是把所有技术栈和所有边角情况都写进计划里最后谁也做不完。

#### 验收标准

1. WHEN 第一阶段范围被确认 THEN System SHALL 明确优先覆盖的技术栈、支持的服务角色和不支持场景。
2. WHEN 仓库超出第一阶段支持范围 THEN System SHALL 明确告诉用户是“未适配”，而不是假装能跑。
3. WHEN 第一阶段交付完成 THEN System SHALL 至少能闭环处理常见前端、Node 后端和常见 JVM/Python 单服务项目的端口冲突。

## 非功能需求

### 非功能需求 1：跨平台一致性

1. WHEN 调试运行在 `macOS/Linux/Windows` THEN System SHALL 依赖跨平台可用的进程、文件和命令调用方式，不把主链路建立在单一操作系统特性上。
2. WHEN 某个技术栈只在部分平台可用 THEN System SHALL 明确标注适配限制，而不是把失败归咎于用户。

### 非功能需求 2：兼容性矩阵必须可维护

1. WHEN 新增或调整框架支持策略 THEN System SHALL 同步更新兼容性矩阵，明确兼容等级、推荐注入方式、额外处理项和 AI 兜底条件。
2. WHEN 产品或实现侧判断某框架“可自动注入” THEN System SHALL 能在矩阵里找到对应依据，而不是凭经验写死。

### 非功能需求 3：可追踪性

1. WHEN 调试启动失败 THEN System SHALL 返回失败发生在哪一层适配链路，例如参数覆盖失败、环境变量无效、覆盖文件未生效、AI 编辑被拒绝。
2. WHEN 平台回收端口 THEN System SHALL 能追溯该端口最后归属过哪个运行时和服务。

### 非功能需求 4：零污染优先

1. WHEN 存在非侵入式覆盖方案 THEN System SHALL 不修改用户仓库中的 tracked 文件。
2. WHEN 不得不生成临时覆盖产物 THEN System SHALL 将其写入平台可控目录或明确忽略路径，避免污染正式提交。

### 非功能需求 5：可维护性

1. WHEN 新增一个技术栈适配器 THEN System SHALL 通过注册新适配器扩展，而不是改动所有启动主链路。
2. WHEN 后续要支持更多框架 THEN System SHALL 允许按“识别器 + 注入器 + 验证器”补齐，不要求推翻现有模型。

## 成功定义

- 平台会先分析项目框架，再决定是否自动开启端口注入
- 平台能用统一模型描述外部仓库的调试服务
- 平台能优先通过非侵入式方式解决大部分端口冲突
- AI 改代码被明确降级为兜底，而不是默认行为
- 第一阶段范围清楚，用户知道什么能跑、什么暂时不能跑

# 20260413-框架兼容矩阵

这份文档只回答几件事：

1. 这个框架要不要自动开启端口注入
2. 推荐先用哪种注入方式
3. 是否要额外处理前后端发现、HMR、回调地址
4. 什么情况下直接判定进入 AI 兜底，什么情况下连 AI 都别进

先说总规则：

- 只有 `兼容等级 = supported/conditional` 才允许自动开启端口注入
- `unsupported/unknown` 默认不自动注入
- AI 兜底不是默认入口，只是前三层都失败后的受限补救

## 兼容等级说明

- `supported`：框架官方就有明确端口覆盖入口，且常见项目写法稳定，平台可默认自动注入
- `conditional`：框架本身可注入，但项目常常需要额外处理服务发现、HMR、回调地址，满足条件后才自动注入
- `unsupported`：第一阶段不自动注入，默认直接拒绝
- `unknown`：没识别出来或证据不足，默认不自动注入

| Next.js | supported | `cli` 优先，`env` 次之 | 常见需要处理 rewrites、前后端发现；SSR 项目通常按单服务处理 | conditional | 端口入口明确，但不要轻易拆成前后端两个服务 |

| Uvicorn / FastAPI | supported | `cli` 优先，`env` 次之 | 若前端分离，需补 API 地址发现 | conditional | 单服务后端兼容度高 |
| Flask | supported | `cli` 优先，`env` 次之 | 若前端分离，需补 API 地址发现 | conditional | 单服务项目很适合第一阶段 |

| Rails | supported | `cli` 优先 | 若有前后端分离或 OAuth callback，需额外提醒 | conditional | 单服务后端兼容较好 |
| ASP.NET Core | supported | `env` 优先 | 若有 SPA proxy 或 callback，需额外校验 | conditional | 官方 URL 注入能力清楚 |
| NestJS | conditional | `env` 优先 | 取决于仓库是否按 `process.env.PORT` 写；若自带 WebSocket/Microservice，要额外分析 | conditional | 框架没问题，仓库写法波动大 |
| Express / Koa / Hono / Node 自定义服务 | conditional | `env` 优先 | 端口常被写死在代码里；若 API 地址硬编码，需额外处理 | allowed | 只有确认读 `PORT` 或可收敛改动文件时才进入 AI |
| Node SSR / BFF 自定义服务 | conditional | `env` 或 `override` | 常见需要处理前后端发现、回调地址 | allowed | 可做，但第一阶段不要承诺全自动 |
| Go 自定义 HTTP 服务 | unsupported | `none` | 端口常直接写死在代码里 | conditional | 第一阶段默认不自动注入，是否进入 AI 看文件是否可收敛 |
| Laravel / PHP 自定义服务 | conditional | `cli/env` 或 `override` | 启动形态差异大，需要先识别是内置 server 还是其他运行方式 | allowed | 不建议第一阶段默认全开 |
| Remix / 复杂全栈 dev server | conditional | `cli/env` | 常见需要处理 HMR、SSR、回调与代理 | allowed | 按单服务看，别急着拆 |
| Electron / Tauri / 原生壳开发模式 | unsupported | `none` | 常见牵扯壳层 dev URL、bridge、CSP、证书 | never | 第一阶段默认拒绝自动注入，也不直接放 AI 进去乱改 |

| 未识别框架 | unknown | `none` | 无法判断额外处理项 | conditional | 默认不自动注入；只有用户显式确认且候选文件可收敛时，才允许受限 AI |

## 推荐注入方式说明

- `cli`
  - 适合官方本来就支持 `--port`、`-p` 这类参数的框架
  - 优点是最少污染、最容易回滚
- `env`
  - 适合官方约定明确使用环境变量读取端口的框架
  - 优点是跨平台、易注入
- `override`
  - 适合可生成临时配置文件、临时脚本或附加启动参数的项目
  - 只有前两种不够时才上
- `none`
  - 当前阶段不应自动注入

## 哪些框架必须额外处理前后端发现 / HMR

### 必须额外处理前后端发现

- Vite 前后端分离项目
- Next.js 接独立后端项目
- CRA / Vue CLI 接独立后端项目
- NestJS / Express / 自定义 Node 后端被前端消费
- 所有前端代码里硬编码 API 地址的项目

推荐做法：

1. 优先改成同源 `/api`
2. 不行就注入 `API_BASE_URL`
3. 再不行才考虑生成临时 override

### 必须额外处理 HMR / WebSocket

- Vite
- CRA
- Vue CLI
- 一些自带 HMR WebSocket 的 SSR dev server

这类项目不能只看 HTTP 端口，还要检查：

- HMR client port
- WebSocket path
- 代理下的 ws 转发

### 必须额外提醒 callback / redirect

- Next.js / Nuxt / Remix 这类带登录流的项目
- Django / Rails / Spring Boot / ASP.NET Core 等带本地 OAuth callback 的项目
- 有 webhook / 本地回调 URL 的项目

## 哪些场景直接判定进入 AI 兜底

只有同时满足下面条件，才允许进 AI：

1. 框架兼容等级是 `supported` 或 `conditional`
2. 已尝试 `cli`、`env`、`override`
3. 候选配置文件可收敛到有限列表
4. 改动范围能限制在端口和开发配置相关文件

常见允许进入 AI 的场景：

- Express/Nest 项目端口支持写在少量配置文件里，但没暴露统一环境变量
- Go/PHP 项目虽然不在第一阶段自动支持范围内，但端口配置文件非常集中
- 前端项目 API 地址集中在单独开发配置文件里，可安全替换

## 哪些场景直接判定不进入 AI

下面这些情况，默认连 AI 都别进：

- 复杂 monorepo，一条命令会起多个隐式子服务
- 原生壳开发模式（Electron/Tauri/移动端桥接）
- 候选文件收敛失败，AI 需要大范围搜索和推断
- API 地址、回调地址、端口写死在大量业务源码里
- 回滚路径不清楚

一句人话：
如果 AI 改完以后你都不知道该怎么撤，那一开始就别让它改。

## 第一阶段落地建议

优先默认支持：

- Vite
- Next.js
- CRA
- Astro
- Nuxt
- Spring Boot
- Uvicorn / Flask / Django
- Rails
- ASP.NET Core

谨慎支持：

- NestJS
- Express / Koa / Hono / Node 自定义服务
- PHP 常见本地服务

第一阶段默认不支持：

- 复杂 monorepo 自动拆服务
- Electron / Tauri / 移动端壳开发模式
- 未识别框架的全自动注入

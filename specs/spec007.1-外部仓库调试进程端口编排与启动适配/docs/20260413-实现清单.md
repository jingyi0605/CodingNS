# 20260413-实现清单

这份文档不是再讲一遍原则，而是把 `spec007.1` 往下压到“可以开始拆开发任务”的层级。

重点回答四件事：

1. 后端需要新增哪些表
2. 框架分析结果 API 怎么定义
3. 前端兼容矩阵页面或调试面板怎么展示
4. 哪些字段要进入 `LauncherProfile / ProcessInstance` 关联模型

## 1. 第一阶段实现目标

第一阶段只做一条能跑通的主链路：

1. 用户选中一个外部仓库或某个 worktree
2. 平台分析项目框架与兼容等级
3. 只有兼容框架才允许自动注入端口
4. 平台为每个调试服务分配端口租约
5. 平台生成启动计划并启动
6. 平台记录运行时、绑定关系和失败阶段

一句人话：
第一阶段先做到“能分析、能判断、能启动、能回收、能解释失败”，不要一上来就做成万能编排器。

## 3. 建议复用而不是新建的现有表

下面这些不要重复造轮子：

- `workspaces`
  - 继续作为路径边界和权限归属
- `workspace_worktrees`
  - 继续作为 worktree 血缘关系来源
- `LauncherProfile`
  - 继续作为底层可执行启动配置
- `ProcessInstance`
  - 继续作为底层进程实例真相源
- `ProcessPortBinding`
  - 继续保留底层端口探测记录

一句人话：
新表只补“外部仓库调试编排”这一层，不重做 `spec007` 已经定义好的地基。

## 4. 框架分析结果 API

第一阶段 API 不要铺太大，先把“分析、查看、刷新、矩阵查询”做实。

### 4.1 `POST /api/debug-targets/analyze`

作用：

- 对某个仓库或 worktree 执行一次框架分析

输入：

```json
{
  "workspaceId": "ws_123",
  "rootPath": "/repo/path",
  "commandHints": ["pnpm dev", "pnpm --filter web dev"]
}
```

输出：

```json
{
  "target": {
    "id": "dt_123",
    "workspaceId": "ws_123",
    "rootPath": "/repo/path",
    "displayName": "demo-repo",
    "sourceType": "worktree"
  },
  "services": [
    {
      "id": "svc_frontend",
      "role": "frontend",
      "name": "web",
      "cwd": "/repo/path/apps/web",
      "command": "pnpm",
      "args": ["dev"]
    }
  ],
  "analyses": [
    {
      "id": "fa_123",
      "serviceId": "svc_frontend",
      "primaryFramework": "vite",
      "confidence": "high",
      "compatibilityLevel": "supported",
      "recommendedInjectionMode": "cli",
      "requiresServiceDiscoveryHandling": true,
      "requiresHmrHandling": true,
      "requiresCallbackHandling": false,
      "aiFallbackPolicy": "conditional",
      "reasons": [
        "命中 vite.config.ts",
        "package.json 含 vite dev 命令"
      ],
      "detectedFiles": [
        "apps/web/vite.config.ts",
        "apps/web/package.json"
      ]
    }
  ],
  "autoInjectionEligible": true
}
```

错误：

- `400 VALIDATION_ERROR`
- `404 WORKSPACE_NOT_FOUND`
- `409 ANALYSIS_ALREADY_RUNNING`

### 4.2 `GET /api/debug-targets/{targetId}/framework-analysis`

作用：

- 返回目标当前保存的分析结果，给前端调试面板直接展示

输出：

```json
{
  "targetId": "dt_123",
  "items": [
    {
      "serviceId": "svc_frontend",
      "primaryFramework": "vite",
      "compatibilityLevel": "supported",
      "recommendedInjectionMode": "cli",
      "requiresServiceDiscoveryHandling": true,
      "requiresHmrHandling": true,
      "requiresCallbackHandling": false,
      "aiFallbackPolicy": "conditional",
      "reasons": ["命中 vite.config.ts"]
    }
  ]
}
```

### 4.3 `POST /api/debug-targets/{targetId}/framework-analysis/refresh`

作用：

- 强制重跑框架分析

输出：

- 与 `POST /api/debug-targets/analyze` 同结构，但目标已存在

### 4.4 `GET /api/framework-compatibility-matrix`

作用：

- 前端查询系统内置的兼容矩阵，用于说明“为什么这个框架自动支持/不支持”

输出：

```json
{
  "version": "2026-04-13",
  "items": [
    {
      "framework": "vite",
      "compatibilityLevel": "supported",
      "recommendedInjectionMode": "cli",
      "requiresServiceDiscoveryHandling": true,
      "requiresHmrHandling": true,
      "requiresCallbackHandling": false,
      "aiFallbackPolicy": "conditional"
    }
  ]
}
```

## 5. 启动计划和运行时 API

这部分不要求一次做完全部功能，但建议从下面这几个口子起步。

### 5.1 `POST /api/debug-targets/{targetId}/launch-plan`

作用：

- 先生成启动计划，不直接启动
- 把租约端口、推荐注入方式、额外处理项先算出来

输出重点：

- 每个服务将用什么端口
- 允许使用哪种注入方式
- 是否缺少服务发现 / HMR / callback 处理
- 当前是否允许自动启动

### 5.2 `POST /api/debug-targets/{targetId}/run`

作用：

- 启动整个调试目标

输出重点：

- `runtimeSession`
- 每个服务的 `processInstanceId`
- 每个服务的租约端口

### 5.3 `GET /api/debug-runtimes/{runtimeId}`

作用：

- 给前端调试面板看当前运行态

输出重点：

- 运行时状态
- 服务状态
- 框架分析结果摘要
- 绑定端口
- 失败阶段

## 6. 前端展示建议

第一阶段不要新长一整套复杂页面，先把信息插进现有工作区管理和进程面板体系里。

### 6.1 工作区管理页新增“调试目标”卡片

建议位置：

- `workspaceManagement` 区域
- 或工作区详情页的新增折叠卡片

建议展示：

- 目标名称
- 仓库根路径
- 服务数量
- 最近分析时间
- 是否允许自动注入

### 6.2 `FrameworkAnalysisCard`

每个服务一张卡，至少展示：

- 服务角色：`frontend/backend/worker`
- 主框架：如 `vite`、`spring-boot`
- 兼容等级：`支持 / 条件支持 / 不支持 / 未识别`
- 推荐注入方式：`CLI / ENV / Override / 不自动注入`
- 额外处理标签：
  - 需要前后端发现
  - 需要 HMR 处理
  - 需要 callback 提醒
- AI 兜底策略：
  - 不允许
  - 条件允许
  - 可作为最后兜底

### 6.3 兼容矩阵说明弹层

建议入口：

- 调试目标面板里的“兼容规则”
- 或设置页里的“框架兼容性”

建议展示：

- 框架列表
- 当前等级
- 推荐注入方式
- 额外处理项
- 是否允许 AI 兜底

这块不要做成营销页，要做成排障说明页。

### 6.4 运行时调试面板

建议在运行态展示：

- 当前运行时状态
- 每个服务的租约端口
- 实际监听端口
- 注入方式
- 失败阶段
- 是否触发了 AI 兜底
- 是否还存在未处理的服务发现/HMR 条件

一句人话：
用户看到“启动失败”，必须一眼知道是框架不支持、HMR 没配、还是端口申请失败。

## 7. `LauncherProfile` 建议新增字段

`LauncherProfile` 还是底层启动配置，不要把所有上层语义塞进去，但下面这些字段值得补：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `sourceType` | string | `manual/debug_service`，区分手工配置和系统生成 |
| `debugTargetId` | string \| null | 归属调试目标 |
| `debugServiceId` | string \| null | 归属调试服务 |
| `frameworkAnalysisId` | string \| null | 命中的框架分析 |
| `adapterKind` | string \| null | `cli/env/override/ai_fallback` |
| `injectionMode` | string \| null | 本次推荐的注入方式 |
| `generatedArtifactRef` | string \| null | 临时覆盖产物引用 |
| `serviceDiscoveryMode` | string \| null | `same_origin/api_base_url/none` |
| `managedBySystem` | boolean | 是否由系统自动生成 |

原则：

- `LauncherProfile` 记录“怎么起”
- 不记录运行态端口真相
- 运行态真相留给 `RuntimeBinding` 和 `ProcessInstance`

## 8. `ProcessInstance` 建议新增字段

`ProcessInstance` 仍然是底层进程实例，但需要和调试编排层连起来。

建议新增：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `runtimeSessionId` | string \| null | 归属调试运行时 |
| `debugTargetId` | string \| null | 归属调试目标 |
| `debugServiceId` | string \| null | 归属调试服务 |
| `launcherSourceType` | string \| null | `manual/debug_service` |
| `launchStage` | string \| null | 当前启动阶段 |
| `failureStage` | string \| null | 失败阶段 |
| `adapterKind` | string \| null | 实际采用的注入方式 |
| `envPatchSummary` | json \| null | 端口和关键环境变量补丁摘要 |
| `artifactRef` | string \| null | 临时覆盖产物引用 |

原则：

- `ProcessInstance` 记录“这次怎么跑的、跑到哪一步挂了”
- 详细端口列表继续放 `ProcessPortBinding`
- 详细租约归属继续放 `port_leases` / `runtime_bindings`

## 9. 建议实现顺序

按这个顺序做，返工最少：

1. 新增表与仓储
2. 落地 `FrameworkAnalysisResult`
3. 做分析 API
4. 做兼容矩阵查询 API
5. 扩展 `LauncherProfile / ProcessInstance`
6. 做启动计划 API
7. 做运行时详情 API
8. 最后再补前端展示

## 10. 第一阶段完成标志

做到下面这些，就算第一阶段真的站住了：

- 用户能看到某个仓库被识别成什么框架
- 系统能明确说出是否允许自动端口注入
- 系统能生成启动计划并分配端口租约
- 运行时能展示每个服务的端口、注入方式和失败阶段
- AI 兜底是否允许，有明确规则和记录

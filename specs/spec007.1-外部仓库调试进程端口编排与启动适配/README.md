# spec007.1-外部仓库调试进程端口编排与启动适配

## 当前定位

`spec007` 解决的是“进程怎么被平台管理起来”。

`spec007.1` 解决的是另一个更脏、更现实的问题：

- 这个 IDE 托管的不是它自己一个仓库，而是很多外部 Git 仓库
- 这些仓库各自有前端、后端、Mock、Worker、HMR、热更新 WebSocket
- 它们默认都爱抢 `3000`、`5173`、`8080`、`8000`
- 如果只会“把命令跑起来”，那多开几个工作树以后一定会撞端口

一句人话：
先把“外部仓库调试进程怎么安全地跑起来”这件事标准化，再谈更高级的并行开发体验。

这个子 Spec 的目标很明确：

- 统一描述外部仓库调试服务的数据模型
- 先用“启动适配 + 运行时端口注入”解决大多数冲突
- 把端口租约、回收、冲突检测做成平台能力
- 明确 AI 改代码只允许当兜底，不允许当默认主路径
- 给第一阶段画清边界，避免一上来就做成半个容器平台

## 计划覆盖

- 外部仓库调试进程统一数据模型
- 启动适配器分层设计
- 端口分配、续租、释放、崩溃回收规则
- AI 兜底编辑的准入条件、记录要求和回滚约束
- 第一阶段最小可落地边界

## 依赖关系

- 前置依赖：`spec001`、`spec005`、`spec006`、`spec007`
- 直接影响：
  - `apps/host`
  - `apps/user-app`
- 后续承接：
  - `spec012.1-Git工作树与工作区分叉基础`
  - `spec012-并行项目编排与结果对比`

## 本阶段明确不做

- 不做 Docker / Dev Container / 容器编排
- 不做操作系统级隔离网络
- 不做 Linux 专属 `netns` 方案
- 不把 AI 改源码当默认主链路
- 不承诺第一阶段覆盖所有技术栈
- 不做“一次识别全仓库所有服务并全部零配置跑通”的神话能力

## 与 spec007 的关系

- `spec007` 负责“进程管理底座”
- `spec007.1` 负责“外部仓库调试运行时编排”

两者不是重复关系，而是上下层关系：

- 没有 `spec007`，`spec007.1` 没有稳定的进程、日志、端口、启动器底座
- 没有 `spec007.1`，`spec007` 只能管理单个命令，解决不了外部仓库多服务、多工作树、多端口冲突

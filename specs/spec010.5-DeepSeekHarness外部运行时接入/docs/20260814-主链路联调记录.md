# 主链路联调记录

## 本次结果

- Provider：`deepseek-harness`
- Sidecar：按需启动，本机 loopback 动态端口，Host 收尾时仅结束自己启动的子进程。
- 创建和发送：`session.create`、`session.prompt`。
- 历史和事件：`session.history`、mux/host 两条下行流；重复或旧 seq 不会再次广播。
- 中断和队列：`session.cancel`、`session.prompt(mode=queue|steer)`。
- 权限和问题：Harness 原始 `rpcId` 保存到现有权限请求，用户回答从 `/api/respond` 回写。
- 附件：仅图片；Host 在读取前校验工作区边界和 10 MiB 上限。
- Fork：DeepSeek 会话级和消息级分叉调用 Harness 原生 `session.fork`；消息级先将 CodingNS 消息 ID 反查为 Harness `seq`。其他 Provider 分叉到 DeepSeek 时，选中范围内的可见用户和助手文本会重建为新会话首条 prompt，不伪造原生跨 Provider 历史复制。
- Skill：`deepseek-harness` 已作为受管理 Skill 目标，根目录为 `DSH_HOME/skills`，默认 `~/.dsh/skills`。Host 启动 sidecar 时传入同一份 `DSH_HOME`；DeepSeek 会话的 Composer `@` 搜索只查这个目标。

## 真实模型故障回归

- 现象：用户发送第二条消息后，界面一直显示生成中，未显示回复。
- 真实证据：Harness 的 `session.history` 返回第二轮从 `turn/start` 到 `turn/end` 的完整事件；其中有连续的 `assistant/chunk`、最终 `assistant/message`，并记录了模型用时和输出 token。这说明凭据、模型路由和上游调用均已成功。
- 根因：CodingNS 在 WebSocket 订阅尚未建立时就发送 `session.prompt`。模型快速完成时，mux/host 事件会落在订阅空窗期，输出和完成状态无法进入现有会话流。
- 修复：事件桥的 `watch()` 现在等待 mux 与 host 两条订阅都连接成功才返回；运行时适配器随后才发送 `session.prompt`。补充了“模型立即完成”夹具回归，断言消息和 completed 状态都会进入事件 sink。
- 本轮修复验证未额外调用真实模型，避免重复消耗用户额度。

## 不支持项

删除、收藏、Changed Files/Diff、Session Share、独立 resume RPC 和 MCP 管理均保持关闭。跨 Provider 的原生历史复制也不提供；目前只支持其他 Provider 到 DeepSeek 的可见文本重建。模型目录只属于 Harness 会话，不进入 CodingNS 的全局模型目录。

## 2026-08-15 Fork 与 Skill 回归

- DeepSeek 内部会话 Fork：调用 `session.fork({ sessionId })`，新会话保存 `native_session_fork` 元数据。
- DeepSeek 消息 Fork：先在完整 Harness history 中定位 CodingNS 消息 ID，再调用 `session.fork({ sessionId, atSeq })`；继承消息数按该完整 Fork turn 映射后的标准消息数量记录，不把 Harness event `seq` 当作消息数。
- 其他 Provider 到 DeepSeek：只把锚点及之前的用户和助手文本作为新会话的初始 prompt；锚点后的文本、源 Provider 私有事件、附件、工具和权限状态不会复制。
- Skill：`deepseek-harness` 已加入 Provider catalog、Skill target adapter、SQLite `skill_target_bindings` 约束和 Composer mention 目标映射。旧库升级时保留原有 Skill 绑定。
- 空 Skill 目录：`DSH_HOME/skills` 在还没有同步任何 Skill 时可以不存在，扫描按正常空态处理，不再显示“还没准备好”；首次同步时自动创建目录。

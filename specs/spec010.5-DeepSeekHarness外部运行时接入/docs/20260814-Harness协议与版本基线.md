# Harness 协议与版本基线

## 固定版本

- 上游仓库：`https://github.com/deepseek-ai/deepseek-harness`
- 固定版本：`0.1.0-rc.5`
- 校验提交：`47f943859bef60e4160492346772ded9b24f765a`
- 运行前提：Node.js 22；Harness 仍是 Developer Preview，升级前必须先跑本 Spec 的 fake server 和适配器测试。

CodingNS 不合并 Harness 源码，也不直接引用它的 TypeScript 类型。Host 只通过本机 HTTP/WebSocket 调用固定协议。

## 启动约束

默认命令：

```text
dsh web --host 127.0.0.1 --port <动态端口>
```

默认绑定 `127.0.0.1`。`CODINGNS_DEEPSEEK_HARNESS_HOST` 只接受 `127.0.0.1` 或 `0.0.0.0`；后者必须由用户显式配置，并会把 sidecar 暴露到所有本机网络接口，部署时应由防火墙和访问网络控制。可用 `CODINGNS_DEEPSEEK_HARNESS_COMMAND` 覆盖可执行文件路径。版本校验调用 `dsh --version`；固定版本的 `host.describe.version` 是上游占位值 `0.0.1`，不能用于版本校验。

## RPC 约定

普通调用为 `POST /api/<method>`：

```json
{
  "type": "client-request",
  "rpcId": "uuid",
  "method": "session.create",
  "payload": { "cwd": "由 Host 校验后的工作区路径" }
}
```

响应必须是同一 `rpcId` 的 `server-response`。HTTP 错误、信封错误与 `result.ok=false` 分别转换为 transport、protocol、business 三类错误。

对 approval/question 的回复必须 `POST /api/respond`，使用原始 `rpcId`：

```json
{
  "type": "client-response",
  "rpcId": "原始 server-request 的 rpcId",
  "result": { "ok": true, "value": {} }
}
```

## 下行事件

- `GET /api/events.mux`：`session/event`、tool、approval、question、queue。
- `GET /api/events.host`：会话运行状态和 Agent 错误。

socket 只做下行推送，不能发送业务命令。`events.mux.since` 在固定版本没有可依赖的恢复实现，连接中断后必须先调用 `session.history` 补齐，再重建 mux/host 订阅。

## 测试夹具

`apps/host/tests/fixtures/deepseek-harness-fake-server.ts` 不读取真实模型密钥、用户主目录或工作区。它覆盖正常结果、业务错误、错配 rpcId、未知方法、mux/host 推送和连接关闭。

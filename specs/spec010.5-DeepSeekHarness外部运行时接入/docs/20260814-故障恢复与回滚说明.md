# 故障恢复与回滚说明

## 运行时故障

| 现象 | Host 行为 | 运维处理 |
| --- | --- | --- |
| sidecar 无法启动 | 返回 `HARNESS_SIDECAR_START_FAILED`，其他 Provider 不受影响 | 检查 `CODINGNS_DEEPSEEK_HARNESS_COMMAND` 和固定版本 |
| HTTP 失败或超时 | 返回 `HARNESS_RPC_TRANSPORT_ERROR` | 确认本机进程和 loopback 端口，没有暴露远程地址 |
| rpcId 或信封异常 | 返回 `HARNESS_RPC_PROTOCOL_ERROR` | 停止升级，使用 fake server 对比协议 |
| WebSocket 断开 | TaskManager 合并 `harness.session.reconcile`，先补历史再重连 | 保留 session binding，不删除会话 |
| history 无法补洞 | 会话进入降级/不可用状态 | 收集脱敏日志，等待 Harness 修复或重新发起会话 |

任务观测使用稳定 taskType：`harness.sidecar.health` 和 `harness.session.reconcile`。可在现有运行时观测中看到 enqueue、dedupe、started、finished、failed 和 timeout。

## 回滚

1. 在 Provider 控制中禁用 `deepseek-harness`，新会话不会再选择它。
2. 重启 Host；Host 只会回收它自己启动的 sidecar，不会影响用户手工启动的 Harness。
3. 保留现有 session index/binding 和外部 `harness://` 引用，避免丢失历史诊断线索。
4. 回滚本 Spec 对应的实现提交；其他 Provider 不依赖 Harness 包或进程，不需要数据迁移。

不要把 Harness 监听地址改为非 loopback；当前 Web API 没有适合公网暴露的认证边界。

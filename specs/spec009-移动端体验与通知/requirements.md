# 需求文档 - spec009-移动端体验与通知

状态：Draft

## 简介

这个 Spec 解决的不是“在手机上再造一个桌面 IDE”，而是让用户在离开工位时也能安全、连续地掌控工作区状态。

移动端第一阶段只做两件事：

- 查看关键信息（会话、文件变化、Git 状态、进程状态、日志）
- 做少量高价值操作（回复会话、小改文件、轻量 Git 操作、启停进程）

同时把通知做好：只提醒真正需要人处理的事情，不做噪音轰炸。

## 术语表

- **System**：`码不能停` 的移动端客户端 + `CodingNS Host`
- **Mobile Client（移动端客户端）**：Android / iOS 应用，复用 `ui-web` 的能力模型
- **Light Action（轻操作）**：在手机上低风险、低输入成本、可快速完成的操作
- **Protected Data（受保护数据）**：工作区、会话、文件、Git、进程、日志等登录后才可访问的数据
- **Notification Rule（通知规则）**：决定“什么事件需要提醒、用什么级别提醒、是否需要人工介入”的规则
- **Intervention Event（人工介入事件）**：系统无法自动处理，必须由用户确认或操作的事件

## 范围说明

### In Scope

- 移动端信息架构与导航方式
- 会话查看与回复
- 文件 / Git / 进程轻操作
- 全屏终端与日志查看边界
- 通知与提醒策略（会话进展、进程状态、关键失败、人工介入）
- 登录态保护与移动端鉴权行为

### Out of Scope

- 在手机上实现桌面级多面板开发体验
- 重新定义 `spec003/004/005/007/008` 已确定的核心协议
- 团队协作通知体系与复杂审批流
- 推送渠道的企业集成（如企业 IM 深度联动）

## 需求

### 需求 1：移动端信息架构必须围绕“查看 + 轻操作”

**用户故事：** 作为移动端用户，我希望首页结构清晰、入口少而准，以便我在几秒内找到当前最需要处理的工作区和会话。

#### 验收标准

1. WHEN 用户打开移动端 THEN System SHALL 在首页展示工作区摘要、待处理会话和关键告警，不要求进入多级菜单才能看到核心信息。
2. WHEN 用户进入工作区 THEN System SHALL 按“会话、文件、Git、进程”组织轻操作入口，并保证返回路径简单。
3. WHEN 交互设计评审 THEN System SHALL 明确“移动端不做桌面 IDE 仿制”，不出现复杂多栏或高密度编辑布局。

### 需求 2：会话查看与回复必须可用且连续

**用户故事：** 作为在外办公的开发者，我希望在手机上继续同一条会话，以便不中断上下文。

#### 验收标准

1. WHEN 用户打开移动端会话页 THEN System SHALL 展示与桌面端一致的会话消息序列和状态，不出现第二套会话记录。
2. WHEN 用户发送回复 THEN System SHALL 支持发送中、成功、失败三态反馈，并允许失败重试。
3. WHEN 网络抖动或中断 THEN System SHALL 在恢复连接后补齐缺失消息，并提示同步状态。

### 需求 3：文件 / Git / 进程能力只提供高价值轻操作

**用户故事：** 作为移动端用户，我希望在手机上能快速处理小问题，而不是被迫做重型操作。

#### 验收标准

1. WHEN 用户访问文件能力 THEN System SHALL 支持文件浏览、预览、小范围编辑和保存，并限制高风险批量操作。
2. WHEN 用户访问 Git 能力 THEN System SHALL 支持状态查看、diff 查看、轻量提交与推送前确认，不要求在手机上完成复杂分支管理。
3. WHEN 用户访问进程能力 THEN System SHALL 支持查看运行状态、日志片段、启动/停止/重启，且操作前展示明确影响范围。

### 需求 4：终端与日志必须以全屏查看为主，输入操作受控

**用户故事：** 作为用户，我希望在手机上看终端和日志时可读性高，不被小屏幕挤压。

#### 验收标准

1. WHEN 用户进入终端或日志页面 THEN System SHALL 使用全屏模式展示输出，保证滚动、复制、检索基础体验可用。
2. WHEN 用户执行终端输入 THEN System SHALL 默认仅允许命令模板或显式确认后的手动输入，避免误触高风险命令。
3. WHEN 日志量较大 THEN System SHALL 支持分段加载或按时间窗口查看，不阻塞页面交互。

### 需求 5：通知必须围绕关键事件，不制造噪音

**用户故事：** 作为移动端用户，我希望收到的通知是真正需要我关注的事件，而不是大量无意义提醒。

#### 验收标准

1. WHEN 会话出现关键进展（例如任务完成、需要确认） THEN System SHALL 发送可操作通知，并指向对应工作区和会话。
2. WHEN 进程状态发生关键变化（崩溃、重启失败、长时间未恢复） THEN System SHALL 发送告警通知并附最小诊断信息。
3. WHEN 事件不需要人工介入 THEN System SHALL 降低通知级别或仅在应用内收件箱展示，不触发高打扰推送。

### 需求 6：所有受保护数据必须基于登录态访问

**用户故事：** 作为系统管理员，我希望移动端和其他端保持同一套安全边界，以免出现移动端漏鉴权。

#### 验收标准

1. WHEN 用户未登录或令牌无效 THEN System SHALL 拦截工作区、会话、文件、Git、进程、日志请求并引导登录。
2. WHEN 建立移动端实时连接 THEN System SHALL 在握手阶段校验令牌，校验失败则拒绝订阅。
3. WHEN 用户主动退出或令牌被撤销 THEN System SHALL 清理本地受保护缓存并停止后台订阅。

### 需求 7：依赖前置 Spec，但不重复定义核心协议

**用户故事：** 作为项目维护者，我希望 spec009 明确复用前置 Spec 的协议与模型，以便减少重复和冲突。

#### 验收标准

1. WHEN 文档描述会话运行时 THEN System SHALL 引用 `spec003` 的消息运行时与能力门控规则，不重复定义协议字段。
2. WHEN 文档描述文件 / Git / 进程能力 THEN System SHALL 分别依赖 `spec004`、`spec005`、`spec007` 的核心接口，只补移动端视图与交互约束。
3. WHEN 文档描述桌面与 H5 关系 THEN System SHALL 继承 `spec008` 的交付边界，不另起一套端侧协议。

## 非功能需求

### 非功能需求 1：性能

1. WHEN 用户打开移动端首页 THEN System SHALL 在 2 秒内完成首屏摘要渲染（弱网下允许骨架屏先呈现）。
2. WHEN 用户进入会话或日志页面 THEN System SHALL 保持滚动和输入流畅，不因单次大请求导致明显卡顿。

### 非功能需求 2：可靠性

1. WHEN 移动网络在 Wi-Fi 与蜂窝间切换 THEN System SHALL 自动恢复实时连接并保持状态一致。
2. WHEN 推送通道短暂不可用 THEN System SHALL 将关键事件写入应用内收件箱，待连接恢复后补发。

### 非功能需求 3：可维护性

1. WHEN 前置 Spec 升级接口 THEN System SHALL 通过适配层集中处理移动端影响，不在多个页面散落协议分支。
2. WHEN 线上问题排查 THEN System SHALL 能按 `workspaceId/sessionId/processId` 关联通知、页面状态和事件日志。

## 成功定义

- 移动端可以稳定完成“看会话 + 回一句 + 处理一个小问题”的主链路。
- 用户能在移动端收到高价值通知，并在 1-2 次点击内进入对应处理页面。
- 没有出现“移动端一套数据规则、桌面端一套数据规则”的分叉。
- 登录态边界一致，未登录无法访问任何受保护数据。

# 需求文档 - spec012-并行会话组与临时子工作区

状态：Draft

## 简介

这份 Spec 解决的是一个已经摆在眼前的工作流问题：

用户不只是想 fork 一条新会话，而是想围绕同一个问题，同时开 2 到 4 条并行会话，让不同 provider、不同模型、不同补充提示词一起试，然后直接在同一个工作台里并排看它们各自往哪跑。

这件事如果继续靠手工做，流程会很脏：

- 先从当前会话点几次 fork
- 再分别改 provider 和模型
- 再手工记哪几个会话其实是一组
- 如果需要隔离目录，还得再单独建正式子工作区
- 最后中间区域还是一次只能舒舒服服看一个，会话信息栏还一直占右边

这不叫并行能力，这叫把体力活分散到几处不同的按钮里。

所以这份 Spec 要做的事很直接：

- 让系统知道“一组并行会话”是正式对象
- 让每个并行会话保留自己的 provider、模型、提示词和可选隔离工作区
- 让创建入口、会话树、分屏布局和信息栏都围绕“并行会话”这个对象重新对齐

## 术语表

- **Parallel Session Group（并行会话组）**：一组围绕同一个问题创建的并行会话容器
- **Parallel Session Member（并行成员）**：并行会话组内的单个真实会话
- **Source Type（来源类型）**：并行组来自现有会话 fork，还是直接从工作区新建
- **Anchor Session（锚点会话）**：仅用于展示和恢复默认分屏顺序的组内主会话，不等于真实父会话
- **Shared Prompt（公共提示词）**：创建并行组时先输入的一段公共提示词，会应用到整组
- **Member Prompt（成员补充提示词）**：某个并行成员单独追加的提示词
- **Temporary Isolated Workspace（临时隔离工作区）**：只服务于某个并行会话的临时 Git worktree 工作区
- **Promoted Child Workspace（正式子工作区）**：把临时隔离工作区升级后，纳入现有正式子工作区体系的工作区
- **Display Parent（展示父节点）**：只用于前端树和连接线投影的展示关系，不能污染真实 `parentSessionId`

## 范围说明

### In Scope

- 定义并行会话组、组成员和临时隔离工作区模型
- 从现有会话消息或会话本身发起并行 fork
- 从工作区直接新建并行会话组
- 配置公共提示词、并行数量、成员级 provider / model / 提示词
- 为成员按需创建临时隔离工作区
- 支持把临时隔离工作区升级为正式子工作区
- 在工作台和会话树中展示并行标签、组颜色和组内关系
- 对话区分屏展示并行会话
- 把右侧会话信息栏改为分屏顶部按钮触发的悬浮层
- 删除并行会话时清理未升级的临时工作区和分支

### Out of Scope

- 对多个并行会话做结果评分和排序
- 自动推荐“哪条答案更好”
- 自动 merge / cherry-pick 建议
- 完整运行时资源编排，例如端口块、数据库目录、缓存目录统一切分
- 跨仓库、跨机器的并行编排平台

## 需求

### 需求 1：系统必须把并行会话组和组成员当成正式模型

**用户故事：** 作为使用者，我希望系统知道“这些会话其实是一组并行尝试”，而不是只看到几条零散会话。

#### 验收标准

1. WHEN 用户创建并行会话组 THEN System SHALL 持久化 `ParallelSessionGroup`，至少记录 `workspaceId`、`sourceType`、`sourceSessionId`、`sourceMessageId`、`sharedPrompt`、`requestedCount`、`anchorSessionId`、`createdAt`。
2. WHEN 系统为组创建成员 THEN System SHALL 为每个成员记录 `sessionId`、`ordinal`、`provider`、`model`、`memberPrompt`、`workspaceIsolationMode` 和必要的时间戳。
3. WHEN Host 重启后恢复工作台 THEN System SHALL 能重新装配并行组、组成员和锚点关系，而不是把这些会话重新当成互不相关的普通会话。

### 需求 2：系统必须支持从现有会话发起并行 fork

**用户故事：** 作为当前会话的使用者，我希望在已有 fork 按钮之外直接发起并行 fork，一次得到多条并行分支。

#### 验收标准

1. WHEN 用户从现有会话或现有会话消息发起并行 fork THEN System SHALL 创建 `sourceType = fork` 的并行组，并记录来源会话和来源消息。
2. WHEN 组成员创建成功 THEN System SHALL 保留每个成员自己的真实 fork 元数据，不能用“并行关系”覆盖真实 `parentSessionId` 和 `session_forks`。
3. WHEN 前端展示这些成员 THEN System SHALL 给这些会话打上“并行”标签，并在连接线中用稳定颜色标出它们属于同一组。

### 需求 3：系统必须支持从工作区直接新建并行会话组

**用户故事：** 作为用户，我希望在新建工作区会话时，直接创建一组并行会话，而不是先建一条再重复建三次。

#### 验收标准

1. WHEN 用户从“新建工作区”附近的入口创建并行组 THEN System SHALL 创建 `sourceType = new` 的并行组。
2. WHEN 组来自工作区新建 THEN System SHALL 不为了凑结构而伪造真实父会话；组成员可以都是根会话。
3. WHEN 组来自工作区新建 THEN System SHALL 用 `anchorSessionId` 指定默认展示锚点；如果锚点会话被删除且组内仍有成员，System SHALL 自动把下一个成员提升为新锚点。

### 需求 4：系统必须支持公共配置和成员级配置的创建流程

**用户故事：** 作为用户，我希望先说清这组并行会话共同要做什么，再分别指定每一条该用什么 provider、模型和补充提示词。

#### 验收标准

1. WHEN 用户进入并行创建弹窗 THEN System SHALL 先要求输入公共提示词。
2. WHEN 用户选择并行数量 THEN System SHALL 支持 2 到 4 个成员，默认值为 2。
3. WHEN 用户配置每个成员 THEN System SHALL 允许分别设置 `provider`、`model`、`memberPrompt` 和是否启用工作区隔离。
4. WHEN 用户提交创建 THEN System SHALL 对成员数、provider、model 和必要输入做校验，发现缺失时明确指出具体成员和字段。

### 需求 5：系统必须支持按成员可选启用临时隔离工作区

**用户故事：** 作为用户，我只想在确实需要代码目录隔离时才开 Git worktree，而不是所有并行会话一刀切地变重。

#### 验收标准

1. WHEN 某个成员启用工作区隔离 THEN System SHALL 为该成员创建临时隔离工作区，并把它绑定到该成员会话。
2. WHEN 某个成员未启用工作区隔离 THEN System SHALL 继续使用现有工作区，不额外创建 Git worktree。
3. WHEN 系统展示会话相关资源 THEN 临时隔离工作区 SHALL 挂在对应会话下，而不是直接混入现有正式子工作区树。

### 需求 6：临时隔离工作区必须支持升级为正式子工作区

**用户故事：** 作为维护者，我希望某条并行会话里临时长出来的代码目录，如果后来证明有价值，可以升级为正式子工作区继续管理。

#### 验收标准

1. WHEN 用户在临时隔离工作区上执行升级 THEN System SHALL 把该工作区纳入现有正式子工作区管理方式和展示方式。
2. WHEN 升级成功 THEN System SHALL 标记原临时记录已提升，不再把它当成“会话删除就跟着删”的临时资源。
3. WHEN 工作台展示该工作区 THEN System SHALL 与现有正式子工作区保持一致的入口、管理动作和视觉结构。

### 需求 7：删除并行会话时必须清理未升级的临时资源

**用户故事：** 作为维护者，我希望删掉并行会话后，未升级的临时目录和分支也一起收掉，避免越跑越脏。

#### 验收标准

1. WHEN 用户删除某个并行成员会话 THEN System SHALL 清理该成员对应的未升级临时隔离工作区和分支。
2. WHEN 用户删除整个并行会话组 THEN System SHALL 逐个清理组内成员对应的未升级临时隔离工作区和分支。
3. WHEN 某个临时隔离工作区已经升级为正式子工作区 THEN 删除会话或组 SHALL NOT 自动删除该正式子工作区。

### 需求 8：工作台和会话树必须能看清并行关系

**用户故事：** 作为用户，我希望会话树里能看出哪些是同一组并行会话，也希望临时隔离工作区能明确挂在对应会话下面。

#### 验收标准

1. WHEN 工作台装配会话树 THEN System SHALL 在不污染真实 `parentSessionId` 的前提下，投影出并行组的展示关系。
2. WHEN 某个会话属于并行组 THEN System SHALL 展示“并行”标签、组颜色和组内顺序信息。
3. WHEN 某个成员会话绑定临时隔离工作区 THEN System SHALL 在该会话的上下文范围内展示该工作区，而不是让用户去顶层工作区列表里猜。

### 需求 9：创建完成后，对话区必须按并行数量分屏

**用户故事：** 作为用户，我希望创建并行会话后，马上在中间区域同时看到这几条会话，而不是再自己来回切。

#### 验收标准

1. WHEN 并行组创建成功 THEN System SHALL 把中间会话区域按成员数量切成并排分屏。
2. WHEN 分屏数量为 2 到 4 THEN System SHALL 收窄每个会话区域的边距和信息密度，使其接近移动端窄视图，但保持桌面端可用。
3. WHEN 用户切换当前并行组 THEN System SHALL 保留该组的分屏顺序和锚点会话，而不是每次随机重排。

### 需求 10：右侧会话信息栏必须默认隐藏，并改为每屏局部悬浮打开

**用户故事：** 作为并行会话使用者，我不希望一个全局右侧栏一直挤压所有分屏，我只想在看某个分屏时临时打开它自己的信息。

#### 验收标准

1. WHEN 用户进入并行分屏视图 THEN System SHALL 默认隐藏原来的全局右侧会话信息栏。
2. WHEN 用户点击某个分屏顶部按钮 THEN System SHALL 只为该分屏悬浮显示对应的会话信息层。
3. WHEN 用户关闭悬浮信息层 THEN System SHALL 恢复分屏布局，不影响其他分屏当前状态。

### 需求 11：新能力不能破坏现有会话、fork 和正式子工作区主链路

**用户故事：** 作为现有系统维护者，我希望不使用并行会话时，原有会话、新建会话、单个 fork、正式子工作区都不变。

#### 验收标准

1. WHEN 用户不使用并行会话功能 THEN System SHALL 保持现有新建会话、单个 fork、会话树和右侧信息栏行为不变。
2. WHEN 并行会话功能接入 THEN System SHALL 复用现有会话创建、fork 和 worktree 基础能力，而不是复制一份平行实现。
3. WHEN 某个并行成员创建失败、清理失败或升级失败 THEN System SHALL 将错误限制在对应成员或对应组范围内，不影响其他普通会话和工作区。

## 非功能需求

### 非功能需求 1：可维护性

1. WHEN 后续新增更多 provider 或模型选项 THEN System SHALL 继续复用并行组和成员模型，而不是继续长特殊分支逻辑。
2. WHEN 排查问题 THEN System SHALL 能快速定位 `groupId`、`sessionId`、`sourceSessionId`、`anchorSessionId`、`temporaryWorkspaceId` 和正式 `workspaceId` 的关系。

### 非功能需求 2：安全性

1. WHEN 系统创建、升级或清理临时隔离工作区 THEN System SHALL 校验路径边界和归属关系，拒绝越权操作。
2. WHEN 删除并行组或成员 THEN System SHALL 只删除仍归属于该会话或该组的未升级临时资源，不能误删用户保留的正式子工作区。

### 非功能需求 3：可靠性

1. WHEN Host 重启或前端刷新 THEN System SHALL 能恢复并行组、组成员、锚点和临时隔离工作区的绑定关系。
2. WHEN 并行组部分成员创建失败 THEN System SHALL 明确标记失败项，并保留已成功成员的稳定状态，不把整组弄成不可恢复的脏状态。

### 非功能需求 4：易用性

1. WHEN 用户进入并行分屏 THEN System SHALL 让每个分屏顶部信息足够明确，用户能快速分辨 provider、模型和是否隔离工作区。
2. WHEN 用户回到普通单会话视图 THEN System SHALL 明显退出并行分屏态，不保留误导性的并行 UI 残影。

## 成功定义

- 系统不再把并行会话理解成几条零散会话，而是有正式的组和成员模型
- 从现有会话 fork 和从工作区新建两种并行创建路径都能走通
- 只有需要时才创建临时隔离工作区，并且能升级为正式子工作区
- 会话树和中间区域都能清楚展示一组并行会话的关系
- 新能力不破坏现有单会话、新建会话、普通 fork 和正式子工作区主链路

# 需求文档 - spec012-并行项目编排与结果对比

状态：Draft

## 简介

这个 Spec 解决的是一个已经很现实的场景：

用户不是只想“在一个工作区里写代码”，而是想让多个 AI CLI 针对同一个问题同时出方案，再分别跑起来验证，最后比较哪条路最靠谱。

这件事如果只靠手工做，流程会烂得很快：

- 先手工建 3 个分支
- 再手工复制 3 份目录
- 再手工改 3 份端口
- 再手工避开数据库和缓存冲突
- 最后再手工对比 diff、日志和测试结果

这不叫能力，这叫体力活。

所以这个 Spec 要做的事很直接：

- 让系统知道“一个问题可以有多个并行尝试”
- 让每个尝试都有自己独立的代码目录和运行时边界
- 让启动、调试、验收、对比、收尾都能被系统管理

## 术语表

- **System**：`CodingNS Host` 与客户端协作的整体系统
- **ParallelCase（并行案例）**：同一个待解决问题的容器，下面可以挂多个并行尝试
- **ParallelAttempt（并行尝试）**：某个 provider 或某个策略针对一个案例的独立试解
- **Provider（提供方）**：例如 `claudecode`、`codex`、`opencode`
- **Worktree（独立工作目录）**：Git 仓库针对某个分支挂出的独立工作目录
- **Runtime Isolation（运行时隔离）**：把端口、数据目录、缓存、日志、临时目录等资源分开，避免尝试之间互相污染
- **RunProfile（运行配置）**：描述某个尝试怎么启动、怎么验活、怎么执行测试的配置
- **AttemptResult（尝试结果）**：记录本次尝试的 diff、测试、健康检查、日志摘要和人工结论

## 范围说明

### In Scope

- 定义并行案例和并行尝试的数据模型
- 管理 `git worktree` 的创建、列出、删除和状态同步
- 为每个尝试分配独立分支名、目录、端口块和运行时目录
- 复用现有进程管理能力启动和停止尝试
- 记录每个尝试的调试结果和验收快照
- 提供多尝试对比视图所需的数据与接口
- 提供合并建议和收尾清理流程

### Out of Scope

- 自动替用户决定哪个分支一定要合并
- 自动解决复杂 merge conflict
- 跨机器或跨仓库的大规模调度
- 把所有 provider 的私有能力都统一成完全一致的交互模型
- 在第一阶段做全自动无人值守修复流水线

## 需求

### 需求 1：系统必须把“并行案例”和“并行尝试”当成正式模型

**用户故事：** 作为使用者，我希望系统知道“同一个问题下有多条尝试”，而不是只看到几个零散分支，这样我才能真正管理并行试解过程。

#### 验收标准

1. WHEN 用户创建一个并行案例 THEN System SHALL 持久化 `ParallelCase`，至少记录标题、问题描述、基础分支、目标工作区和创建时间。
2. WHEN 用户在案例下创建多个尝试 THEN System SHALL 为每个尝试记录 `providerId`、`branchName`、`worktreePath`、`runtimeDir`、`status` 等稳定字段。
3. WHEN 用户查看案例详情 THEN System SHALL 返回该案例下全部尝试及其当前状态，而不是要求用户自己拼接 Git 和进程信息。

### 需求 2：每个并行尝试必须绑定独立的 `git worktree`

**用户故事：** 作为调试者，我希望每个尝试都有自己的代码目录，这样多个 CLI 才能并行修改和运行，不会互相踩工作区。

#### 验收标准

1. WHEN 用户创建并行尝试 THEN System SHALL 基于指定基础分支或提交创建独立 `git worktree`，而不是只创建分支名。
2. WHEN 系统列出并行尝试 THEN System SHALL 能同步 worktree 是否存在、路径是否可用、分支是否已检出。
3. WHEN 用户删除尝试 THEN System SHALL 支持清理对应 worktree，并保留必要的结果记录和审计信息。

### 需求 3：每个并行尝试必须有独立的运行时隔离边界

**用户故事：** 作为维护者，我希望不同尝试的进程互不污染，这样我才能相信调试结果是真的，而不是被共享端口和缓存串坏了。

#### 验收标准

1. WHEN 系统为尝试准备运行环境 THEN System SHALL 为其分配独立的端口块、数据目录、日志目录、缓存目录和临时目录。
2. WHEN 不同尝试同时运行 THEN System SHALL 避免端口冲突、数据库文件冲突、缓存目录冲突和用户数据目录冲突。
3. WHEN 尝试结束或重建 THEN System SHALL 支持回收或重置运行时资源，但不误删其他尝试正在使用的数据。

### 需求 4：并行尝试必须能复用统一的启动与调试流程

**用户故事：** 作为用户，我希望系统不是只会建目录，还能把每个尝试真正跑起来，并持续看到它的运行状态。

#### 验收标准

1. WHEN 用户为尝试绑定 `RunProfile` THEN System SHALL 允许定义启动命令、工作目录、环境变量、预期端口、健康检查和测试命令。
2. WHEN 用户启动尝试 THEN System SHALL 复用现有进程管理链路启动对应 worktree 下的进程，并记录实例状态。
3. WHEN 用户查看尝试调试状态 THEN System SHALL 返回进程状态、日志入口、端口绑定和最近一次健康检查结果。

### 需求 5：系统必须能同时编排多个 provider 的尝试

**用户故事：** 作为使用者，我希望一个案例里能同时挂 `claudecode`、`codex`、`opencode` 等尝试，而不是只能支持单一 provider。

#### 验收标准

1. WHEN 用户基于一个案例批量创建尝试 THEN System SHALL 支持按 provider 列表一次性创建多个尝试。
2. WHEN 系统展示尝试列表 THEN System SHALL 能明确区分 provider、分支、状态和运行结果。
3. WHEN 后续新增第四家 provider THEN System SHALL 尽量复用现有并行案例模型和编排流程，而不是重写一套特殊逻辑。

### 需求 6：每个尝试都必须有统一结果快照，方便比较

**用户故事：** 作为决策者，我希望对比多个尝试时不靠印象，而是看到统一格式的结果快照。

#### 验收标准

1. WHEN 尝试运行结束或用户手动触发采集 THEN System SHALL 生成 `AttemptResult`，至少包含 commit、diff 摘要、测试结果、健康检查结果和日志摘要。
2. WHEN 用户打开案例对比页 THEN System SHALL 返回全部尝试的结果快照，支持按同一维度比较。
3. WHEN 某个尝试没有完整结果 THEN System SHALL 明确标记缺失项，而不是伪装成“通过”。

### 需求 7：系统必须给出可追踪的合并建议，但不能擅自替用户做决定

**用户故事：** 作为代码维护者，我希望系统能告诉我哪条尝试看起来更稳，但最终 merge 仍由我确认，避免把垃圾自动合进主分支。

#### 验收标准

1. WHEN 系统完成多尝试对比 THEN System SHALL 提供基于 diff 范围、测试状态、健康检查和人工标注的合并建议。
2. WHEN 用户选择一个尝试作为主候选 THEN System SHALL 支持生成后续 merge 或 cherry-pick 所需的信息。
3. WHEN 存在冲突风险或验证缺失 THEN System SHALL 明确警告，不能把结果包装成“安全可合并”。

### 需求 8：并行尝试的清理和回收必须可控

**用户故事：** 作为维护者，我希望跑完一批尝试后能干净回收目录、端口和脏数据，而不是越跑越脏。

#### 验收标准

1. WHEN 用户归档或删除案例 THEN System SHALL 支持批量停止相关进程并清理 worktree 和运行时目录。
2. WHEN 某个尝试被单独删除 THEN System SHALL 只清理该尝试的资源，不影响其他尝试。
3. WHEN 系统执行清理 THEN System SHALL 保留必要的结果记录与操作日志，便于后续追溯。

### 需求 9：并行编排能力不能破坏现有工作区、Git 和进程能力

**用户故事：** 作为现有系统维护者，我希望新增并行编排能力时，不会把原本单工作区、单进程、单 provider 的主链路打坏。

#### 验收标准

1. WHEN 用户不使用并行案例功能 THEN System SHALL 维持现有工作区、Git、进程、provider 主链路行为不变。
2. WHEN 并行案例功能接入 THEN System SHALL 复用现有 Git、进程、provider 抽象，避免复制一份平行实现。
3. WHEN 并行尝试失败 THEN System SHALL 将错误限制在尝试范围内，不影响其他工作区和其他尝试的运行。

## 非功能需求

### 非功能需求 1：可靠性

1. WHEN 多个尝试同时运行 THEN System SHALL 维持独立状态和日志，不因单个尝试失败拖垮整组案例。
2. WHEN Host 重启 THEN System SHALL 能恢复并行案例、尝试状态和结果快照，不丢失关键索引。

### 非功能需求 2：可维护性

1. WHEN 新增新的 provider、测试命令或隔离资源类型 THEN System SHALL 通过扩展点接入，而不是继续塞满条件分支。
2. WHEN 排查问题 THEN System SHALL 能快速定位到案例、尝试、分支、目录、端口和进程实例之间的关系。

### 非功能需求 3：安全性

1. WHEN 系统创建 worktree、执行命令或清理目录 THEN System SHALL 校验路径边界，拒绝越权操作。
2. WHEN 系统生成环境变量和运行目录 THEN System SHALL 避免把敏感凭据无差别散落到任意文件中。

### 非功能需求 4：可观测性

1. WHEN 并行尝试创建、启动、停止、采集结果或清理失败 THEN System SHALL 输出可检索的结构化日志。
2. WHEN 用户查看案例详情 THEN System SHALL 能展示关键时间线，例如创建、启动、通过、失败、清理。

## 成功定义

- 系统不再把“并行试解”理解成几条零散分支，而是有正式的案例和尝试模型
- 每个尝试都有独立 `worktree` 和独立运行时边界，可以真正并行开发和调试
- 多个 provider 可以在同一个案例下同时尝试，且结果可追踪、可比较
- 用户能看到统一结果快照和合并建议，而不是靠人肉整理信息
- 新能力不破坏现有工作区、Git、进程和 provider 主链路

# spec012-并行项目编排与结果对比

## 当前定位

这个 Spec 解决的不是“多建几个分支”这么浅的问题。

真正的问题是：当用户想让 `Claude Code`、`Codex`、`OpenCode` 这些 CLI 针对同一个问题并行试解时，系统能不能把这些尝试当成一等对象来管理，而不是靠人手工记目录、记端口、记日志、记哪个分支跑过。

如果这件事继续靠手工做，后面一定会乱：

- 分支是有了，但工作目录互相踩
- 进程能跑，但端口、数据库、缓存互相污染
- 改完能看 diff，但说不清哪个尝试真的跑通了
- 最后只能靠人肉比较 3 份结果，风险大、效率低

所以 `spec012` 的目标很明确：

- 把“同一个问题下的多个并行尝试”做成正式模型
- 用 `git worktree` 管好多份独立工作目录
- 给每个尝试分配独立运行时边界，包括端口、数据目录、缓存和日志
- 统一启动、停止、调试、验收这些并行尝试
- 把结果快照、对比和最终合并建议做成可追踪流程

## 计划覆盖

- `ParallelCase`、`ParallelAttempt`、`AttemptResult` 数据模型
- `git worktree` 生命周期管理
- 端口块、数据目录、缓存目录等运行时隔离
- 多 CLI 并行尝试编排
- 启动配置与调试流程复用
- 尝试结果采集、对比和验收
- 合并建议与清理流程

## 依赖关系

- 前置依赖：`spec001`、`spec005`、`spec007`、`spec010`、`spec012.1`
- 后续依赖：并行尝试结果可视化、自动合并辅助、更多 provider 编排能力

其中 `spec012.1` 先把 worktree 的创建、继续 fork、合并、清理和工作台展示打成正式基础，这样 `spec012` 就不用再背 worktree 地基建设。

## 本阶段明确不做

- 分布式任务调度
- 容器集群编排
- 自动替用户做最终 merge
- 云端多人协同编排平台
- 把不同 provider 的内部推理过程统一成同一套协议

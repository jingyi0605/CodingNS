# spec012-并行会话组与临时子工作区

## 当前定位

这份 Spec 现在不再讨论“并行项目编排”和“结果对比平台”那套重型方案。

当前真实需求更直接：

- 用户要能从现有会话一次派生多个并行会话
- 用户也要能在新建会话时，直接创建一组并行会话
- 每个并行会话都可以单独选 provider、模型和补充提示词
- 只有在需要时，才给某个并行会话挂临时隔离工作区
- 创建完成后，中间会话区域要直接分屏，不是再跳去另一套页面

一句人话：
先把并行会话建对、看清、收干净，再谈结果对比、自动评估和高级编排。

如果这一步不先做，后面一定会继续长歪：

- 会话树里只剩一堆真假难辨的父子关系
- `parentSessionId` 会同时承担“真实 fork”与“并行展示锚点”两种脏职责
- 想隔离代码目录时，只能硬塞正式子工作区，生命周期完全不对
- 右侧信息栏和单会话布局继续假装世界上只有一个会话

所以这份 Spec 的目标很明确：

- 把“并行会话组”和“组成员会话”做成正式模型
- 明确“真实父子关系”和“并行展示关系”不是一回事
- 把会话级临时隔离工作区做成独立对象，并支持升级为正式子工作区
- 在现有工作台里加入口、弹窗、分屏和悬浮信息栏，而不是再造一套平行页面

## 计划覆盖

- 并行会话组、组成员、临时隔离工作区的数据模型
- 从现有会话 fork 并行组
- 从工作区直接新建并行组
- 公共提示词、成员级 provider / model / 提示词配置
- 可选的会话级工作区隔离与 Git worktree 创建
- 临时隔离工作区升级为正式子工作区
- 会话树里的并行标签、组颜色和展示投影
- 对话区分屏布局与每个分屏顶部的悬浮信息栏
- 删除并行会话时的资源清理与零破坏兼容

## 本阶段明确不做

- 不做并行结果评分、胜负排序和自动推荐
- 不做自动 merge / cherry-pick 建议
- 不做完整运行时隔离，例如端口块、数据库目录、缓存目录统一分配
- 不做跨仓库、跨机器、跨项目的大规模编排
- 不把不同 provider 的内部推理过程统一成同一套协议

# 需求文档 - spec001.8-登录设备管理与主设备控制

状态：Draft

## 简介

当前系统只有“能登录”和“能登出”，没有“这个账号现在到底在哪些设备登录着”的正式能力。

这会直接带来几个现实问题：

- 用户看不到当前设备和其他设备的登录状态
- 用户看不到最近登录发生过什么
- 用户丢了某台设备以后，没有一个正式入口把其他设备踢下线
- 系统里也没有“主设备”这个可解释、可验证、可持久化的状态

更糟的是，如果直接把 `token` 当设备来管，最后只会得到一堆特殊情况：

- 同一台设备刷新一次 token，看起来像换了一台设备
- 旧 token 还没失效时，同一设备会被拆成多条
- 最近登录记录和在线设备列表会互相污染

所以这个 Spec 要解决的是一个非常具体的问题：
在不破坏现有登录链路的前提下，把设备、会话和最近登录记录拆开，并给设置页一个真正可用的设备管理入口。

## 术语表

- **Device（设备）**：同一个账号下，一个稳定的客户端实例。第一阶段由 `clientInstanceId + clientType` 识别。
- **Client Type（客户端类型）**：客户端大类，例如 `desktop`、`web`、`ios`、`android`。
- **Device Session（设备会话）**：某台设备上某一次有效登录关联出来的 token 集合。
- **Recent Login Record（最近登录记录）**：最近发生过的成功登录事件。第一阶段只保留最近 10 条。
- **Primary Device（主设备）**：由当前登录设备通过管理员密码显式设置出来的受信设备。主设备不唯一。
- **Source Address（来源地址）**：Host 从请求上下文解析出的最近来源地址，不做地区解析。
- **Legacy Session（旧登录态）**：上线本 Spec 前已经存在、还没有设备元数据的历史 token 记录。

## 范围说明

### In Scope

- 登录时识别或创建设备，并绑定当前 token 会话
- 在设置页展示当前设备、其他在线设备、最近登录记录
- 当前设备通过管理员密码设置或取消主设备状态
- 主设备执行“退出其他设备”
- 最近登录记录保留最近 10 条
- 兼容旧 token，不因为表结构升级直接把老登录态全部打死

### Out of Scope

- 多用户共享设备治理
- 异地登录风控
- 登录失败告警
- 单条历史记录删除
- 单个其他设备逐条下线
- 地区/IP 画像

## 需求

### 需求 1：系统必须能识别稳定设备，而不是把 token 当设备

**用户故事：** 作为用户，我希望系统能稳定识别我正在使用的设备，而不是每次 token 刷新都把我当成一台新设备。

#### 验收标准

1. WHEN 同一客户端实例刷新 token THEN System SHALL 仍然识别为同一台设备。
2. WHEN 同一账号从不同客户端实例登录 THEN System SHALL 识别为不同设备。
3. WHEN 系统记录设备 THEN System SHALL 至少包含 `clientInstanceId`、`clientType`、最近来源地址和最近在线时间。
4. WHEN 设备信息缺失 THEN System SHALL 返回明确的兜底显示，而不是报错或直接丢记录。

### 需求 2：设置页必须能展示当前设备和其他在线设备

**用户故事：** 作为用户，我希望在设置页里看见当前登录设备和其他还在线的设备，而不是只能盲猜。

#### 验收标准

1. WHEN 用户进入设备管理页 THEN System SHALL 展示当前设备。
2. WHEN 当前账号还有其他未失效的设备会话 THEN System SHALL 单独列出其他在线设备。
3. WHEN 某台设备被标记为主设备 THEN System SHALL 明确显示主设备标记。
4. WHEN 某条在线设备来自旧登录态且缺少完整设备信息 THEN System SHALL 以“未知设备”之类的兜底文案展示，而不是隐藏。

### 需求 3：设置页必须展示最近登录记录，并且只保留最近 10 条

**用户故事：** 作为用户，我希望看到最近登录发生过什么，但不需要系统无限堆积旧记录。

#### 验收标准

1. WHEN 用户进入设备管理页 THEN System SHALL 展示最近登录记录。
2. WHEN 记录一条新的成功登录 THEN System SHALL 保证同一用户只保留最近 10 条记录。
3. WHEN 展示最近登录记录 THEN System SHALL 至少包含发生时间、客户端类型和来源地址。
4. WHEN 当前没有最近登录记录 THEN System SHALL 明确显示空状态。

### 需求 4：主设备必须由管理员密码显式设置，且主设备不唯一

**用户故事：** 作为用户，我希望自己信任的设备可以被标记成主设备，但这个动作必须经过管理员密码确认。

#### 验收标准

1. WHEN 当前登录设备请求设为主设备 THEN System SHALL 要求输入管理员密码。
2. WHEN 管理员密码验证通过 THEN System SHALL 把当前设备标记为主设备。
3. WHEN 管理员密码错误 THEN System SHALL 拒绝设置主设备，并返回明确错误。
4. WHEN 一个账号已经有主设备 THEN System SHALL 仍允许其他设备再设为主设备，不能强制只有唯一主设备。

### 需求 5：只有主设备才能退出其他设备的登录状态

**用户故事：** 作为用户，我希望在我信任的设备上把其他设备全部踢下线。

#### 验收标准

1. WHEN 当前设备不是主设备 THEN System SHALL 拒绝“退出其他设备”操作。
2. WHEN 当前设备是主设备并执行“退出其他设备” THEN System SHALL 撤销当前设备之外的其他有效交互式登录会话。
3. WHEN “退出其他设备”执行成功 THEN System SHALL 保留当前设备会话，不把自己一起踢掉。
4. WHEN 其他设备的 token 被撤销 THEN System SHALL 在它们后续请求时表现为未授权，并引导重新登录。

### 需求 6：新能力不能破坏现有登录、刷新、登出主链路

**用户故事：** 作为系统维护者，我希望设备管理上线后，现有登录链路还能继续工作，不要为了多一个设备列表把登录搞坏。

#### 验收标准

1. WHEN 旧客户端还没有携带完整设备头 THEN System SHALL 仍允许现有登录、刷新、登出流程继续工作。
2. WHEN 历史数据库升级到新结构 THEN System SHALL 不强制所有现有登录态立刻失效。
3. WHEN 设备元数据缺失 THEN System SHALL 允许后续通过刷新或新登录补齐，而不是直接报错。
4. WHEN 新能力未被调用 THEN System SHALL 不改变原有公开/受保护接口的基本行为。

## 非功能需求

### 非功能需求 1：兼容性

1. WHEN 系统升级数据库结构 THEN System SHALL 保留旧 token 记录的可读性与可撤销能力。
2. WHEN 设备管理页展示旧登录态 THEN System SHALL 给出清晰兜底文案，而不是要求迁移脚本一次性补齐所有历史数据。

### 非功能需求 2：安全性

1. WHEN 设置主设备 THEN System SHALL 重新校验管理员密码，不能只靠当前 token 默认放行。
2. WHEN 系统记录来源地址 THEN System SHALL 只信任 Host 从请求上下文解析出的地址。
3. WHEN 退出其他设备 THEN System SHALL 只处理交互式用户会话，不误伤内部助手运行时 token。

### 非功能需求 3：可维护性

1. WHEN 设计设备管理数据结构 THEN System SHALL 区分设备、设备会话和最近登录事件，不把三种概念混成一张表。
2. WHEN 前端接设备管理接口 THEN System SHALL 使用统一 DTO，不让页面直接拼 auth 仓储结构。
3. WHEN 最近登录记录超过 10 条 THEN System SHALL 在写入时裁剪，而不是依赖前端只展示前 10 条。

## 成功定义

- 设置页里能看到当前设备、其他在线设备和最近 10 条登录记录
- 当前设备可以通过管理员密码设为主设备，且主设备不唯一
- 主设备可以安全地退出其他设备，不会把自己一起踢掉
- 现有 `login / refresh / logout` 主链路继续可用
- 历史登录态不会因为这次改动被粗暴打断

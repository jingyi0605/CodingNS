# spec013 服务接口草案

状态：Draft

## 1. 目标

这份草案定义 `spec013` 在宿主端的 HTTP 接口轮廓，要求只有一个：

**接口风格必须贴着当前 `apps/host/src/routes/*.ts` 的现实来写。**

所以这里不搞 GraphQL，不搞事件总线 API，不搞一套新的 RPC 方言，就沿用现有：

- `/api/...` 路由前缀
- `controller + service` 组织方式
- 资源型 REST 风格

## 2. 设计原则

### 2.1 项目是顶层资源

大部分 butler 行为都围绕项目展开，所以主资源一定是：

- `/api/butler/projects`

而不是先从会话开始再倒查项目。

### 2.2 复用现有 session API，不重复发明

如果是“读已有 session 消息”“发消息给 session”“中断 session”这种能力，继续走现有 `/api/sessions/...`。

Butler API 只负责：

- 项目登记
- 会话纳管
- 巡视
- 记忆
- 验证
- 授权
- 审计

### 2.3 先把控制面接口做全，执行面接口做受控

MVP 阶段优先保证：

- 能看清楚
- 能登记
- 能巡视
- 能验证

至于“自动开发”入口，先保持显式受控，不搞隐式后台乱跑。

## 4. 详细接口

### 4.1 `GET /api/butler/projects`

用途：列出当前工作区范围内的代码管家项目。

查询参数：

| 参数 | 类型 | 说明 |
| --- | --- | --- |
| `workspaceId` | `string` | 可选，按工作区过滤 |
| `status` | `string` | 可选，`active/paused/archived` |
| `riskLevel` | `string` | 可选，`low/medium/high` |

响应示例：

```json
{
  "items": [
    {
      "id": "bp_001",
      "workspaceId": "ws_001",
      "name": "host-app",
      "repoRoot": "/repo/host",
      "approvalMode": "controlled",
      "lifecycleStatus": "active",
      "riskLevel": "medium",
      "lastPatrolAt": "2026-04-02T09:00:00.000Z",
      "lastVerificationAt": "2026-04-02T09:20:00.000Z"
    }
  ]
}
```

失败场景：

- `400`：查询参数非法
- `500`：数据库读取失败

### 4.2 `POST /api/butler/projects`

用途：创建一个受管项目。

请求体：

```json
{
  "workspaceId": "ws_001",
  "name": "host-app",
  "repoRoot": "/repo/host",
  "defaultProvider": "codex",
  "approvalMode": "controlled",
  "config": {
    "defaultBranch": "main",
    "patrolFocus": ["progress", "test", "risk"]
  }
}
```

响应示例：

```json
{
  "project": {
    "id": "bp_001",
    "workspaceId": "ws_001",
    "name": "host-app",
    "repoRoot": "/repo/host",
    "defaultProvider": "codex",
    "approvalMode": "controlled",
    "lifecycleStatus": "active",
    "riskLevel": "low"
  }
}
```

失败场景：

- `400`：路径越界或字段缺失
- `404`：`workspaceId` 不存在
- `409`：同一工作区下 `repoRoot` 已注册

### 4.3 `GET /api/butler/projects/:projectId`

用途：读取项目详情。

响应字段建议：

- 项目基本信息
- 默认 provider
- 项目级配置
- 最近巡视摘要
- 最近验证摘要
- 活跃会话数量

失败场景：

- `404`：项目不存在

### 4.4 `PATCH /api/butler/projects/:projectId`

用途：更新项目配置。

请求体允许：

- `name`
- `defaultProvider`
- `approvalMode`
- `lifecycleStatus`
- `riskLevel`
- `config`

失败场景：

- `400`：状态枚举非法
- `404`：项目不存在

### 4.5 `GET /api/butler/projects/:projectId/overview`

用途：返回项目总览，给 UI 首页直接消费。

响应字段建议：

```json

  "latestPatrolRun": {},
  "latestVerificationRun": {},
```

说明：

### 4.6 `GET /api/butler/projects/:projectId/sessions`

用途：列出纳入管家管理的会话。

响应字段建议：

- `butlerSessionId`
- `sessionId`
- `provider`
- `title`
- `role`
- `ownershipMode`
- `status`
- `runningState`
- `lastCheckpointAt`

说明：

- `provider`、`title`、`runningState` 来自联表 `session_bindings/session_indices/session_states`

### 4.7 `POST /api/butler/projects/:projectId/sessions/import`

用途：把已有宿主 session 纳管进项目。

请求体：

```json
{
  "sessionId": "session_001",
  "role": "adhoc",
  "ownershipMode": "observed"
}
```

失败场景：

- `404`：项目不存在或 session 不存在
- `409`：该 session 已被纳管

### 4.8 `POST /api/butler/projects/:projectId/sessions/start`

用途：按 butler 语义启动一个新会话。

请求体：

```json
{
  "provider": "codex",
  "role": "patrol",
  "cwd": "/repo/host",
  "instructionProfileId": "default-butler",
  "goal": "巡视当前项目进展，输出风险和下一步建议"
}
```

响应字段建议：

- `butlerSession`
- `sessionBinding`
- `instructionEnvelopeSummary`

失败场景：

- `400`：目标路径越界、provider 不支持
- `403`：项目处于 `paused/archived`
- `502`：provider 启动失败

## 8. 核心判断

### 【核心判断】

✅ 值得做：这套接口拆分足够支撑 butler 控制面，又没有去抢现有 session/provider API 的职责。

### 【关键洞察】

- 数据结构：项目是顶层资源，其他资源全部挂在项目下面
- 复杂度：执行类 API 复用现有 session 能力，butler 只暴露控制面增量
- 风险点：如果把消息收发、中断、续接也重新做一套 butler API，后面一定会和现有 `/api/sessions` 分叉

### 【Linus式方案】

1. 让 butler API 只负责项目级编排对象
2. 底层会话操作继续复用现有 `/api/sessions`
3. 先做读模型和手动触发入口，再逐步放开受控执行
4. 不要把所有能力都塞到一个超大接口里

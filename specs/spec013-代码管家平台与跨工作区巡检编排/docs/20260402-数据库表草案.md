# spec013 数据库表草案

状态：Draft

## 1. 目标

这份草案只解决一件事：把 `spec013` 里“代码管家平台”的核心对象压成可以落到当前宿主端 SQLite 的表结构。

边界很明确：

- 复用现有 `workspaces`、`session_bindings`、`session_indices`、`session_states`
- 不重复存 provider 已经能稳定提供的底层会话绑定数据
- 平台自己持久化项目、巡视、记忆、验证、授权、审计这些 provider 不该拥有的状态

一句话版本：**底层会话还是现有宿主管，代码管家只补自己的控制面对象。**

## 2. 与现有表的关系

### 2.1 直接复用的现有表

- `workspaces`
  - 继续作为项目的工作区归属根对象
- `session_bindings`
  - 继续作为 provider 会话的权威绑定表
- `session_indices`
  - 继续提供标题、父子会话、消息数量等只读索引
- `session_states`
  - 继续提供运行态、用户收藏、最近活动时间等状态
- `session_status_snapshots`
  - 继续提供同步状态，不在 butler 表里重复造一份

### 2.2 新表与现有表的关系

- 一个 `workspace` 下可以有多个 `butler_projects`
- 一个 `butler_project` 下可以挂多个 `butler_sessions`
- 一个 `butler_session` 必须指向一个现有 `session_bindings.session_id`
- 巡视、验证、授权、审计都以 `butler_project` 为归属中心
- 记忆以 `project` 为主，不直接绑死 provider

## 3. 设计原则

### 3.1 不做重复绑定

`provider`、`provider_session_id`、`raw_store_ref` 已存在于 `session_bindings`，`butler_sessions` 不应再复制一遍。复制出来只会制造双写和脏数据。

### 3.2 状态枚举尽量少

状态枚举只保留真正需要平台判断的那几个，不为了“未来可能有用”预埋十几种状态。

### 3.3 JSON 字段只装弱结构

能拆成一等列的，就拆成一等列；只有 tags、建议列表、附加配置、产物列表这类变化快又不值得频繁联表查询的内容，才放 JSON 文本。

## 4. 建议新表

### 4.1 `butler_projects`

用途：登记“被代码管家托管”的项目。

建议字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | `TEXT PRIMARY KEY` | 项目 ID |
| `workspace_id` | `TEXT NOT NULL` | 关联 `workspaces.id` |
| `name` | `TEXT NOT NULL` | 项目显示名 |
| `repo_root` | `TEXT NOT NULL` | 项目仓库根路径，必须落在工作区边界内 |
| `default_provider` | `TEXT` | 默认 provider，例如 `codex` / `claude-code` |
| `instruction_profile_id` | `TEXT` | 指令画像或模板引用，MVP 可先留空 |
| `approval_mode` | `TEXT NOT NULL` | `readonly` / `controlled` / `auto` |
| `lifecycle_status` | `TEXT NOT NULL` | `active` / `paused` / `archived` |
| `risk_level` | `TEXT NOT NULL` | `low` / `medium` / `high` |
| `config_json` | `TEXT NOT NULL` | 项目级配置快照 |
| `last_patrol_at` | `TEXT` | 最近巡视时间 |
| `last_verification_at` | `TEXT` | 最近验证时间 |
| `created_at` | `TEXT NOT NULL` | 创建时间 |
| `updated_at` | `TEXT NOT NULL` | 更新时间 |
| `archived_at` | `TEXT` | 归档时间 |

约束与索引：

- `FOREIGN KEY (workspace_id) REFERENCES workspaces(id)`
- `UNIQUE (workspace_id, repo_root)`
- `CHECK (approval_mode IN ('readonly', 'controlled', 'auto'))`
- `CHECK (lifecycle_status IN ('active', 'paused', 'archived'))`
- `CHECK (risk_level IN ('low', 'medium', 'high'))`
- 索引：
  - `idx_butler_projects_workspace_id`
  - `idx_butler_projects_status`

### 4.2 `butler_sessions`

用途：把“代码管家视角的会话”挂接到现有宿主的真实 session。

建议字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | `TEXT PRIMARY KEY` | 代码管家会话 ID |
| `project_id` | `TEXT NOT NULL` | 关联项目 |
| `session_id` | `TEXT NOT NULL` | 关联 `session_bindings.session_id` |
| `role` | `TEXT NOT NULL` | `patrol` / `execution` / `verification` / `adhoc` |
| `ownership_mode` | `TEXT NOT NULL` | `managed` / `observed` |
| `status` | `TEXT NOT NULL` | `idle` / `running` / `blocked` / `failed` / `closed` |
| `last_summary` | `TEXT` | 最近总结 |
| `last_checkpoint_at` | `TEXT` | 最近采样时间 |
| `created_at` | `TEXT NOT NULL` | 创建时间 |
| `updated_at` | `TEXT NOT NULL` | 更新时间 |

约束与索引：

- `FOREIGN KEY (project_id) REFERENCES butler_projects(id)`
- `FOREIGN KEY (session_id) REFERENCES session_bindings(session_id)`
- `UNIQUE (session_id)`
- `CHECK (role IN ('patrol', 'execution', 'verification', 'adhoc'))`
- `CHECK (ownership_mode IN ('managed', 'observed'))`
- `CHECK (status IN ('idle', 'running', 'blocked', 'failed', 'closed'))`
- 索引：
  - `idx_butler_sessions_project_id`
  - `idx_butler_sessions_status`

说明：

- `provider` 等底层会话信息应通过联表 `session_bindings` 读取，不在这里重复存。
- 这样才能避免同一会话两边状态打架。

### 4.3 `session_checkpoints`

## 5. 建议查询路径

### 5.1 项目首页

联表路径：

- `butler_projects`
- 左联 `patrol_runs` 取最近一次
- 左联 `verification_runs` 取最近一次
- 左联 `butler_sessions` + `session_indices` + `session_states` 取活跃会话

### 5.2 会话巡视页

联表路径：

- `butler_sessions`
- `session_bindings`
- `session_indices`
- `session_states`
- `session_checkpoints`

### 5.3 项目记忆页

联表路径：

- `project_memories`
- 左联 `butler_sessions`
- 左联 `session_checkpoints`

## 6. 迁移顺序建议

按这个顺序做，最稳：

1. `butler_projects`
2. `butler_sessions`
3. `session_checkpoints`
4. `project_memories`
5. `patrol_plans`
6. `patrol_runs`
7. `verification_runs`
8. `approval_requests`
9. `audit_events`

理由很简单：

- 先立项目和会话根对象
- 再立记忆和巡视
- 最后接验证、授权、审计

别一上来先做审计和 fancy 报表，那是顺序错了。

## 7. MVP 裁剪建议

MVP 阶段建议只真正落库以下核心表：

1. `butler_projects`
2. `butler_sessions`
3. `session_checkpoints`
4. `project_memories`
5. `patrol_plans`
6. `patrol_runs`
7. `verification_runs`

`approval_requests` 和 `audit_events` 可以第一批同时建表，但允许功能上先做最小闭环：

- 授权先支持 `pending/approved/denied`
- 审计先只记关键事件，不做复杂查询面板

## 8. 核心判断

### 【核心判断】

✅ 值得做：这套表结构是平台层成立的最低前提。没有这些权威对象，所谓“代码管家”就只是 provider 会话列表套壳。

### 【关键洞察】

- 数据结构：项目是根，会话是挂件，记忆/巡视/验证/授权/审计都围着项目转
- 复杂度：底层 session 绑定复用现有表，别在 butler 层再复制一套 provider 元数据
- 风险点：最容易出问题的是 `butler_sessions` 和 `session_bindings` 双写失真，所以必须单向依赖现有绑定表

### 【Linus式方案】

1. 先把 `butler_projects` 和 `butler_sessions` 立稳
2. 用最少的状态枚举把巡视和验证跑起来
3. 让 `project_memories` 独立存在，不绑死某个 provider
4. 所有底层 provider 会话信息都从 `session_bindings` 读，别复制

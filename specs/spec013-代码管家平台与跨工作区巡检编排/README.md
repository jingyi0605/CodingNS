# spec013-代码管家平台与跨工作区巡检编排

## 当前定位

这个 Spec 解决的不是“再接一个 provider”这么小的事。

真正的问题是：当用户同时维护多个工作区、多个项目、多个 AI 会话时，系统能不能有一个统一的“代码管家”控制面，持续知道：

- 哪些项目在推进
- 哪些会话卡住了
- 哪些改动没有验证
- 哪些风险已经出现但没人盯
- 哪些任务可以交给 agent 继续做

如果这件事继续靠人脑硬扛，最后一定烂：

- 会话一多，没人记得哪个项目停在哪
- provider 一多，指令文件、会话续接、权限模式全部不一致
- 记忆一散，昨天学到的东西今天又得重讲一遍
- 验证一弱，agent 说“完成了”就只能靠信仰

所以 `spec013` 的目标很明确：

- 把“代码管家”做成正式的平台能力，而不是几条散命令
- 在平台层统一编排 `Codex`、`Claude Code` 等 provider
- 统一项目级长期记忆、周期巡视、验证与授权控制
- 支持只读巡检、建议输出、受控执行、验证回写这一整条闭环

## 计划覆盖

- `ButlerProject`、`ButlerSession`、`ProjectMemory`、`PatrolPlan`、`VerificationRun` 数据模型
- `Codex` / `Claude Code` provider 适配层
- 指令注入适配：`AGENTS.md`、`CLAUDE.md`、system prompt 注入统一编排
- 项目级长期记忆存储与回灌
- 周期巡视与定时任务调度
- 浏览器/视觉验证执行器
- 开发执行授权、风险闸门与审计
- 项目建议、进展总结、自动化执行结果回写

## 依赖关系

- 前置依赖：`spec001`、`spec002`、`spec006`、`spec007`、`spec010`、`spec012`
- 后续依赖：代码管家工作台 UI、跨设备通知、更细粒度自治策略

## 本阶段明确不做

- 让不同 provider 的原生能力表现得一模一样
- 完全无人值守地替用户自动合并所有代码
- 分布式集群调度
- 无限期无约束的“全自动开发”
- 把浏览器验证直接绑死到某一个 provider 的私有能力上

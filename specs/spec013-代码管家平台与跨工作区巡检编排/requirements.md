# 需求文档 - spec013-代码管家平台与跨工作区巡检编排

状态：Draft

## 简介

这个 Spec 讨论的是一个真实问题，不是概念玩具。

用户不是只想“在当前工作区里继续聊一轮”，而是想让系统像一个长期在线的代码管家一样，跨多个工作区和项目持续巡检、记忆、建议、验证，并在授权范围内替用户推进开发。

如果没有平台层统一兜底，这件事会在三个地方直接崩掉：

- **能力边界不一致**：`Codex` 与 `Claude Code` 的指令文件、会话续接、权限模型、自动化方式并不相同
- **长期记忆不可靠**：provider 自带记忆是局部能力，不是跨工作区、跨 provider 的权威记忆
- **验证链路不闭环**：agent 说“做完了”和真的跑通了，是两回事

所以这个 Spec 的核心不是“再包装一下对话界面”，而是明确平台必须自己承担的职责：

- 统一项目、会话、记忆、巡视和验证模型
- 统一 provider 适配，而不是让上层到处写分支判断
- 统一授权与审计，避免自动执行把项目搞坏

## 可实现性结论

### 结论

这个能力 **可以实现**，但实现路径必须是：

- 在 `CodingNS` 平台层实现统一编排、记忆、调度、验证与授权控制
- 把 `Codex`、`Claude Code` 视为 provider 适配目标，而不是平台本身
- 把 provider 原生能力当成可复用部件，而不是平台真相来源

### 已验证事实

1. `Codex` 官方支持 `AGENTS.md` 分层加载，可以作为项目级指令注入基础。
2. `Claude Code` 官方支持 `CLAUDE.md`、`--append-system-prompt`、`--system-prompt-file` 等方式注入会话人格与规则。
3. `Codex` 和 `Claude Code` 都具备定时/自动化能力，但能力模型不完全一致。
4. 浏览器自动化与视觉验证可以通过独立验证执行器实现，不必依赖单一 provider。
5. 联网搜索、真实页面访问、截图验证在当前环境中已经实际可用。

### 平台判断

- ✅ 值得做：这是多项目并行开发时非常实际的控制面问题
- ✅ 能落地：现有 `spec001/spec002/spec006/spec007/spec010/spec012` 已经提供底座
- ❌ 不能偷懒：如果不做统一适配层和统一记忆层，后面一定变成一坨 provider 特判

## 术语表

- **Butler（代码管家）**：平台层的统一项目管理与执行控制能力，不等于某一个 provider
- **ButlerProject（管家项目）**：被代码管家托管的项目实体，关联工作区、仓库、会话与记忆
- **ButlerSession（管家会话）**：平台登记的可被巡检、续接、总结、验证的 agent 会话
- **ProviderAdapter（提供方适配器）**：封装 `Codex`、`Claude Code` 差异的统一接口层
- **InstructionAdapter（指令适配器）**：负责把项目规则转换为 provider 可消费的启动上下文
- **ProjectMemory（项目记忆）**：项目级长期记忆存储，记录架构、约束、决策、故障、验证经验
- **PatrolPlan（巡视计划）**：定义一个项目或项目组多久被巡视一次、巡视要做什么
- **PatrolRun（巡视执行）**：一次实际的巡检任务执行记录
- **VerificationRunner（验证执行器）**：负责测试、浏览器、截图、指标检查等验证任务
- **ApprovalGate（授权闸门）**：决定哪些动作可自动执行，哪些必须显式授权
- **SessionCheckpoint（会话快照）**：对会话当前状态、摘要、产出、风险的结构化采样

## 范围说明

### In Scope

- 定义代码管家平台的项目、会话、记忆、巡视、验证、授权模型
- 适配 `Codex` 与 `Claude Code` 的会话启动、续接、总结与执行入口
- 统一指令注入，支持 `AGENTS.md`、`CLAUDE.md` 和 system prompt 注入映射
- 实现项目级长期记忆存储、检索、回灌与人工校正
- 实现周期巡视计划和巡视执行记录
- 实现开发建议、进展总结、风险提示输出
- 实现受控开发执行与验证回写闭环
- 实现浏览器/视觉验证能力的统一入口

### Out of Scope

- 第一阶段做完全无人值守的自动合并与发布
- 强行统一不同 provider 的内部推理过程
- 依赖 provider 私有记忆作为唯一事实来源
- 直接接入所有可能的第三方 agent/CLI
- 第一阶段实现跨机器分布式调度

## 技术边界

### 边界 1：不能假设所有 provider 都原生支持同一份指令文件

- `Codex` 原生支持 `AGENTS.md`
- `Claude Code` 主路径是 `CLAUDE.md`，也支持 CLI 注入 prompt
- 平台必须做 `InstructionAdapter`

### 边界 2：不能把 provider 的会话持久化能力当平台真相

- 会话是否可续接、如何续接、会话 ID 如何管理，provider 差异明显
- 平台必须维护自己的 `ButlerSession` 索引与快照

### 边界 3：不能把 provider 自带 memory 当跨项目长期记忆

- provider memory 只适合做局部补充
- 平台必须维护自己的 `ProjectMemory`

### 边界 4：不能把“执行成功”与“验证通过”混为一谈

- agent 完成任务不等于项目结果可用
- 平台必须把验证作为独立一等能力

### 边界 5：不能默认允许 agent 随意写代码和操作环境

- 代码管家能力天然带有高破坏风险
- 平台必须有授权模式、风险级别和审计记录

## 需求

### 需求 1：系统必须把“代码管家项目”和“代码管家会话”做成正式模型

**用户故事：** 作为使用者，我希望系统知道哪些项目正在被管家托管、哪些会话属于哪个项目、会话当前处于什么阶段，这样我才能真正管理多项目状态。

#### 验收标准

1. WHEN 用户将一个仓库纳入代码管家管理 THEN System SHALL 持久化 `ButlerProject`，至少记录工作区、仓库路径、项目标题、默认 provider、默认授权策略和创建时间。
2. WHEN 平台为项目创建或登记会话 THEN System SHALL 持久化 `ButlerSession`，至少记录 `providerId`、`sessionRef`、`cwd`、`status`、`lastCheckpointAt`、`lastSummary` 等字段。
3. WHEN 用户查看项目详情 THEN System SHALL 返回项目下全部受管会话、最近巡视、最近验证和关键风险摘要。

### 需求 2：系统必须通过统一适配层支持 `Codex` 与 `Claude Code`

**用户故事：** 作为维护者，我希望上层逻辑不需要关心 provider 私有差异，这样系统才能持续扩展，而不是第三个 provider 来了就炸。

#### 验收标准

1. WHEN 平台请求启动、续接、总结或执行任务 THEN System SHALL 通过 `ProviderAdapter` 调用 provider，而不是在上层散落 provider 特判。
2. WHEN provider 不支持某项能力 THEN System SHALL 显式返回能力缺失或降级策略，而不是伪装成已支持。
3. WHEN 后续新增新的 provider THEN System SHALL 尽量复用项目、会话、记忆、巡视和验证主流程。

### 需求 3：系统必须统一管理会话指令注入和“代码管家人格”

**用户故事：** 作为使用者，我希望不同 provider 启动出来的会话都具备一致的代码管家认知，而不是一个像助手、一个像裸 CLI。

#### 验收标准

1. WHEN 平台为项目准备会话上下文 THEN System SHALL 生成统一的管家指令模型，包括项目规则、目标、边界、记忆摘要和当前任务。
2. WHEN provider 为 `Codex` THEN System SHALL 支持以 `AGENTS.md` 或等效上下文方式注入规则。
3. WHEN provider 为 `Claude Code` THEN System SHALL 支持以 `CLAUDE.md`、`--append-system-prompt` 或等效方式注入规则。
4. WHEN 平台无法将某条规则映射到 provider 原生能力 THEN System SHALL 记录映射降级，而不是静默丢失。

### 需求 4：系统必须具备项目级长期记忆

**用户故事：** 作为用户，我希望系统能长期记住项目架构、约束、决策和踩坑记录，而不是每次换会话都从零开始重新解释。

#### 验收标准

1. WHEN 用户或系统写入项目记忆 THEN System SHALL 持久化 `ProjectMemory`，至少记录内容、类型、来源、置信度、作用范围和更新时间。
2. WHEN 平台启动或巡视会话 THEN System SHALL 能检索与当前项目、任务、目录相关的记忆片段并回灌给会话。
3. WHEN 记忆被证明错误或过期 THEN System SHALL 支持修正、降权或归档，而不是让错误记忆永久污染后续会话。

### 需求 5：系统必须支持周期巡视与计划执行

**用户故事：** 作为用户，我希望系统能按计划主动检查项目进展、测试状态和风险，而不是等我想起来才去问。

#### 验收标准

1. WHEN 用户为项目配置巡视计划 THEN System SHALL 持久化 `PatrolPlan`，至少记录频率、执行内容、目标项目或项目组、默认只读/可写模式。
2. WHEN 到达计划时间 THEN System SHALL 创建 `PatrolRun` 并执行配置的巡视动作。
3. WHEN 巡视完成 THEN System SHALL 输出结构化总结，包括进展、风险、建议、是否需要人工介入，以及关联的会话和验证结果。

### 需求 6：系统必须先支持只读巡检，再支持受控写入执行

**用户故事：** 作为维护者，我希望系统第一步先会看、会总结、会告警，再逐步放开它写代码，不然一开始就会闯祸。

#### 验收标准

1. WHEN 项目处于只读巡检模式 THEN System SHALL 允许读取代码、会话、日志、测试和验证信息，但 SHALL NOT 自动修改代码或执行高风险命令。
2. WHEN 项目启用受控执行模式 THEN System SHALL 仅在授权策略允许时执行代码修改、命令运行、测试和验证。
3. WHEN 某个动作超出授权范围 THEN System SHALL 阻止执行并产出待审批项。

### 需求 7：系统必须能输出开发建议、进展总结和风险提示

**用户故事：** 作为项目负责人，我希望系统不只是会跑命令，还能告诉我项目当前到底推进到哪、问题在哪、下一步该干什么。

#### 验收标准

1. WHEN 巡视或会话总结完成 THEN System SHALL 产出结构化项目总结，至少包含进展、阻塞、验证状态、建议动作和风险等级。
2. WHEN 发现测试失败、会话停滞或高风险改动 THEN System SHALL 产出明确警告，而不是继续报喜不报忧。
3. WHEN 多个项目同时被巡视 THEN System SHALL 支持输出项目维度的优先级排序建议。

### 需求 8：系统必须具备统一验证能力，包括浏览器和视觉验证

**用户故事：** 作为用户，我希望系统能真正去验证页面、流程和指标，而不是只读代码后靠猜。

#### 验收标准

1. WHEN 项目配置了验证任务 THEN System SHALL 支持运行命令测试、健康检查、浏览器自动化和截图采样。
2. WHEN 验证涉及浏览器或页面交互 THEN System SHALL 通过独立的 `VerificationRunner` 执行，而不是耦合在某个 provider 私有能力里。
3. WHEN 验证完成 THEN System SHALL 记录 `VerificationRun`，至少包含结果状态、关键产物路径、摘要和执行时间。

### 需求 9：系统必须把执行、验证和记忆回写串成闭环

**用户故事：** 作为维护者，我希望系统不是做完一步就失忆，而是能把执行结果、验证结果和新学到的东西持续沉淀回项目。

#### 验收标准

1. WHEN 任务执行完成 THEN System SHALL 将结果摘要挂到对应 `ButlerSession` 和 `ButlerProject`。
2. WHEN 验证完成 THEN System SHALL 回写验证结论和关键证据索引。
3. WHEN 本次执行产生稳定经验 THEN System SHALL 支持将其转写为候选 `ProjectMemory`，待自动或人工确认后入库。

### 需求 10：系统必须具备审计和回溯能力

**用户故事：** 作为维护者，我希望知道是谁、什么时候、以什么授权、通过哪个 provider 对项目做了什么，这样出了问题能追责和回滚。

#### 验收标准

1. WHEN 平台启动会话、执行任务、修改代码、运行验证或更新记忆 THEN System SHALL 记录审计事件。
2. WHEN 用户查看项目时间线 THEN System SHALL 展示关键事件，包括巡视、执行、验证、授权决策和记忆回写。
3. WHEN 系统发生异常或误执行 THEN System SHALL 能定位到对应项目、会话、provider、任务和验证记录。

### 需求 11：代码管家能力不能破坏现有工作区、会话和进程主链路

**用户故事：** 作为现有系统维护者，我希望新增代码管家能力后，不会把现有单会话主链路打烂。

#### 验收标准

1. WHEN 用户不启用代码管家功能 THEN System SHALL 维持现有工作区、会话、终端、进程和 provider 主链路行为不变。
2. WHEN 代码管家功能接入 THEN System SHALL 复用现有底座和 provider 适配边界，而不是复制一套平行实现。
3. WHEN 代码管家任务失败 THEN System SHALL 将影响限制在任务或项目范围内，不得波及无关工作区。

## 非功能需求

### 非功能需求 1：可靠性

1. WHEN Host 重启 THEN System SHALL 恢复项目、会话、巡视计划、最近快照和验证记录索引。
2. WHEN 单个巡视或验证失败 THEN System SHALL 不得导致整个代码管家服务不可用。

### 非功能需求 2：可维护性

1. WHEN 新增 provider 或验证类型 THEN System SHALL 通过适配扩展点接入，而不是继续堆条件分支。
2. WHEN 排查问题 THEN System SHALL 能快速定位项目、会话、巡视、验证和记忆之间的关系。

### 非功能需求 3：安全性

1. WHEN 平台执行写操作或高风险命令 THEN System SHALL 受 `ApprovalGate` 与授权策略约束。
2. WHEN 平台使用联网、浏览器或本地执行能力 THEN System SHALL 明确记录能力来源与风险等级。

### 非功能需求 4：可观测性

1. WHEN 巡视、执行、验证、记忆回写完成或失败 THEN System SHALL 输出结构化日志。
2. WHEN 用户查看项目状态 THEN System SHALL 展示最近巡视时间、验证时间、风险等级和会话健康度。

## MVP 切分

### MVP-1：只读巡检闭环

- 项目登记与会话登记
- `Codex` / `Claude Code` 基础适配
- 指令注入适配
- 项目级长期记忆存储与回灌
- 周期巡视计划
- 只读进展总结、风险提示、建议输出

### MVP-2：验证闭环

- 命令测试与健康检查
- 浏览器/视觉验证执行器
- 验证结果回写与时间线展示

### MVP-3：受控执行闭环

- 授权策略
- 受控代码修改与命令执行
- 执行结果、验证结果、记忆候选回写

### 当前明确不进 MVP

- 自动合并代码
- 完全无人值守开发
- 分布式多机调度
- 全 provider 一次性接入

## 成功定义

- 系统能够把跨工作区多项目的 agent 会话当成正式对象管理
- 系统能够统一适配 `Codex` 与 `Claude Code`，而不是在上层散落特判
- 系统能够按计划巡视项目并输出可信的进展、风险和建议
- 系统能够把长期记忆沉淀在平台层，而不是依赖单个 provider 私有能力
- 系统能够对执行结果做真实验证，而不是只听 agent 自己说“完成了”
- 新能力不破坏现有工作区、会话、终端、进程和 provider 主链路

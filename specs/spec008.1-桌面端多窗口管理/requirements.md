# 需求文档 - spec008.1 桌面端多窗口管理

状态：Draft

## 简介

这个子 Spec 解决的是：

- 怎样在 `Desktop` 端把现有工作台拆成多个可控窗口
- 怎样先做一批最不容易把系统搞烂的窗口
- 怎样在支持多窗口的同时，保证现在的单窗口工作台继续可用

这里不讨论 `H5`，也不讨论“未来也许会有的酷炫窗口编排”。先把真正需要的数据结构、壳层命令和第一批安全窗口做出来。

## 术语表

- **Window Descriptor（窗口描述）**：描述一个桌面窗口是什么、显示什么、属于哪个工作区、现在处于什么模式的最小数据结构。
- **Docked Window（停靠窗口）**：仍然显示在主工作台里的视图。
- **Floating Window（悬浮窗口）**：仍在主窗口内，但作为浮层或悬浮容器存在的视图。
- **External Window（外部窗口）**：由 `Tauri` 创建的独立原生窗口。
- **Focus Owner（焦点拥有者）**：当前拥有某个可交互资源前台控制权的窗口 ID。
- **Interactive Terminal Window（终端主交互窗）**：允许发送输入和尺寸变更的终端窗口。
- **Read-only Terminal Mirror（终端只读镜像窗）**：只能看输出，不能发送输入和尺寸变更的终端窗口。

## 范围说明

### In Scope

- `Desktop` 端多窗口数据结构和前端窗口注册表
- `Tauri` 多窗口命令和窗口生命周期管理
- 第一批外部窗口：文件、Git、进程管理
- 窗口 ID、窗口类型、窗口模式、尺寸位置的最小持久化
- 终端多窗口交互规则定义
- 单窗口工作台兼容和默认入口保留

### Out of Scope

- `H5` 多窗口或浏览器弹窗体系
- 聊天窗口独立拆出
- 终端多窗口同时交互
- 自由拼接、平铺、吸附、工作区模板编排
- 为了多窗口重写现有 Host 业务协议

## 需求

### 需求 1：系统必须先有一个最小但清楚的窗口描述模型

**用户故事：** 作为开发者，我希望系统先有统一的窗口描述数据，而不是先写一堆窗口特判，这样后续新增窗口类型时不会继续堆垃圾判断。

#### 验收标准

1. WHEN 系统创建或恢复桌面窗口 THEN System SHALL 使用统一 `WindowDescriptor` 描述窗口，而不是在多个组件里散落字段。
2. WHEN 定义窗口描述 THEN System SHALL 至少包含 `windowId`、`kind`、`workspaceId`、`sessionId`、`terminalId`、`mode`、`bounds`、`focusOwner`。
3. WHEN 新增窗口类型 THEN System SHALL 通过 `kind` 扩展，不要求改动现有窗口数据结构。

### 需求 2：桌面壳必须提供最小可用的多窗口命令

**用户故事：** 作为前端实现者，我希望 `Tauri` 明确提供创建、关闭、聚焦、同步窗口状态的命令，这样前端不需要把窗口控制逻辑硬塞进页面代码。

#### 验收标准

1. WHEN 前端请求打开外部窗口 THEN System SHALL 通过桌面壳命令创建指定 `windowId` 的独立窗口。
2. WHEN 前端请求关闭、聚焦或更新窗口尺寸 THEN System SHALL 通过桌面壳命令执行，而不是直接操作平台私有细节。
3. WHEN 外部窗口启动 THEN System SHALL 能读取自己的窗口描述，而不是靠页面硬编码猜测当前要显示什么。

### 需求 3：第一批只允许拆出文件、Git、进程管理窗口

**用户故事：** 作为产品维护者，我希望第一批多窗口只拆读多写少的安全面板，这样不会一上来把聊天和终端都搞乱。

#### 验收标准

1. WHEN 用户从主工作台打开外部窗口 THEN System SHALL 只支持 `files`、`git`、`processes` 三类窗口。
2. WHEN 外部窗口打开 `files`、`git`、`processes` THEN System SHALL 复用现有工作区上下文和数据来源，不发明第二套业务协议。
3. WHEN 第一批范围评审 THEN System SHALL 明确不包含 `chat` 和可交互 `terminal` 外部窗口。

### 需求 4：现有单窗口工作台必须保持默认且零破坏

**用户故事：** 作为现有用户，我希望不打开多窗口时，今天怎么用，之后还怎么用，而不是被新能力打断原有流程。

#### 验收标准

1. WHEN 用户不使用多窗口 THEN System SHALL 保持现有单窗口工作台为默认入口。
2. WHEN 新增多窗口能力 THEN System SHALL 不改变现有聊天页、终端页、文件面板、Git 面板的主窗口使用方式。
3. WHEN 关闭所有外部窗口 THEN System SHALL 不影响主工作台继续工作。

### 需求 5：窗口状态必须有最小持久化，但不能把壳层做成业务真相

**用户故事：** 作为桌面用户，我希望窗口能记住最基本的尺寸和位置；作为架构维护者，我又不希望壳层变成业务数据中心。

#### 验收标准

1. WHEN 外部窗口关闭后再次打开 THEN System SHALL 恢复上次保存的 `bounds` 和 `mode`。
2. WHEN 保存窗口状态 THEN System SHALL 只保存窗口元数据，不保存业务真相副本。
3. WHEN 主窗口和外部窗口同时存在 THEN System SHALL 通过统一窗口注册表管理窗口元数据，不允许每个页面各存一份。

### 需求 6：终端多窗口必须先锁定交互所有权

**用户故事：** 作为终端用户，我希望终端窗口行为可预测，而不是两个窗口同时抢输入和尺寸，把会话搞坏。

#### 验收标准

1. WHEN 同一个 `terminalId` 在多个窗口中显示 THEN System SHALL 只允许一个窗口成为主交互窗。
2. WHEN 窗口不是主交互窗 THEN System SHALL 禁止该窗口发送终端输入和尺寸变更。
3. WHEN 主交互窗关闭或失去所有权 THEN System SHALL 明确回收交互权，不自动把交互权偷偷转给别的窗口。

### 需求 7：本子 Spec 明确只做 Desktop，不做 H5

**用户故事：** 作为项目负责人，我希望范围被钉死在桌面端，否则实现会被浏览器限制拖死。

#### 验收标准

1. WHEN 编写本子 Spec 任务 THEN System SHALL 只包含 `Desktop` 多窗口内容。
2. WHEN 评审实现范围 THEN System SHALL 不包含 `window.open`、浏览器弹窗管理或 H5 多窗口兼容。
3. WHEN 后续出现 H5 多窗口需求 THEN System SHALL 作为新的独立问题处理，不混入本子 Spec。

## 非功能需求

### 非功能需求 1：可维护性

1. WHEN 新增窗口类型 THEN System SHALL 优先扩展 `WindowDescriptor` 和窗口注册表，而不是往页面里再加一层 `if/else`。
2. WHEN 排查窗口问题 THEN System SHALL 能清楚区分“前端窗口注册问题”和“桌面壳窗口命令问题”。

### 非功能需求 2：兼容性

1. WHEN 多窗口能力关闭或不可用 THEN System SHALL 回退到现有单窗口工作台，不影响主要业务路径。
2. WHEN 窗口恢复失败 THEN System SHALL 允许用户继续从主工作台打开对应功能，不把用户锁死。

### 非功能需求 3：可靠性

1. WHEN 外部窗口异常关闭 THEN System SHALL 能正确回收窗口注册状态。
2. WHEN 主窗口仍然存在 THEN System SHALL 不因为外部窗口异常导致工作区主状态崩溃。

## 成功定义

- `Desktop` 端已经有统一 `WindowDescriptor` 和窗口注册表，不再靠组件局部状态拼窗口行为。
- `Tauri` 已补齐最小多窗口命令，前端可以稳定创建和回收外部窗口。
- 第一批 `files / git / processes` 外部窗口可用。
- 现有单窗口工作台保持默认入口且不被破坏。
- 终端多窗口交互规则已经定死：一个主交互窗，其余明确只读。

# 20260531-开源网盘外部变更检测借鉴

这份补充文档只回答一个问题：

**为什么事务文档库的自动刷新方案，不该继续走“递归 watcher 盯整棵树”这条路？**

## 1. 先说结论

像 ownCloud、Nextcloud 这类开源私有网盘，长期跑下来并不是靠“每个目录都挂 watcher，发现一点变化就全量重扫”。

它们真正靠谱的做法更接近下面这四步：

1. 维护自己的索引/缓存层
2. 拿到事件时先记成“这里可能脏了”
3. 已知范围时只补刷受影响路径
4. 再用低频周期扫描兜底，接受最终一致

这和 `spec016.2` 现在定下来的方向是一致的。

## 2. 为什么不能继续迷信 watcher

原因很现实：

- 目录多时，递归 watcher 很容易把句柄数打爆
- 不同平台、不同文件系统、不同同步盘对事件支持并不一致
- 很多编辑器是原子写，不会老老实实给你一个干净的“目标文件已修改”事件
- 网络盘、同步盘、外部存储经常只给模糊目录事件，甚至直接漏事件

一句人话：

**watcher 只能算“提示器”，不能算唯一真相来源。**

## 3. ownCloud / Nextcloud 最值得借鉴的点

### 3.1 索引层是主角，不是文件系统本体

这些系统真正依赖的是自己的元数据索引：

- 路径
- 时间戳
- 目录关系
- 标签或附加元数据

所以它们优化的重点不是“如何多开 watcher”，而是“如何让索引层只更新必要范围”。

### 3.2 事件先入队，再慢慢处理

成熟系统通常不会在通知回调里直接做重活。

更典型的做法是：

- listener 只负责收通知
- 先写成队列或脏信号
- 后台任务再按批处理

这和 `spec016.2` 的 `watcher -> 脏标记 -> TaskManager` 主链路是一回事。

### 3.3 已知范围时优先局部补刷

如果已经知道是哪个目录、哪个文件变了，就先补这一小块。

不要把“改了一篇文档”当成“全盘重建索引”的借口。

### 3.4 漏事件就认，靠周期兜底

这类系统不会假装外部事件永远完整可靠。

正确做法是：

- 实时事件尽量接
- 漏掉的部分，用低频周期补扫兜底
- 接受最终一致，而不是追求理论上的绝对实时

## 4. 对当前事务文档库最直接的借鉴

### 4.1 本轮必须借鉴的五件事

#### 借鉴 1：watcher 只是报信器，不是真相来源

事件到了，只说明“这里可能脏了”。
真正的真相还是以后续索引刷新和导出快照为准。

#### 借鉴 2：单根监听，不再递归开目录 watcher

句柄数量应该跟资料库数量相关，而不是跟子目录数量一起爆炸。

#### 借鉴 3：普通变更优先 targeted refresh，同时保留周期补扫

知道目标路径，就只刷那一块；漏掉的部分，再靠低频周期补回来。

#### 借鉴 4：dirty 事件先进统一调度链路

不要在回调里直接跑重活。
先合并、去重、延后，再让后台任务处理。

#### 借鉴 5：索引产物缺失时自动重建

成熟系统不会把索引产物缺失当成“只能人工修”的异常。
缺了就该进入恢复链路。

### 4.2 下一轮继续借鉴的三件事

#### 借鉴 6：按目录归并批处理

别一直按文件碎片化刷新。目录才是更稳的批处理单位。

#### 借鉴 7：失败时保留最近一次可用结果

自动刷新失败不等于前端必须全空。状态和数据要分开看。

#### 借鉴 8：结构化观测

要能回答：

- watcher 还活着吗
- 最近一次为什么没刷新
- 是被去重了，还是任务失败了
- 是没事件，还是有事件没处理掉

### 4.3 后面再借鉴的东西

#### 借鉴 9：目录版本戳 / etag-like 机制

这是后续优化成本和规模上限时很有价值的方向，但不是第一波必做。

#### 借鉴 10：pending state 的持久化恢复

适合在 Host 重启恢复这类问题上继续补。

#### 借鉴 11：专用存储通知适配器

以后如果真要适配某些存储的专用通知，再单开一层，不要抢跑。

## 5. 不借鉴什么

- 不照搬网盘那套庞大的 filecache / share / activity 全家桶
- 不为了“更实时”再回到递归 watcher
- 不为极端边界先上复杂分布式通知系统

## 6. 这份文档对 spec016.2 的意义

它不是拿来装饰的。

它的实际作用只有一个：

**提醒后续实现时，不要再掉回“事件一来就全量重活”“目录一多就递归 watcher”这种低级坑里。**

# 需求文档 - spec016.2-事务文档库外部变更感知与自动刷新

状态：Draft

## 简介

`spec016.1` 解决了“事务视图文档库要接真实数据”的问题，但还没有彻底解决“真实数据怎么保持新鲜”。

现在真正的使用方式是：

- 用户经常在外部编辑器里改文档
- 同步盘会在后台创建、替换、删除文件
- 有些编辑器不是直接覆盖，而是先写临时文件，再 rename 替换
- 某些场景下 `.ai-index` 或导出快照还可能被手动删除

如果系统只能处理应用内写入，它就是半残。

这份需求文档要把目标写清楚：

1. 普通外部文件改动后，事务文档库要能自动刷新
2. 刷新不能靠递归 watcher 把句柄数打爆
3. 刷新不能在读接口或 watcher 回调里直接跑重活
4. watcher 漏掉的情况，要靠低频周期刷新兜底
5. 索引产物丢了，要能自动重建，而不是一直卡在旧状态

## 术语表

- **System**：`CodingNS`
- **外部变更**：不是通过 `CodingNS` 应用内文件写入产生的资料库文件变化
- **targeted refresh**：已知受影响路径时，只刷新该路径相关索引和导出，而不是全量重扫
- **周期刷新**：固定较低频率触发的兜底刷新，用来弥补 watcher 漏事件或通知不可靠
- **脏标记**：只表达“这里可能已经变了，需要后续刷新”，不代表当场已经算完
- **索引产物**：`.ai-index` 下的数据库、导出快照、状态文件等索引相关文件
- **原子写中间产物**：编辑器或同步工具在正式替换目标文件前写出的临时文件

## 范围说明

### In Scope

- 事务文档库外部文件变更感知
- 外部变更后的自动刷新调度
- 临时文件过滤和原子写兼容
- 周期自动刷新兜底
- 索引产物缺失时的自动重建
- 状态模型、日志和验证口径

### Out of Scope

- 文件内容级 diff 展示
- 多设备跨端推送同步协议
- 全文搜索结果的实时增量更新 SLA
- 所有底层存储类型的专用通知适配器
- 分布式消息队列或独立通知服务

## 需求

### 需求 1：系统必须支持普通外部文件变动后的自动刷新

**用户故事：** 作为主要在外部编辑器里改资料的人，我希望改完文件后事务文档库能自己更新，而不是总靠手动刷新。

#### 验收标准

1. WHEN 资料库根目录下有普通文档被新增、修改、删除或重命名 THEN System SHALL 记录对应脏标记，并自动调度后续刷新。
2. WHEN watcher 能识别出具体受影响路径 THEN System SHALL 优先走 targeted refresh，而不是立刻全量重扫。
3. WHEN 同一工作区短时间内连续收到多次文件事件 THEN System SHALL 先经过 quiet window 合并，再统一提交刷新。
4. WHEN 当前已有同类刷新任务在跑 THEN System SHALL 去重或延后，不得并发重复跑第二份同类重活。

### 需求 2：系统必须支持周期自动刷新兜底

**用户故事：** 作为主要依赖外部编辑的人，我希望就算 watcher 漏事件，系统也能在之后自己补上，而不是永远停在旧数据。

#### 验收标准

1. WHEN watcher 漏掉外部改动、网络盘通知不稳定或系统重启错过事件 THEN System SHALL 通过低频周期刷新补齐缺口。
2. WHEN 周期刷新触发时 THEN System SHALL 先判断当前是否已有阻塞中的索引任务，避免重复堆叠重活。
3. WHEN 周期刷新只是兜底检查而不是明确局部路径变更 THEN System SHALL 允许走更宽范围的刷新，但不得在每次周期到点时无脑全盘重建。
4. WHEN 周期刷新已经成功补齐最新结果 THEN System SHALL 更新最近完成时间和状态，而不是继续停留在旧时间戳。

### 需求 3：系统必须过滤常见临时文件和原子写中间产物

**用户故事：** 作为使用各种外部编辑器的人，我希望系统不要把 `.tmp`、`.swp`、`#xxx#` 这种垃圾中间文件当成真实文档变化。

#### 验收标准

1. WHEN watcher 捕获到常见临时文件类型 THEN System SHALL 默认忽略这类路径，不把它们当正式文档刷新来源。
2. WHEN 编辑器采用“写临时文件再替换正式文件”的原子写策略 THEN System SHALL 尽量把最终影响收口到真实目标路径，而不是为中间文件反复触发刷新。
3. WHEN 目录级事件本身不够精确 THEN System SHALL 允许通过短时间窗口内的目录扫描补出最近真实目标，但仍需继续忽略临时文件。

### 需求 4：系统必须保证自动刷新链路不重新引入 EMFILE 和主线程重活

**用户故事：** 作为维护者，我希望自动刷新真的能长期跑，而不是换来一堆句柄爆炸和主线程卡死。

#### 验收标准

1. WHEN 为事务文档库开启外部变更监听 THEN System SHALL 让监听数量与资料库数量相关，而不是与子目录数量线性增长。
2. WHEN watcher 收到事件 THEN System SHALL 只做轻量路径处理和脏标记，不得在回调里直接做重扫描或重导出。
3. WHEN 自动刷新需要跑索引任务 THEN System SHALL 继续复用 `TaskManager` 和 `helper_process` 链路，不得重新长私有 `timer`、私有 `inflight`、私有任务队列。
4. WHEN Host 读取文档库快照 THEN System SHALL 继续只读最近结果和状态，不得因为自动刷新需求回退成读接口现算。

### 需求 5：系统必须在索引产物缺失时自动重建

**用户故事：** 作为使用者，我希望就算 `.ai-index` 被删了，系统也能在下一次自动刷新或进入视图时补回来，而不是一直报旧状态。

#### 验收标准

1. WHEN `.ai-index`、导出快照或状态文件缺失 THEN System SHALL 把当前状态标记为需要重建，而不是继续把旧缓存假装成最新结果。
2. WHEN 工作区进入事务视图、触发周期刷新或收到外部变更时发现索引产物缺失 THEN System SHALL 自动入队重建任务。
3. WHEN 自动重建成功 THEN System SHALL 生成新的索引产物，并更新最近完成时间和状态。
4. WHEN 自动重建失败 THEN System SHALL 返回结构化错误，并保留最近一次仍可读的结果（如果存在）。

### 需求 6：系统必须把自动刷新状态明确暴露给前端和日志

**用户故事：** 作为使用者和维护者，我希望知道系统最近有没有自动刷新、为什么刷新、有没有失败，而不是只能猜。

#### 验收标准

1. WHEN 自动刷新任务入队、开始、完成、失败或被去重 THEN System SHALL 记录结构化日志，至少包含 workspaceId、reason、targetPath、taskId、taskType 和结果摘要。
2. WHEN 前端读取文档库状态 THEN System SHALL 能看到最近一次自动刷新相关的时间、状态和必要错误摘要。
3. WHEN 最近完成时间长时间没有更新 THEN System SHALL 能通过状态或日志看出是 watcher 停了、任务失败了，还是根本没有新事件。

## 非功能需求

### 非功能需求 1：性能

1. WHEN 外部变更只影响少量路径 THEN System SHALL 优先走 targeted refresh，避免反复全量导出。
2. WHEN 自动刷新持续运行 THEN System SHALL 避免监听句柄随着目录树规模线性膨胀。
3. WHEN 同一工作区短时间内有事件风暴 THEN System SHALL 通过 quiet window、去重和任务串行把重活数量压住。

### 非功能需求 2：可靠性

1. WHEN watcher 漏事件、目录事件不精确或外部存储通知不稳定 THEN System SHALL 通过周期刷新和缺失重建保证最终一致。
2. WHEN 自动刷新失败 THEN System SHALL 不把整个读链路一起拖死，而是保留最近一次可读结果并暴露失败信息。

### 非功能需求 3：可维护性

1. WHEN 后续继续补更强的变更通知来源（例如专用存储通知） THEN System SHALL 复用当前“脏标记 -> 后台任务 -> 状态更新”的主链路。
2. WHEN 后续继续优化导出内存峰值或刷新粒度 THEN System SHALL 复用当前 targeted refresh 和周期兜底的分层模型，而不是推倒重来。

## 成功定义

- 用户主要在外部编辑文件时，事务视图文档库仍能自动变新
- 自动刷新不再依赖递归 watcher，句柄数不会随目录数暴涨
- watcher 漏事件时，系统能靠周期兜底补回最新结果
- 临时文件不会再反复触发无意义刷新
- `.ai-index` 被删掉后，系统能自动重建索引产物
- 前端和日志都能清楚看到最近一次自动刷新状态

# spec016.2-事务文档库外部变更感知与自动刷新

## 这份 Spec 现在解决什么问题

`spec016.1` 已经把事务视图文档库接上真实对象，也把索引服务和后台任务接进了 Host。

但现在还差一个根问题：

**用户大多数时候不是在 `CodingNS` 里改文件，而是在外部编辑器、Finder、同步盘、脚本或别的工具里改。**

如果系统只能感知“应用内写入”，那事务视图里的文档库很快就会变旧。用户看到的就是：

- 文档明明已经改了，列表和摘要还是旧的
- 新文件已经进资料库了，但事务视图里迟迟不出现
- 某些文件删掉或重命名了，视图里还挂着旧条目
- 为了补救，只能靠手动刷新，体验非常差

一句人话：

**真实使用场景里，外部改动才是主流。事务视图如果接不住外部改动，那这套文档库就不算真的能用。**

这份 Spec 就专门解决这件事：

- 怎么在不把 Host 句柄数撑爆的前提下感知外部文件变化
- 怎么把这些变化收口成便宜的脏标记，而不是 watcher 里直接跑重活
- 怎么优先走 targeted refresh，只刷新受影响的路径
- 怎么再加一层低频周期刷新，给 watcher 漏事件、网络盘抖动、原子写替换这些情况兜底
- 怎么在 `.ai-index` 被删掉、导出快照缺失时自动走重建，而不是让事务视图长期卡在旧状态

## 这次计划覆盖什么

- 事务文档库的外部文件变更感知模型
- watcher、脏标记、quiet window、后台任务去重的接法
- targeted refresh 和全量刷新各自什么时候用
- 周期自动刷新的触发条件、频率和边界
- 临时文件过滤规则，避免把编辑器原子写中间产物当成真实文档变更
- 索引产物缺失时的自动重建策略
- Host 状态、日志和可观测性要求
- 必要的前端状态提示和验证口径
- 目录切换时的异步 directory hint refresh

## 这次明确不做什么

- 不回到递归 `chokidar` 盯整棵资料树的老路
- 不在 watcher 回调里直接做重扫描、重 SQLite 或重导出
- 不一上来做复杂分布式事件总线、跨设备实时同步协议
- 不重做整个索引引擎的数据结构
- 不把“自动刷新”扩成全文搜索、语义检索或推荐系统
- 不为极少数边界场景追求 100% 毫秒级实时一致

## 这次借鉴什么，先后顺序怎么排

这次不是只借鉴四条口号，而是借鉴一整套分层模型。

### 本轮必做

1. **watcher 只报信，不负责真相**
   - watcher 只产出脏信号
   - 真正结果仍以后续索引刷新和导出产物为准
2. **保留单根 watcher + targeted refresh + 周期补扫**
   - 单根 watcher 解决句柄问题
   - targeted refresh 解决“小改动别全量重跑”
   - 周期补扫解决漏事件和外部存储通知不稳定
3. **dirty 事件先进统一队列，不在回调里干重活**
   - 先合并、去重、延后
   - 后面再交给 `TaskManager` 和 helper 跑真正任务
4. **读链路只读快照，但目录切换可以异步发 hint**
   - 页面读取不允许重新变成“读一下就顺手重扫一下”
   - 但前端在切换当前目录时，可以额外异步提交一次当前目录增量刷新 hint，让后台自己补新
5. **索引产物缺失时自动重建**
   - `.ai-index`、导出快照、状态文件缺失时，系统要自己恢复

### 下轮应做

1. **把 refresh 从按文件触发升级成按目录归并批处理**
   - 避免十几个文件连改时打出十几次碎片刷新
2. **失败时保留最近一次可用结果**
   - 自动刷新失败时，前端仍能看到最近一次成功快照
3. **补齐结构化观测**
   - 要能看出 watcher 有没有活着、最近一次为什么没刷新、任务是失败还是被去重

### 后续再做

1. **目录版本戳 / etag-like 机制**
   - 用来进一步减少不必要下钻和重读
2. **更强的 pending state 恢复**
   - 例如 Host 重启后，短窗口内未处理脏信号如何恢复
3. **专用存储通知适配器**
   - 比如某些网络盘、SMB、云盘专用通知来源

一句人话：

**这轮先把“外部编辑也能自动变新”做稳，不要抢跑到复杂目录版本系统和存储专用适配器。**

## 为什么要单独起 spec016.2

因为这不是 `spec016.1` 里一句“顺手补个 watcher”能解决的小问题。

这里至少牵涉四条硬边界：

1. **句柄边界**：之前递归 watcher 已经打出过 `EMFILE: too many open files`
2. **任务边界**：watcher 只能打脏标记，不能重新长私活
3. **性能边界**：自动刷新不能把导出链路反复打成高内存峰值
4. **一致性边界**：用户主要从外部编辑，系统必须接受“事件可能漏、通知可能抖”，所以要有周期兜底和缺失重建

这几件事混着做，最后一定烂。

## 硬边界先写死

### 边界 1：watcher 只报信，不干重活

- watcher 回调里只允许：规范化路径、过滤临时文件、合并脏标记、调度后台任务
- 不允许 watcher 直接跑重扫、导出、重 SQLite、重建全文索引

### 边界 2：句柄数量必须跟“资料库数量”相关，不跟“目录树规模”线性增长

- 不允许再给每个子目录挂独立 watcher
- 优先采用每个资料库根目录一个监听入口的模型

### 边界 3：优先 targeted refresh，实在不行才补全量

- 已知具体文件或目录时，优先刷那一小块
- 只有目标路径丢失、事件过于模糊、索引产物缺失或周期兜底时，才走更重的刷新

### 边界 4：自动刷新要接受“最终一致”，不要假装永远绝对实时

- watcher 漏事件、原子写替换、网络盘通知不稳定，这些都是真问题
- 所以必须有低频周期刷新兜底
- 但周期兜底也不能粗暴到几分钟就全盘重建一次

### 边界 5：临时文件和原子写中间产物默认不纳入正式跟踪

- 常见编辑器会先写 `.tmp`、`~$`、`#xxx#`、`.swp`、`.crdownload` 一类中间文件
- 这些文件默认忽略，避免误触发一堆无意义刷新

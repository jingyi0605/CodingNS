# 中继密文验收记录

日期：2026-04-20

这份记录回答一个很具体的问题：`relay-edge` 能不能直接看到业务明文？

结论先写在前面：

1. **不能直接看到业务明文。**
2. `relay-edge` 当前能看到的是：
   - 会话标识
   - 绑定关系
   - 隧道域名
   - 帧字节数
   - WebSocket 上下游连接状态
3. 真正的 HTTP / WebSocket 业务包明文，只在客户端和 Host 两端解密。

## 验收环境

本次不是靠口头描述，而是基于仓库内现有自动化测试和代码路径做等价验收。

涉及组件：

1. `apps/codingns-proxy/apps/relay-edge`
2. `apps/user-app`
3. `apps/host`

本次使用的验证命令：

```bash
pnpm --filter @codingns-proxy/relay-edge test -- src/app.test.ts
pnpm --filter user-app exec vitest run src/network/relay-tunnel-client-session.test.ts
pnpm --filter host test -- tests/integration/relay-tunnel-runtime-adapter.test.ts
```

## 验证方法

### 1. 看中继实际转发了什么

`relay-edge` 的核心转发逻辑在：

- `apps/codingns-proxy/apps/relay-edge/src/session-registry.ts`

关键观察点：

1. 中继收到 `socket.on("message", payload, isBinary)` 后，直接把 `payload` 原样转给对端：
   - `target.send(payload, { binary: isBinary })`
2. 中继做的额外动作只有：
   - 读取 `payload` 字节数
   - 更新剩余额度
   - 上报 `usageId / upstreamBytes / downstreamBytes / observedAt`
3. 这条链路里没有解析 HTTP path、header、body，也没有解析 WebSocket 业务消息体。

这说明中继是“盲转发”，不是“看懂内容再转发”。

### 2. 看客户端送进中继的到底是不是密文

客户端侧验证在：

- `apps/user-app/src/network/relay-tunnel-client-session.test.ts`

关键观察点：

1. 客户端先发 `client_hello`
2. 握手完成后，业务包不再直接发 `http.request` / `ws.message` 明文 JSON
3. 客户端实际送到原始信道里的包类型是：
   - `encrypted_frame`
4. 测试里只有拿到 Host 侧会话密钥后，才可以把这个 `encrypted_frame` 解回真实业务包

这说明中继链路上看到的是密文帧，不是业务明文。

### 3. 看 Host 侧什么时候才能拿回明文

Host 侧验证在：

- `apps/host/tests/integration/relay-tunnel-runtime-adapter.test.ts`

关键观察点：

1. 下游发给 Host 的包先是：
   - `type: "encrypted_frame"`
2. Host 侧通过会话密钥解密后，才得到：
   - `http.request`
   - `ws.open`
   - `ws.message`
3. 解密成功后，本地 Host 才能继续把请求转发给本地 HTTP / WebSocket 服务

这说明明文恢复发生在 Host 端，而不是发生在中继端。

## 观察结果

综合三条证据，能得到下面这个更精确的结论：

1. 客户端和 Host 之间的真实业务内容，在进入中继前已经被包成 `encrypted_frame`。
2. `relay-edge` 只知道“这是一帧数据”和“这帧有多少字节”，不知道里面是 HTTP header、JSON body，还是终端输出。
3. Host 必须拿到握手生成的会话密钥后，才能把 `encrypted_frame` 解回业务包。

## 中继当前可见信息边界

不要把“中继看不到明文”说成“中继什么都不知道”。当前中继仍然能看到这些元数据：

1. `sessionId`
2. `bindingId`
3. `accountId`
4. `tunnelDomain`
5. 上下游是否连上
6. 每一帧的字节数
7. 流量是否耗尽

所以正确说法是：

**中继看不到业务明文，但看得到路由和计费所必需的元数据。**

## 本次验收没有假装覆盖的边界

下面这些内容，这份记录不冒充已经验证过：

1. 不等于公网真实抓包截图；本次是基于自动化测试和代码路径的等价记录。
2. 不等于客户端或 Host 自己不产生日志；这里只说明中继层不解析业务明文。
3. 不等于“元数据完全匿名”；当前会话和计费元数据本来就要暴露给中继。
4. 不等于未来所有新增包类型自动安全；后续若新增新的隧道包类型，仍要重新核对是否继续走 `encrypted_frame`。

## 验收结论

本次验收满足 `spec001.9.1` 对“中继不可见业务明文”的最低要求：

1. 已明确测试环境和验证方法。
2. 已明确中继层看到的是 `encrypted_frame + 字节数`，不是业务明文。
3. 已明确明文只在客户端和 Host 两端解密。
4. 已把可见元数据和未覆盖边界写清楚，没有夸大。

# 流量扣量断流与恢复记录

日期：2026-04-20

这份记录只回答三个问题：

1. 流量是不是会真的扣掉
2. 流量耗尽后是不是会真的断
3. 用户补到新流量后，是不是能真的恢复后续连接

## 当前结论

这轮已经拿到的结论：

1. `relay-edge` 会按上下行字节数正式扣量
2. 钱包耗尽后，会拒绝新会话预留，并中断当前会话
3. 用户兑换激活码后，后续新会话可以恢复
4. 运营人工补发订单 grant 后，后续新会话也可以恢复
5. Host 侧状态和 `user-app` 设置页已经能看到剩余流量、超额状态和最近错误原因

这轮没有假装完成的部分：

1. Paddle 真实沙箱支付恢复还没验完

## 证据 1：超额后会断流并拒绝新会话

验证文件：

- `apps/codingns-proxy/apps/relay-edge/src/app.test.ts`

这条链路已经覆盖：

1. 建立双端 WebSocket 会话
2. 发送消息并消耗掉最后一笔剩余额度
3. 当前上下游都收到 `QUOTA_EXHAUSTED`
4. 再次尝试 `reserve` 新会话时，返回：
   - `403`
   - `errorCode: QUOTA_EXHAUSTED`

这说明超额不是只改一个数字，而是真的会阻断后续接入。

## 证据 2：兑换激活码后可以恢复后续连接

同一个文件里新增了恢复测试：

- `relay-edge app > 流量耗尽后，兑换激活码会恢复后续会话预留`

覆盖顺序：

1. 先把默认 4 字节额度消耗完
2. 确认新的会话预留被 `QUOTA_EXHAUSTED` 拒绝
3. 通过控制面接口兑换一枚 `5g` 激活码
4. 再次发起新的会话预留
5. 新会话预留恢复成功，并拿到新的 `remainingBytes`

这说明恢复不是“钱包页面数字变了”，而是真能恢复后续连接建立。

## 证据 3：用户侧能看到超额状态和最近错误

验证文件：

- `apps/user-app/src/settings/RelayTunnelPanel.tsx`
- `apps/user-app/src/settings/RelayTunnelPanel.test.tsx`

这轮补上的显示规则：

1. 状态卡继续显示：
   - 当前状态
   - 剩余流量
2. 当 Host 状态里有 `lastError` 时，面板明确显示：
   - `最近错误：...`

当前用户侧最少能看到：

1. 余量
2. `流量耗尽` 状态
3. 最近一次错误原因

## 证据 4：人工补发后可以恢复后续连接

验证文件：

- `apps/codingns-proxy/apps/relay-edge/src/app.test.ts`

这轮新增了恢复测试：

- `relay-edge app > 流量耗尽后，人工补发订单 grant 会恢复后续会话预留`

覆盖顺序：

1. 先建立会话并把默认额度耗尽
2. 确认新的会话预留被 `QUOTA_EXHAUSTED` 拒绝
3. 在 `control-api` 创建一笔待处理订单
4. 通过内部补发入口按订单重放 grant
5. 再次发起新的会话预留
6. 新会话预留恢复成功，并拿到新的 `remainingBytes`

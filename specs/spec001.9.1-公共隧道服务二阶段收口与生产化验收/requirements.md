# 需求文档 - spec001.9.1 公共隧道服务二阶段收口与生产化验收

状态：Draft

## 简介

`spec001.9` 第一阶段已经把几条最关键的链路搭出来了：

1. Host 可以绑定公共隧道
2. 客户端 / H5 可以通过中继访问 Host
3. 客户端与 Host 之间已经有端到端加密主链路
4. 控制面、数据面、支付和流量账本已经有第一版骨架

但现在还存在一堆不能装看不见的问题：

- `console-web` 还是空目录
- `control-api` 还是文件仓储，不是正式服务数据真相
- 邮箱验证码还是内存发送器，不是真实邮件
- 三级域名还是演示规则，不是真正可运营的域名池
- Paddle 还没做真实沙箱验收，也没有异常对账和人工补发工具
- `relay-edge` 还是内存会话表，离生产化差得远
- 主仓库和子仓库的最终验收记录还没补齐

这次二阶段要解决的事情很明确：

1. 把云端站点从“骨架可跑”收口到“可部署、可运维、可付费”
2. 把支付、流量、域名、会话和邮件这些运营关键链路补成正式实现
3. 把第一阶段没做完的验收补齐，拿到真实上线前基线

## 术语表

- **二阶段收口**：不是新开大功能，而是把第一阶段已经铺出来的链路补到可上线
- **正式持久化存储**：用于线上服务的数据库，不再是 JSON 文件或进程内内存
- **域名池**：一组可分配、可保留、可释放的正式三级域名前缀和根域配置
- **邮件通道**：真实可发信的邮件服务接入，例如 SMTP 或第三方邮件服务商
- **支付对账**：核对订单状态、支付回调状态和流量钱包发放状态是否一致
- **人工补发工具**：给运营者在异常情况下补发流量或重放回调的正式工具
- **验收基线**：后续改动公共隧道链路时必须重新核对的最小验证集

## 范围说明

### In Scope

- `apps/codingns-proxy/apps/console-web` 的正式控制台站点实现
- `control-api` 正式数据库落地、迁移、基础索引和幂等约束
- 真实邮箱验证码发送、验证码注册、密码登录和密码找回
- 正式三级域名分配、冲突处理、释放和保留规则
- `relay-edge` 的共享状态、会话回收、幂等扣量和生产边界
- Paddle 沙箱联调、订单对账、异常回放和人工补发
- 主仓库设置页、公共隧道 profile 和三种接入方式并存回归
- 中继不可见业务明文的验收记录
- 部署、配置、出款和运维文档

### Out of Scope

- 团队套餐、企业组织、子账号和复杂权限模型
- 共享流量池、月结账单、发票和税务系统
- 多支付渠道并行支持
- 自定义用户自带域名
- 跨区域多活、全球调度和边缘智能路由

## 需求

### 需求 1：控制台站点必须真正落地

**用户故事：** 作为公共隧道用户，我希望能直接在官方站点完成注册、登录、绑定 Host、查看订单和购买流量，而不是只能通过 API 或主仓库设置页硬调接口。

#### 验收标准

1. WHEN 二阶段完成 THEN System SHALL 在 `apps/codingns-proxy/apps/console-web` 提供正式站点代码，而不是只保留占位 README
2. WHEN 用户访问控制台站点 THEN System SHALL 支持最小注册、登录、Host 绑定状态查看、流量钱包查看、套餐下单和订单查看
3. WHEN 用户完成 Host 绑定或购买流量 THEN System SHALL 在站点内看到最新状态，不得长期停留在假数据或占位文案

### 需求 2：控制面必须使用正式数据库，而不是文件仓储

**用户故事：** 作为维护者，我希望账号、绑定、订单、流量钱包和支付事件有正式数据真相，而不是把线上服务压在一个 JSON 文件上。

#### 验收标准

1. WHEN 控制面进入二阶段 THEN System SHALL 把账号、验证码、会话、绑定、钱包、订单和支付事件迁移到正式数据库
2. WHEN 服务重启、并发写入或异常恢复 THEN System SHALL 保持数据一致性，不依赖单进程内存状态
3. WHEN 支付回调或记账重复到达 THEN System SHALL 通过唯一键或幂等约束避免重复发量或重复扣量

### 需求 3：邮箱注册必须接真实邮件通道，并补密码找回

**用户故事：** 作为公共隧道用户，我希望邮箱验证码真的能收到，忘记密码时也能自助恢复，而不是让站点停留在演示模式。

#### 验收标准

1. WHEN 用户申请注册验证码 THEN System SHALL 通过真实邮件通道发送验证码
2. WHEN 用户完成注册 THEN System SHALL 支持后续通过邮箱和密码登录
3. WHEN 用户忘记密码 THEN System SHALL 支持申请重置验证码并完成密码重设
4. WHEN 邮件发送失败、过于频繁或验证码过期 THEN System SHALL 返回明确错误，不得假装发送成功

### 需求 4：三级域名必须从演示规则升级到正式域名分配模型

**用户故事：** 作为运营者，我希望每个 Host 拿到的三级域名都来自正式可控的域名池，而不是代码里写死 `codingns.example`。

#### 验收标准

1. WHEN 用户绑定 Host THEN System SHALL 从正式配置的根域或域名池中分配三级域名
2. WHEN 域名冲突、保留词命中或绑定释放 THEN System SHALL 按正式规则处理，而不是简单字符串拼接
3. WHEN 控制面返回绑定信息 THEN System SHALL 返回真实可访问的域名和入口地址

### 需求 5：relay-edge 必须补到生产化最低标准

**用户故事：** 作为维护者，我希望数据面不是“本地测试刚好能跑”，而是至少达到单区域正式服务的最低标准。

#### 验收标准

1. WHEN `relay-edge` 进入二阶段 THEN System SHALL 把会话预留、Host challenge、claim lease 和回收状态放到共享状态层，而不是只存在单进程内存里
2. WHEN relay 连接异常断开、Host 未领取、downstream 放弃或配额耗尽 THEN System SHALL 正式回收会话，避免悬挂状态一直堆积
3. WHEN 扣量请求重复、超时或控制面短暂失败 THEN System SHALL 具有幂等或补偿机制，不得把钱包扣乱
4. WHEN 当前实现仍不支持多节点 THEN System SHALL 在部署说明里明确写死这一约束，不得假装已经支持

### 需求 6：支付链路必须完成真实沙箱联调、对账和人工补发

**用户故事：** 作为运营者，我希望支付成功后流量一定到账，支付失败不加量，回调异常时也有办法补救。

#### 验收标准

1. WHEN 二阶段完成 THEN System SHALL 完成 Paddle 沙箱环境下的真实下单、跳转、回调和到账联调
2. WHEN webhook 重复、乱序或临时失败 THEN System SHALL 保持订单状态和流量钱包一致
3. WHEN 某笔订单已支付但自动发量失败 THEN System SHALL 提供人工补发或重放工具
4. WHEN 运营排查支付问题 THEN System SHALL 能查看订单、支付事件和发量记录之间的对应关系

### 需求 7：流量扣量、超额断流和恢复必须形成闭环

**用户故事：** 作为公共隧道用户，我希望流量限制是可预期的，买完套餐后能恢复，超额时也知道为什么被断开。

#### 验收标准

1. WHEN 会话持续传输数据 THEN System SHALL 正式记录上下行字节数并更新剩余额度
2. WHEN 钱包额度耗尽 THEN System SHALL 拒绝新连接，并按规则中断现有会话
3. WHEN 用户购买成功或运营补发流量 THEN System SHALL 允许后续连接恢复
4. WHEN 用户或 Host 查看状态 THEN System SHALL 能看到余量、超额状态和最近错误原因

### 需求 8：主仓库必须补齐公共隧道回归与验收

**用户故事：** 作为项目维护者，我希望新增公共隧道后，本地直连和 Tailscale 不被打断，设置页和运行时切换也有正式回归基线。

#### 验收标准

1. WHEN 二阶段完成 THEN System SHALL 补齐本地直连、Tailscale、公共隧道三种访问方式并存的回归验证
2. WHEN 设置页修改公共隧道 profile、保存配置、启用、停用、解绑 THEN System SHALL 具有正式测试覆盖
3. WHEN 公共隧道被启用 THEN System SHALL 继续保持现有 HTTP / WebSocket 业务语义不变

### 需求 9：必须拿到“中继看不到业务明文”的正式验收记录

**用户故事：** 作为架构维护者，我希望端到端加密不是停留在代码注释里，而是有验收记录证明中继只看到密文和字节数。

#### 验收标准

1. WHEN 二阶段验收 THEN System SHALL 通过抓包、日志或等价记录证明中继无法直接读取业务明文
2. WHEN 输出验收文档 THEN System SHALL 明确记录测试环境、验证方法、观察结果和边界说明
3. WHEN H5 入口和三级域名入口被说明 THEN System SHALL 继续明确可信主域与隧道入口的信任边界

### 需求 10：必须补齐部署、配置和出款文档

**用户故事：** 作为实际运营者，我希望知道服务怎么部署、环境变量怎么配、Paddle 收款后怎么出款到中国大陆银行卡，而不是继续靠聊天记录找答案。

#### 验收标准

1. WHEN 二阶段完成 THEN System SHALL 提供控制面、数据面和控制台站点的部署说明
2. WHEN 新环境接入 THEN System SHALL 提供最小 `.env` 样例或等价配置清单
3. WHEN 运营者查阅支付文档 THEN System SHALL 明确记录 Paddle 收款、Payoneer 出款和中国大陆银行卡提现路径

## 非功能需求

### 非功能需求 1：向后兼容

1. WHEN 用户仍只使用本地直连或 Tailscale THEN System SHALL 保持现有主流程不变
2. WHEN 公共隧道控制面暂不可用 THEN System SHALL 不得破坏 Host 本地服务启动和现有业务认证链路

### 非功能需求 2：可维护性

1. WHEN 后续继续做团队套餐或企业能力 THEN System SHALL 能在二阶段明确的数据真相和订单模型上扩展
2. WHEN 排查生产问题 THEN System SHALL 能区分邮件失败、支付失败、回调重复、扣量失败、域名冲突和隧道断线这几类问题

### 非功能需求 3：可观测性

1. WHEN 用户或运营查看订单和流量 THEN System SHALL 能看到关键状态，而不是只有一串内部错误
2. WHEN 服务出现异常 THEN System SHALL 有正式日志字段和追踪键，便于对账和补救

## 成功定义

- `codingns-proxy` 控制台站点真正可用，不再是占位目录
- 控制面和数据面不再依赖 JSON 文件和进程内内存作为唯一真相
- 邮箱注册、登录、找回密码和 Host 绑定形成正式用户闭环
- Paddle 沙箱已完成真实联调，订单、支付事件和流量钱包能对上
- 主仓库完成三种远程访问方式并存回归
- 有正式文档说明怎么部署、怎么验收、怎么收款和怎么出款

# spec001.9.1-公共隧道服务二阶段收口与生产化验收

## 当前定位

这是 `spec001.9` 下的新子 Spec。

它只解决一件事：

- 把 `spec001.9` 第一阶段已经跑通的“公共隧道主链路”继续收口成可上线、可验收、可运营的正式版本。

一句人话：
第一阶段已经证明“这条路能跑”，第二阶段要解决的是“这玩意能不能真的拿去卖、拿去部署、拿去长期维护”，而不是继续堆概念。

## 计划覆盖

- `codingns-proxy` 控制台站点真正落地，不再只是占位目录
- 控制面从文件仓储升级到正式持久化存储
- 邮箱验证码从内存发送器升级到真实邮件通道，并补密码找回闭环
- 三级域名分配从演示规则升级到正式可配置域名池
- `relay-edge` 的生产化收口：共享状态、会话回收、幂等扣量、单点边界明确
- Paddle 沙箱联调、订单对账、人工补发与异常处理
- 流量钱包、扣量、超额断流、恢复的闭环验收
- 主仓库 `user-app` / `host` 的公共隧道回归与验收基线
- 部署说明、环境变量样例、运营出款路径说明和验收记录

## 依赖关系

- 前置依赖：
  - `spec001-平台底座与工作区基础`
  - `spec001.9-公共隧道服务接入与端到端加密远程访问`
- 强相关依赖：
  - `spec001.2-后端任务调度与主线程压力治理`
  - `spec001.4-Tailscale接入与实例级远程访问`
  - `spec008-桌面端与H5交付增强`

## 本阶段明确不做

- 不重新发明新的隧道协议，继续沿用 `spec001.9` 已定下来的端到端加密边界
- 不在主仓库实现云端控制台和支付代码
- 不在第二阶段顺手扩到团队套餐、企业后台、共享流量池、多租户权限系统
- 不做“支持所有支付平台”的抽象层，支付继续收口在 Paddle
- 不为了多云、多区域这些远期问题把当前实现先抽象烂

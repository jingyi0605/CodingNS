# 需求文档 - spec013.2-助手内部API与代理执行编排

状态：Draft

## 简介

现在 Butler 已经有控制会话，也已经能看一部分聚合上下文，但还没有一套正式的“内部能力面”。

当前问题不是没有接口，而是接口长得太散：

- 查项目，要走 butler 路由
- 查会话，要走 sessions 路由
- 查终端，要走 terminals 路由
- 发消息、fork、取历史，也各走各的

这对前端页面还能勉强接受，但对“代码助手”本身不够。

真正的代码助手不应该自己直接写业务代码，也不应该靠 prompt 硬猜系统有哪些路由。它应该：

1. 先通过统一能力接口查清楚项目、会话、终端和当前状态
2. 需要推进开发时，只通过真实项目会话或受控终端代理执行
3. 能把这些能力统一暴露成 Host 内部 API、CLI 命令和 Skill 导航，给 Butler 以及后续不同 CLI provider 共用

如果这一层不补，最后一定继续烂成三种情况：

1. 助手靠提示词记接口，接口一变就傻
2. 不同 provider 各接一套私有工具，维护成本爆炸
3. 助手表面上说“我不会直接写代码”，底下其实还在偷偷落盘

## 可实现性结论

### 结论

这个能力 **值得做，而且必须尽快做**。

它不是锦上添花，而是把 Butler 从“能聊天的控制面”升级成“受控代码助手”的关键中间层。

### 已确认事实

1. `apps/host` 已经有项目、会话、终端、fork、运行态、butler 聚合等现成路由。
2. Butler 当前自动生成的 `BUTLER_API.md` 已经开始教模型按需查内部接口，但还只是文档级约束，不是正式能力面。
3. 当前 Butler 控制会话如果要推进开发，仍然缺少统一的“选项目 -> 选会话 -> 发消息 -> 取结果 -> 必要时 fork / 查终端”的动作协议。
4. 现有终端和会话链路已经具备真实执行能力，不需要重新发明运行时，只需要统一封装。

### 平台判断

- ✅ 值得做：这是 Butler 从“会说”到“会受控推进”的关键层
- ✅ 能落地：底层事实和执行能力大多已经存在
- ❌ 不能继续散着长：否则后面 CLI、MCP、Butler 各维护一套接口认知

## 术语表

- **Assistant Capability API（助手能力接口）**：宿主系统对助手暴露的统一内部能力面，不等于现有所有 REST 路由的简单透传
- **Capability Facade（能力门面）**：把散落的项目、会话、终端、搜索、fork 能力收束成稳定模型的中间层
- **Proxy Execution（代理执行）**：Butler 不自己改代码，只把任务发给真实项目会话或受控终端执行
- **Managed Session（受管会话）**：平台登记并允许助手续接、发消息、fork、追踪状态的真实开发会话
- **Managed Terminal（受管终端）**：平台登记并允许助手读取历史、发送输入、跟踪状态的真实终端
- **Capability Receipt（能力回执）**：一次能力调用的结构化结果，至少包含是否成功、核心结果、审计引用和后续可继续操作的对象 ID
- **Tool Surface（工具表面）**：同一能力在 Host API、CLI、内部 help、Skill 上的统一映射

## 范围说明

### In Scope

- 定义统一助手能力模型和第一阶段最小能力集
- 定义 Host 内部 API、CLI、内部 help、Skill 这几层统一映射
- 定义项目查询、会话查询、终端查询、会话发消息、fork、终端发命令这些核心能力
- 定义 Butler “禁止直接写代码、只能代理执行”的正式边界
- 定义能力调用的授权、审计和结果回执规则
- 定义第一阶段 Butler 如何发现能力、调用能力、回收结果

### Out of Scope

- 重做现有全部 REST 路由
- 第一阶段支持浏览器自动化所有细节
- 第一阶段支持任意第三方 CLI 供应商无约束接入
- 让 Butler 绕过项目会话直接编辑项目文件
- 定义最终的自然语言工具调用提示词细节

## 技术边界

### 边界 1：Butler 不能直接写项目代码

- Butler 控制会话可以看、可以分析、可以发起动作
- 但真正的代码修改必须落到真实项目会话或受控终端
- 如果某个能力会直接修改项目文件，这个能力必须显式标成高风险，并走授权闸门

### 边界 2：统一能力面不是现有路由目录的镜像

- 现有路由是服务端实现边界
- 新的能力面是给助手和工具链消费的语义边界
- 它应该按“助手想完成什么”分组，而不是按后端模块名分组

### 边界 3：CLI、内部 help 和 Skill 必须共用同一套能力语义

- 不能 CLI 一套参数，帮助文本和 Skill 又各说各话
- 它们可以有不同的包装方式
- 但动作语义、返回结构、错误码必须尽量对齐

### 边界 4：第一阶段只开放最小可用能力

- 先解决“查清楚”“续接会话”“发消息”“查终端”“向终端发命令”“fork 会话”
- 不要一上来就把所有后台对象都做成工具

### 边界 5：能力调用必须可审计、可回放

- 每次能力调用至少要知道谁调的、调了什么、目标对象是谁、结果如何
- 不能出现“助手说它查过 / 做过，但系统里没有记录”

## 需求

### 需求 1：系统必须定义统一的助手能力模型

**用户故事：** 作为维护者，我希望 Butler、CLI 和 Skill 用的是同一套能力语义，这样后续扩展不会变成多套平行实现。

#### 验收标准

1. WHEN 平台定义助手内部能力 THEN System SHALL 提供统一的能力枚举、输入结构、返回结构和错误码约定。
2. WHEN 同一能力同时暴露到 Host API、CLI、内部 help、Skill THEN System SHALL 复用同一份语义定义，而不是各自发挥。
3. WHEN 某个能力暂未实现 THEN System SHALL 明确返回“不支持”或“未开放”，而不是静默缺失。

### 需求 2：系统必须提供项目与会话查询能力

**用户故事：** 作为助手，我希望先查清楚当前有哪些项目、哪些会话、它们现在是什么状态，这样我回答和调度时才不是瞎编。

#### 验收标准

1. WHEN 助手请求列出托管项目 THEN System SHALL 返回项目基本信息、生命周期、风险等级、最近活动和关键摘要。
2. WHEN 助手请求列出某个项目的会话 THEN System SHALL 返回会话标题、provider、运行态、最近更新时间和可续接标识。
3. WHEN 助手请求读取某个会话详情 THEN System SHALL 返回运行态、最近消息时间、当前 provider 会话引用和必要的 fork/发送能力声明。

### 需求 3：系统必须提供终端查询与受控输入能力

**用户故事：** 作为助手，我希望能先看终端现在是不是活着、最近输出了什么，再决定要不要发命令。

#### 验收标准

1. WHEN 助手列出终端 THEN System SHALL 返回终端所属工作区、状态、cwd、shell、最近活跃时间和关联调试信息。
2. WHEN 助手读取终端历史 THEN System SHALL 返回可分页或窗口化的终端输出，而不是只给一个模糊摘要。
3. WHEN 助手向终端发送输入 THEN System SHALL 记录输入内容、目标终端、发送时间和结果状态。

### 需求 4：系统必须提供向指定项目会话发送消息并获取结果的能力

**用户故事：** 作为助手，我希望在不直接写代码的前提下，把任务发给真实开发会话，然后拿到 accepted 结果和后续状态。

#### 验收标准

1. WHEN 助手向指定会话发送消息 THEN System SHALL 调用真实项目会话的发送链路，而不是创建伪消息。
2. WHEN 消息被接受 THEN System SHALL 返回 accepted 时间、目标会话标识和可继续追踪的引用。
3. WHEN 会话当前仍在运行且不支持即时追加 THEN System SHALL 返回明确阻断原因或排队策略。

### 需求 5：系统必须支持从指定会话或消息点 fork 新会话

**用户故事：** 作为助手，我希望在保留现有上下文的前提下，从某条消息继续开新分支，而不是手工复制一坨历史。

#### 验收标准

1. WHEN 助手请求从会话 fork THEN System SHALL 支持会话级 fork。
2. WHEN 助手请求从消息点 fork THEN System SHALL 在 provider 支持时优先走原生 fork，不支持时按既有重建策略返回结果。
3. WHEN fork 成功 THEN System SHALL 返回新会话标识、fork 来源和使用的方法。

### 需求 6：系统必须把 Butler 的执行边界固化为“只读分析 + 代理执行”

**用户故事：** 作为产品设计者，我希望 Butler 永远先查事实、再通过项目会话推进，而不是自己直接落代码。

#### 验收标准

1. WHEN Butler 工作在默认模式 THEN System SHALL 禁止它直接调用会改项目文件的本地写入能力。
2. WHEN 用户要求推进开发 THEN System SHALL 优先引导 Butler 选择目标项目会话或受控终端执行。
3. WHEN 某个动作会突破这一边界 THEN System SHALL 明确要求授权，或者直接拒绝。

### 需求 7：系统必须把统一能力面暴露成 Host API、CLI、内部帮助和 Skill 几种入口

**用户故事：** 作为平台维护者，我希望后续不管是 Butler、自家 CLI，还是 Codex Skill，都走同一套能力核心，而不是把完整工具说明塞进每次会话。

#### 验收标准

1. WHEN 平台落地第一阶段能力 THEN System SHALL 至少定义 Host API、CLI、内部帮助、Skill 这几种入口的映射关系。
2. WHEN CLI 调用某个能力 THEN System SHALL 能对应到同名或同语义的能力门面。
3. WHEN Skill 指引代理使用某个命令 THEN System SHALL 要求代理优先通过 CLI help 和能力发现获取具体用法，而不是把完整命令文档长期塞进上下文。

### 需求 8：系统必须提供能力发现与能力声明

**用户故事：** 作为助手，我希望先知道当前环境下哪些能力可用、哪些目标对象可操作，而不是碰到报错才反应过来。

#### 验收标准

1. WHEN 助手请求能力发现 THEN System SHALL 返回当前启用的能力列表、版本、主要限制和授权模式。
2. WHEN 某个会话或终端不可操作 THEN System SHALL 在能力响应里明确说明原因。
3. WHEN 后续新增能力 THEN System SHALL 通过能力发现接口暴露，而不是靠文档暗示。

### 需求 9：系统必须为每次能力调用记录审计与结果回执

**用户故事：** 作为维护者，我希望知道 Butler 调了什么能力、命中了什么对象、结果是什么，出了问题能追。

#### 验收标准

1. WHEN 发起一次能力调用 THEN System SHALL 生成审计记录。
2. WHEN 调用完成 THEN System SHALL 返回结构化回执，至少包含成功/失败、结果摘要、目标对象引用和时间。
3. WHEN 调用失败 THEN System SHALL 返回明确错误码和失败原因。

### 需求 10：系统不能破坏现有路由和现有工作流

**用户故事：** 作为当前系统维护者，我希望新增能力门面之后，现有前端页面、现有 Host 路由和现有 provider 运行链仍然能按原方式工作。

#### 验收标准

1. WHEN 新能力门面接入 THEN System SHALL 复用现有会话、终端、butler 服务，而不是复制一套平行实现。
2. WHEN 旧页面继续调用原有 REST 路由 THEN System SHALL 保持行为不变。
3. WHEN 第一阶段能力门面失败 THEN System SHALL 将影响限制在助手和工具入口，不破坏普通会话链路。

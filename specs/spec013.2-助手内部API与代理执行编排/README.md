# spec013.2-助手内部API与代理执行编排

## 当前定位

`spec013.1` 已经把 Butler 控制会话、聚合上下文和聊天入口立起来了，但还缺一条真正能落地的执行链：

- 助手到底能查哪些内部事实
- 助手到底能操作哪些项目会话和终端
- 这些能力怎么统一暴露成稳定接口，而不是散在一堆路由里
- 怎么强制助手自己不直接写代码，只通过代理会话和受控终端推进工作

一句人话：

这一步要把“助手能说什么”和“助手能做什么”之间那层正式能力面补起来。

## 计划覆盖

- 统一内部能力模型：项目、会话、终端、消息、fork、验证、搜索
- 统一宿主接口契约：Host 内部 API、CLI 命令、MCP 工具三层映射
- 明确只读分析 / 代理执行 / 高风险阻断三种动作边界
- 给 Butler 控制会话补正式的能力发现、调用、结果回收和审计规则
- 收敛现有散落接口，定义第一阶段最小可交付能力集

## 依赖关系

- 前置依赖：`spec013`、`spec013.1`、`spec002`、`spec003.5`、`spec006`
- 直接影响：`apps/host`、`apps/user-app`、后续 `packages/codingns`
- 后续受益：Butler 真正通过 CLI / MCP 调项目会话和终端，多 provider CLI 统一接入

## 本阶段明确不做

- 不重新设计 Butler 聊天页面
- 不让 Butler 自己直接改项目代码
- 不把所有现有 REST 路由一次性重写掉
- 不在第一阶段开放任意 shell 全自动执行
- 不在第一阶段支持所有外部 CLI 提供商

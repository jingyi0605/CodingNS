# spec013 模块目录草案

状态：Draft

## 1. 目标

这份草案回答一个很实际的问题：

`spec013` 真开始写代码时，`apps/host/src` 目录到底该怎么落，不至于一开工就把模块切碎成一地玻璃渣。

先说结论：

**MVP 阶段不建议上来就做很深的分层目录。当前仓库明显偏向“按业务域 + 平铺 service/controller 文件”的风格，butler 也应该先沿用这个现实。**

## 2. 现有宿主端风格判断

当前可以看到的模式很稳定：

- 路由层：`apps/host/src/routes/*.ts`
- 业务模块：`apps/host/src/modules/<domain>/*.ts`
- 存储仓储：`apps/host/src/storage/repositories/*-repository.ts`

典型例子：

- `workspace/` 目录里就是 `workspace-controller.ts`、`workspace-service.ts`
- `sessions/` 目录里也是围绕一个域平铺多个 service/helper 文件
- 没有必要为了 butler 突然引入一套多层 DDD 树

所以目录方案必须服从这个现实，而不是反过来教育代码库。

## 3. 推荐目录

### 3.1 路由层

建议新增：

```text
apps/host/src/routes/
  butler.ts
```

职责：

- 注册 `/api/butler/...` 下的所有路由
- 只做路由映射，不塞业务逻辑

### 3.2 模块层

建议新增：

```text
apps/host/src/modules/
  butler/
    butler-controller.ts
    butler-project-service.ts
    butler-session-service.ts
    project-memory-service.ts
    patrol-plan-service.ts
    patrol-run-service.ts
    verification-run-service.ts
    approval-request-service.ts
    audit-event-service.ts
    provider-adapter-registry.ts
    instruction-adapter.ts
    patrol-scheduler.ts
    patrol-summary-builder.ts
    verification-dispatcher.ts
    butler-dto.ts
    butler-errors.ts
```

### 3.3 存储层

建议新增：

```text
apps/host/src/storage/repositories/
  butler-project-repository.ts
  butler-session-repository.ts
  session-checkpoint-repository.ts
  project-memory-repository.ts
  patrol-plan-repository.ts
  patrol-run-repository.ts
  verification-run-repository.ts

```

### 3.4 存储 schema

建议修改：

```text
apps/host/src/storage/sqlite/
  schema.sql
```

职责：

- 补 `spec013` 相关表
- 索引与外键在同一处维护

## 4. 为什么先平铺，而不是先分十个子目录

这是个典型的“别过度设计”问题。

如果一开始就拆成：

- `project/`
- `session/`
- `memory/`
- `patrol/`
- `verification/`
- `approval/`
- `audit/`
- `provider/`
- `instruction/`

你会很快得到两个结果：

1. 目录看起来很专业
2. 实际上每个目录只有 1 到 2 个文件，来回跳转烦得要死

这是坏味道，不是架构。

当前仓库的现实是“同域平铺，文件名把责任写清楚”。那我们就先按这个来，等 butler 模块真的长到撑爆一个目录，再二次重构。

## 5. 文件职责草案

### 5.1 `butler-controller.ts`

职责：

- 接收所有 `/api/butler/...` 请求
- 参数校验
- 调用各 service
- 组装 DTO

不该做：

- 直接写 SQL
- 直接调 provider helper
- 直接拼接复杂调度逻辑

### 5.2 `butler-project-service.ts`

职责：

- 创建项目
- 更新项目
- 读取项目详情和总览
- 协调项目级默认策略

依赖：

- `butler-project-repository`
- `patrol-run-repository`
- `verification-run-repository`
- `butler-session-repository`

### 5.3 `butler-session-service.ts`

职责：

- 纳管已有 session
- 启动受管会话
- 查询受管会话详情
- 写入会话 checkpoint

依赖：

- `butler-session-repository`
- `session-checkpoint-repository`
- 现有 session 相关 service
- `provider-adapter-registry`
- `instruction-adapter`

### 5.4 `project-memory-service.ts`

职责：

- 写入记忆
- 检索记忆
- 修正、归档、替换记忆
- 为会话启动提供记忆回灌数据

依赖：

- `project-memory-repository`

### 5.5 `patrol-plan-service.ts`

职责：

- 创建和修改巡视计划
- 计算下次执行时间
- 启停巡视计划

依赖：

- `patrol-plan-repository`

### 5.6 `patrol-run-service.ts`

职责：

- 触发巡视
- 记录巡视运行状态
- 汇总巡视结果

依赖：

- `patrol-run-repository`
- `butler-session-service`
- `project-memory-service`
- `patrol-summary-builder`

### 5.7 `verification-run-service.ts`

职责：

- 创建验证任务
- 记录验证结果
- 保存截图、日志、指标等引用

依赖：

- `verification-run-repository`
- `verification-dispatcher`

### 5.8 `approval-request-service.ts`

职责：

- 创建授权请求
- 处理批准/拒绝
- 提供待处理列表

依赖：

- `approval-request-repository`
- `audit-event-service`

### 5.9 `audit-event-service.ts`

职责：

- 统一记录关键审计事件
- 提供查询接口

依赖：

- `audit-event-repository`

### 5.10 `provider-adapter-registry.ts`

职责：

- 注册 `Codex`、`Claude Code` 适配器
- 暴露能力位查询
- 统一启动与续接入口

说明：

- 这是 butler 模块和现有 provider 模块之间的连接点
- 不建议把 provider 细节继续散落到每个 service 里

### 5.11 `instruction-adapter.ts`

职责：

- 把统一 `InstructionEnvelope` 映射成 provider 可接受输入
- 处理 `AGENTS.md` / `CLAUDE.md` / system prompt 注入差异
- 记录降级信息

### 5.12 `patrol-scheduler.ts`

职责：

- 定时扫描 `patrol_plans`
- 生成待执行巡视任务
- 避免同项目重复调度

说明：

- 这是后台调度入口
- 逻辑应尽量傻，复杂结论交给 `patrol-run-service`

### 5.13 `patrol-summary-builder.ts`

职责：

- 把原始会话信息、验证结果、记忆和风险汇总成稳定输出结构

说明：

- 把“总结生成”独立出来是值得的，因为这部分很快会变复杂
- 但只拆到文件，不必马上拆目录

### 5.14 `verification-dispatcher.ts`

职责：

- 按验证类型分发到不同执行器
- 初期至少覆盖：
  - 测试命令验证
  - 浏览器验证
  - 视觉截图验证
  - 指标快照验证

## 6. 后续扩展时的二次拆分条件

只有满足下面任一条件，才建议把 `modules/butler/` 继续拆子目录：

1. 单目录文件数持续超过 18 到 20 个
2. 某一类子能力已经形成独立变化节奏，比如验证模块暴涨
3. 测试目录已经自然按子域分组，代码目录跟不上

到那个时候，再按下面方向拆：

```text
apps/host/src/modules/butler/
  project/
  session/
  memory/
  patrol/
  verification/
  approval/
  audit/
```

但那是第二阶段的事，不是现在。

## 7. 初始化依赖关系建议

建议依赖方向：

```text
butler-controller
  -> butler-project-service
  -> butler-session-service
  -> project-memory-service
  -> patrol-plan-service
  -> patrol-run-service
  -> verification-run-service
  -> approval-request-service
  -> audit-event-service

butler-session-service
  -> provider-adapter-registry
  -> instruction-adapter

patrol-run-service
  -> butler-session-service
  -> project-memory-service
  -> verification-run-service

verification-run-service
  -> verification-dispatcher
```

规则：

- controller 不跨层直接碰 repository
- service 之间允许少量编排依赖，但别搞环
- repository 保持 dumb，不塞业务判断

## 8. 配套文件建议

除了主代码目录，建议同步准备这些测试或配套文件：

```text
apps/host/src/routes/butler.ts
apps/host/src/modules/butler/*.test.ts
apps/host/src/storage/repositories/*butler*.test.ts
```

如果当前仓库测试布局另有约定，再贴着现有约定走；但 butler 这种控制面模块，没有测试就是裸奔。

## 10. 核心判断

### 【核心判断】

✅ 值得做：butler 模块应该独立成域，但不应该为了“显得架构高级”一开始就切得稀碎。

### 【关键洞察】

- 数据结构：路由、模块、仓储三层已经是当前宿主端真实存在的组织方式
- 复杂度：MVP 先把 butler 目录平铺，后续再按增长点拆子目录
- 风险点：最大的风险不是文件太多，而是一开始人为分层过深，导致职责分散、来回跳转和循环依赖

### 【Linus式方案】

1. 新增一个独立 `butler` 域
2. 模块内部先平铺 service/controller 文件
3. repository 按实体一对一新增
4. 等复杂度真的长出来，再二次重构目录

# spec002.3-设置页会话清理工具与跨Provider级联删除

## 当前定位

这个 Spec 只解决一个真问题：

- 项目里的会话越积越多，扫描和索引压力越来越大
- 这些旧会话不仅存在于 CodingNS 自己的索引里，还散在 Codex、Claude Code、OpenCode 各自的磁盘和数据库里
- 现在缺一个正式工具，能让用户安全地批量看、批量备份、批量删除、按需恢复

结果就是：

- 性能问题会持续累积，而不是自己消失
- 用户想清理时，只能去不同 CLI 的目录和数据库里手工删，风险很高
- 如果只删 CodingNS 自己的记录，provider 侧残留还会回来污染扫描
- 如果只删 provider 侧原始记录，CodingNS 自己的索引和附件又会变成脏数据

这不是“顺手加个设置页按钮”的事，这是会话生命周期治理缺口。

## 这次要解决什么

这次不重写整套会话系统，也不把所有 provider 的存储强行改成统一格式。

这次只做下面几件事：

1. 在设置页新增一个正式的会话清理工具入口
2. 支持扫描 Codex、Claude Code、OpenCode 的会话，并按 provider、时间范围、多选结果做筛选
3. 支持把选中的会话打成压缩备份
4. 支持从备份包里浏览会话并选择性恢复
5. 支持删除时同步清理 CodingNS 本地索引、磁盘文件、以及 provider 侧数据库或原始记录
6. 把整个流程接进正式后台任务，保证可观测、可取消、可追踪

## 计划覆盖

- 设置页清理工具入口、列表、筛选、确认、备份和恢复交互
- Host 侧会话清理扫描、备份、恢复、删除任务
- Codex / Claude Code / OpenCode 三家 provider 的级联删除和恢复策略
- 备份包格式、清单文件、压缩读写和部分恢复
- 删除前预检、删除后索引修复、失败汇总和观测

## 依赖关系

- 前置依赖：`spec001.2`、`spec001.2.1`、`spec002`、`spec002.1`、`spec008.2`
- 后续依赖：Host 侧实现、设置页前端实现、集成验证、性能回归验证

## 本阶段明确不做

- 不在这个 Spec 里扩展 Gemini、Kimi、Legna 等其他 provider
- 不做自动定期清理策略
- 不做“按消息内容关键词”这类重搜索能力
- 不做跨机器增量同步备份
- 不承诺恢复后所有 provider 内部运行态都原样回放，只保证会话记录和 CodingNS 可见链路恢复

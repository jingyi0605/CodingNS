# spec001.9.4-公共隧道盲中继收口与可信接入端直连

## 当前定位

这是 `spec001.9` 下的新子 Spec。

它只解决一件事：
把现在“`relay-edge` 既做中继、又做公网 HTTP / WebSocket 业务桥接”的混合方案，收口成真正的盲中继方案。

这次要解决的真问题不是“把现在的链路继续补补丁”，而是把边界重新钉死：

- 中继节点到底能不能看到客户端和 Host 之间的业务明文
- H5 在必须支持的前提下，最短、最稳的接入链路应该是什么
- Host、桌面客户端、H5 客户端、Channel 端之间，哪些步骤可以砍掉
- 哪些握手和授权步骤必须保留，才能保证中间会话安全

一句人话：
这次不是做“公共隧道 3.0 花活”，而是把当前已经跑偏的公网业务代理链路砍掉，让 `relay-edge` 退回成真正的 dumb pipe。

## 计划覆盖

- `relay-edge` 去掉公网业务 HTTP / WebSocket 明文桥接
- `control-api` 提供可信接入端最小连接初始化入口
- Host 改成单条持久上游信道，而不是每个会话再去 claim / attach 一次
- H5 和桌面客户端共用同一套隧道接入 SDK
- `*.tunnelDomain` 收口成入口标识或跳转入口，不再承载业务代理
- 保留客户端与 Host 之间的端到端加密，不再让 Channel 端参与业务解密
- 梳理迁移路径，保证现有本地直连、Tailscale 和业务认证不被破坏

## 本阶段明确不做

- 不把 H5 改成浏览器不可用的 raw TCP 方案
- 不推翻现有 Host 本地 `/api/*` 和 `/ws` 业务语义
- 不在这一步重做支付、订单或管理员后台
- 不承诺这一步就把 `relay-edge` 做成跨多节点的全局分布式中继
- 不把“业务认证”和“隧道接入认证”再次混成一个 token 体系

## 这次改完以后应该变成什么样

目标链路只有这一条：

1. 可信 H5 从固定可信域名加载，桌面客户端从本地 bundle 启动
2. 客户端向 `control-api` 请求连接初始化信息
3. 客户端直接连 `relay-edge`，与 Host 完成端到端加密
4. `relay-edge` 只负责会话配对、密文字节转发和按字节计量
5. Host 解密后继续走本地现有业务接口

一句人话：
Channel 端只负责“让两头接上”和“记账”，不再负责“替你看 HTTP 请求再转发”。

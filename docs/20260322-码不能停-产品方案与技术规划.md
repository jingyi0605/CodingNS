# Coding Nerver Stop（码不能停）产品方案与技术规划

## 0. 文档目的

本文档用于为 `Coding Nerver Stop`（中文名：`码不能停`）规划一套可长期演进、可多端落地、可扩展多种 AI CLI 工具的新产品方案与技术架构。

本文档重点回答四个问题：

1. 这个产品到底要解决什么问题
2. 产品能力应该如何拆层，避免后期越改越乱
3. 技术架构如何同时支持桌面端、移动端、H5 和后续 CLI 扩展
4. 第一阶段应该怎么落地，避免一上来做成大而全的垃圾

---

## 1. 核心判断

### 【核心判断】

✅ 值得做，而且必须从第一天就按“产品级工作台”来设计，不能再做成“网页套终端”的半成品。

当前市场上类似项目大多停留在这几个层面：

- 把 CLI 会话塞进 Web 页面
- 提供一个能看的文件树
- 提供一个勉强能用的 Git 面板

这类方案能演示，不能长期工作。

这里需要额外强调一条已经明确的前端约束：

`码不能停` **不是网页版 CLI 控制台**，也不是传统后台管理页面。  
它必须是一套：

- 完整美观
- 对话式
- 响应式
- 移动优先但不牺牲桌面效率
- 面向编程工作流的对话工作台

前端视觉与交互风格可以参考 `happy` 这类项目，但**只参考样式与交互气质，不参考其业务结构和服务架构**。

`码不能停` 真正应该做的不是“远程聊天界面”，而是：

**一个围绕 AI CLI 会话驱动的远程开发工作台。**

它的核心不是终端，而是以下三件事：

- 会话同步是产品护城河
- 工作区管理是产品骨架
- 进程与启动器能力是产品从“能看”到“能干活”的分水岭

### 【关键洞察】

- 数据结构：一切都应该围绕 `Workspace`、`Session`、`Process`、`Terminal`、`GitRepository` 五类核心实体设计
- 复杂度：多端不是核心复杂度，真正的复杂度来自“CLI 会话同步 + 工作区状态一致性 + 进程生命周期管理”
- 风险点：如果从一开始不把会话层、工作区层、UI 层拆开，后面每加一个 CLI、每加一种客户端都会把系统拖成一团

### 【Linus式方案】

1. 第一步永远是简化数据结构，不要先画页面
2. 把“会话同步”和“工作区管理”拆成独立核心
3. 前端只是壳，不拥有业务真相
4. 所有客户端共享同一套领域模型和服务协议
5. 先把 Claude Code / Codex 做透，再开放 provider 扩展机制

## 2. 产品定位

## 2.1 产品定义

`码不能停` 不是“把 CLI 画到前端上”的产品，而是一套以 `CodingNS Host` 为核心、以 AI CLI 为执行引擎、以多端客户端为访问入口的开发工作台。

它的基本形态应该是：

- `CodingNS Host` 在工作区内统一接入 Claude Code、Codex 等 CLI
- Host 负责会话同步、能力探测、文件 / Git / 终端 / 进程状态管理
- 桌面端、移动端、H5 只是同一套后端能力的不同访问面，不是三套业务实现
- 用户在同一工作区内续接已有会话和上下文，而不是重新开一个“前端自己的聊天窗口”

## 2.2 目标用户

- 重度使用 Claude Code / Codex 的个人开发者
- 多设备切换办公的开发者
- 需要远程查看项目状态、修改文件、提交代码、查看运行日志的用户
- 后续可扩展到小团队协作，但第一阶段不建议先做团队系统

## 2.3 产品边界

### 第一阶段必须做

- 工作区管理
- Claude Code / Codex 会话同步
- 文件管理
- Git 管理
- 终端管理
- 进程管理
- Windows/macOS 桌面客户端
- Android/iOS 移动端
- H5 客户端

### 第一阶段不建议做

- 多人协同编辑
- 云端托管工作区编排
- 权限系统复杂化
- 企业级审计系统
- 插件市场

原因很简单：这些东西都不是第一阶段的生死线。真正的生死线是“单人工作流是否顺滑”。

## 2.4 前端形态约束

### 明确排除的形态

以下前端形态不符合产品目标：

- 传统后台式左侧菜单 + 右侧表格面板
- “终端嵌在中间，旁边堆按钮”的运维控制台
- 聊天区只是页面中一个模块，而不是主舞台
- 过于工程师后台风、缺少产品感和移动端亲和力的界面

### 明确要求的形态

`码不能停` 的主界面必须是“编程对话窗口优先”的工作台：

- 对话流是核心视觉中心
- 输入区是高频操作核心，不是底部一条普通文本框
- 文件、Git、进程、终端是围绕会话展开的上下文工具，不是主界面抢焦点的大面板
- 手机上要像高级原生对话应用，桌面端要像高密度创作工作台

### 样式参考来源说明

可参考 `happy` 的以下特点：

- 对话页面是第一入口
- 输入区是复合操作面板，而不是裸文本框
- 移动端和 Web 保持统一产品气质
- 响应式布局不是简单缩放，而是重新组织信息密度
- 整体更像“编程对话产品”，而不是“远程控制面板”

但要明确：

- 不参考 `happy` 的后端同步模式
- 不参考 `happy` 的业务边界
- 不绑定 `happy` 的组件结构
- 不复制 `happy` 的代码实现

## 3. 产品原则

## 3.1 核心原则

### 原则一：会话必须可续接，不重造上下文

用户已经在 CLI 中做了一半的工作，移动端和桌面端看到的必须是同一条会话，不是另一个“前端自己的聊天记录”。

### 原则二：工作区是一等公民

会话、终端、文件、Git、进程、启动配置都必须挂在 `Workspace` 下。

### 原则三：前端只负责表达，不负责伪造状态

会话状态、Git 状态、进程状态都必须由后端核心统一管理。  
不要让 Web、本地桌面、移动端各自维护一套真假难辨的状态缓存。

### 原则四：支持范围先窄后宽

初期只做：

- `Claude Code`
- `Codex`

后续 CLI 扩展必须通过 `session-sync-core` 的 provider 适配器实现，而不是把判断逻辑散落到页面和路由里。

### 原则五：先把“能持续开发”做好，再追求炫技

漂亮 UI 要做，但不能以牺牲结构为代价。  
产品不是 Dribbble 页面，是每天要打开十几个小时的工作界面。

## 4. 产品能力全景

## 4.1 一级模块

产品整体划分为 7 个一级模块：

1. 工作区管理
2. 会话同步
3. 文件管理
4. Git 管理
5. 终端管理
6. 进程管理
7. 多端客户端

## 4.2 模块说明

### 1. 工作区管理

负责：

- 工作区创建、导入、归档、收藏
- 本地目录与 Git 仓库识别
- 启动配置、环境变量、常用命令管理
- 工作区最近活动、最近会话、最近进程聚合

### 2. 会话同步

负责：

- 发现 CLI 会话
- 读取原生会话存储
- 归一化成统一消息模型
- 支持续接已有会话
- 支持新会话创建与状态推送

### 3. 文件管理

负责：

- 文件树浏览
- 文件读取、保存、创建、删除、上传
- 搜索、筛选、最近打开
- 文件预览与基础编辑

### 4. Git 管理

负责：

- 状态、diff、暂存、提交、分支、历史
- 远程同步
- 按规则生成提交信息
- 变更集合视图

### 5. 终端管理

负责：

- 多终端实例
- 终端会话复连
- 工作区绑定终端
- 命令模板执行

### 6. 进程管理

负责：

- 列出当前工作区相关进程
- 启动 / 停止 / 重启开发服务
- 前后端快捷启动
- 端口探测
- 启动日志查看
- 自动识别常见项目启动命令

### 7. 多端客户端

负责：

- H5 Web 客户端
- Tauri 桌面客户端（Windows/macOS）
- Tauri Mobile 客户端（Android/iOS）

## 5. 产品形态规划

## 5.1 客户端形态

### H5 客户端

适合：

- 任意浏览器访问
- 快速查看会话、日志、文件和 Git 状态
- 临时操作与轻量编辑

### Windows/macOS 原生客户端

适合：

- 主力开发入口
- 多窗口操作
- 更稳定的本地能力调用
- 更好的终端体验和文件交互体验

### Android/iOS 客户端

适合：

- 查看会话进展
- 回复 CLI 会话
- 处理 Git 提交和审查
- 查看日志和启停进程
- 紧急改动小文件

## 5.2 跨平台壳层建议

这里建议采用 `Tauri 2` 作为桌面端和移动端壳层。

原因：

- 同一套前端可以覆盖桌面、移动和 H5
- 桌面端支持 Windows/macOS，移动端支持 Android/iOS
- 相比 Electron 更轻，安装包和运行时成本更低
- 对“前端统一、后端服务独立”的架构更友好

注意：

- `Tauri` 只是客户端壳，不应该承载核心业务逻辑
- 核心业务逻辑仍然放在 Node.js 服务中
- H5 与桌面端尽量共享同一套 UI 代码和状态模型

## 6. 总体技术架构

## 6.1 三层核心架构

### 1. `session-sync-core`

职责：

- 发现不同 CLI 的原生会话
- 解析原生会话存储
- 抽象统一的会话、消息、状态事件
- 输出 provider 能力声明，告诉前端哪些能力能用、哪些不能用
- 提供会话历史拉取与实时同步
- 为后续新 CLI 扩展提供 provider 适配机制

### 2. `workspace-core`

职责：

- 管理工作区元数据
- 文件系统操作
- Git 操作
- 终端实例管理
- 进程管理
- 启动器与命令模板
- 环境变量与配置持久化

### 3. `ui-web`

职责：

- 全新设计系统
- 统一路由、布局、状态管理
- 多端响应式适配
- 与核心服务通过 HTTP / WebSocket 通信
- 基于 capability descriptor 做功能门控和降级提示
- 支持桌面壳、移动壳、浏览器三类运行环境

## 6.2 运行形态

系统建议采用下面的运行关系：

1. 本地或远程机器上运行 `CodingNS Host`
2. `CodingNS Host` 内部承载 `session-sync-core` 和 `workspace-core`
3. 客户端通过 `HTTP + WebSocket` 连接 Host
4. H5 / 桌面端 / 移动端共享 `ui-web`

这样做的好处：

- 所有客户端看到的是同一份工作区真相
- 移动端只是远程视图，不需要本地具备 CLI 环境
- 后续扩展更多 CLI 时，只改 provider 层，不用推翻前端

## 8. session-sync-core 设计

## 8.1 目标

`session-sync-core` 是整个产品的核心壁垒。

它必须解决三个问题：

1. 怎么发现不同 CLI 的会话
2. 怎么把不同 CLI 的原生结构转成统一结构
3. 怎么同时支持历史拉取和实时状态同步

## 8.2 模块拆分

建议拆成以下子模块：

- `provider-registry`
- `capability-registry`
- `provider-claude-code`
- `provider-codex`
- `session-discovery`
- `session-parser`
- `message-normalizer`
- `session-index`
- `realtime-bridge`

## 8.3 Provider 适配接口

每个 provider 必须实现统一接口：

- `detectWorkspaces()`
- `detectSessions(workspacePath)`
- `readSessionHistory(sessionId, options)`
- `subscribeSession(sessionId)`
- `resumeSession(sessionId, runtimeOptions)`
- `startSession(workspacePath, runtimeOptions)`
- `normalizeMessage(raw)`
- `getSessionMeta(sessionId)`
- `getProviderCapabilities()`
- `getSessionCapabilities(sessionId)`

这层必须保持简单。  
不要把 UI 逻辑、HTTP 逻辑、数据库逻辑塞进去。

## 8.4 能力标准化边界

必须统一的，是“基础能力协议”：

- 工作区发现
- 会话发现
- 历史消息读取
- 实时订阅
- 新建会话
- 续接会话
- 统一消息模型
- 统一错误码和事件协议

不要假装统一的，是“provider 专属增强能力”：

- `subagent`
- `interrupt`
- `structured tool call`
- `token usage`
- `checkpoint / snapshot`
- `attachments`
- `permission prompt / sandbox`

正确做法不是把所有 CLI 硬压成一样，而是让 provider 明确声明能力，再由前端按能力渲染。

建议定义统一的 `ProviderCapabilities`：

- `canStartSession`
- `canResumeSession`
- `supportsSubagents`
- `supportsInterrupt`
- `supportsStructuredToolCalls`
- `supportsTokenUsage`
- `supportsAttachments`
- `supportsPermissionPrompt`
- `supportsCheckpoint`
- `limitations`

## 8.5 前端如何处理能力差异

前端不应该把 provider 名字写死在页面逻辑里，也不应该假装所有 CLI 都一样。

正确做法：

- 页面只消费后端返回的 `ProviderCapabilities`
- 能力开关在统一的 UI capability registry 里收口，不把 `if provider === ...` 散在组件里
- 不支持的能力直接隐藏，或置灰并明确提示原因
- 能力名称优先沿用 provider 原生术语，避免前端自创概念误导用户
- 会影响行为的差异必须在会话头部或输入区直接可见，而不是点半天才发现不能用

## 8.6 初期支持范围

### 第一阶段

- `Claude Code`
- `Codex`

### 第二阶段

- `Gemini CLI`
- 其他兼容 CLI

## 8.7 会话数据流

建议数据流如下：

1. Provider 扫描 CLI 原生存储
2. 识别出工作区与会话映射
3. 把原始消息解析成统一消息结构
4. 写入 `Session Index`
5. 前端通过 REST 拉历史
6. 实时事件通过 WebSocket 推送

## 8.8 关键技术要求

- 必须支持分页读取历史消息
- 必须支持消息去重
- 必须支持断线重连
- 必须支持 provider 原生 session id 与系统 session id 映射
- 必须保留原始消息引用，便于排查兼容问题
- 必须允许 provider 单独演进，不影响其他 provider
- 必须向前端暴露 provider / session 两级 capability descriptor

## 8.9 风险点

### 风险一：不同 CLI 存储格式变化

解决方式：

- provider 单独版本化
- 原始消息保留
- 增加 provider 兼容性测试样本

### 风险二：实时状态和历史状态不一致

解决方式：

- 历史数据以 provider 原始存储为准
- 实时流只做增量补丁
- 客户端重连后自动做一次 server refresh

## 9. workspace-core 设计

## 9.1 目标

`workspace-core` 是整个系统的骨架。  
它负责把“单个目录”提升为“可管理的开发工作区”。

## 9.2 子模块拆分

建议拆成：

- `workspace-service`
- `file-service`
- `git-service`
- `terminal-service`
- `process-service`
- `launcher-service`
- `config-service`
- `search-service`

## 9.3 工作区管理

功能要求：

- 添加已有目录
- 从 Git 仓库克隆并创建工作区
- 收藏与分组
- 最近使用排序
- 工作区标签
- 绑定默认 CLI provider
- 绑定默认启动配置

## 9.4 文件管理

功能要求：

- 树形浏览
- 新建、删除、重命名、移动
- 上传下载
- 搜索
- 文件类型预览
- 最近打开
- 收藏文件

后续增强：

- 全文搜索
- 批量操作
- 文件比较
- 大文件懒加载

## 9.5 Git 管理

功能要求：

- 状态面板
- 暂存 / 取消暂存
- diff 查看
- commit / amend / revert local commit
- 分支创建 / 切换 / 删除
- fetch / pull / push / publish

关键增强：

- 提交信息规则模板
- 提交前检查流水线
- 基于工作区规范生成 commit message
- 提交说明预设

### 提交信息规则设计建议

不要只做“AI 生成一句 conventional commit”。  
要做成规则系统：

- 支持项目级提交模板
- 支持组织级提交规范
- 支持 AI 生成后再做规则校验
- 支持手工修改后二次校验

规则引擎至少要支持：

- `type(scope): subject`
- 是否强制中文 / 英文
- 最大长度
- 是否生成 body
- 是否包含 issue 编号

## 10. ui-web 设计

## 10.1 目标

`ui-web` 不是普通管理后台。  
它应该是一套面向“长时间开发使用”的工作台界面。

这里再加一条硬约束：

**主界面首先是编程对话产品，其次才是工作区工具集合。**

如果最后做出来的感觉像“带聊天框的后台页面”，那就是做错了。

## 10.2 设计方向

视觉上应避免传统后台味道：

- 不要做成纯白底蓝按钮的通用后台
- 不要做成满屏细边框和弱层次感
- 要突出工作区、会话、终端、进程的“运行感”
- 桌面端与移动端不是两套产品，而是一套架构下的两种视图

视觉与交互方向建议补充如下：

- 对话区必须具备产品感，不是 Markdown 文本堆砌区
- 输入区必须具备“复合控制面板”特征，允许承载模型、权限、Git 状态、发送、语音、快捷入口等操作
- 消息气质上应偏“高质量移动端对话产品”，而不是论坛帖子列表
- 桌面端需要在保留对话主舞台的前提下，引入更强的多栏效率布局
- 移动端要优先保证拇指操作路径、输入舒适度、会话沉浸感

### 样式参考原则

前端样式可重点参考 `happy` 所体现出的这些设计特征：

- 原生感很强的消息布局
- 浮动感和卡片感兼具的输入区
- 对话主视图优先
- 会话、工具、上下文信息以轻量方式嵌入，而不是抢占主体
- 从手机到 Web 的统一设计语言

但本项目应在此基础上继续增强：

- 更强的桌面工作台能力
- 更完整的工作区上下文
- 更成熟的文件 / Git / 进程联动

## 10.3 信息架构建议

### 桌面端

推荐采用三栏或四区布局：

- 左侧：工作区 / 会话导航
- 中间：主对话舞台
- 右侧：上下文侧栏（文件、Git、进程、详情）
- 底部可选：终端 / 日志抽屉

注意：

- 中间区域必须始终以对话流为核心
- 文件、Git、进程不应让主界面退化成 IDE 仿制品
- 这是“对话驱动工作台”，不是“网页 IDE”

### 移动端

推荐采用堆栈式结构：

- 首页：工作区总览
- 工作区页：会话、文件、Git、进程 tab
- 会话页：主对话视图
- 终端和日志采用全屏子页面

移动端对话页必须满足：

- 顶部信息简洁
- 中部消息沉浸
- 底部输入区可承载复合操作
- 侧功能通过 sheet、tab、二级页面呈现
- 不让文件树和复杂面板破坏消息体验

## 10.4 一级导航建议

- 工作区
- 会话
- 文件
- Git
- 终端
- 进程
- 设置

## 10.5 状态管理建议

建议前端按领域拆 store：

- `workspace-store`
- `session-store`
- `git-store`
- `file-store`

## 12. 数据存储规划

## 12.1 数据分层

### 原始数据

来源于各 CLI 原生存储：

- Claude Code 原始会话
- Codex 原始会话

### 系统索引数据

由 `CodingNS Host` 维护：

- 工作区元数据
- 会话索引
- 自定义标题
- 收藏与最近记录
- 启动配置
- Git 配置

### 运行时数据

- 活跃终端实例
- 运行中的进程
- WebSocket 连接
- 日志缓冲

## 12.2 存储建议

### SQLite

第一阶段可以用，但必须带约束，不是无脑塞进去就完了。

用于：

- 工作区表
- 会话索引表
- 自定义命名
- 启动配置
- 最近记录
- 用户偏好
- provider 能力缓存与映射索引

使用前提：

- 只存元数据、索引和配置，不把原始会话全文和长日志持续灌进 SQLite
- 同一份数据库默认只由一个 `CodingNS Host` 进程负责写入
- 开启 `WAL` 模式和合理的 `busy_timeout`
- 所有写操作保持短事务，并通过写队列串行化提交
- 数据库文件只放本地磁盘，不放网络共享盘

### 文件系统

用于：

- 日志缓存文件
- 大消息快照
- 导出文件
- 上传临时文件

## 12.3 SQLite 并发边界

多工作区、多会话本身不是问题。真正的问题是“有多少写者”和“写事务有多长”。

在下面条件下，SQLite 足够：

- 单用户
- 单 `CodingNS Host` 进程
- 高频的是读操作；写操作主要是索引更新、收藏、配置变更、状态快照
- 大消息正文、终端滚动输出、进程长日志落文件系统

在下面条件下，该准备迁移 PostgreSQL：

- 多个 Host 进程同时写同一份库
- 远程多用户并发操作同一实例
- 把实时消息流、终端输出、长日志直接当数据库主写入路径
- 需要复杂查询、统计和跨工作区共享

结论：
SQLite 不会天然“写死锁”，但设计垃圾时会出现 `database is locked`。解决办法不是嘴硬，而是从一开始把写路径收窄、事务缩短、日志分层。

- Provider 是否支持 subagent

- 只能根据 capability descriptor 决定显示什么操作，不能在业务组件里到处散落 provider 名字判断

## 18. 关键技术决策

## 18.1 服务端核心直接用 TypeScript，而不是先写 JavaScript 再迁移

原因：

- `session-sync-core`、`workspace-core`、`ui-web` 之间有大量共享协议，类型漂移的代价很高
- provider 能力声明、事件协议、消息结构都需要稳定 contract，靠 `JSDoc` 顶不住长期演进
- 这是长期产品，不是一次性脚本；从第二个 provider 开始，TypeScript 的约束就已经回本
- Node.js 22 + `tsx` + `tsc` 的工具链已经足够成熟，这不是过度设计

保留的例外：

- 探测 CLI 原始存储格式的临时脚本可以用 JavaScript
- 一次性迁移脚本、诊断脚本可以用 JavaScript

结论：
核心 Host、共享协议、前端应用默认使用 TypeScript；JavaScript 只留给探针脚本和临时工具。

## 18.2 选择 Tauri 2，而不是 Electron 作为默认方案

原因：

- 桌面与移动复用价值更高
- 更符合本项目“轻客户端 + 强 Host”的结构
- 后期 H5 也更容易共享 UI 层

## 18.3 第一阶段仍选 SQLite，但前提是把写路径设计对

原因：

- 当前是单用户、单 Host、单机优先场景，SQLite 足够扛住工作区索引、会话索引、配置数据
- 它部署简单，Host 可以零依赖启动，这对桌面端和远程轻部署都重要
- 真正高频、体积大的东西本来就不该塞进关系库，而应该放文件系统或 provider 原始存储

硬约束：

- Host 统一写入，启用 `WAL + busy_timeout + 短事务 + 写队列`
- 大消息正文、终端输出、长日志不直接打进 SQLite
- 一旦进入多用户或多 Host 并发写，再迁移 PostgreSQL，不要死扛

结论：
SQLite 不是问题，糟糕的写入模型才是问题。

## 18.4 进程管理必须做成独立服务，不挂靠终端

终端是交互界面，进程是运行实体。  
这两个如果混在一起，后面一定是一堆特殊情况。

## 19. 产品风险与应对

- 先定领域模型
- 再定 API

- 一开始就引入 `LauncherProfile`

## 20. 结论

`码不能停` 不应该做成“另一个 Web 终端面板”，而应该做成：

**以工作区为核心，以 CLI 会话同步为护城河，以进程管理和多端访问为差异化能力的 AI 开发工作台。**

从架构上，正确答案不是把所有逻辑塞进一个服务文件，而是明确拆成：

- `session-sync-core`
- `workspace-core`
- `ui-web`

从产品上，第一阶段不该追求面面俱到，而该追求：

- Claude Code / Codex 真正可续接
- 工作区、文件、Git、终端、进程打通
- 桌面端优先，H5 可用，移动端先满足查看和轻操作

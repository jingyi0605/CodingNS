# CodingNS NPM 包打包、发布与本地离线安装说明

本文档只说明 `@jingyi0605/codingns` 这个独立 NPM 包的完整流程，包含：

如果你的目标是正式发布，不要只单独跑本地 pack。发布前默认统一入口已经改成：

```bash
bash scripts/verify-release-ci.sh
```

这个脚本会先执行本地 npm 打包测试，再触发远端桌面端验包和 Windows 安装回放。

1. 版本号如何修改
2. 如何本地打包
3. 如何发布到 npm
4. 如何做本地离线安装测试
5. 常见报错如何排查

## 一、这套流程里的关键文件

- 根目录版本源：`VERSION`
- 版本同步脚本：`scripts/sync-version.mjs`
- 根目录快捷命令：`pnpm version:sync`
- NPM 包目录：`packages/codingns`
- 独立包构建脚本：`packages/codingns/scripts/build.mjs`
- 安装后 Codex 依赖修复脚本：`packages/codingns/scripts/postinstall.mjs`
- 发布脚本：`scripts/publish-npm-package.sh`

## 二、版本号修改流程

现在项目的产品版本以根目录 `VERSION` 为准。

例如当前版本：

```txt
0.1.1
```

如果要升级版本，按下面顺序做：

```bash
# 1. 修改根目录 VERSION
echo 0.1.2 > VERSION

# 2. 同步各处版本号
pnpm version:sync
```

执行后会自动同步这些真正需要统一的版本源：

- `packages/codingns/package.json`
- `apps/desktop/package.json`
- `apps/host/package.json`
- `apps/desktop/src-tauri/tauri.conf.json`
- `apps/user-app/src-tauri/tauri.conf.json`
- `apps/desktop/src-tauri/Cargo.toml`
- `apps/user-app/src-tauri/Cargo.toml`
- `scripts/user-app-ios-project.yml`

注意：

- `apps/user-app/src-tauri/Cargo.lock`
- `apps/user-app/src-tauri/gen/apple/...`

这类文件通常会在后续构建时自动更新，不是手工主版本源。

## 三、本地打包流程

### 1. 环境要求

- Node.js `>= 22`
- npm `>= 10`
- pnpm `>= 9`

先安装依赖：

```bash
pnpm install
```

### 2. 先构建独立包

在仓库根目录执行：

```bash
pnpm build:standalone
```

这条命令实际会构建：

- `packages/session-sync-core`
- `apps/user-app`
- `apps/host`
- `packages/codingns`

### 3. 生成 tgz 包

进入包目录，或者直接在根目录调用都可以。最直接的是：

```bash
cd packages/codingns
npm pack
```

生成结果类似：

```bash
jingyi0605-codingns-0.1.1.tgz
```

如果希望把产物放到固定目录，便于发给其它机器测试，推荐这样做：

```bash
mkdir -p /private/tmp/codingns-export-011
npm pack --pack-destination /private/tmp/codingns-export-011
```

如果要直接走交互脚本，现在有 4 个选项：

```bash
bash scripts/publish-npm-package.sh
```

- 选项 `1`：基于当前工作区代码做本地 `npm pack`
- 选项 `2`：基于当前工作区代码发布到 npm
- 选项 `3`：从最近 `5` 次 Git 提交里选一个版本，本地打包
- 选项 `4`：从最近 `5` 次 Git 提交里选一个版本，发布到 npm

其中选项 `3` 和 `4` 会用临时 `git worktree` 检出目标提交，不会直接改你当前工作区。  
如果是选项 `3`，生成的 tgz 会放回当前仓库的 `packages/codingns` 目录，并在文件名后追加提交短 SHA，避免覆盖当前版本包。

### 4. 只做打包预检查

如果只想确认发布清单，不想真的生成正式包：

```bash
pnpm publish:npm:dry-run
```

或者：

```bash
cd packages/codingns
npm pack --dry-run
```

## 四、正式发布到 npm

### 1. 发布前确认

先确认版本号已经同步完毕：

```bash
cat VERSION
pnpm version:sync
```

再做一次预演：

```bash
pnpm publish:npm:dry-run
```

如果这次是正式发版，默认还要先跑统一发布前校验：

```bash
bash scripts/verify-release-ci.sh
```

### 2. 正式发布命令

在仓库根目录执行：

```bash
pnpm publish:npm
```

实际调用的是：

```bash
bash scripts/publish-npm-package.sh
```

这个脚本现在支持两类来源：

- 当前工作区代码
- 最近 `5` 次 Git 提交里选中的代码版本

无论选哪种来源，发布时都会做三件事：

1. 构建独立服务包
2. 用 `npm pack --dry-run` 校验打包清单
3. 在 `packages/codingns` 下执行 `npm publish`

### 3. 指定 dist-tag 或 provenance

如果需要：

```bash
bash scripts/publish-npm-package.sh --tag latest
bash scripts/publish-npm-package.sh --tag beta
bash scripts/publish-npm-package.sh --provenance
```

### 3.1 发布前后怎么判断 beta 版是否真的成功

不要再只盯着：

```bash
npm view "包名@版本号" version
```

这条命令在预发布版本场景里很容易把人带沟里。更稳的检查方式是：

```bash
PACKAGE_NAME=$(node -p "require('./packages/codingns/package.json').name")
PACKAGE_VERSION=$(node -p "require('./packages/codingns/package.json').version")
PACKAGE_TAG=$(node -e "const version=require('./packages/codingns/package.json').version; process.stdout.write(version.includes('-') ? 'beta' : 'latest')")

npm view "$PACKAGE_NAME" versions --json --registry https://registry.npmjs.org/
npm view "$PACKAGE_NAME" dist-tags --json --registry https://registry.npmjs.org/
```

判断标准只有两条：

1. `versions` 列表里已经出现这次版本号。
2. 这次用到的 dist-tag（beta 或 latest）已经指向这个版本。

脚本现在已经按这套规则做发布前检查和发布后校验，beta 版本不会再被误报成失败。

### 4. 发布权限注意事项

如果发布时报这个错误：

```txt
403 Forbidden - Two-factor authentication or granular access token with bypass 2fa enabled is required to publish packages.
```

说明当前 CLI 发布凭证不够。

这里要分清楚：

- 只有网页通行密钥，不代表 CLI `npm publish` 一定能直接通过
- 对命令行发布，最稳的是使用启用了 `bypass 2FA` 的 npm granular access token

也就是说：

- 本地手工登录网页不等于命令行已经具备发布权限
- 如果是 GitHub Actions 或无头环境，必须用 token

## 五、本地在线安装测试

### 1. 从 npm 官方源安装

```bash
npm install -g @jingyi0605/codingns
```

启动：

```bash
codingns start --port 3002
```

### 2. 从本地 tgz 安装

```bash
npm install -g ./jingyi0605-codingns-0.1.1.tgz
```

Windows 下建议写成：

```bash
npm install -g .\jingyi0605-codingns-0.1.1.tgz
```

如果路径里有空格，直接把完整路径包起来：

```bash
npm install -g "C:\Code\jingyi0605-codingns-0.1.1.tgz"
```

### 3. 安装时查看详细日志

为了确认安装阶段是否拉取并修复 Codex 运行时依赖，推荐带上：

```bash
npm install -g ./jingyi0605-codingns-0.1.1.tgz --foreground-scripts --loglevel notice
```

如果要看更详细的内部过程：

```bash
npm install -g ./jingyi0605-codingns-0.1.1.tgz --foreground-scripts --loglevel verbose
```

安装时看到下面这些日志，说明链路正常：

```txt

[codingns] 正在修复 Codex SDK 与当前平台二进制，请稍候...
[codingns] Codex CLI 已就绪：codex-cli 0.116.0
[codingns] Codex 运行时依赖修复完成
```

## 六、本地离线安装测试

这里说的“离线安装”，不是完全零缓存的新机器纯离线安装。

当前实现的真实含义是：

- 安装来源是本地 `tgz`
- 安装时不访问外网
- 但本机 npm 缓存里必须已经有需要的依赖包

换句话说：

- 如果之前完全没有拉过 `@openai/codex-sdk`、`@openai/codex`、原生模块预编译包
- 又强行 `--offline`
- 那就不可能成功

### 1. 推荐的离线测试步骤

先准备本地包：

```bash
mkdir -p /private/tmp/codingns-export-011
cd packages/codingns
npm pack --pack-destination /private/tmp/codingns-export-011
```

卸载旧版本：

```bash
npm uninstall -g @jingyi0605/codingns
```

校验并整理 npm 缓存：

```bash
npm cache verify
```

离线安装：

```bash
npm install -g /private/tmp/codingns-export-011/jingyi0605-codingns-0.1.1.tgz --offline --foreground-scripts --loglevel notice
```

### 2. 当前离线安装的真实行为

安装时 `postinstall` 会做两件事：

1. 先检查 `@openai/codex-sdk` 和 Codex CLI 是否已经就绪
2. 如果没就绪，就在当前包目录下执行一次本地修复安装

也就是说，离线安装能不能成功，取决于两点：

1. 本地 npm cache 是否已有 Codex 相关依赖
2. 本机是否已有对应平台的原生预编译缓存，或者具备本地编译能力

### 3. 已验证通过的离线场景

本仓库当前已经验证过：

- macOS 本机：卸载旧包后，用本地 `0.1.1` tgz 离线安装成功
- Windows 本机：在线 tgz 安装后 Codex 运行时可自动修复

### 4. 安装完成后的检查命令

```bash
npm ls -g @jingyi0605/codingns @openai/codex-sdk @openai/codex
codingns --help
codingns start --port 3009
```

如果 `npm ls -g` 能看到：

- `@jingyi0605/codingns`
- `@openai/codex-sdk`
- `@openai/codex`

并且 `codingns --help` 正常输出，说明安装已经落稳。

## 七、推荐的完整实战流程

如果你要发一个新版本，建议按下面顺序走：

### 场景一：准备发布新版本

```bash
# 1. 修改版本
echo 0.1.2 > VERSION

# 2. 同步版本源
pnpm version:sync

# 3. 构建独立包
pnpm build:standalone

# 4. 本地预演
pnpm publish:npm:dry-run

# 5. 导出本地 tgz
mkdir -p /private/tmp/codingns-export-012
cd packages/codingns
npm pack --pack-destination /private/tmp/codingns-export-012

# 6. 本机安装验证
npm uninstall -g @jingyi0605/codingns
npm install -g /private/tmp/codingns-export-012/jingyi0605-codingns-0.1.2.tgz --foreground-scripts --loglevel notice

# 7. 正式发布
cd /Users/jackson/Code/CodingNS
pnpm publish:npm
```

### 场景二：只做跨平台安装测试，不立即发布

```bash
# 1. 构建
pnpm build:standalone

# 2. 导出 tgz
mkdir -p /private/tmp/codingns-export-test
cd packages/codingns
npm pack --pack-destination /private/tmp/codingns-export-test

# 3. 把 tgz 发到目标机器

# 4. 目标机器安装
npm uninstall -g @jingyi0605/codingns
npm install -g ./jingyi0605-codingns-0.1.1.tgz --foreground-scripts --loglevel notice
```

## 八、常见问题

### 1. `npm install -g .\jingyi0605-codingns-0.1.1.tgz` 报文件不存在

通常是路径写错了。

例如这条：

```bash
npm install -g .\jingyi0605-codingns-0.1.1.tgz
```

在某些 shell 里会被解释错，建议直接：

```bash
npm install -g ./jingyi0605-codingns-0.1.1.tgz
```

或者使用完整绝对路径。

### 2. 安装成功了，但 Codex 无法对话

先看安装日志里有没有这些内容：

```txt
[codingns] 正在校验 Codex 运行时依赖...
[codingns] 正在修复 Codex SDK 与当前平台二进制，请稍候...
[codingns] Codex CLI 已就绪：codex-cli 0.116.0
```

如果没有，重新安装时加上：

```bash
--foreground-scripts --loglevel notice
```

再检查：

```bash
npm ls -g @jingyi0605/codingns @openai/codex-sdk @openai/codex
```

### 3. 离线安装失败

先问自己一个最基本的问题：本机缓存里到底有没有依赖。

如果没有缓存，`--offline` 失败是正常行为，不是包坏了。

解决办法只有两个：

1. 先联网安装一次，让 npm cache 预热
2. 不用 `--offline`，直接让安装阶段联网拉取依赖

### 4. `npm publish` 报 403

优先检查：

1. 当前 npm 账号是不是包所属 owner
2. 当前凭证是不是支持 CLI 发布
3. 是否需要带 `bypass 2FA` 的 granular access token

## 九、当前版本的补充说明

从 `0.1.1` 开始，这个包的 Codex 安装链路已经调整为：

- 不再把所有平台二进制提前塞进 tgz
- 安装时根据当前平台检查并修复 Codex 运行时依赖
- 支持本地 tgz 安装
- 支持在已有缓存前提下做离线安装验证

这套方案比 fat 包更实用，原因很简单：

- 包体更小
- 安装时只拉当前平台所需内容
- 更适合真实用户场景
- 也更适合本地先测、确认没问题再发 npm

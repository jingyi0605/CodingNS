# Android 应用打包说明

## 这套流程现在稳不稳定

### 【核心判断】

✅ 值得用：当前仓库里用于打 Android 包的**稳定入口**已经明确，就是项目根目录下的 `scripts/build-android.sh`。

但要把话说清楚：

- 稳定的是“**按脚本走**”这条路
- 不稳定的是“**手工直接敲 `tauri android build`**”这条路

原因很直接。前者会统一处理 `JAVA_HOME`、Android SDK / NDK、签名密钥、`key.properties` 和产物输出；后者很容易因为环境变量或签名配置缺失直接失败。

### 【关键洞察】

- 数据结构：Android release 打包依赖四个核心输入，分别是 `JDK`、`Android SDK/NDK`、`Rust Android target`、`release keystore`
- 复杂度：真正该记住的命令只有一条，不应该每次都手工拼 `tauri android build`
- 风险点：最大的破坏性风险不是代码本身，而是误用 `debug` 包、`unsigned` 包，或者绕开脚本直接打 release

## 以后统一怎么打

```bash
bash scripts/build-android.sh release
```

如果只是打调试包：

## GitHub Actions 现在会做什么

Android 这条线现在不是只能靠本地手工打包了。

当你推送 `v*` tag 时，GitHub Actions 会额外做这几件事：

1. 自动构建 `app-universal-release.apk`
2. 自动计算 APK 的 `sha256`
3. 自动生成 `android-apk.json`
4. 自动把 APK 和清单上传到 GitHub Release

稳定下载地址统一走：

- `https://github.com/jingyi0605/CodingNS/releases/latest/download/app-universal-release.apk`
- `https://github.com/jingyi0605/CodingNS/releases/latest/download/android-apk.json`

这意味着 Android 客户端更新不再依赖“某台机器手工拷文件到发布目录”，而是直接吃 Release 资产。

## 这次到底修了什么

### 【核心判断】

✅ 已经收口：`bash scripts/build-android.sh release` 现在不仅是“推荐命令”，也是这次验证通过的**可复用稳定入口**。

这次真正的坑，不在 `tauri android build` 本身，而在 Android Gradle 工程里的 `buildSrc`。

原来 `buildSrc` 明明只有两段很小的构建逻辑，却用了 `kotlin-dsl` 插件。结果就是：

- Gradle 一启动就要去 `plugins.gradle.org`
- 一旦本机 Java / Gradle 的 TLS 链路不稳定，就会在插件解析阶段直接死掉
- 表面看像“网络偶发失败”，本质上是构建链多了一条不必要的远程依赖

这次已经把这条坏链路砍掉了：

- `buildSrc` 从 `kotlin-dsl` 改成了 `java-gradle-plugin`
- 原本那两段 Kotlin 构建逻辑改成了 Java 版本
- 现在 `buildSrc` 不再因为一个小插件先去远程仓库绕一圈

对应文件：

- [apps/user-app/src-tauri/gen/android/buildSrc/build.gradle.kts](/Users/jackson/Code/CodingNS/apps/user-app/src-tauri/gen/android/buildSrc/build.gradle.kts)

### 这意味着什么

以后遇到 Android 打包问题，优先按下面这个顺序判断：

1. 先确认是不是直接走了脚本：`bash scripts/build-android.sh release`
2. 再看是不是环境缺失：`JAVA_HOME`、`ANDROID_HOME`、`NDK_HOME`
3. 如果报错里出现 `plugins.gradle.org`、`plugins-artifacts.gradle.org`、`TLS handshake`，不要先怀疑业务代码，先检查 `buildSrc` 有没有又被改回 `kotlin-dsl`

### 明确不要再做什么

- 不要为了“看起来高级”把 `buildSrc` 再改回 `kotlin-dsl`
- 不要把 Android 打包失败第一时间归因到前端业务改动
- 不要在没有确认根因前，把时间浪费在反复切网络、反复删缓存、反复重装 SDK 上

如果以后又看到类似报错：

```text
Could not resolve org.gradle.kotlin:gradle-kotlin-dsl-plugins
Could not GET / HEAD https://plugins.gradle.org/...
Remote host terminated the handshake
```

第一反应应该是：

- 检查 `buildSrc` 有没有重新引入 `kotlin-dsl`
- 检查是不是有人绕过仓库脚本，自己手搓了 Android Gradle 入口

## 受限环境离线打包

### 这一步到底在解决什么

有些环境里，默认的 `~/.gradle` 不能稳定写锁文件，或者访问远程 Maven / Gradle 插件仓库时 TLS 握手抽风。

这种时候，表面报错每次都不一样，但本质还是同一类问题：

- Gradle 用户目录不可写
- 本地缓存不完整
- 远程仓库访问不稳定

解决办法不要绕，直接把可用的 `~/.gradle` 复制到 `/tmp`，删掉锁文件，再让 Gradle 只吃本地缓存。

### 标准做法

第一步：复制当前 `~/.gradle` 到临时目录

```bash
tmp_gradle_home="/tmp/codingns-gradle-$(date +%Y%m%d-%H%M%S)"
cp -R "$HOME/.gradle" "$tmp_gradle_home"
find "$tmp_gradle_home" -name '*.lck' -delete
echo "$tmp_gradle_home"
```

第二步：用临时 Gradle 目录离线打包

```bash
GRADLE_USER_HOME="$tmp_gradle_home" \
GRADLE_OPTS='-Dorg.gradle.offline=true' \
bash scripts/build-android.sh release
```

### 什么时候该用这套兜底

如果你看到下面这些报错，就别再假装它们是不同问题了：

- `Timeout waiting to lock journal cache`
- `Could not resolve ...`
- `Could not GET / HEAD https://plugins.gradle.org/...`
- `Remote host terminated the handshake`
- `The server may not support the client's requested TLS protocol versions`

这几种报错的共同点都是：

- 不是业务代码挂了
- 不是前端页面改坏了
- 是 Gradle 缓存目录、远程仓库、TLS 链路里至少有一个不稳定

### 这套兜底验证过没有

已经验证过。当前仓库最近一次成功 release 打包，就是按下面这条命令打出来的：

```bash

GRADLE_OPTS='-Dorg.gradle.offline=true' \

```

### 明确不要做什么

- 不要一报错就删整个 `~/.gradle`
- 不要一报错就重装 Android Studio
- 不要把同一类 Gradle 环境问题误判成“这次又是新问题”
- 不要绕过项目脚本，直接手搓一长串 `gradlew` 和 `tauri android build`

## 常见坑

### 1. 直接执行 `pnpm --filter user-app tauri:android:build`

这条命令不是不能用，而是它太依赖当前 shell 环境。

常见死法：

- `JAVA_HOME` 没配
- release 签名配置没准备好
- `key.properties` 缺失

结论：

- **不要把它当成日常稳定入口**
- 日常打包统一走脚本

### 2. 把 debug 包当成 release 包

最容易混的是这几种文件：

- `app-universal-release.apk`
- `app-universal-debug.apk`
- `app-universal-release-unsigned.apk`

这里面只有 `app-universal-release.apk` 是正式发布包。

### 3. 误以为有两套签名

当前仓库里确认到的 release keystore 只有一份：

- [codingns-release.jks](/Users/jackson/Code/CodingNS/apps/user-app/src-tauri/target/codingns-release.jks)

如果你觉得“签名不一致”，优先检查：

1. 你对比的是不是 debug 包
2. 你对比的是不是 unsigned 包
3. 你拿到的 APK 是否来自当前仓库这条脚本流程

### 4. 看到 TLS / plugins.gradle.org 报错就开始瞎折腾网络

这是最浪费时间的一种死法。

如果报错长这样：

```text
Could not resolve org.gradle.kotlin:gradle-kotlin-dsl-plugins:5.2.0
Could not GET / HEAD https://plugins.gradle.org/...
Remote host terminated the handshake
```

先别急着做这些没用功：

- 先别上来就删整个 `~/.gradle`
- 先别上来就重装 Android Studio
- 先别上来就怀疑业务代码把 APK 打挂了

先确认两件事：

1. 当前仓库里的 `buildSrc` 还是不是 `java-gradle-plugin`
2. 你执行的是不是 `bash scripts/build-android.sh release`

如果这两件事都对，才去看本机 Java / Gradle / 代理链路。

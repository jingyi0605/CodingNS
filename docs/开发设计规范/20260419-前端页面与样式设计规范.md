# 20260419-前端页面与样式设计规范

这份规范只回答一个问题：

后续在 `apps/user-app` 写前端页面、区块、表单、按钮和常规交互时，默认应该长成什么样。

别把它当灵感文档。它是前端默认做法，不是“有空参考”。

## 1. 适用范围

下面这些改动，开始前都必须先看这份文档：

- 新建页面
- 新建标签页、侧栏、设置分组、详情分组
- 改页面布局、区块结构、按钮风格、表单风格
- 改列表、卡片、空态、说明文案

不在范围里的只有两类：

1. 纯逻辑改动，没有 UI 变化
2. 第三方组件的最小兼容修补，且这次不改整体样式

## 2. 总原则

### 2.1 先统一，再谈美化

- 先接入现有样式基线和组件语义，再谈特殊视觉
- 不允许每个页面自己长一套按钮、输入框、分组边框
- 如果你要新写一套 class，先回答一句：现有规则到底缺了什么

### 2.2 信息要平铺，不要网页式堆卡片

- 同级信息优先平铺
- 用间距、标题、细分割线区分层级
- 只有在“拖拽对象”“强状态对象”“媒体内容容器”这类场景下，才允许独立底板

### 2.3 普通用户视角优先

- 文案不要写成工程后台
- 不要把“provider”“runtime”“workspace route”直接端给普通用户
- 文案优先说“能做什么”“现在是什么状态”“下一步点哪里”

### 2.4 不准继续长分裂的按钮体系

- 设置页按钮是当前项目默认按钮母版
- `primary-button`、`secondary-button`、`ghost-button`、`settings-button`、`workbench-secondary-button` 这些类只允许保留语义，不允许再各自长不同皮肤
- 危险操作统一走危险按钮语义，不允许再单独发明“橙色危险”“黑底危险”“弹窗专用危险”

## 3. 页面结构规则

### 3.1 页面骨架

- 页面优先拆成：标题区、摘要区、内容区、操作区
- 标题区负责说明当前页面是干什么的
- 摘要区负责给用户判断当前状态，不要塞成帮助文档
- 内容区按任务分组，不按实现模块分组
- 操作区放当前页面真正会点的动作，不要把低频动作放得比主动作还显眼

### 3.2 分组规则

- 一个分组只做一件事
- 分组标题要能直接回答“这块是干什么的”
- 分组内部优先纵向排列，避免为了“看起来高级”强行做复杂网格
- 桌面端可以双列，但每一列都必须在窄宽度下能自然回落

### 3.3 列表和详情

- 列表优先做成平铺行
- 行内结构优先是“主信息 + 次信息 + 右侧动作”
- 详情块优先做成键值对或简短说明，不要堆嵌套盒子
- 行和行之间优先用细分割线，不要默认加整块底色

### 3.4 空态

- 空态必须说清楚“现在为什么是空的”
- 如果用户下一步有明确动作，直接给按钮
- 不要只写“暂无数据”

## 4. 按钮规则

### 4.1 默认按钮风格

- 默认按钮统一使用设置页同款浅底、细边框、轻 hover 强调
- 默认按钮文字色跟随正文色
- hover 时重点是边框和背景轻微变化，不要再做夸张渐变和浮起阴影

### 4.2 危险按钮风格

- 危险按钮统一使用浅红底、浅红边框、红色文字
- 危险按钮只表达危险语义，不负责“更显眼”
- 普通操作不要因为想醒目就套危险色

### 4.3 语义类和视觉类分离

- `primary-button` 不再意味着蓝底主按钮，它只表示“当前主动作”
- `secondary-button` 不再意味着另一套皮肤，它只表示“次要动作”
- 视觉统一由全局按钮基线决定
- 只有移动端全宽主操作这种特殊场景，才允许在尺寸上放大，不允许换另一套皮肤

### 4.4 什么时候不能乱加按钮

- 同一块里主操作超过 1 个，先反省信息架构
- 一行里按钮太多，优先合并、折叠或转次级入口
- 低频动作不要放在高频动作前面

## 5. 表单和输入规则

- 输入框、选择器、文本域默认接现有全局基线
- 标签文案要说人话，不要写内部字段名
- 描述文案只补充必要限制，不要把帮助文档塞进表单
- 校验反馈优先贴近字段本身
- 多字段表单优先按任务顺序排，不按数据库字段顺序排

## 6. 文案规则

- 首次出现的技术词，如果普通用户可能看不懂，就换成人话
- 状态文案优先描述结果，不要描述内部实现
- 按钮文案优先用动作动词，例如“保存配置”“刷新状态”“解除绑定”
- 避免“提交”“确认”“处理”这种过于空泛的词，除非上下文已经足够清楚

## 7. 什么时候允许例外

只有下面这些情况可以偏离这份规范：

1. 需要复用现有成熟页面，改动范围必须压到最小
2. 需要兼容第三方组件结构，没法立即拆掉
3. 需要保留某个强交互控件的专门视觉，例如编辑器、diff、媒体预览

出现例外时，至少补清楚三件事：

- 哪一条规则不能直接套
- 为什么不能直接套
- 这次是临时兼容，还是以后就允许长期存在

## 8. 落地检查清单

开始提交前，至少自查这几项：

1. 有没有继续硬编码显示文案
2. 有没有继续长新的按钮皮肤
3. 有没有把同级信息做成一堆嵌套卡片
4. 有没有把工程术语直接暴露给普通用户
5. 有没有在 `apps/user-app` 之外改历史前端目录

如果这五条里有一条答不上来，就别急着交。
